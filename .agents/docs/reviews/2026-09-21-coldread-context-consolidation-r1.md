## Verdict: DESIGN NEEDS REVISION / IMPLEMENTATION NOT READY

Two concrete gaps block a first-pass implementer, both in Phase 2 ("Stop the regrowth" — the phase whose whole point is to close the loop that caused BUG-085): (1) the new rule text for `agents/bugs.md` asks the `bugs` subagent to determine whether a Go test *would fail*, but that agent's `tools:` list has no Bash/`run_command` — it structurally cannot execute `go test`; (2) the new retro-table row that routes "rule scoped to a file type or path" findings to `rules/<name>.md` is added now even though the plan itself defers building any `rules/` file, the cited assessment explicitly says this exact row belongs "in the same commit as the first rule file," and the new size-test gate (Step 2 item 5) is worded to cover only `context/AGENTS.md`/`context/dev-setup.md`, not `rules/` — which shares the same 24,000-byte block per the row's own text. ## (1) Gaps

- **`agents/bugs.md` new bullet requires an execution capability the agent does not have.** `agents/bugs.md:1-7` frontmatter: `tools: Read, Grep, Glob, Edit, Write` — no Bash/`run_command`. The plan's Interfaces text (line 40) adds: "A recommended permanent home is never `context/AGENTS.md` or `context/dev-setup.md` when `TestRenderedContextFitsAntigravityBlock` **would fail** with the sentence added…" Determining whether a test *would* fail requires running it (or reproducing its byte-counting logic by hand from files the agent can `Read`/`Grep` — not specified). Nothing in the plan's Surfaces-touched list mentions adding Bash to this agent's `tools:` (that omission would itself need `internal/harness/derive.go`'s `toolMap`, per this repo's `AGENTS.md` rule on adding a tool). Phase 2's verification for this task ("the record's Related must name the size test") only checks that the test is *named*, not that the agent correctly determined pass/fail — so the behavioural check as designed cannot catch an agent that names the test but guesses wrong. This is a real interface gap between the new rule and the calling agent's capabilities, not decided anywhere in the plan.
- **Phase 2's new retro-table row is not gated the way Phase 2's own new gate is worded, and contradicts the cited assessment's sequencing.** Plan Interfaces (line 39) adds the row `| Rule scoped to a file type or path | .agents/rules/<name>.md | rules/<name>.md (shares Antigravity's 24,000-byte block with the context — REQUIREMENTS § Known limits) |` and, separately, Step 2 item 5: "Before a harness proposal adds to `context/AGENTS.md` or `context/dev-setup.md`, run `TestRenderedContextFitsAntigravityBlock`…". Item 5's trigger names only those two files — a proposal that creates `rules/<name>.md` is not covered by its own wording, even though the row it sits beside says that file shares the very same byte block. Read `.agents/docs/plans/2026-09-21-context-audit-assessment.md` §"The `rules/` question": "Rules do not change the growth engine. The retro target table and the `bugs` graduation rule route every new rule into the context; a `rules/` row and a delete/merge action in that table are what change the next retro's output, and they **belong in the same commit as the first rule file**." That section's own Recommendation is "later" — after pruning shows whether MOVE-TO-SCOPED residue exists, "with a smoke check per rule file on both CLIs before any content depends on it." The plan under review explicitly puts "any `rules/` file" Out of scope (line 15: "deferred: the block cap makes a split worthless until the context has room") yet adds the routing row anyway, ahead of the file it's meant to accompany, with no smoke check and no size gate reaching it. No D-row addresses this divergence from the assessment's explicit sequencing. BUG-085's own probe result (quoted in the bug record) found a second rules file was silently dropped once the block filled, with no error — exactly the failure mode this ungated row could reintroduce on the very next retro.
- **D9 cites a test that does not exist.** "a release binary renders the same bytes (`TestEmbeddedPlanEqualsCheckout`) — by: implementer." `grep -rn "TestEmbeddedPlanEqualsCheckout"` over `cmd/` and `internal/` returns nothing; the only embedded-related tests are `TestEmbeddedInstallStateAndRecord` (`source_test.go:217`) and `TestKnownCheckoutRefusesEmbeddedManifest` (`main_test.go:1048`), neither of which compares rendered bytes. The underlying claim is plausibly true by construction (`EmbeddedSource` reads `styrman.Files`, a `go:embed` of the same tree the checkout test reads, so a release binary built from a given commit embeds the identical `context/*.md` bytes that commit's checkout test would see) — but the plan asserts this via a citation to a nonexistent test rather than stating the construction argument, so a reader has no way to check the claim as written. Low severity (the reasoning holds once traced), but it is an assumption asserted, not checked, exactly as it stands in the file.
- **E2E edge criterion names an ambiguous test fixture.** Verification §E2E "Edge": "with `context/AGENTS.md` padded by 2,100 bytes **in a scratch copy of the repo**, `TestRenderedContextFitsAntigravityBlock` fails naming the excess." But the test's own Interfaces spec (line 37) hardcodes `DirSource(filepath.Join("..", ".."))` relative to the `internal/harness` package directory — it can only ever read the checkout it is compiled from. "A scratch copy of the repo" therefore either means (a) a full second git clone under `.agents/scratch/`, with `go test` invoked from *within that clone's* `internal/harness`, so its own `../..` resolves correctly — a nontrivial, unstated mechanism — or (b) an in-place edit of the live `context/AGENTS.md` with a saved backup, matching this repo's already-established must-fail-mutation protocol (`AGENTS.md` Hard rules: "restored from a saved copy… `git diff` read to confirm nothing else moved"), in which case "in a scratch copy of the repo" is loose wording for "with a copy kept in scratch." These are materially different procedures and the plan does not say which.

## (3) Readiness

Questions a first-pass implementer would have to ask before starting:

1. **BLOCKING** — How does the `bugs` agent (no Bash tool) determine whether `TestRenderedContextFitsAntigravityBlock` would fail with a proposed sentence added? Do we add Bash to its `tools:` (a `derive.go` `toolMap` change not in Surfaces touched), or reword the rule to not require execution?
2. **BLOCKING** — Does the new retro-table `rules/` row go in now (Phase 2), unguarded by the size test, ahead of any actual rule file — or does it wait, as the cited assessment recommends, until the first `rules/` file and its smoke check land in the same commit? Two implementers would build genuinely different retro-skill text.
3. **BLOCKING** — For the E2E must-fail mutation, is "a scratch copy of the repo" a second full clone (test run from inside it) or an in-place edit-and-restore of the live `context/AGENTS.md`? The mechanisms differ materially and the size-test's hardcoded `../..` path makes the first non-obvious to implement.
4. NON-BLOCKING — `TestEmbeddedPlanEqualsCheckout` doesn't exist; a reasonable implementer drops the false citation or replaces it with the construction argument (`go:embed` of the same tree) without asking.
5. NON-BLOCKING — Plan's cited line numbers are off by one in two places (`skills/retro/SKILL.md:52-59` — table actually starts line 53; `README.md:208` — context row is actually line 209); trivially found by content match.

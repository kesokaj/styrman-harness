# Review — preflight-v1.0.0   (2026-09-16)

Range reviewed: `4aa19be..HEAD` (c7e3688), 14 commits, 75 files, 2585 insertions. Code lens, whole range as one body of work.

## Verdict: REQUEST CHANGES

The worst problem is the last commit in the range. `toolchain go1.25.8` (c7e3688, `go.mod:4`) is a hard build requirement under Go's DEFAULT `GOTOOLCHAIN=auto`: a host with go1.24.x and no reachable toolchain download fails the build outright, and `sh-agent install`'s own rebuild step (`internal/harness/repo.go:159`) has no fallback — a build failure is fatal. ADR-028 measured `auto`+network and `local`+offline and concluded "a soft upgrade and not a break"; it did not measure the default `auto` offline, which is the configuration of a locked-down or air-gapped host. I reproduced the failure. Since this tag becomes root-adjacent code that styrman-crew's channel fetches and runs on another machine, that is the finding that should gate the release. Two further issues sit in the new guards: `adopt --force` can now destroy the existing skill AND the replacement if the rename leg fails, and the new `update` dirty check is fail-open because `Inspect` discards git's error.

## Findings

- **[high / confidence: high]** `go.mod:4` — `toolchain go1.25.8` breaks the build on a host with an older Go and no toolchain download. Reproduced in `.agents/scratch/tc` (a throwaway module with `go 1.24.4` / `toolchain go1.26.0`): `GOTOOLCHAIN=auto GOPROXY=off go build ./...` → `go: download go1.26.0 for linux/amd64: toolchain not available`, exit 1; `GOTOOLCHAIN=local go build ./...` → exit 0. `auto` is the default, so a consumer must opt OUT to keep building. `internal/harness/repo.go:159` runs `go build -o bin ./cmd/sh-agent` and `if err := build.Run(); err != nil { return ... }` — no fallback to the running binary (that fallback is gated on `go` being absent or the tree being a plain copy, BUG-015), so `sh-agent install` and `sh-agent update` both hard-fail on such a host where they previously succeeded. ADR-028's "Consequences" paragraph asserts the opposite for every case it lists. Concrete fix, cheapest first: set `GOTOOLCHAIN=local` on the rebuild's env in `Reinstall` when the installed toolchain already satisfies the `go` directive (`build.Env = append(os.Environ(), "GOTOOLCHAIN=local")`), so the pin governs the harness's own release builds and never a consumer's install; or drop the `toolchain` line and raise the `go` directive if the patched stdlib is actually required.
- **[medium / confidence: high]** `go.mod:4` — the pin does not deliver what the commit message claims for a consumer. `toolchain` is advisory: under `GOTOOLCHAIN=local` (ADR-028's own "downstream mirror building offline" shape) the module builds with the OLD stdlib and the two advisories `GO-2026-4602`/`GO-2025-3956` are still present, silently. ADR-028 says this in its Consequences, but the commit subject says "govulncheck goes from 2 affecting to 0" without that qualifier, and the tag is what crew ships. Only the `go` directive enforces a minimum. If clearing the advisories on the shipped artifact is the goal, the `go` directive is the mechanism; if it is not the goal, the release note should not claim it.
- **[medium / confidence: high]** `internal/harness/adopt.go:84-95` (rename at :92) — `adopt --force` can lose both copies. The sequence is `RemoveAll(dest)` → `Rename(staging, dest)`, and the rename's error branch runs `os.RemoveAll(staging)` before returning. If the rename fails (the code's own comment concedes the same-filesystem assumption — `.agents/scratch` on a different mount or bind gives `EXDEV`, and `os.Rename` does not fall back to a copy), the original skill is already deleted and the error handler then deletes the complete replacement, leaving the operator with neither. That is the exact outcome the staging rewrite was introduced to prevent, moved one step later. The `defer os.RemoveAll(staging)` already covers cleanup, so the three explicit `RemoveAll(staging)` calls buy nothing; delete at least the one in the rename branch and return an error naming the staging path so the operator can move it into place by hand. `TestAdoptFailedCopyKeepsTheExistingSkill` covers only the copy leg, so nothing catches this.
- **[medium / confidence: medium]** `internal/harness/repo.go:94` and `cmd/sh-agent/main.go:357` — the new `update` dirty guard is fail-open. `Inspect` does `status, _ := gitOut(repo, "status", "--porcelain", "--untracked-files=all")` and reports `Dirty: status != ""`, so any git failure (dubious-ownership under a different uid, a corrupt or locked index, a hook or config error) yields `Dirty=false` and `update` proceeds to install the working tree — the precise BUG-046 outcome the guard exists to stop, under the hourly timer that caused it. A security guard must not be unable to say "I could not tell". `Behind()` narrows the window (its `git fetch` errors out first on some of these), but not all of them. Fix: give `Inspect` an error-returning sibling, or check the error in `update` and refuse on it; the refusal message already exists.
- **[low / confidence: high]** `internal/harness/plan.go:119` (patterns at :207) — the comment "The names match the context's Git rule" is not accurate. The rule names `.env*`; `secretShaped` matches `.env` and `.env.*` only, so `.envrc` — a direnv file that routinely holds credentials — is deployed to both vendor directories on every machine. Either add `.env*` to the pattern list or change the comment to say which shapes are covered. `*.tfstate` is in the list but has no case in `TestPlanRefusesSecretShapedFiles`.
- **[low / confidence: high]** `internal/harness/harness_test.go:999` — `TestWriteAtomicIsAtomicAndDurable` cannot fail if the `Sync` it names is reverted; the doc-comment admits this ("not directly observable from a test"). The honesty is right, the NAME is the problem: a test named `...AndDurable` reports coverage of a durability guarantee it does not exercise. Rename it to what it asserts (atomicity, mode, no leftover temp) so a later reader does not treat the Sync as tested.
- **[low / confidence: high]** `cmd/sh-agent/main_test.go:921` (`TestReadSettingsProblems`) — `if strings.Contains(problem, "SECRET")` cannot fail: three lines earlier the same `problem` is asserted equal to the constant `"could not be read"`. It re-asserts a constant against itself. The intent (no file bytes in the problem string) is worth keeping; assert it against a path where `problem` is derived from the file, or drop it.

- **[low / confidence: high]** `internal/harness/repo.go:94` — operational consequence of `--untracked-files=all` that only a whole-range reader sees: this repo's own workflow produces untracked files constantly (every agent artifact under `.agents/docs/`). Right now, at the commit being tagged, `git status --porcelain --untracked-files=all` lists three review/verify reports, so the operator's hourly `update` timer will refuse until they are committed. That is the correct fail-closed direction and I am not asking for it to change, but the release note and `deploy/remote.md` should say it plainly: after this tag, `update` is a no-op on any box whose harness checkout holds an uncommitted artifact, and the refusal repeats every hour.

## Outcome

1. [high] `toolchain go1.25.8` is a hard build requirement under the default `GOTOOLCHAIN=auto`, so `install`/`update` fail on a host that cannot fetch it — **confirmed and fixed**. Reproduced independently with an empty module cache: `GOMODCACHE=<fresh> GOTOOLCHAIN=auto GOPROXY=off go build ./cmd/sh-agent` → `go: download go1.25.8 for linux/amd64: toolchain not available`, exit 1; the same command with `GOTOOLCHAIN=local` exits 0. My first attempt at reproducing it passed only because this box had already cached the toolchain, which is exactly how the original measurement missed the case. Fix: `Reinstall` sets `GOTOOLCHAIN=local` on its `go build`, so installing never needs to download a compiler (`internal/harness/repo.go`), guarded by `TestReinstallBuildsWithTheLocalToolchain`. ADR-028 carries an amendment stating what was measured wrong and what the pin actually is.
2. [medium] the pin is advisory, and the commit subject's "2 affecting to 0" does not hold for a consumer — **accepted and stated**. ADR-028's amendment says it plainly: the pin is a ceiling for builds made in this checkout (development, tests, the gate) and not a floor for a consumer, whose binary `Reinstall` builds with that host's Go. The operator-run system upgrade remains the real fix for consumers. The commit subject is on a pushed commit and stands; the ADR is the record that corrects it.
3. [medium] `adopt --force` could lose both copies when the rename failed — **fixed**. The destination is renamed aside to a backup, the staging copy is renamed in, the backup is removed only on success, and on failure the backup is restored; staging is never deleted on an error path, and the error names where the prepared copy is (`internal/harness/adopt.go`). `TestAdoptFailedCopyKeepsTheExistingSkill` gained a rename-failure leg that makes `skills/` unwritable and asserts the original survives.
4. [medium] the dirty guard was fail-open because `Inspect` discarded git's error — **fixed**. `RepoInfo` gained `StatusUnknown`, set when the status command fails; `update` and `Pull` both refuse on it with a message that says git could not report the state, so "git failed" can no longer read as "the tree is clean" (`internal/harness/repo.go`, `cmd/sh-agent/main.go`). `TestInspectFailsClosedOnUnknownStatus` forces it with a `.git` that is a file.
5. [low] `.envrc` and similar not matched by `secretShaped` — **fixed**: the list now covers `.envrc`, `.netrc`, `.npmrc`, `.pypirc`, `*.env`, `*.p12`, `*.pfx`, `*.keystore`, `*.jks`, `*.tfstate.backup`, and the four `id_*` private-key names — the last of which is the signing key's own filename, which the security review raised in parallel.
6. [low] `TestWriteAtomicIsAtomicAndDurable` cannot fail on the durability it names — **accepted, already stated in the test**: only crash injection would show `Sync`'s effect, and the test says so in its comment. What it does assert (bytes, mode, no temp file left on either outcome) can fail and does when `writeAtomic` breaks.
7. [low] tautological assertion in `TestReadSettingsProblems` — **fixed**: the assertion now checks that the problem strings are a closed set of fixed phrases, which is the property worth holding, rather than checking a fixed phrase for a secret it could never contain.

# Security review — BUG-079 stale-running-binary note, round 3   (2026-09-18)

Range reviewed: c868ed4..a078848

## Verdict: FINDINGS

No high. The round-2 medium is closed on the release path: all fifteen returns of
`UpdateFromRelease` that install nothing now come BEFORE `NoteRunningElsewhere`
(`internal/harness/release.go:178`, each traced below), so the branch that had just proved the
running file newer than every release can no longer advise replacing it, and the message no
longer asserts staleness — it states file identity, which is what the code knows. Tracing that
gate, however, put the ordering guard it leans on under the lamp, and the guard has a
normalization hole that is the worst thing in this report: `IsReleaseVersion` accepts leading
zeros (`^v[0-9]+\.[0-9]+\.[0-9]+$`, `internal/harness/source.go:44`) while `releaseParts` runs
each field through `strconv.Atoi` (`release.go:384-391`), so `v1.02.2` and `v1.2.2` compare
EQUAL though the strings differ — the switch's three `return`s are all skipped and the update
proceeds. The signed payload is the `SHA256SUMS` content only (`verifyRelease:239-244` feeds it
to `ssh-keygen -Y verify`; asset names are tag-independent), so a previous release's binary,
`SHA256SUMS` and `SHA256SUMS.sig` republished under a tag spelled `v1.02.2` verifies genuinely
and installs over a running `v1.2.2` — a rollback the comment at `release.go:109-112` says the
guard exists to prevent, needing GitHub write access and no signing key. That code is
pre-existing and outside the diff; it is in the blast radius because the round-2 fix's entire
argument is "past this switch the installed file is newer". The rest is low: the checkout path
prints the note after a `Reinstall` that is not proven newer, and `NoteRunningElsewhere` is
`home`-blind, so under `--home` it offers to point a PATH-resolved `sh-agent` at a scratch-tree
binary or remove the real one. Exporting `NoteRunningElsewhere` widens nothing outside the
module. Nothing in the range touches secrets, auth, hand-rolled crypto, dependencies or the GCP
surface.

## Answers to the four checkable questions

1. **Is the medium closed? On the release path yes, subject to finding 1 — traced.**
   `UpdateFromRelease` (`internal/harness/release.go:90-180`) reaches the note at line 178 only
   past every other exit: `gh` missing (92), `LatestRelease` error (96), non-`vX.Y.Z` tag (103),
   `tag == version` (107-108, round-2 state (b)), running version not a release (114-115),
   `compareRelease(tag, version) < 0` (117-118, round-2 state (a)), `checkOnly` (121-122),
   `sshKeygen` (129), `MkdirAll base` (137), `MkdirTemp` (146), download (153), verify (157),
   `MkdirAll` of `dest`'s directory (164), `writeAtomic` (167), and the new binary's own
   `install` (176). So it prints only after `home/.local/bin/sh-agent` was replaced by a
   signature- and checksum-verified binary of a tag `T` for which the switch established
   `T != version`, `version` is a release, and `compareRelease(T, version) >= 0`. That `>=`
   rather than `>` is finding 1: with a leading-zero tag the relation is `== 0` and the running
   file can be the newer one after all. Two further residues: the checkout path has no such
   proof at all (finding 2), and after a successful `writeAtomic` whose subsequent child
   `install` FAILS (176) the installed file is new, the running one is behind, and nothing says
   so — fail-silent, not a weakness, recorded for completeness.
2. **Is the `ln -sfn` ownership concern addressed or only softened? Softened.**
   `internal/harness/pathguard.go:119` still offers `ln -sfn` FIRST and unconditionally and then
   conditions only the *preference* on a fact the program does not check although
   `RunningElsewhere` holds `from`'s `FileInfo`; "root-owned" is also not the whole risk class
   (finding 3).
3. **Does exporting `NoteRunningElsewhere` widen anything? Not outside the module.**
   `internal/harness` is an `internal/` package of module `github.com/kesokaj/styrman-harness`
   (go.mod, untouched in range), so the toolchain refuses any import from another repository;
   `grep -rn` finds exactly two call sites, `cmd/sh-agent/main.go:509` and `release.go:178`, plus
   tests. The function takes neither PATH nor exe from its caller — it reads `os.Getenv("PATH")`
   and `os.Executable()` itself — so a caller can influence only `home` and `out`, and the
   function only stats and prints: it never writes, removes or execs. The one thing a caller can
   get wrong is `home`, which is finding 4.
4. **Can the note be lost or misattributed after a noisy install? Not lost; misattributable.**
   The child's stdout and stderr both go to the same `out` (`release.go:174`) and `cmd.Run` →
   `Wait` does not return until those copies finish, so the note is always the last line on that
   path; with `out` an `*os.File` the child writes the descriptor directly and has already
   exited — same ordering. Nothing can interleave inside the note, which is one `Fprintf`. The
   residual is human: it follows the installed binary's own install output, including that
   binary's `warning: … comes before … on PATH` line about the same file, so a reader may take
   "note:" for part of the install. It self-identifies with "this update ran from", and a pasted
   log preserves the order. No finding.

## Findings

- **[medium / confidence: high]** `internal/harness/source.go:44` with
  `internal/harness/release.go:105-119,384-391` (pre-existing, in the blast radius of the gate
  the round-2 fix relies on) — the "never sideways or backwards" guard can be walked past with a
  leading-zero tag, which turns `update` into a rollback channel for anyone who can publish a
  release without holding the signing key. `IsReleaseVersion` accepts `v1.02.2`; `releaseParts`
  `Atoi`s each field, so `compareRelease("v1.02.2", "v1.2.2") == 0`; the switch returns only on
  `==` by string, a non-release running version, or `< 0`, so execution falls through to the
  download. `verifyRelease` signs nothing tag-specific — `ssh-keygen -Y verify` is fed the
  `SHA256SUMS` bytes, whose lines are `<hash>  sh-agent-linux-amd64`, identical across releases —
  so the attacker republishes an older release's three assets verbatim under the new tag and
  every check passes. Result on each binary-only place that runs `update`: an older genuine
  binary replaces the newer one and then installs its own older embedded context, skills and
  agents; the new note then tells the operator their newer running copy is "not the installed
  binary" and offers to remove it. Prerequisite is GitHub write access to the release repository;
  the yield is limited to previously signed artifacts, which is why this is medium and not high.
  Remediation, one character plus its message: make the guard strict —
  `case compareRelease(tag, version) <= 0:` — so only a strictly greater release installs, and
  additionally reject a tag whose text is not its own canonical form (compare `tag` with
  `fmt.Sprintf("v%d.%d.%d", parts...)`) so a non-canonical spelling can never name a release at
  all. Stdlib only; no dependency, nothing to justify. Longer term, bind the tag into the signed
  payload (a line in `SHA256SUMS`), which also kills asset replay across releases.
  Validated in both directions with a scratch probe that copies `releaseVersion`, `releaseParts`
  and `compareRelease` verbatim (`.agents/scratch/security-bug079-3/probe.go`, gitignored, no
  network, nothing published): `tag=v1.02.2 running=v1.2.2 -> isRelease=true cmp=0
  fallsThroughToInstall=true` (must-fail state), against `v1.2.2/v1.2.2 -> false`,
  `v1.2.1/v1.2.2 -> false` and `v1.02.1/v1.2.2 -> false` (must-pass states). It exercises a copy
  of the predicates, not the package's own unexported ones — a reviewer may not add a test to
  `internal/harness`.
- **[low / confidence: medium]** `cmd/sh-agent/main.go:461-509` — on the checkout path the note
  prints after `Reinstall` with no evidence that the installed binary is newer than the process
  that ran the update, and then offers `ln -sfn`/removal against that process's file. `update`
  prints "up to date with upstream" (467) and, when `!checkOnly`, falls through to `Reinstall`
  (508) and the note (509); `Reinstall` rebuilds from the working tree, so a binary is always
  written and the operator's D2 gate ("only after a binary was actually written") holds — but
  "written" is not "newer". Concrete state: a copy on PATH built from a local commit ahead of
  `origin/main`, or from a branch never pushed, runs `sh-agent update`; the checkout
  fast-forwards to the older `origin/main`, `Reinstall` writes that older build, and the note
  advises pointing the newer file at it or removing it. `ResolveSource`
  (`internal/harness/repo.go:22-48`) keeps a RELEASE binary off this path entirely — it always
  returns `EmbeddedSource` — so the running process here is a development build, which is also
  why the round-2 remediation is awkward: `buildinfo` gives such a build a VCS stamp, not a
  version. Narrow, hence low; confidence medium because I did not exercise it. Remediation:
  compare the two builds' VCS revisions (`main.go:377` already reads the installed file's build
  info) and drop the remedy clause unless the installed one is ahead; or, simpler and shorter,
  keep only the first sentence of the note — the identity fact plus `hash -r` — and delete the
  remedy from both paths.
- **[low / confidence: high]** `internal/harness/pathguard.go:119` — `ln -sfn` is still offered
  first and unconditionally for a path whose ownership the program has already stat'ed and
  chooses not to read. Following it on the BUG-079 machine means
  `sudo ln -sfn ~/.local/bin/sh-agent /usr/local/bin/sh-agent`, after which a root-owned,
  system-wide PATH entry resolves to a file inside one user's home that that user — and every
  agent this harness dispatches as that user — can overwrite, so anyone running `sh-agent` from
  the system path (another account, `sudo sh-agent …`, a unit, a cron job) executes
  user-writable content. The added clause lowers the chance of that but leaves the unsafe option
  first and delegates the decision to the reader's knowledge of a fact the program holds.
  Root-ownership is not the whole class either: a package-manager path, `/opt/devbox/bin`, or a
  path owned by another non-root account weaken the same way. Low because the step is the
  operator's own on single-operator machines. Remediation: decide it in code — offer `ln -sfn`
  only when `from` is under `os.UserHomeDir()`, otherwise name removal alone (or say the path is
  the operator's to decide, and what changes if they link it). A lexical home check needs no
  build tags; `info.Sys().(*syscall.Stat_t).Uid` is the alternative if ownership is preferred
  over location.
- **[low / confidence: high]** `internal/harness/pathguard.go:112-120` with
  `cmd/sh-agent/main.go:509` — the note is `home`-blind: it calls `filepath.Join(home, BinPath)`
  "the installed binary" for whatever `home` the run used, so under `--home` it recommends
  wiring a PATH-resolved `sh-agent` to a binary outside the real home, or removing the real one.
  Reachable with the ordinary checkout-place setup this repository mandates: `~/.local/bin/sh-agent`
  is a development build (so `ResolveSource` takes the checkout path) and a PATH entry reaches it
  by name (the gate); the operator runs `sh-agent update --home .agents/scratch/x` to exercise an
  install, `Reinstall` writes `.agents/scratch/x/.local/bin/sh-agent`, and the note names THAT as
  the installed binary and offers `ln -sfn` it over — or removal of — their real
  `~/.local/bin/sh-agent`. `.agents/scratch/` is gitignored and written by every agent this
  harness dispatches, so the link version moves a PATH-resolved name onto an agent-writable path
  (and a dangling symlink as soon as scratch is cleaned); the removal version deletes the working
  install. Exploitable without an attacker (self-inflicted) and with one (any writer of
  `.agents/scratch/`). Low because the step is the operator's own with both paths printed in
  front of them, and because the pre-existing `PathShadows` warnings share the class — the note
  extends it rather than inventing it. Remediation: print the note only when `home` equals
  `os.UserHomeDir()` (stdlib, already used in home resolution) and stay silent otherwise, or keep
  the identity sentence and drop the remedy when it does not.

### Rebuttals and round-2 items re-checked

- **Raw `%s` of PATH-derived paths — still rebutted.** `from` comes from the operator's own PATH
  entries and `installed` from `--home`/`$HOME`; no untrusted producer reaches either, and `%q`
  would stop the output matching `which -a`/`type`, which the docs tell the reader to compare
  against. Round 2's log-injection caveat is unchanged and unacted on, as its Outcome says.
- **`os.Executable()` only stat'ed — still rebutted.** `exe` is consumed once
  (`pathguard.go:80`) and the returned value is always `cand`, built from a PATH entry; a
  `" (deleted)"` or stale-relative `exe` makes the `Stat` fail and the function returns
  `"", false` — fail-closed, pinned by the `exe missing` case.
- **`ln -sfn` argument order** — unchanged, and unchanged in consequence: `writeAtomic` replaces
  a symlink at `dest` by rename rather than writing through it, so a reversed link cannot
  redirect a later install out of `--home` (carried over from round 2's reading of `apply.go`).
- **`RunningElsewhere` stats PATH candidates without `executableAt`'s directory and exec-bit
  checks, unlike `PathShadows` — checked, no finding.** The comparison is `os.SameFile` against
  a file this process is executing; a directory or a mode-0 inode cannot be the same inode as a
  running executable, and hard and symbolic links share the inode's mode. No TOCTOU either: the
  result is printed, never acted on.
- **`--check` on both paths — silent, and tested in the must-be-silent state.**
  `cmd/sh-agent/main_test.go:1543` (release path, up to date, with and without `--check`) and the
  `--check` assertion inside `TestCheckoutUpdateNamesTheBinaryItRanFrom`. The side effect sits
  below every read-only early return on both paths.

## Outcome

The rest is outside this fix and goes to the audit phase of `.agents/docs/plans/2026-09-18-sh-agent-works-everywhere.md` (Phase 2), each as its own box there:

- [medium, pre-existing] `v1.02.2` passes `IsReleaseVersion` and compares equal to `v1.2.2`, skipping the not-newer refusal — **left, owner Phase 2 audit**, with one correction to the finding's blast radius: the rollback channel as described stops at `verifyRelease`'s marker check (internal/harness/release.go:283), which requires the SIGNED `SHA256SUMS` first line to equal the tag string exactly — an older release's signed file names its own version, and nobody without the key can sign `# styrman-harness v1.02.2`. What remains is that a non-canonical tag reaches the download at all, and that `compareRelease` treats it as equal; Phase 2 rejects a non-canonical spelling and uses `<= 0`, with a must-fail test for `v1.02.2` and `v01.2.2`.
- [low] `ln -sfn` offered first regardless of who owns the path — **left, owner Phase 2 audit**: `RunningElsewhere` holds `from`'s `FileInfo`; the note can say "remove it" alone when the file or its directory is not the caller's.
- [low] the note is `--home`-blind: with `--home .agents/scratch/x` it calls a scratch binary "the installed binary" — **left, owner Phase 2 audit**: print the note only for the default home, or name the home in it.
- [low] the checkout path rebuilds and notes when `behind == 0` — **left** (main agent): the note's statements stay true (the process is not the file just written; that file is a fresh build); no wrong advice follows from it.

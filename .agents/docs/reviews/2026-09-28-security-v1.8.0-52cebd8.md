## Status: COMPLETE

## Verdict: FINDINGS (none blocking; one carried medium stays open by decision)

**The worst problem is the medium carried from both earlier rounds, and it is still open.** Whoever supplies a zip can leave `SHA256SUMS`/`SHA256SUMS.sig` out. The zip then installs with exit 0, marked `UNVERIFIED` in a single stdout line (`internal/harness/release.go:445-447` → `cmd/sh-agent/main.go:1085-1087`).

**Why it does not block this gate.** This is the behaviour R9 approves, word for word. ADR-039 (Consequences, "Open"), the plan's Follow-ups and the change entry all record it honestly. Every path this range adds either verifies or refuses, so the exposure is strictly narrower than the v1.8.0 that shipped.

**Two conditions, which only the gate writer can meet:**
- (a) the v1.9.0 gate report carries it as an open medium, narrowed but not closed;
- (b) the release handoff's Next Steps asks the operator the `--unverified` question. The only handoff in the range (`2026-09-28-1806`) predates this change and asks a different question.

**What I verified fresh:**
- The verification code (read whole: `release.go`, `zip.go`, `updateFromZip`).
- Release step 3b: executed, must-pass and must-fail.
- The pinning of the removed bypass hint: both mutations that survived round 2 now fail named subtests.
- `govulncheck`: clean.

The findings below are low: one unrecorded trust verdict, one stale comment on the trust anchor, one pre-existing gap in the release procedure, one skill instruction, and the optional archive scope.

## Findings

- **[medium / confidence: high] Carried from round 1 and round 2. OPEN by decision; not blocking under conditions (a) and (b).**
  - **Where:** `internal/harness/release.go:445-447` (`VerifyZipSums` returns `ErrZipUnsigned` when both files are absent) together with `cmd/sh-agent/main.go:1085-1087` (the closure turns that into nil, and the zip unpacks and installs).
  - **The weakness:** trust is decided by whether two files are present, and the party who supplies the zip controls that. Unchanged since round 1.
  - **Remediation (unchanged):** an explicit opt-in, for example `--unverified`, without which a zip with no sums is refused. This is an R9 change, so it is the operator's decision, with an ADR (project rule 3).
  - **If that flag lands:** the accepted downgrade (see the status table) becomes the remaining route for an attacker. Revisit it then: on a release binary, warn when `compareRelease(verifiedTag, buildVersion()) < 0`. Both are existing helpers, so no dependency.

- **[low / confidence: high] The trust verdict is not recorded anywhere that outlives the command's output.** `cmd/sh-agent/main.go:1112`.
  - **What happens:** the manifest origin is `zip:sha256:<hex>` whether the zip was VERIFIED or UNVERIFIED. `status` prints `from zip sha256:<hex>` either way: E2E log run 1, README § Install from a zip. `sh-agent report` carries the same value.
  - **Why it matters:** once the one stdout line is gone, neither the operator nor a later session nor a feedback report can tell that an unverified zip became the agents' instructions. That weakens the only control the medium above has, which is disclosure.
  - **Remediation:** record the verdict in the manifest (`verified vX.Y.Z` or `unverified`) and print it in `status`. This is a manifest change, which the plan scoped Out, so it is the operator's call. It can land with the flag in the first finding.

- **[low / confidence: high] Carried from round 1 and round 2, neither fixed nor rebutted: stale comment on the trust anchor.** `internal/harness/release.go:34-35`.
  - **What it says:** `releaseSigner` is "a variable only so a test can substitute a test key's line".
  - **What is true:** the variable is also what `-ldflags -X` replaces at link time. Measured this round: a build with `-X …/internal/harness.releaseSigner=gate@signer …` accepted a scratch key's signature and printed `VERIFIED` (`.agents/scratch/sec-gate-3b/`). The CLI test also reaches it through `SwapReleaseSigner` (`release.go:415-422`).
  - **Why it matters:** a reader auditing the trust anchor learns the wrong thing about how it can be replaced.
  - **Fix:** the comment names `-X`, release step 3b as the guard against it, and `SwapReleaseSigner`.
  - **Optional hardening (round 2):** a test that parses the module's non-test files with stdlib `go/parser` and fails on any reference to `SwapReleaseSigner` besides its declaration. Today there is none (grep), and the linker drops it from the binary (round 2, `go tool nm`).

- **[low / confidence: medium] Pre-existing, not introduced by this range: the binaries and the release zip come from different sources.** `.agents/docs/deploy/remote.md` § Releases, steps 0-1 (lines 131-144) against step 1b (line 147).
  - **The two sources:**
    - Step 1 builds the binaries from the WORKING TREE, and step 0 re-checks only the five embedded trees.
    - Step 1b archives the TAG's object tree.
  - **The gap:** say a tracked file under `cmd/` or `internal/` changes after line 108's whole-tree clean check, which runs before the tag and the pushes. The change is compiled into every binary and signed into `SHA256SUMS`. Meanwhile the signed tag and the zip describe other code.
    - Step 3b catches this only when the change touches the signer.
    - `TestEmbedHoldsOnlyTrackedFiles` compares file lists, not content, and only for the five trees.
    - Step 1's comment ("from the tag's own tree") is therefore guaranteed for the five trees only.
  - **Why it is low:** the window is minutes inside one `/preflight` turn, and nothing is expected to write source then.
  - **Fix, cheapest first:**
    - repeat line 108's `test -z "$(git status --porcelain --untracked-files=all)"` in step 0;
    - or build from a `git archive vX.Y.Z` export, so the binaries and the zip share one source and the embed contamination guard becomes unnecessary.
  - **Confidence is medium** because I read only preflight's Step 6 by grep, not in full.

- **[low / confidence: low] The restored `find-skills` tells agents to install third-party skills globally without confirmation.** `skills/find-skills/SKILL.md`, Step 6.
  - **Provenance:** it is verbatim upstream at `435076e`; reviewer confirmed byte-identical via `gh api`.
  - **What it says:** `npx skills add <owner/repo@skill> -g -y`, where "`-g` installs globally … `-y` skips confirmation prompts".
  - **What the context says:** `context/AGENTS.md` § Global vs project says a found skill goes into the checkout's `skills/` and is "never only into a vendor directory".
  - **Why it matters:** a third-party skill is instructions every later session reads. The checkout route keeps a commit and provenance in `VENDORED.md` as the review point. A `-g` install has neither, and `sh-agent install` never removes it (the old local text said so).
  - **What is measured:** the context sentence wins 2 of 2 on Claude Code (`testing/2026-09-28-verify-find-skills-routing.md`). Antigravity is not exercised.
  - **Remediation:**
    - run that log's question once on Antigravity;
    - optionally name `-g` in the context sentence ("not `npx skills add -g`").

    The vendored file stays verbatim, per `skills/VENDORED.md`.

- **[low / confidence: medium] Carried from round 1 and round 2; optional: the release zip carries the whole tracked tree.** `.agents/docs/deploy/remote.md:147` (step 1b).
  - **What it ships:** the tag's whole tracked tree, including `.agents/docs/`. That tree holds hostnames, machine paths, the operator's email and a report record's contents; the same section's own paragraph lists them.
  - **What is new:** the zip is now a first-class asset that README sends zip places, meaning corporate workstations, to download. It is about 3.1 MB (measured on a 52cebd8 archive), far below the 64 MiB read cap.
  - **Why it stays low:** the content equals GitHub's own source zip for the tag, and the repository is private.
  - **Optional minimisation:** `git archive … vX.Y.Z context skills agents commands rules`. `UnpackZip` accepts it, since `zipRoot` needs only `top/context/AGENTS.md`. Check it against R9's "a zip of its tree" wording.

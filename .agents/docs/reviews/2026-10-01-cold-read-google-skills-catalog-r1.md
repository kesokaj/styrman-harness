## Status: COMPLETE

## 1. Gaps

Confirmed against the code:

- **G1 (high) `TestNoTmpInHarnessProse` is not in the plan and fails as soon as the catalog lands.** `harness_test.go:1020-1050` walks every `.md` under each skill directory that is not in `vendoredSkills`, and `google-catalog` is deliberately not vendored (plan § Interfaces last bullet: "the router is harness-authored"). The walk starts at `skills/google-catalog` and recurses into `catalog/`, so any "/tmp" in 141 entries' markdown (very likely: Google's cloud skills use `/tmp` in examples) is reported. The plan skips the catalog subtree only in `TestSkillLinksResolve`. Decide: skip `catalog/` in this test too, and search for every other test that walks `skills/` (`TestSkillLinksResolve`, this one; check `zip_test.go`, `phase8_test.go` for the same pattern). The plan should list the walkers it audited.
- **G2 (high) `restatement-grep.sh` will not treat the catalog as vendored, and the phase-1 positive-control verify clause cannot pass.** The script derives vendored paths with `grep -E '^\| [a-z0-9-]+ \|'` (`restatement-grep.sh:45`). The class `[a-z0-9-]` has no `/`, so a first cell of `google-catalog/catalog` is never matched, and a backticked cell is not matched either. The catalog's ~thousands of tracked files stay in the "living files" list, and the verify "output for a word that appears only in a catalog entry is empty" fails. The plan names the script as touched, but not this regexp. Decide the cell shape (plain `google-catalog/catalog`) and the regexp change, and add the mutation (cell present vs absent) to the verify clause.
- **G3 (high) Install and embed refuse content the plan never checks upstream for.** The vendored tree is deployed by the existing skill walk, which refuses on: a symlink (`plan.go:108`), a secret-shaped name (`plan.go:120`, `secretShaped` at `plan.go:216`: `.env.*`, `*.key`, `*.pem`, `credentials`, `*credentials*.json`, `*.tfvars`, `.npmrc` ...; a sample `.env.example`, `service-account-key.json`, `terraform.tfvars` in a Google sample entry is plausible), and `.gitignore` (lines 8-34) stops `git add` of the same shapes, so such a file would be fetched by the script, left untracked, then reported by `TestEmbedHoldsOnlyTrackedFiles` as embedded-but-untracked in the release binary and absent from the zip — and from CHECKSUMS-vs-git. Also `go:embed` silently drops any subdirectory that holds a `go.mod` (and rejects names with invalid characters), which would trip the "tracked but not embedded" direction of the same test (`embed_test.go:54-95`). The plan's failure modes say nothing about these. Decide per case: the refresh script detects each (symlink, secret-shaped name, nested `go.mod`, gitignored path) before touching the tree and exits 1, and the plan states what happens to an entry that has one (exclude the entry with a MANIFEST note? exclude the file, which breaks "byte-identical"? — an operator choice, and D7 shows the plan knows "only local change" is a recorded line).
- **G4 (medium) The "red against an empty catalog fixture" verify clause cannot be red.** Phase 1 box 2 says the three tests are written first "against an empty catalog fixture (red)". `TestCatalogMatchesChecksums` (both directions over zero files), `TestCatalogIndexMatchesEntries` (zero dirs, zero lines) and `TestCatalogHoldsNoExecutable` (zero files) all pass vacuously on an empty tree; "silence is not evidence". The plan must say each test also asserts a non-empty catalog (without hard-coding 141, which `refresh` changes — e.g. at least one entry and CHECKSUMS non-empty), and that is what is red. Also state the test's behaviour when `catalog/` does not exist (fail, not skip).
- **G5 (medium) Assumption "a skill may read files under its own directory without a permission prompt" is checked last, but the whole design rests on it.** Phase 4 is after the 141-file vendoring, the security slices and the docs. Claude Code in a project outside `~/.claude` may prompt for (or deny) reads of `~/.claude/skills/google-catalog/catalog/...` and Antigravity's `~/.gemini/antigravity/skills` path likewise (path as in `AgyRoot`; plan does not name it). A denial makes the catalog useless on that CLI; the probe is minutes of work. Add a Phase 0 / first box: one throwaway sandbox read of a nested file by a stub router on each CLI, before Phase 1.
- **G6 (medium) The refresh script's contract has holes.** (a) The source-path list (agents-cli `skills/` dirs, the single `extensions/langchain/template/.agents/skills/agents-cli-langchain`, google/skills `skills/cloud/*`, `skills/developers/*`) lives where? Constants in the script is the obvious answer, but unstated; the plan's count "131 + 2 + 7 + 1" is not checked by the script (`expect 141` only in the verify clause). (b) Flat `catalog/<name>/` across four source sets: a name collision between sources overwrites silently; the script must exit 1 on a duplicate. (c) "Exit 1 ... before touching the tree" while also "replaces entries (removing entries upstream dropped)": the staging mechanism (build in scratch, then swap) is unspecified; a mid-way `cp` failure leaves a half-replaced tree — caught only by the checksum test, which the script regenerated itself. (d) Frontmatter extraction in bash for INDEX.md: upstream descriptions can be block scalars, quoted, multi-line or contain `—`; "whitespace folded, cut at 220" does not say whether cutting is by bytes or characters (a byte cut can split UTF-8 in a line the Go test then parses). Say which parser, and that the Go test and the script agree on the line grammar. (e) `<name>` in the index: directory name or frontmatter `name`? § Interfaces says "upstream's directory names" for entries and the research notes frontmatter-name clashes (`gke-basics`); the test "every directory with a SKILL.md has exactly one index line" needs one definition. (f) The script is mode 0644 (embed test refuses exec; see restatement-grep header) and is run with `bash`; the plan does not say 0644 for it, and says "clears exec bits" for entries only; state it. (g) Pin resolution: the pins `2c39459`/`d5d9052` are 7-char abbreviations; a full-clone `git checkout` resolves them, a shallow clone does not — say "full clone".
- **G7 (medium) The listing-budget test's metric is not pinned to what Claude Code measures.** `Skill` has `SlashOnly` (`inventory.go:19`): a `disable-model-invocation` skill is not listed, but the plan's sum "over `LoadSkills`" counts all. My own count over `skills/*/SKILL.md` with folded whitespace is 19,294 for 34 skills (plan: 19,310 in the research brief), so the plan's numbers are plausible but the test's definition (folded vs raw description; the `description: |` block scalars such as `cloud-run-deploy`'s keep a trailing newline) is unspecified, and the "at or under 19,300 after trim" expectation depends on it. Decide: sum over non-SlashOnly skills, description as `LoadSkills` returns it. Also: nothing bounds the Antigravity listing (research: 109 of 173 listed — count cap or character cap?); at 35 skills it is under 109, but the test only guards Claude Code's characters; say so.
- **G8 (medium) Router ordering/guard unspecified in test form.** The router `description` limit (300 chars) and its must-NOT clause have no test (`TestLintDescriptionLimit` allows 1,024). Only the aggregate budget guards it. Either a test pins the router's description at most 300 and containing its "Do NOT use" pointers, or state that the aggregate is the whole guard.
- **G9 (low) A task changing a command/flag/deploy-step with no docs clause:** Phase 1 changes `restatement-grep.sh` behaviour (a script a skill runs) — its header comment ("minus the vendored skills named in skills/VENDORED.md") and `skills/review/SKILL.md` mention are restatements; no `docs:` clause names them. The refresh script is a new command but its usage lives only in the plan; name where it is documented (`skills/VENDORED.md` "Update via" cell and `AGENTS.md` third-party rule are mentioned for the rule only). The "Update via" cell for the catalog row is not specified.
- **G10 (low) D14's "put to the operator in chat as a one-line choice before Phase 1's first commit" is not a phase box.** A decision of an implementer superseding an operator-approved location (D1, D9) with an unticked gate is the kind of thing that gets skipped. Add it as the first Phase 1 box, with who: user. R5 says "the installer maps each directory to its place under both vendors"; a nested catalog inside a skill directory fits it, but AGENTS.md rule 3 ("changing a path is a design question") is the sentence the operator should see quoted.
- **G11 (low) E2E criteria:** "names the catalog entry it read" does not say how it is observed on each CLI (transcript tool call? the model's own statement is not evidence). "Skill count 35" is a count that goes stale with the next skill; the criterion should read "the count equals the skill directories on disk plus none" (the check is `sh-agent list` vs `ls skills`). "install under 10 s" has no stated baseline. None of these name an implementation choice, but the first can pass on a hallucinated claim.
- **G12 (low) `allowed-tools` in vendored entries (D6).** `LoadSkills` refuses `allowed-tools`/`hooks` in harness skills (`inventory.go:206`, BUG-143) precisely because a skill's frontmatter is a permission surface; the plan's claim "in a catalog the key grants nothing" is asserted, not checked. It holds only because nothing registers the nested file as a skill; the sandbox `catalog-route` row on Claude Code should check that reading such an entry runs its tools prompted, not unprompted (research found two entries: `agent-platform-alert-configuration`, `cloud-run-alert-configuration`). Name that row and its pass criterion.

Checked and found consistent (no gap): `LoadSkills` reads `skills/<dir>/SKILL.md` only (`inventory.go:150-185`), so nested `catalog/<e>/SKILL.md` files are neither loaded, linted, nor counted in the 35; `plan.go` copies regular files at `Perm&0o755|0o600`, so a 0644 `LICENSE-google-skills` or `.py` file passes and an executable bit would survive into both homes (hence the exec-bit test is right); `TestVendoredRowsCarryAPin` would read a `google-catalog/catalog` row (`vendoredSkills` stats `skills/google-catalog/catalog`, a directory, and the row needs `github.com/` and a hex pin) and the key is inert for `TestSkillLinksResolve`/`TestNoTmp...` because those match on the first path element, so the explicit skip the plan adds is needed and sufficient there; `forkSkills`'s state machine keeps `inForks` true past the new section (harmless: rows resolve no existing directory except the catalog path, which is inert); no REQUIREMENTS edit needed (R5, R8 are not touched; no new path on the README map). The 7+1+131+2 = 141 arithmetic holds. The size pins: the catalog sits in `skills/`, not in `context/`, so `TestRenderedContextFitsAntigravityBlock` moves only by the one inventory line (research: 19,548 at 173 skills, so fine at 35).

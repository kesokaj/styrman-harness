## (1) Gaps

- **BLOCKING (new) — `--kind`'s accepted values and the global index's actual kind values disagree.** Interfaces § Commands, line 58: "`--kind` one of `bug adr plan change handoff review testing retro spec deploy trail code doc`" — 13 values. Interfaces § Storage's last sentence (line 118): "The global index stores `feedback.jsonl`, `retros.jsonl` and `proposals/*.md` under project `~config`... kind `feedback`, `retro`, `proposal`." Two of those three kinds — `feedback` and `proposal` — are not in the `--kind` enum. `retro` is already covered (docs-root `retros/` also maps to `retro`), so it's fine; `feedback` and `proposal` are not. As written, an implementer validating `--kind` against the documented enum (which Phase 1's query task will do — the enum is exactly what `TestSearchRanksAndCaps`/kind-filter logic needs to check against) has no way to let a user filter `--global --kind feedback` down to just the feedback log, even though rows with that exact kind exist in the database by design. Two implementers diverge concretely here: one silently extends the enum to 15 values so the global kind values are reachable; one implements exactly the documented 13-value enum, in which case `feedback` and `proposal` rows are permanently unfilterable by kind (present in unfiltered/`trail`-adjacent search, invisible to any `--kind` query) — a real behavioural difference, not a style choice. This needs one sentence in Interfaces before the Phase 1 query task and the Phase 2 global-kind task both lock in a `--kind` value list independently.
- **Non-blocking — whether `--global` self-registers the invoking project.** Interfaces § Global registry: "`search` and `index` **without** `--global` upsert `(root, base name, now)` into the global `projects` table after the project reconcile. `--global` reconciles `~config`... then each **registered** project." Taken literally, a project's very first-ever `sh-agent` invocation being `search --global` would reconcile every *other* already-registered project plus `~config`, but never register or reconcile itself (registration only happens on the non-`--global` path) — so a fresh project's own trail would be silently absent from its first global search. In practice this is unlikely to bite: `/init-project` and normal workflow will run a plain `search`/`index` before anyone reaches for `--global`, and the plan's own E2E criterion for `--global` is run from this already-dogfooded repository. A reasonable implementer would most likely make `--global` also perform the local project reconcile+register as a first step (matching user expectation that "global" includes "here"), so I call this non-blocking, but it's worth one explicit sentence given it's cheap to state and the current wording, read strictly, says the opposite.
- Everything else I checked against real repo state matches the plan's claims exactly (not just "R1 said so"): the pre-`ResolveSource` verb switch (`main.go`, `version`/`uninstall`/`report` cases before `harness.ResolveSource`) is exactly where D10 says `search`/`index` will sit; `reorder`'s `takesValue` map and its BUG-002 comment match the plan's flag-ordering claim; `report.go`'s `Collect` is a closed per-name allowlist (`feedback.jsonl`, `retros.jsonl`, `state.json`, `proposals/*.md`) with no wildcard, so "search.db is never collected" is accurate only once an explicit skip entry is added, which is exactly what the Phase 1 task and `TestCollectNeverSendsSearchDB` do; the ADR heading regex correctly parses every irregular status string I tried it against by hand (ADR-035's colon-containing title, ADR-039/042's "superseded... by ADR-041"/"superseded in part by ADR-044" trailing clauses, ADR-044's "amends ADR-042"); the handoff skill's fence-scan awk at `skills/handoff/SKILL.md:154` matches the plan's paraphrase exactly; a real `BUG-*.md` file's frontmatter (`id:`, `status:`, `date:`, `# ` title) matches Records § Bug, and `status: open` (not some other token) is the literal value used by all files carrying it, confirming `--open`'s bug clause.

## (1) Gaps

- **New — Interfaces item 2's insert-after-`{` technique produces invalid JSON for an empty settings file, and no recovery step is named for a failed parse check [medium-high severity, high confidence, BLOCKING].** Plan Interfaces, Step 5b item 2 (line 39): "present without the key → add the key with the Edit tool as one new line after the opening `{` (`"autoMemoryDirectory": "~/.config/sh-agent/memory/<slug>",`), touching no other line... then `python3 -c 'import json,sys; json.load(open(sys.argv[1]))' .claude/settings.local.json` to prove it still parses." When the existing file is `{}` (a freshly created or otherwise empty settings file — a real case: "present without the key" explicitly includes this), inserting a comma-terminated line right after the opening `{` yields `{\n  "autoMemoryDirectory": "...",\n}` — a trailing comma before `}`, which is invalid JSON and would fail the very parse check the plan specifies. The plan states the check but never what to do when it fails: retry with no comma, insert before the closing `}` instead, or a different technique for the empty-object case specifically. A literal implementation of the instruction as written is a bug that the plan's own verification step would catch at test time (if the fixture happens to include an empty `{}` case) but has no defined fix path — an implementer hitting this has to invent a recovery on the spot, and the init-project SKILL.md's Step 5b description (the actual buildable text an implementer edits) inherits whatever they invent. Fix: state the rule for the empty-object case (e.g., "when the file's only content is `{}`, write `{"autoMemoryDirectory": "...")}` with no trailing comma" or a general "look at the next non-whitespace character after the insertion point; add a comma only when it is not `}`"), and state what happens when the post-edit parse check still fails (abort and report the file's raw content for the user to fix, per the existing headless-refusal pattern).

- **D12's "empty store" message has no Failure-modes row or verify coverage, despite D12's claim [low-medium severity, high confidence, NON-BLOCKING for implementation, but a real verification gap].** D12 (line 115) says the "default store empty" behaviour is "in Interfaces, the Failure modes and the `init-memory-absent` runs." Checked against the actual text: Interfaces item 3 (line 40) does state it ("when `old` exists and is empty, print `default store empty at <old>`"). But the Failure modes table (lines 54–61) has only a row titled "No default store at the computed path... `no default store at <old>` plus the hint list" — nothing for the empty-but-present case — and the `init-memory-absent` matrix row's base is explicitly "the `init-memory` base **without the seeded default store**" (i.e. the absent case, not an empty-but-present one) with a check that only greps for `no default store at`. So the "empty store" message is specified once (Interfaces) and never exercised by any stated verify clause or matrix row — it could ship silently broken (wrong message text, wrong trigger condition) and nothing in the plan's Verification section would notice. Since the text in Interfaces is unambiguous, this is not a fork-in-implementation risk (NON-BLOCKING), but it is a coverage gap worth a Phase-1 task or a third matrix-row variant before this is called tested.

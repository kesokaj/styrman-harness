This is the `review-standards` §3 rule that every restatement of a changed rule changes with it. Fix: `"signal": "correction|override|restatement|format|gap|redirection"` at `:48`.
- **[medium / confidence: high]** `agents/verifier.md:18` vs `agents/verifier.md:71` — the rewritten rule requires the log to carry "a Status line of IN PROGRESS", and states that "a log that still says IN PROGRESS when the run is cut off is a failed dispatch", but the Verification log template in the same file declares `## Status: PASS | FAIL | BLOCKED`. `IN PROGRESS` is not a legal value of the field the rule now depends on, and the caller (and `/preflight`) reads that Status line. Fix: add `IN PROGRESS` to the template's Status line (`## Status: IN PROGRESS | PASS | FAIL | BLOCKED`) in the same change.
- **[low / confidence: medium]** `agents/verifier.md:18` vs `agents/verifier.md:24,28-34` — "Write your log file after the FIRST command you run" is unsatisfiable as written on the Pre-flight path: the first commands are `pwd` and `git status --short`, and `$docs_root` is not resolved until Pre-flight step 1, which runs after them; the BLOCKED early return also sits before any write. BUG-083 records this rule binding in only 1 of 3 runs, and an instruction an agent cannot follow at the moment it names is a plausible contributor. Fix: phrase it as "after the first verification command" (i.e. after Pre-flight resolves `$docs_root`), or move the `pwd`/`git status` orientation explicitly outside the count.

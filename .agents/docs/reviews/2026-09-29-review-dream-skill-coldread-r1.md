# Review — dream-skill-coldread-r1   (2026-09-29)

Range reviewed: `.agents/docs/plans/2026-09-29-dream-skill.md` (cold-reader check, not a diff), plus the code/docs surfaces it names: `REQUIREMENTS.md`, `internal/harness/inventory.go`, `skills/retro/SKILL.md`, `.agents/docs/testing/skill-matrix.md`, `.agents/docs/plans/2026-09-29-research-memory-and-prompt-audit.md`, and the operator's real Claude Code auto-memory store (`~/.claude/projects/-home-kesokaj-workspace-styrman-harness/memory/`).

## Status: COMPLETE

## Verdict: design needs revision / implementation not ready

The plan is unusually well-grounded for most of its claims (the store path formula, the frontmatter shape, the `originSessionId`/`modified` fields, and the agy-has-no-memory conclusion all check out against the real filesystem and the sibling research doc). But its one load-bearing, untested claim — that Claude Code has a settings key `autoMemoryDirectory` and a `--settings` flag that can redirect the auto-memory store for a test run — has zero citation anywhere in this repo or on this machine, unlike every other factual claim in the plan and its sibling research doc, and the entire Phase 1 behavioural design (fixture isolation, the control run, the "5 of 5" expectation) depends on it working exactly as assumed. A second interface gap (what "originSessionId differs" means for a `promote` verdict, given the real store shows exactly one `originSessionId` per file) would produce two different fixtures from two implementers. Both are answerable in one sitting but must be answered before Phase 1 is dispatched.

## (1) Gaps

- **[high / confidence: medium] `skills/dream/SKILL.md` interface, lines 40, 95, 120 — `autoMemoryDirectory` and `--settings` are asserted as fact with no citation.** Every other factual claim in this plan and in the sibling `2026-09-29-research-memory-and-prompt-audit.md` carries an evidence trail ("verified 2026-09-29", a doc URL, `strings $(which agy)`, a forum thread). This one has none. `grep -rn autoMemoryDirectory` over the whole repo and a filesystem-wide search for the string on this machine (`~/.claude/settings.json`, every JSON file under the home directory) turn up nothing outside the plan itself. If the key doesn't exist, or is named differently, the Phase 1 behavioural run's fixture-isolation mechanism (`--settings '{"autoMemoryDirectory":"<clone>/.agents/scratch/mem"}'`) silently does nothing: Claude Code falls back to the real per-project default store for the scratch clone's own absolute path (which is empty, not wrong-but-different), the seeded five-memory fixture is never read, and the run fails in a way that looks like a skill defect rather than a wrong assumption about the CLI. The Risks section (line 120) only checks "accepts a relative path or a path inside the repository", which presupposes the key already works — it does not check that the key exists or has any effect at all. Fix: confirm the key and the flag against Claude Code's actual settings schema (the docs page the sibling research doc already cites, `code.claude.com/docs/en/memory`, or a direct probe: run `claude -p` with `--settings` pointing at a scratch dir and confirm a memory write lands there) as the literal first task, before anything else in Phase 1.
- **[medium / confidence: medium] `promote` verdict test, line 53 vs. the observed real store — "seen from two or more sessions (`originSessionId` differs)" does not correspond to any field shape the real CLI produces.** Every memory file examined in this project's actual store (`asking-format.md`, `fallback-paths-stay-simple.md`, `read-neighbours-before-inserting-rules.md`) carries exactly one `originSessionId` in its frontmatter — never a list, never two. It is unclear whether "differs" means: (a) two separate memory files about the same fact with different `originSessionId` (but that is already the `merge` verdict's trigger — "two files on one fact" — making `merge` and `promote` compete for the same fixture), or (b) a single file whose `originSessionId` changes across edits (unconfirmed that Claude Code ever rewrites a memory file in place rather than deleting/recreating it). The plan's own Phase 1 fixture (line 95) asks for "one `feedback` with two `originSessionId`s" as a single seed distinct from the `merge` pair — which, given the one-field-per-file format actually observed, isn't achievable by any real memory file the CLI writes. Two implementers would build two different fixtures here. Fix: state precisely what a promotable memory looks like on disk (most likely: it is decided from the `merge` pair plus a cross-check against `~/.config/sh-agent/feedback.jsonl`'s `originSessionId`s for the same `rule_ref`/topic — the plan already names that second path at line 53's parenthetical — and the "originSessionId differs" clause should be dropped or rewritten to describe that comparison instead of an in-file property).
- **[low / confidence: low] Skill-matrix row, Phase 2 task "`skill-matrix.md` row `dream`" (plan line 112) — the matrix's existing seeding conventions don't cover this skill's fixture.** `.agents/docs/testing/skill-matrix.md` § Procedure seeds every row from either `feedback.jsonl` entries or a committed code regression on one reused demo-app clone; no row redirects a per-project store the way this skill's own Phase 1 test does with `--settings`. The plan doesn't say whether the matrix row reuses that override (not mentioned in the matrix's Procedure section, which the plan doesn't propose editing) or seeds the fixture some other way compatible with the matrix's per-run throwaway clone path. Non-blocking — a competent implementer can adapt the `review-prompts` row's precedent (which added an `--add-dir` variant for its own need) — but it is unaddressed, and the checkpoint task ("the row's check command runs on the fixture", line 112) can't be verified until this is decided.
- No Verification clause names an implementation choice beyond what's above, and no test fixture in the plan is contradicted by a syscall or code path I could find — the store-path formula, the frontmatter fields and the agy-has-no-memory conclusion are all confirmed against the real filesystem.

## (2) Scope

Everything in `## Scope — In` traces to the `## Why` paragraph (auto memory sits beside the learning loop, unread by it; a graduated memory keeps loading for nothing). No extra endpoint, no second shape for the same operation, and no configuration surface for a value that doesn't vary — `<store>` legitimately differs per project, and `--dry-run` is the one flag, matching the harness's existing `--dry-run` convention on `/retro`. The `## Scope — Out` items (no Antigravity store, no timer, no third-party plugin, no cross-project read) are each grounded in a D-row (D4, D6) or the sibling research doc's Part 1 conclusion. Nothing found here that the request didn't name.

## (3) Readiness

Questions a first-pass implementer would have to ask:

1. **BLOCKING** — Does Claude Code actually expose `autoMemoryDirectory` as a settings key, and does `--settings '{...}'` on `claude -p` honor it? (Gap 1 above.) Two implementers who guess differently here either build a working fixture-isolation mechanism or one that silently no-ops.
2. **BLOCKING** — What exactly makes a memory `promote`-eligible on disk, given a real memory file carries one `originSessionId`? (Gap 2 above.) Two implementers would seed and detect this differently.
3. NON-BLOCKING — How is the skill-matrix row's fixture seeded, given the matrix's existing conventions don't cover a per-project auto-memory redirect? A reasonable implementer follows the `review-prompts` row's precedent (add whatever flag/`--add-dir` the row needs) and documents it in the matrix's Procedure section as part of the same task.
4. NON-BLOCKING — Ordering of the record-write vs. the deletions when the operator approves edits (line 64's "the table is the undo point"). A reasonable default is: write the record with full quoted text first, then delete, so a partial failure still leaves recoverable evidence; the plan doesn't say this explicitly but nothing in Verification depends on the order.
5. NON-BLOCKING — Exact YAML key path for `type` (`feedback`/`project`/`user`/`reference`) used by the `stale`/`promote` verdicts — the real files observed here only exemplify `type: feedback`. Since this is a natural-language skill instruction, not code, an implementer reading a `project`-typed file when one appears will handle it the same way; not a coding interface that needs pinning now.

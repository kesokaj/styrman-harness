## Verdict: FINDINGS (all low; the two round-2 defects this delta targeted are closed and verified)

Nothing in this delta is exploitable as it stands, and the round-2 bypass is genuinely gone: a named `--repo` or `$SH_AGENT_REPO` that is not a checkout is now an error, so there is no longer a value that disables `knownCheckout` while the repo comes from the directory walk. Verified against a scratch lookalike with a manifest naming a different installed checkout — neither-named refuses, `SH_AGENT_REPO=/nonexistent-not-a-harness` errors, `--repo /nonexistent-not-a-harness` errors, all three without building anything. What is left is fragility rather than a hole. The guard still asks "is this flag non-empty?" while its correctness now depends entirely on an invariant living in another package (`FindRepo` returns a path derived from that flag or nothing at all), and no test binds the two — re-add one usability fallback to `FindRepo` and round-2 finding 1 silently returns with a green suite. Alongside that: `$SH_AGENT_REPO` is an inherited environment variable that switches the manifest comparison off completely, and the real (non-dry-run) install path never prints which tree it built from, so a stale export or a wrapper substituting the checkout is invisible; and `git -C <dir>` ascends to an enclosing repository, so the "reads the checkout's git state" claim in the new comment, the manifest's `Commit` provenance stamp, and `update`'s `git pull --ff-only` can all be about a different repository than the one being installed.

My recommendation on process: this mechanism has converged. Nothing above medium remains, the two named round-2 items are closed, and the residual items are either one line of hardening in `knownCheckout` or belong to `gitOut`, a different mechanism. A round 4 on the guard is not warranted; findings 3 and 5 below should be tracked as their own small item rather than another round on this code.

## Findings

- **[low / confidence: high]** `cmd/sh-agent/main.go:341` — `knownCheckout` returns nil on the *non-emptiness* of `repoFlag` / `$SH_AGENT_REPO`, not on the named value being the one that produced `repo`. The round-2 bypass is closed only because `FindRepo` (`repo.go:21-28`) now refuses a named non-checkout instead of walking, i.e. the guard is correct by an invariant held at a distance, in another package, with no test asserting the coupling. `TestKnownCheckout` (`main_test.go:135-164`) calls the guard directly with hand-supplied arguments and therefore cannot notice if `FindRepo` starts falling through again; the obvious future edit ("a typo'd `--repo` shouldn't hard-fail, keep walking") reinstates a bypass that runs `go build` in an operator-unchosen tree and deploys it to `~/.claude`, `~/.gemini/config` and `~/.local/bin/sh-agent` (`repo.go:107-134`, `apply.go`). Remediation, one line and self-contained: compare values instead of emptiness — `if (repoFlag != "" && samePath(repoFlag, repo)) || (env != "" && samePath(env, repo)) { return nil }` — which makes the guard true on its own terms regardless of what `FindRepo` does later.
- **[low / confidence: high]** `cmd/sh-agent/main.go:341`, `internal/harness/repo.go:21` — `$SH_AGENT_REPO` is an inherited environment variable and it disables the manifest comparison entirely, and the real install path prints nothing about which checkout it built from. Verified with `--dry-run` only: `SH_AGENT_REPO=<lookalike> sh-agent install --home <scratch>` with a manifest naming a different installed checkout plans `write ~/.claude/AGENTS.md`, `write ~/.gemini/config/rules/AGENTS.md`, `write ~/.local/bin/sh-agent` from the lookalike — the guard is satisfied because the operator "named" it. That is the accepted design, and the design is defensible; the gap is that the naming channel is the same kind of ambient state as `SH_AGENT_CHILD` (round-1 finding 6) — a stale `export`, an `.envrc`, a wrapper script, or a parent process (an agent session included) names it just as well as the operator does, and the guard docstring's "standing in a harness-shaped directory (a mirror, a clone under review) must not be enough" does not hold when an env var points at that same directory. Remediation without changing the policy: print the source on the build path too, not only under `--dry-run` (`main.go:124`) — e.g. `building from <repo> (named by $SH_AGENT_REPO)` before `Reinstall` — so a substituted checkout is visible in the transcript the operator reads.
- **[low / confidence: high]** `internal/harness/repo.go:137` (`gitOut`), reaching `apply.go:79-81`, `repo.go:70-72,78-81,91-96` — `git -C <dir>` ascends to an enclosing repository when `<dir>` is not itself a git root, and `IsRepo` (`repo.go:49-56`) is two stats that never ask. Verified in the scratchpad: from a non-repo directory nested inside a git repo, `git -C <inner> rev-parse --short HEAD` returns the *outer* repo's commit and `git -C <inner> status --porcelain` the outer repo's status. Three consequences inside this delta's blast radius: (a) the new comment's claim that a dry run "still reads the checkout's git state" (`main.go:119-121`) is false for a plain copy nested in another repo — it reads the enclosing repo's; (b) `Install` stamps the manifest `Commit`/`+dirty` from that unrelated history (`apply.go:79-83`), so the provenance record and `status`'s "older than the repo" comparison describe a different tree — and `TestInstallMarksDirtyTree` (`harness_test.go:682-717`) passes either way because its fixture is its own git root; (c) `update` runs `git fetch --quiet` and `git pull --ff-only` in that directory (`repo.go:78,94`), which on a nested copy fetches and fast-forwards the *enclosing* repository — a write to a repo the operator did not name. Remediation: pin the git root — pass `--git-dir`, set `GIT_CEILING_DIRECTORIES`, or assert `rev-parse --show-toplevel == repo` once in `gitOut` and treat a mismatch as "not a git checkout" (which is the contract `Inspect` already documents).
- **[low / confidence: high]** `cmd/sh-agent/main.go:113,163` vs `internal/harness/repo.go:70-72` — the rebuttal for leaving `status`/`diff`/`adopt` outside the guard ("they never build or write into the home") is accurate about those two effects and incomplete about a third: they run git subprocesses *inside the walk-discovered tree*, and git executes programs named by repository-local config (`core.fsmonitor` for `status --porcelain`; more for `fetch`/`pull`). Verified that the invocations happen: `sh-agent status` run from inside the lookalike printed it as `repo`, read its branch/commit/dirty state, and enumerated its skills, with no guard in the way. `safe.directory` does not help when the hostile checkout is owned by the invoking user, which is the normal case for a clone under review. I did not plant repo-local config or demonstrate execution — no exploit, by policy — so treat the execution step as argued, not shown. Remediation is not more guard wiring: harden `gitOut` once for the read-only queries (`-c core.fsmonitor=`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`) and every caller, guarded or not, benefits. This is round-1 finding 7 restated because the round-2 rebuttal touched it; it is pre-existing and outside the changed lines.
- **[low / confidence: medium]** `cmd/sh-agent/main_test.go:184-186` — the cross-package race is genuinely fixed (the repo-wide glob is now a stat of this process's own `sh-agent-build-<pid>`), but the assertion it replaced it with cannot fail: `Reinstall` does `defer os.RemoveAll(dir)` (`repo.go:115-118`), so the build directory is gone by the time any call returns, whether or not a build happened. It is a monitor that reports nothing because it cannot emit, which the global rule names specifically. The test is still sound — its second assertion (`<home>/.claude` absent) does fail on a regression, and harder than before: since the child is no longer passed `--dry-run` (`main.go:126-135`), a regression would perform a *real* install into the scratch home. Remediation: drop the build-dir stat as evidence-free, or keep it and say in the comment that the `.claude` assertion is the load-bearing one, so a later reader does not mistake it for the proof.
- **[low / confidence: high]** `internal/harness/repo.go:112` — `govulncheck ./...` still reports two reachable stdlib vulnerabilities on go1.24.4: **GO-2025-3956** (`exec.LookPath`, fixed go1.24.6) traced to `Reinstall`, and **GO-2026-4602** (`os`, fixed go1.25.8) traced to `LoadSkills` (`inventory.go:71`). Tracked in `TODO.md:15` as a toolchain upgrade, not a code change, and accepted as such; on the register because the first lands on exactly the `go` lookup whose result `Reinstall` then executes, so it compounds the guard's job rather than sitting apart from it.

### Round-2 findings this delta closes

- **Round-2 finding 1 (guard bypassed by any non-empty `--repo`/`$SH_AGENT_REPO`) — closed, verified.** `FindRepo` now returns `"<path> is not a harness checkout (no context/AGENTS.md and skills/)"` for a named non-checkout instead of walking. Re-ran the round-2 cases against a lookalike with a manifest naming a different installed checkout: case A (neither named) refuses with the guard's message, case B (`SH_AGENT_REPO=/nonexistent-not-a-harness`) errors, case C (`--repo /nonexistent-not-a-harness`) errors. No build directory appeared and nothing was written into the scratch home in any case. The residual is shape, not behaviour — first finding above.
- **Round-2 finding 2 (guard fails open on a `LoadState` error) — closed, verified by reading.** `main.go:344-347` now returns `fmt.Errorf("reading the manifest before building: %w", err)`; only `!found || st.Repo == ""` (first install) still passes, which is the intended fail-open. This matches every other `LoadState` caller in the package.
- **Round-2 finding 3 (dry-run comment overclaimed) — closed by accurate documentation.** The comment now says a dry run still reads the checkout's git state, which matches `apply.go:79-81` running `rev-parse` and `status --porcelain` unconditionally. The accompanying reasoning ("any checkout that is installed from is trusted, and the guard makes it one the operator named or installed before") holds for the guarded commands; see the fourth and third findings for the two places where it does not — unguarded `status`/`diff`, and the enclosing-repo ascent.
- **Round-2 finding 5 (cross-package test race on the build-dir glob) — fixed;** see the fifth finding for what the replacement assertion does and does not prove.

## Checked

- **Secrets** — none. Grepped the delta for password/secret/token/api-key/bearer/`AKIA`/`ghp_`/PEM patterns: zero hits. New error strings disclose local directory paths (the candidate checkout, the installed checkout, the manifest path) to the operator running the command, never environment values or file contents; no secret-shaped file in the range.
- **Injection** — no shell on any path. Every subprocess is `exec.Command` with an explicit argv (`repo.go:94,109,121,126,138`; the test helper `gitIn` likewise), so `--repo`/`--home`/`$SH_AGENT_REPO` values cannot break out of argv. The live surface is a *path*, not a string: which tree gets compiled and executed, and which git repository `-C` resolves to — findings 1-4.
- **Authz/authn** — no identity surface; the tool runs wholly as the invoking user. The boundary is process trust (which tree is built, which binary is executed, which context is deployed into both CLIs), which is precisely what `knownCheckout` gates; the manifest it reads lives in the home it is protecting, so an attacker who can write `~/.config/sh-agent/state.json` could also write `~/.local/bin/sh-agent` directly — not a new boundary.
- **Crypto** — nothing cryptographic, nothing hand-rolled, nothing added. `samePath` (`main.go:357-364`) uses `filepath.EvalSymlinks` and falls back to raw string equality when either side fails to resolve, which is fail-closed for a refusal decision (a moved or deleted previous checkout compares unequal and the run is refused). The `Commit`/`+dirty` stamp remains a freshness hint, not an integrity check — and per the third finding it may be a hint about the wrong repository.
- **Dependencies** — `go.mod` declares no third-party requirements and this delta adds none (stdlib only, per the repo rule); the new test imports are `fmt` and the already-present `os/exec`/`strings`. `govulncheck ./...`: exit 2, the same two reachable stdlib vulnerabilities as round 2, plus 2 imported-but-uncalled and 43 required-but-uncalled. `npm audit` not applicable and not run — no `package.json`, pure Go module. `go version go1.24.4 linux/amd64`, `git version 2.47.3`.
- **GCP surface** — nothing touched. No IAM binding, service account, Cloud Run flag, `--allow-unauthenticated`, or key file anywhere in the range.
- **Build/test health** — `gofmt -l .` clean, `go vet ./...` clean, `go test -race ./...` green (`cmd/sh-agent` 1.127s, `internal/harness` 1.376s).

## Findings

- **[low / confidence: high]** `agents/verifier.md:14` with `:38` and `:76`.
  - The text: "re-dispatches with the command quoted and the same slug, so that this log is the one updated and no BLOCKED log is left behind".
  - Why it fails: the log is `$docs_root/testing/$(date +%F)-verify-<slug>.md`, named for the run's own date. When the main agent re-dispatches with the same slug on a later day (a gate that crosses midnight, or a fix taken up in the next session), the verifier writes a new file and the BLOCKED log stays in the range.
  - Who is misled: the main agent, who believes the same-slug re-dispatch clears the gate. `skills/preflight/SKILL.md:61` ("A log in the range whose Status is FAIL or BLOCKED is carried to Step 5 as it is and blocks there — never replaced by a re-run cited alone") then makes it NO-SHIP.
  - Fix, `:14`: "re-dispatches with the command quoted and the BLOCKED log's path, which this run updates in place (keeping its file name), so that no BLOCKED log is left behind". `context/AGENTS.md:15` needs no change.
  - Owner: main.
- **[low / confidence: medium]** `agents/verifier.md:79`.
  - The text: "`git init -q` the copy's directory first … without a `.git` of its own, a git command in the copy acts on the real repository, and a test that reads git fails for that reason alone. Run the copy's must-pass first, so that a must-fail result is the mutation's."
  - Why it fails: a fresh `git init` tracks nothing. A test that reads what git tracks still fails in the copy for that reason alone. In this repo that is `TestEmbedHoldsOnlyTrackedFiles` (`embed_test.go:54`, `git ls-files` at `:62`), so the copy's whole-suite must-pass is red before any mutation.
  - Who is misled: a verifier that follows the text expects a green must-pass in the copy. When it is red, the definition gives no next step: stop, narrow, or `git add` and commit in the copy. A verifier may cite a must-fail that is not the mutation's, or write BLOCKED for no reason.
  - Fix: append "a must-fail result counts only for a test that passed in the copy's must-pass; a test that fails there (one that reads what git tracks fails in a fresh `git init`) is named, and that control is not evidence".
  - Owner: main.
- **[low / confidence: medium]** `skills/preflight/SKILL.md:61` vs `agents/verifier.md:14` and `skills/preflight/SKILL.md:88`.
  - The text, `:61`: "whose `## Status:` heading is PASS satisfies this row …; carry whatever its Scope line names as not run (a tier, a command the change edited) to the gate report's 'What was not checked', where Step 5 reads it against the blocking conditions."
  - Why it fails: the verifier's contract says an edited command named as not run makes the Status "`BLOCKED`, never `PASS`". Step 5's blocking list (`:88`) has no condition for an unrun edited command. A log that breaks that contract (a PASS whose Scope names an edited command as not run) therefore satisfies the row and ships.
  - Who is misled: the main agent at the gate, who is told the item is "read against the blocking conditions" when none of them matches it.
  - Fix, `:61`: "(a tier; a command the change edited, named as not run, makes the row unmet as BLOCKED does)".
  - Owner: main.
- **[low / confidence: low]** `skills/VENDORED.md:58-59` vs `skills/google-catalog/scripts/refresh-catalog.sh:46-49`.
  - What the script's header now says: "While git runs, the value is one of its arguments, which other users of the machine can read in the process list, and `bash -x` prints it: a token belongs in a credential helper, never in the URL."
  - What `VENDORED.md` still says: the script "never shows or records such a value", with no caveat. `VENDORED.md` is the page `skills/google-catalog/SKILL.md:23` sends a refresher to.
  - Who is misled: an operator on a shared machine who reads only `VENDORED.md` may put a secret-bearing path into an override. The value is limited to an `https://` URL with no user information or query string, or an absolute path, hence low.
  - Fix: after "terminal prompt are off for the script's calls", add "; while git runs the value is in the process list, so a token belongs in a credential helper".
  - Owner: main.

## Verdict: FINDINGS

Four findings, all low. No high, no medium. Worst first: the kit preamble's new fingerprint never descends a symlinked `~/.config/sh-agent`, and it skips a symlinked file inside it. That layout is one the installer supports: `internal/harness/state.go:104` prints a note for it. In that layout, a run that appends to the real feedback log, or adds a file there, leaves the fingerprint unchanged and the kit passes. This was probed with the shipped function, with must-pass and must-fail controls. `find -L` closes both cases. Second: the refresh script's new pin check still accepts a tag named like a short pin when the tag's commit was minted with the pin's prefix. That costs about 2^28 hashes for the 7-digit pins `VENDORED.md` records. Third: the gate now works out the edited verification commands itself, but only from `AGENTS.md` and `testing/guide.md`. Steps defined elsewhere (this range's own new matrix row, the kit preamble) are not on its list. Fourth, older: in a repository without tags, the gate's base comes from a file the gated range can add. On the dispatch's other questions there is no finding: the copy recipe, the log rules, `KIT_ASSERT_COMMIT` (probed) and govulncheck.

1. **[low / confidence: high]** `.agents/docs/testing/kit-preamble.sh:70-73` (`kit_fingerprint`, the two `find` calls at `:71-72`). The claim that it works is restated at `:57-60` ("covers names and contents"), `.agents/docs/testing/guide.md:178` ("a run that writes the real config (the kit fails)"), `.agents/docs/bugs/BUG-158-kit-preamble-died-without-config-dir.md:20` and `bugs/INDEX.md:112`.
   - **Weakness:** `find` defaults to `-P`, so it does not follow a symlink, not even the starting point.
     - When `~/.config/sh-agent` is a symlink to a directory, both finds print only the link, and the fingerprint is constant.
     - A symlinked file inside a real directory fails `-type f`, so its content is never checksummed.
     - `kit_list_real_config` (`:69`, `ls -la` on the link) shows only the link, too.
   - **Actor and path:** any agent or CLI under test in a kit run that writes the real config, as BUG-107 and BUG-123 recorded. This gate saw it once more: changes entry `:23`, a run voided because the real search index changed. The machine needs a symlinked config directory or files, which dotfile managers do and which the installer accepts (`state.go:104`).
   - **Probed:** the shipped lines `:63-73` were run in scratch homes, and the instrument was validated first: no change gives SAME, an append to a plain directory gives DIFFERS.
     - A symlinked directory, after an append: SAME. After a new file: SAME.
     - A symlinked file, after an append: SAME.
     - With `find -H`, both directory cases are DIFFERS, but the symlinked file is still SAME.
     - With `find -L`, all three are DIFFERS.
   - **Fix:** use `find -L "$kit_real_config"` in both calls. `find` reports a loop on stderr, which is already discarded. Add two cases to `TestKitPreambleAssertsCommit`: the config directory as a symlink, and a symlinked `feedback.jsonl`, each with an append, each wanting exit 1.

2. **[low / confidence: high on the mechanism]** `skills/google-catalog/scripts/refresh-catalog.sh:227-233` (checkout, then the new prefix check). The pin shape is checked at `:170-174` (7 to 40 digits), and the pins recorded at `skills/VENDORED.md:45` are 7 digits (`2c39459 and d5d9052`). The claim "a pin that names a tag or branch at the source is refused" is made at `skills/VENDORED.md:48`, `guide.md:145`, `bugs/BUG-155-…md:29` and the changes entry `:14`.
   - **Weakness:**

     - Correct the four restatements to "a short pin is refused" or "only a full id".
   - **Exposure if shipped:** a short pin's content is still chosen by whoever names refs at the source, at small cost. "The pins identify the content" (manifest template `:366`) holds only for a full id.

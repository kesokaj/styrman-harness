## Verdict: FINDINGS

**No high in the range, so under preflight nothing here blocks.**

**The worst item is the unsigned-zip medium, still open by decision and waiting on the operator.** `update --from-zip` installs an archive nobody verified as the global context of both CLIs and as subagent definitions. Three files record it as awaiting the operator: ADR-038 Consequences, the plan's Follow-ups and the 1752 change entry. No trail file records the operator accepting it. Preflight Step 6 requires the gate report to record that decision (accepted, and named in the release entry with its reason) before the tag.

**Second: the skill-matrix sandbox grants.** They were accepted under option 1. This review rates them medium, where r2 and r3 said low: the lists are now wider than when the 381e86d report rated them medium, and the one "protection" the matrix names does not cover what it says is in reach.

**Every item changed after r3 holds up**, checked by reading and by the targeted tests:
- the sweep now runs after a successful install;
- a `-`-prefixed value is refused;
- the `RemoveAll` warning is in `updateFromZip`;
- `isolate` is in `TestFromZipRefusedOnOtherCommands`;
- ADR-034's heading and ADR-038's Rejected bullet are fixed.

What remains is low.

## Findings

- **[medium / confidence: high]** `cmd/sh-agent/main.go` `updateFromZip`, ADR-038 Consequences — **an unverified zip becomes agent instructions.** Carried from update-from-zip r1–r3. **Status: open by decision, pending the operator.**
  - **Why it is exploitable in principle.** Suppose the operator is induced to download the wrong zip: a look-alike repository, a tampered mirror, or a swapped file on the corporate machine.
    - That zip becomes `~/.claude/AGENTS.md`, the agy rules, and the skill and agent definitions (agents with `Bash`).
    - Those run with the operator's credentials.
    - The printed sha256 has no reference value to compare against.
    - `status` says `from zip sha256:…` but never "unverified".
  - **Bounded this round.** The installer writes into `~/.claude/settings.json` only the constant attribution fragment (`main.go:779-836`), never content from the tree. So a zip cannot plant Claude Code hooks: its reach is instructions and agent definitions, not direct execution. That is why this stays medium.
  - **Remediation, unchanged and with no new dependency:**
    - `/preflight` publishes a `git archive` zip listed in the already-signed `SHA256SUMS`.
    - `--from-zip` checks its `crypto/sha256` through `release.go`'s existing `ssh-keygen -Y verify` path.
    - `status` says `unverified` for a zip install.
  - **Until then:** the operator's explicit acceptance goes into the gate report and the release entry. ADR-038 ("awaits the operator's decision") is not that acceptance.

- **[medium / confidence: medium]** `.agents/docs/testing/skill-matrix.md:13-14` — **the sandbox allowlists reach the operator's real credentials.** Accepted under matrix option 1 (plan D5; Outcome of `review-v1.7.0-381e86d-code.md`).
  - **What the text gets right.** It says the list "is NOT a security boundary" and that `go`, `git`, `bash` and `python3` "reach the real home".
  - **What it gets wrong.** The next sentence, "The protection is that the copied token lives only for the batch and is deleted by name after it", protects only the copy. The real reach, per the 381e86d report, is:
    - the real `~/.ssh`, because OpenSSH resolves it through passwd, not `$HOME`, which matters on a machine that also holds the release-signing key;
    - the real CLI and `gh` tokens.
  - **`sh-agent` is fully granted.** `Bash(sh-agent:*)` and `command(sh-agent)` include `report`, whose push BUG-094 proved is real.
  - **Untrusted content can enter a run.** Plain `curl` is granted under `acceptEdits`, so the `research` and `find-skills` rows can fetch web pages into a run.
  - **Why medium.** The lists are wider than when the 381e86d report rated this medium: `bash`, `python3` and plain `curl` were restored. Acceptance changes the status, not the severity. It is not shipped code, and it does not block.
  - **Remediation:**
    - replace the "protection" sentence with the residual itself: a run can read and send anything the operator's UID can;
    - narrow `sh-agent` to the verbs the rows use;
    - the only real boundary is a separate OS user, or a container without the operator's home. That is the operator's design decision.
  - The 381e86d `toolPermission` finding is partly closed. A `grep -c toolPermission … printing 0` check before the batch is now named, but there is no parse check and no must-fail proof.

- **[low / confidence: high]** `internal/harness/zip.go:86-90` — **`UnpackZip`'s deferred `os.RemoveAll(tmp)` still discards its error.** This is the residual of r3's finding 3; the `updateFromZip` site now warns.
  - **What a failed removal leaves.**
    - A refused zip whose `zip-*` cannot be removed leaves it under `~/.config/sh-agent`.
    - `RemoveCreated` then silently keeps the chain as well.
    - A later successful run's sweep reports it only after an hour.
    - Under the system temp directory (a dry run on a fresh home), it is never reported.
  - **Why low.** The content is the zip's five trees inside a 0700 directory, so nothing is exposed.
  - **Remediation:** join the cleanup error into the returned error (`errors.Join`).

- **[low / confidence: high]** **Texts that state a removed or superseded property.**
  - `internal/harness/repo.go:23-28` says "A RELEASE binary installs the harness built into it and nothing else … signed and verified on the way in … no tree on this machine takes part: … not one named on the command line".
    - This is false since `--from-zip`: a release binary now installs a tree nobody verified, unpacked from a file named on the command line.
    - It states the very trust property the first finding is about, and a reader takes it as a guarantee.
    - Fix: add "except a zip named with `update --from-zip` (ADR-038), which is not verified".
  - `.agents/docs/plans/2026-09-28-update-from-zip.md:28` (Scope, Out) still gives "a zip is unsigned and trust rests on the operator's own download" as a constraint. r3 had that reason reworded in ADR-038, and the plan's own `:33` calls it a pending operator decision.
  - ADR-038 "What is unpacked" still omits the 64 MiB archive cap and the 1,024-byte / 32-level name bounds. This understates the protections, so it is harmless.
  - BUG-093's Fix section and the E2E log's "Fix made during the E2E" describe the first of three layers ("`UnpackZip` creates its own parent directory, only after every entry-name check"). D13 and the 1752 entry record the final mechanism: `updateFromZip` creates the chain with `MkdirAllTracked` and removes it on any failure. Past records are append-only, so this is noted, not a request to edit them.

# Review — preflight v1.2.1 code   (2026-09-18)

Range reviewed: v1.2.0..288e52d (`main`, tree clean at review time; sources read from the working tree, which matches 288e52d)

## Verdict: APPROVE WITH NITS

Nothing in this range is broken. `ResolveSource`'s split does what ADR-034 says: a release binary cannot reach a tree by any path (working directory, recorded manifest path, `--repo`, `$SH_AGENT_REPO`), a development build keeps plan D4's order unchanged, and the D15 "refused, never silently replaced" habit is preserved in both branches. `shedKeptClone` is correctly gated off `--check` and runs on the release-binary up-to-date path. The one thing worth fixing before or with the release is documentation, not code: `README.md:132` still states the old source order as unconditional, so the file that describes the flag now contradicts the binary (project `AGENTS.md`: "a new command, flag, endpoint, or deploy step is not done until the file that describes it says so"). That is medium, non-blocking by the letter of this repo's rules only if `/review --docs` and the `documentation` step pick it up in this same release; otherwise v1.2.1 ships with a README that tells a bundle user to do something the binary refuses.

Verification run (read, not just cited): `GOPROXY=off go test -race ./...` → all three packages ok; `gofmt -l cmd internal` → empty; `go vet ./...` → clean. No network, no real `$HOME`, no tree-changing git command.

## Findings

- **[medium / confidence: high]** `README.md:132` — "Without `--repo`, sh-agent finds the checkout from `$SH_AGENT_REPO`, then the working directory or any of its parents, then the path it recorded at the last install" is now false for a release binary, which is the only kind of binary a README reader who followed § Install without cloning has. The same sentence still offers `--repo DIR` without qualification. Concrete failure: an operator on `argolis-devbox` or the Mac reads this paragraph, runs `sh-agent install --repo /opt/devbox/deploy/harness`, and gets the ADR-034 refusal the README says will not happen — the exact machine-stranding scenario BUG-077 came from, now with the docs pointing the wrong way. The change entry `.agents/docs/changes/2026-09-18-release-binary-only-embedded.md` § Docs considered only "README § Install without cloning" and missed this paragraph. Fix: add the release-binary clause to `README.md:132`, matching the usage text already updated at `cmd/sh-agent/main.go:50`.

- **[low / confidence: high]** `internal/harness/repo.go:36` — the refusal interpolates the path but not where it came from: for `$SH_AGENT_REPO` the operator sees `… so /home/x/harness is refused — drop it …` with nothing on their command line to drop. An exported `SH_AGENT_REPO` in a shell profile then blocks `install`, `status`, `diff`, `list`, `render` and `update` on that machine with a message that does not name the variable. This is the same class of defect as BUG-076, which this very release fixes elsewhere ("say what the code actually knows"). Fix: carry the origin into the loop and print `--repo` or `$SH_AGENT_REPO` alongside the path.

- **[low / confidence: medium]** `cmd/sh-agent/main.go:242-248` — `adopt --repo <checkout>` was reachable from a release binary before this change (the named tree became `src.Dir`); now it is refused at `ResolveSource` and the refusal's advice is install-worded ("build sh-agent from that tree and run that build's install"), while dropping `--repo` yields "adopt needs a harness checkout; this install is a release binary". The workaround is correct, so nothing is unreachable in practice, but ADR-034 and the plan line ("`adopt` requires a checkout and says so") do not name this as an intended consequence. Fix (optional): one clause in ADR-034's Consequences, or let `adopt` keep an explicit path.

- **[low / confidence: medium]** `cmd/sh-agent/main.go:199-205` — on the release path `shedKeptClone` runs *before* `UpdateFromRelease`, so the clone is shed even when the update then fails (no `gh`, a download or signature-verification failure, `ErrNewerRelease`). The checkout path sheds only after its refusal checks, i.e. only when the update will proceed. No data loss: `RemoveKeptClone` already refuses a dirty clone or one holding commits its remote-tracking refs lack, so the failure mode is only "a cleanup happened during a run that reported an error". Fix (optional): move the call after the `UpdateFromRelease` error handling, or state in the comment that shedding is deliberately independent of the update's outcome.

- **[low / confidence: high]** `internal/harness/harness_test.go:539-648` — coverage note on the question the dispatch asks. The development-build order is pinned for the explicit-path leg (`:584`), the recorded-path leg (`:592`), the `embedded:` skip (`:646`) and the not-found message (`:555-570`); `TestResolveSourceRefusesNamedNonRepo:838` pins the named-non-repo refusal for both kinds of build. The **working-directory walk leg is not pinned anywhere**: no test chdirs into a harness tree and resolves a development build with no `--repo` and no recorded state (`:546` uses the walk only as a skip-guard; `cmd/sh-agent/main_test.go` chdirs only into empty temp dirs at `:1077`, `:1179`, `:1290`). Deleting the walk from the development branch would leave the suite green. This is a pre-existing gap, not introduced by the split — the old test pinned explicit and recorded only, with a release version — but the split moved the walk into a branch that now has exactly one class of caller, which makes the gap easier to trip over. Fix: one case chdir'd into `repo` with an empty home asserting `src.Dir == repo`.

### Dispatch item 3 — `internal/harness/report.go`

Not in this range. `git diff v1.2.0..288e52d -- internal/harness/report.go` is empty; both message changes (`RemoveKeptClone`'s ahead-count basis, c7a6116; the settling-command wording, a1d2ee8) shipped **inside v1.2.0**. So "did a decision path change with them" is answered by construction for v1.2.1: `report.go` is byte-identical to the released v1.2.0. The only new caller of `RemoveKeptClone` is `shedKeptClone`, and it passes the same `(home, harness.FeedbackURL, out)` triple the checkout path always passed, with the same "reported, never fatal" handling — behaviour identical for both callers, verified by reading the extracted helper against the block it replaced.

### Dispatch item 1 — can a release binary still reach a tree?

No. `ResolveSource` returns before any candidate is built: `explicit` and `$SH_AGENT_REPO` error out, everything else returns `EmbeddedSource(version)` (`repo.go:34-40`). Downstream, `repo := src.Dir` is `""` for every release binary (`main.go:122`), which is what routes `install` to the embedded branch and `update` to `UpdateFromRelease`. A development build cannot reach `repo == ""` either — `ResolveSource`'s error is returned at `main.go:117` before the switch — so neither branch can be entered by the wrong kind of build. The recorded-path branch still skips an `embedded:` value (`repo.go:68`, pinned at `harness_test.go:646`). The refusal message leaks only the path the operator supplied plus the release version — no home, no manifest content. The duplication between the two `[]string{explicit, os.Getenv(...)}` loops is two lines and reads clearly; the drift risk is a third rule being added to one loop and not the other, which is speculative and not a finding.

### Dispatch item 2 — `shedKeptClone`

Runs on the release path whenever `!*check`, before `UpdateFromRelease`, so the up-to-date path is covered (pinned by `TestReleaseBinaryUpdateShedsKeptClone`, which asserts both `up to date (v1.0.0)` and the removal in the same run). Never under `--check` on either path (the same test asserts the clone survives `update --check`). The extracted helper is a verbatim move of the checkout path's block; both callers get identical behaviour.

### Dispatch item 4 — can the tests pass for the wrong reason?

`TestResolveSource`'s five release cases assert `src.Dir == ""` with `err == nil`, and the first also asserts `src.Version == "v1.2.3"`, so an error path cannot satisfy them and an accidental `DirSource("")` would still be caught by the version assertion in the first case. The refusal cases match on `"release binary"`, which only the new message contains. `TestReleaseBinaryUpdateShedsKeptClone` plants a real git clone with `origin` set to `FeedbackURL` and asserts the directory is gone *and* the message printed — it would fail if the call were removed, and its PATH holds only the fake `gh` and a symlinked `git`, so no network and no real `gh`. `TestReleaseBinaryWithoutCheckout` now asserts `"never a tree on disk"` for both a non-tree and a real tree, which the old code could not produce. One weakening: `TestResolveSourceRefusesNamedNonRepo:844,848` asserts only `err == nil` failure, so for `v1.2.3` it now passes on the ADR-034 refusal rather than the "not a harness checkout" refusal it was written for — still correct, still failing if the refusal were dropped, but no longer distinguishing the two. Not a finding. The uncovered leg is the development-build cwd walk, above.

## Outcome

Read against the diff by the main agent, 2026-09-18. All three findings fixed before the tag; the two lower notes answered.

1. **[medium] `README.md:132` still stated the old source order and offered `--repo` unqualified.** Correct, and my own miss: the changes entry's Docs section said README needed nothing because I checked § Install without cloning and not the § Daily commands paragraph that describes the flags. Fixed: that sentence now scopes the order to a build made FROM a checkout and says a release binary uses none of it and refuses `--repo` (ADR-034), matching `main.go`'s usage text.
2. **[low] the refusal named the path but not its origin.** Correct and worth the fix for the reason given: with `$SH_AGENT_REPO` exported in a shell profile, every command on the machine fails and "drop it" does not say what to drop. The message now reads `… so --repo=/path is refused` or `… so $SH_AGENT_REPO=/path is refused`. The test asserted only that the message named the release, so the mutation removing the origin PASSED at first — the assertion now requires the origin and the path, and the mutation fails.
3. **[low] the working-directory walk was pinned nowhere.** Correct, and pre-existing: deleting the walk kept the suite green. `TestResolveSource` now stands inside the tree and inside a nested directory under it and requires both to resolve to the tree; deleting the walk fails it.

**Answered, not fixed**

- **`adopt --repo` is unreachable from a release binary, which ADR-034 does not name.** True, and intended: `adopt` already refuses on a release binary with its own message (`adopt needs a harness checkout; this install is a release binary`), so the path was unreachable before this change too — ADR-034 did not create it. Recorded here rather than amending the ADR, which is append-only.
- **`shedKeptClone` runs before `UpdateFromRelease`, so it sheds during a run that then fails.** Accepted: what it sheds is a clone that is clean, fully pushed, origin-verified and not a symlink — dead weight by then — and shedding it does not depend on the download succeeding. Moving it after would mean a failed download leaves the machine holding other places' reports for another cycle, which is the worse end.

Security's three low findings for the same range are in `.agents/docs/reviews/2026-09-18-security-preflight-v1.2.1.md`; all three are fixed, one of them a regression this release introduced (an exported `$SH_AGENT_REPO` made `report` send a null record).

Must-fail, five mutations (`.agents/scratch/v121-mustfail/mutate.py`): a release binary reaching a tree again, the refusal losing its origin, the walk deleted, `RemoveKeptClone` accepting redirect variables, and `report` going back through the refusal — each fails the test that covers it, after the test for the second was strengthened. `gofmt`, `go vet`, `go test -race -count=1 ./...` clean.

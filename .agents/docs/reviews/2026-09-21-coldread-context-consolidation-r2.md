## (1) Gaps

- **Retro `SKILL.md` Step 2 "item 5" is a numbering collision and a sequencing gap.** Plan Interfaces (line 39): "Step 2 gains item 5: 'Before a harness proposal adds to `context/*.md` or `rules/*.md`… run `go test ./internal/harness -run TestRenderedContextFitsAntigravityBlock -count=1` with the addition in place…'" But `skills/retro/SKILL.md` Step 2 already has five numbered items (`SKILL.md:49` item 1 through `SKILL.md:71` item 5, "Write the rule that fired on every proposal"), so the plan's "item 5" would literally collide with an existing item 5 — a reasonable implementer renumbers it item 6, but the plan doesn't say so (minor, non-blocking on its own). The larger problem: Step 2 is the per-finding *target/scope classification* loop, which runs before Step 3 drafts the exact diff and before Step 6 ever writes a file to disk. "Run the test with the addition in place" cannot execute during Step 2 — there is no addition yet, and nothing is on disk until Step 6's apply. Two implementers would build genuinely different things here: one inserts the sentence verbatim into Step 2 (where it cannot be literally followed — no drafted text exists to test), another moves the check to Step 3 (after drafting, testing against a scratch/mutated copy — needing the same save-restore protocol D12 gives the E2E edge, which this instruction doesn't reference), a third folds it into Step 6's existing "run the project's checks" (where it would be redundant with `go test -race ./...` already running the same test post-hoc, not pre-emptively as "before… adds" implies). The plan does not decide which, nor how "the addition" gets onto disk to be measured without either already committing it (defeating the "before… adds" gate) or an unstated mutate/restore step.
- **Pruning-review class `MOVE-TO-SCOPED` has no defined disposition, and the plan's own scope forecloses its natural one.** Interfaces (line 38) requires every paragraph classified into `{KEEP, DERIVABLE, VAGUE, COMMON-KNOWLEDGE, MOVE-TO-SCOPED, MOVE-TO-SKILL, MOVE-TO-ENFORCEMENT (always "n/a: R3"), DUPLICATE, CONFLICT, STALE}`. `MOVE-TO-ENFORCEMENT` gets an explicit forced default ("n/a: R3") precisely because this plan does no enforcement work. `MOVE-TO-SCOPED`'s natural destination — a `rules/<name>.md` file — is explicitly Out of scope in this same plan (line 15: "any `rules/` file (deferred…)"), and Phase 1's "Apply approved actions" task (line 73) only names two actions: "deletions; merges land in the named skill in the same commit." Nothing says what happens to a row classified MOVE-TO-SCOPED: does it stay in `context/AGENTS.md` untouched (in which case it still counts against the 22,000-byte budget Phase 1 must hit, and the class was pointless to compute), or is it deleted now with no destination file (content lost from the live docs, recoverable only via `git log`, with the future `rules/` file left to reconstruct it from memory)? The Follow-ups line ("the retro table's `rules/` row, which lands in the same commit as the first rule file") implies deletion-now-rebuild-later is intended, but this is nowhere stated for the pruning-review's own Apply step, and it is exactly the kind of implementation choice two engineers would resolve differently — one keeps MOVE-TO-SCOPED rows (correct but blows the budget), the other deletes them (hits budget but silently orphans content the class was invented to protect).

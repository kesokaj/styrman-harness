# Security review — BUG-078 PATH shadow warning (4cdc0b5..52574a0)

Range reviewed: 4cdc0b5..52574a0

## Verdict: FINDINGS

Nothing in the Go change is exploitable: `PathShadows`/`ResolveExecutable` only `Lstat`/`Stat` PATH candidates,
never open or execute one, and print strictly less than `which -a` (the candidate path, never the
`EvalSymlinks` target, and only entries ahead of the install dir). The worst problem is in the docs half of
the diff: `README.md:86` tells a first-time installer to build the release trust anchor themselves from a
placeholder (`'YOUR_EMAIL ssh-ed25519 AAAA…'`) when the genuine line is already sitting in this repository at
`internal/harness/release.go:40` and `.agents/docs/deploy/remote.md:80`, and it leaves that `allowed-signers`
file permanently in `~/.local/bin` — a user-writable trust anchor in a PATH directory, which is exactly the
artifact `remote.md` § Releases deletes on the signing side ("a signer file left on disk is the artifact
release.go refuses to trust"). A reader with no key source named will take it from the release page that also
serves the artifact, which makes the signature check self-certifying. Secondary: the same fenced block still
offers two install routes with no verification at all beside the newly verified one. Everything else is low:
advisory output that cannot be the integrity check the docs nearly read as, and message-correctness edges.

## Findings

- **[medium / confidence: high]** `README.md:86-88` — the only place a NEW machine can bootstrap trust names
  no key. The snippet writes `allowed-signers` from a literal placeholder into `~/.local/bin` (a PATH
  directory), never says where the real signer line comes from, and never removes the file. Two distinct
  weaknesses. (a) *Unspecified trust anchor*: the obvious source for the missing key is the release page that
  serves `SHA256SUMS.sig`, so signature verification certifies the channel with the channel's own key. A
  literal paste fails loudly (`ssh-keygen -Y verify` rejects `AAAA…`), so there is no silent bypass — the
  realistic failure is a reader who fetches the key from whatever page is in front of them, or skips the step.
  (b) *Durable writable anchor*: `remote.md` § Releases removes `allowed_signers` immediately after each use
  and says why; the README instead leaves one in a PATH dir and tells the reader to repeat these steps on
  every update, so anyone who can write `~/.local/bin/allowed-signers` (any process running as the operator,
  any earlier compromise, any sync tool) makes a forged `SHA256SUMS` verify from then on. Remediation: print
  the real line and its fingerprint in the README —
  `ostling.simon@gmail.com ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIBkx0BICH1xG18f0a0F/02Vw0OvBTfSOVNXkPkO62NCR`,
  `SHA256:5HpYQJjpG+yE1xXBTOIZPsTkbkgkVnV8z0eG8hBawyU` (a public key, not a secret; it is already in this
  repository twice, compiled into the binary at `internal/harness/release.go:40` as `releaseSigner` and
  documented at `remote.md:80`) — add one line saying it must not be taken from the release page, write the
  signer file to a temp dir, and `rm -f` it after the verify. The in-binary copy cannot bootstrap the *first*
  install, which is why the README must carry the key rather than point at it. Secondary: `remote.md:26` also
  names `allowed-signers` without pointing at line 80 for its contents and without deleting it afterwards.
- **[low / confidence: high]** `README.md:88-105` — the same fenced block that now verifies route 1 leaves two
  unverified routes beside it, with nothing marking the difference. The browser-download route
  (`chmod +x ~/Downloads/sh-agent-darwin-arm64 && mv …`) has no checksum and no signature step at all, and the
  `xattr -d com.apple.quarantine` note below it reads as an endorsement of that route on macOS. The
  `go install` route with `GOPRIVATE='github.com/kesokaj/*'` disables both `GONOPROXY` and `GONOSUMDB` for that
  path (verified with `go env`: `GOPRIVATE` is their default), so it fetches source directly over SSH with the
  checksum database switched off and performs no release-signature check either — its entire trust basis is
  GitHub plus a tag, and "a pushed tag is never moved" is this project's policy, not an enforced property.
  Both are plausible in principle against a compromised GitHub account or session, which is precisely the
  threat `SHA256SUMS.sig` exists to cover. Remediation: repeat the two verification lines for the browser
  route, and label the `go install` route as unverified-by-design in one clause so a reader chooses knowingly.
- **[low / confidence: high]** `README.md:110,115` and `.agents/docs/deploy/remote.md:31,35` — `sh-agent version`
  unqualified is presented as the check that "matters"/"comes first on purpose", but the binary that answers it
  is the one under suspicion: a shadowing `sh-agent` prints any version string it likes, and so does a
  shadowing binary asked for the new `warning:`/`shadowed` lines (`cmd/sh-agent/main.go:393,683`) — the guard
  runs inside the artifact it vouches for. The unqualified check separates STALE from FRESH, never GENUINE
  from FORGED. Both documents do the authentic check correctly (signature + checksum over the file, then
  `./sh-agent-<os>-<arch> version` by path, before the `mv`); the exploitable gap is only that a reader may
  substitute the cheap check for the real one on a later update. Remediation: one sentence saying the
  unqualified check detects the wrong binary winning, not a tampered one, and that the file checks are what
  establish authenticity.
- **[low / confidence: medium]** `.agents/docs/deploy/remote.md:182` — Verify now accepts "`sh-agent status`
  with … no `shadowed` line", but the absence of that line is not evidence. `status` emits it only when
  `binOnPath(home)` is true (`cmd/sh-agent/main.go:391`), and `binOnPath` (`main.go:656-665`) is an exact
  string match with a single `TrimSuffix(p, "/")`, while `PathShadows` normalises with `filepath.Clean`
  (`internal/harness/pathguard.go:32`). Two normalisations for one question: a PATH entry spelled
  `~/.local/bin//`, a `$HOME` reached through a symlink, a case-different entry on macOS, or an install into a
  system path all silence the check, and `main.go:651` then prints "is not on PATH" about a directory that is.
  Separately `os.Getenv("PATH")` is this process's PATH, not the operator's interactive shell's (differs under
  `sudo`, `env -i`, login vs non-login shells, and a shell whose `hash` table caches an older location), so a
  quiet `status` says nothing about what the next prompt will run. Remediation: make `binOnPath` use
  `filepath.Clean` — the same comparison `PathShadows` already uses — and keep `sh-agent version` unqualified
  as the deciding line in § Verify, with the `shadowed` line marked corroborating rather than a pass condition.
- **[low / confidence: medium]** `internal/harness/pathguard.go:60-66` — `install` and `status` now walk every
  PATH entry with `EvalSymlinks` + `os.Stat` where they previously did a pure string comparison. The FIFO and
  device-node concern is moot: `stat(2)` does not open the file and does not block on either. A hung
  NFS/autofs/FUSE mount on PATH does block `os.Stat` uninterruptibly, so `sh-agent install` and `sh-agent
  status` can hang where they previously could not. Input is the operator's own PATH, impact is availability
  of the operator's own command, and every shell PATH lookup already has the same property — accepted-risk
  shaped, recorded for the record rather than for a fix. Symlink loops and 255-deep chains return an error and
  are handled.
- **[low / confidence: medium]** `internal/harness/pathguard.go:51`, `cmd/sh-agent/main.go:393,648,683` — a
  candidate path is printed to the terminal verbatim. A PATH entry may hold any byte but `:` and NUL,
  including ESC, CR and newline, so a directory named with an ANSI sequence can rewrite the warning line (hide
  it, or forge a reassuring one). The precondition — an attacker-controlled directory on the operator's PATH
  holding an executable `sh-agent` — is strictly worse than the escape, since that attacker already gets code
  execution the next time the operator types `sh-agent`; this is an amplifier, not a way in. No leak beyond
  `which -a`: only the candidate is printed, the resolved target never is, and `sh-agent report` collects
  files (`state.json`, the feedback log), not command output, so these paths do not reach the feedback
  repository. Remediation (cheap): print with `%q`, which escapes control bytes and, as a bonus, fixes the
  next finding's ambiguity.
- **[low / confidence: low]** `internal/harness/pathguard.go:29-30,47` — an empty PATH entry correctly becomes
  `.` (POSIX), but `filepath.Join(".", "sh-agent")` yields the bare relative name, so the message reads
  "warning: sh-agent comes before /home/u/.local/bin/sh-agent on PATH". That is unactionable text for the one
  case where a planted `./sh-agent` is most likely — the working directory. Remediation: report `./sh-agent`
  or the absolute path; the current form is pinned by `pathguard_test.go` ("an empty PATH entry means the
  working directory"), so the test moves with the fix.

Not findings, checked and sound: the shadow walk never executes a candidate — the only `exec` reachable from
`cmd/sh-agent/main.go` is the pre-existing `exec.LookPath("go")` at line 153 for the rebuild decision, outside
this range and unchanged; no shell, no user-controlled format string; `--dry-run` only reads; a dry run on a
home with no installed binary yet loses the same-file suppression, but a link to a not-yet-existing target is
dangling and therefore unresolvable, so it cannot produce a false shadow. `haveTarget && got == target`
correctly silences a symlink to the installed binary and is covered both in unit and end-to-end tests. The
README's verify → run → `mv` order runs the downloaded binary only after its signature and checksum pass.
`grep -v '^#' SHA256SUMS | sha256sum -c - --ignore-missing` cannot pass vacuously — measured here, GNU
`sha256sum` and Perl `shasum` both exit 1 with "no file was verified" when every listed file is absent, and
both accept `--ignore-missing`. One divergence worth knowing but not a finding: on a malformed checksum line
GNU exits 1 and `shasum` exits 0, unreachable here because the file is signature-verified before it is parsed.
Stripping the `# styrman-harness vX.Y.Z` line does mean the manual path never binds `SHA256SUMS` to the
version asked for, the way `sh-agent update` does (D26); `gh release download vX.Y.Z` pins the assets, so this
is a hardening note only — `grep -q '^# styrman-harness vX.Y.Z' SHA256SUMS` before the `-c` would close it.

## Checked
- **Secrets** — no credential, token or key added. The signer public key and operator email in `remote.md:80`
  and `internal/harness/release.go:40` are public material and predate this range; `README.md:86` adds only a
  placeholder. No `.env`, `*.pem`, `*.key` in range; nothing echoed into logs beyond PATH-derived paths the
  operator already knows (finding 6). Neither markdown file gained private data or instruction-shaped text
  that would steer an agent — every added command is a verification or a move, and the two placeholder forms
  (`…/sh-agent-<os>-<arch>`, `AAAA…`) fail loudly rather than silently doing something else.
- **Injection** — no shell, no `exec`, no SQL, no template. PATH is split with `filepath.SplitList` and each
  entry joined with `filepath.Join`; the only sink is `fmt.Fprintf` to an `io.Writer` with a constant format
  string. Terminal-control injection in the printed path is finding 6.
- **Authz/authn** — none in range; no endpoint, no identity decision. The one trust decision is release
  signature verification, covered by findings 1, 2 and 3.
- **Crypto** — nothing hand-rolled and nothing added. The diff consumes `ssh-keygen -Y verify` and
  `sha256sum -c` as designed, in the namespace (`sh-agent-release`) the signing procedure uses and the binary
  compiles in (`ReleaseNamespace`, `release.go:25`); no primitive, token, session or auth flow is implemented
  or composed here.
- **Dependencies** — none added; `go.mod`/`go.sum` untouched in the range, stdlib only (`os`, `path/filepath`,
  `fmt`, `strings`), consistent with the repo's stdlib-only rule. `govulncheck` is installed
  (`/home/kesokaj/.go/bin/govulncheck`) and the toolchain is go1.27.1, but it was NOT run: it fetches
  `vuln.go.dev` and this review is under a no-network limit. Per `AGENTS.md` it reports clean on go1.25.8+, so
  a run here would add no signal about this diff; re-run it in a networked gate. No npm ecosystem in this repo.
- **GCP surface** — nothing in range: no IAM binding, service account, Cloud Run flag, or secret-as-env-var.

## Outcome

Written by the main agent after the fix, in the fix's commit; the fix itself is the re-dispatch's input.

- [medium] placeholder signer, and a signer file left in a PATH dir — **fixed**: the README's block now carries the real line, the one compiled into `internal/harness/release.go` and printed in `remote.md` § Releases, with the instruction to take it from a checkout or a binary already trusted and never from the release page (README.md:91); every file is downloaded and verified in a `mktemp -d` directory that is removed after the one `mv` of the binary (README.md:85). `remote.md`'s block says the same of its `$D`.
- [low] browser and `go install` routes unlabelled — **fixed**: the `go install` comment names what that route trusts and that neither the checksum database nor a release signature is checked (README.md:100); the browser route now says to fetch the two checksum files and run the same three checks before the `mv` (README.md:112).
- [low] `sh-agent version` and the new lines are the suspect binary's own output — **fixed**: README (README.md:124) and `remote.md` (.agents/docs/deploy/remote.md:35) both say it tells stale from fresh, never genuine from forged, and that authenticity is the file checks before the move.
- [low] `remote.md` Verify's "no `shadowed` line" could pass vacuously through `binOnPath` — **fixed** with the code reviewer's high finding: one definition of "on PATH" (internal/harness/pathguard.go:22); `local.md` § Verify says the same now (.agents/docs/deploy/local.md:87).
- [low] `stat(2)` on every PATH directory; a hung network mount would hang `install` and `status` — **rebutted**: the same `stat` is what the shell does to resolve `sh-agent` at all, and what `which -a` does; a PATH entry on a hung mount already hangs every command lookup on that machine, so this adds no hang that was not there. No code change.
- [low] control bytes in a printed PATH entry — **rebutted**: the printed strings are the operator's own `PATH` entries, printed exactly as `which -a` prints them; nothing untrusted reaches them, and quoting would make the path unusable for copy-paste, which is what the line is for. No code change.
- [low] an empty PATH entry printed as a bare `sh-agent` — **fixed**: it prints as `./sh-agent` (internal/harness/pathguard.go:37), asserted by `TestPathShadows` (internal/harness/pathguard_test.go:349) with `t.Chdir`.

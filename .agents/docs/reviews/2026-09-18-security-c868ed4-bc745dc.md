# Security review — BUG-079 stale-running-binary note   (2026-09-18)

Range reviewed: c868ed4..bc745dc

## Verdict: FINDINGS

The note `update` now prints is an instruction an operator executes, and it fires in states where its premise is false. `UpdateFromRelease` has three `return nil` branches that install NOTHING (`up to date (V)`, "this binary reports version … leaving it alone", "the newest release … is older … nothing installed`), and `main.go` gates the note only on `!*check` and a nil error — so a run that changed nothing still prints "this update ran from `<X>`, which update never replaces; the installed binary is `<home>/.local/bin/sh-agent` … — or remove it". `RunningElsewhere` swallows the `os.Stat(binPath)` error, so the named "installed binary" need not exist: on a place installed by hand into `/usr/local/bin` (the README "Install without cloning" route — the exact devbox shape in BUG-079), the note names a file that is not there as the replacement and tells the reader to remove the machine's only, current `sh-agent`. This is the asserted behaviour, not a hypothesis: `TestUpdateNamesTheBinaryItRanFrom` drives the `tag == version` path with a `t.TempDir()` home holding no `.local/bin/sh-agent`, and passes. Nothing in the range touches crypto, auth, secrets or dependencies; the release signature/checksum gate is untouched and still runs before this note.

## Findings

- **[medium / confidence: high]** `cmd/sh-agent/main.go:654-663` with `internal/harness/release.go:105-119` and `internal/harness/pathguard.go:82` — the note fires after an update that installed nothing, and can name a non-existent file as "the installed binary" while ending in "or remove it". Three branches of `UpdateFromRelease` return nil without writing `home/.local/bin/sh-agent`; the caller's only guards are `!*check` and `err == nil`. `RunningElsewhere` ignores the `os.Stat(binPath)` error rather than treating a missing installed file as "nothing was replaced, say nothing" — the harness's own test case `installed file missing: a reachable other copy still reported` (pathguard_test.go:450) fixes that as intended. Exploitable in principle as self-inflicted destruction on the program's own advice: the operator is told the binary they are running is superseded when it is the newest and possibly the only one, and the remedy is `rm`. No attacker is needed; a plain `sh-agent update` on an up-to-date binary-only place is the trigger. Remediation: have `UpdateFromRelease` report whether it actually wrote `dest`, and print the note only then; additionally require `os.Stat(installed)` to succeed inside `RunningElsewhere` (an installed file that does not exist cannot be behind anything) and state the version of each side, so the premise is shown rather than asserted.

- **[low / confidence: high]** `cmd/sh-agent/main.go:661` — "or remove it" is unqualified and names the PATH-entry spelling, not the running file. The path reported may be root-owned (`/usr/local/bin/sh-agent`, the BUG-079 path: the `rm` needs `sudo`), manager-owned and read-only (`/nix/store/…`, a Homebrew link, `/opt/devbox/bin`), or a symlink under another name to the stale binary — the function's own test `reached only through a link: reported at the PATH entry, not the exe path` (pathguard_test.go:449) makes that the documented output, in which case removing what is named deletes the link and leaves the stale binary in place while the reader believes it is gone. README.md and `deploy/remote.md` qualify the parallel advice ("point the earlier one at this binary (`ln -sfn`) or remove it — a link to the same file is not a shadow"); the program's own note does not. Remediation: name the exe path and the PATH spelling when they differ, put the non-destructive fix first (`ln -sfn <installed> <from>`), and offer removal only for a path under the user's home.

- **[low / confidence: high]** `internal/harness/pathguard.go:86-91` — `RunningElsewhere` drops the empty-PATH-entry convention its sibling handles on purpose. `PathShadows` maps a `""` entry to `./sh-agent` (pathguard.go:35-39) precisely because "Join would print it as a bare name that reads like a command, not a file". Here `filepath.Join("", "sh-agent")` is `"sh-agent"`, statted against the cwd and printed bare, so with a PATH carrying an empty element (`PATH=$PATH:` out of a sloppy profile) and a link to the running binary in the cwd the note reads "this update ran from sh-agent … or remove it" — a token that reads as a command name, and a reader acting on it runs `rm sh-agent` in whatever directory they are in by then. A local user who can write the operator's cwd can plant that link. Remediation: reuse the `"." + separator + name` mapping, or skip empty entries; either way the two functions should agree.

- **[low / confidence: medium]** `cmd/sh-agent/main.go:661` (same shape pre-existing in `pathHint`, main.go:672+, and in `status`'s `shadowed` line) — environment-derived paths are printed raw with `%s` into an advisory that contains shell commands. `from` comes from `PATH` and `installed` from `--home`/`$HOME`; `filepath.SplitList` splits on `:` only, so a PATH element may contain `\n`, `\r` or ESC. A directory whose name carries a newline, holding a link to the running binary, forges an extra line of `sh-agent`'s own output; with ESC it rewrites the line in a terminal or in a pasted verification log. The note is the thing an operator acts on and it is copied into `.agents/docs/testing/` logs, so a forged line outlives the run. Remediation: print env-derived paths with `%q` — Go quoting escapes control bytes and makes a trailing space visible. Stdlib only; no dependency, nothing to justify.

- **[low / confidence: medium]** `internal/harness/pathguard.go:78-88` — `os.Stat(exe)` re-resolves a path string rather than the running inode, and `os.Executable()` returns a path, not a handle. On Linux Go returns `readlink("/proc/self/exe")` with a literal `" (deleted)"` suffix trimmed, so a binary replaced or deleted during the run yields a path whose current occupant is a *different* file — that occupant is what gets statted and compared — and a genuine path ending in `" (deleted)"` is mangled. On darwin `os.Executable` resolves `_NSGetExecutablePath` against the process's initial cwd, so a relative-path exec followed by a move yields a stale path; macOS is a first-class place for this harness. The consequence is confined to the advisory's accuracy — the program mutates nothing on the basis of these stats. Answering the two cases the dispatch asked about, neither is a finding: `exec -a` rewrites argv[0] only and cannot move `/proc/self/exe`, and a process started through a symlink gets the resolved target while the PATH walk reports the spelling a shell uses (covered by pathguard_test.go:449). Remediation: none required for the Linux path beyond finding 1; treat the returned path as advisory and say "the binary at …" rather than "this update ran from …" if precision is wanted.

- **[low / confidence: high]** `.agents/docs/plans/2026-09-18-recon-bug-079-diagnosis.md:21` — the committed doc contains `warning`: two U+0646 ARABIC LETTER NOON inside an ASCII word. Arabic letters are strong RTL, so a bidi-aware renderer reorders the run around them. Nothing here is source and the surrounding meaning is unaffected, but `.agents/docs/` is read back as agent input, and unexpected strong-directional non-ASCII in text an agent consumes is the trojan-source class. Remediation: correct the word; a non-ASCII grep over `.agents/docs/` outside the intended typography set (em dash, curly quotes) catches the next one. `git diff --numstat` shows no `-`/`-` pair, so nothing in the range is binary.

**TOCTOU between the stats and the message — moot as an exploit, not as correctness.** Between the two `os.Stat` calls and the `Fprintf` the program acts on nothing: no unlink, no exec, no write, no trust decision. There is no window in which a racing local user gains anything from the code itself. The race only widens the interval in which the printed text is wrong, and a human executes the remedy — which is findings 1, 2 and 5, not a separate one.

## Checked

- **Secrets** — none: no credential, token or key in the eight changed files; no `.env*`, `*.pem`, `*.key`, `*.tfvars` or credential JSON added; no high-entropy string in the diff. The new output prints only paths; a `$HOME`-derived path discloses the username in a pasted log, which every other `sh-agent` line already does. `gh auth login` appears in prose only.
- **Injection** — nothing in the range execs, queries or templates. The only injection-shaped surface is terminal/log injection of `PATH`- and `$HOME`-derived text into the advisory (finding 4); `filepath.Join` on a PATH entry cannot escape anywhere that matters because the result is only statted and printed, never written or removed by the program. The new test's fake `gh` is confined to a `t.Setenv("PATH", …)` and a `t.TempDir()`.
- **Authz/authn** — no auth path in range. The one authorization-adjacent effect is the remedy inviting a privileged `sudo rm` of a system path (finding 2).
- **Crypto** — nothing hand-rolled and nothing crypto-adjacent added; the new code has no crypto call. `release.go`'s `ssh-keygen` signature and checksum gate is outside this range and untouched, and the note prints after it, changing no trust decision. No finding.
- **Dependencies** — `go.mod`/`go.sum` untouched; the added code imports `os` and `path/filepath` only, holding the repo's stdlib-only rule. `gofmt -l cmd internal` clean, `go vet ./...` clean, and `go test -run 'TestRunningElsewhere|TestUpdateNamesTheBinaryItRanFrom|TestCheckoutUpdateNamesTheBinaryItRanFrom'` passes on both packages (that pass is what pins finding 1). `govulncheck` IS installed at `/home/kesokaj/.go/bin/govulncheck` but was **not run**: it fetches the database from vuln.go.dev and this dispatch forbids network. `npm audit` not applicable — no JavaScript in this repository.
- **GCP surface** — nothing in range: no IAM binding, service account, key file, Cloud Run flag, `--allow-unauthenticated`, or secret-as-env-var.

## Outcome

Written by the main agent after the round-2 change, in its commit.

- [medium] the note fires after an update that installed nothing, into a home with no installed binary, and names a file that does not exist while telling the reader to remove their only binary — **fixed**: `RunningElsewhere` returns nothing unless the installed file exists (internal/harness/pathguard.go:86); pinned by a fresh-home release-path case (cmd/sh-agent/main_test.go:1524) and the unit case (internal/harness/pathguard_test.go:450), and by a must-fail mutation that swallows the `Stat` error again. On an "up to date" run into a home that DOES hold an installed file the note still prints — the running file is still not that one, a shell hash pointing at it is still the hazard for the next update — and the wording now says only what is true in both cases (cmd/sh-agent/main.go:661).
- [low] "or remove it" unqualified, naming a path that may be root-owned, manager-owned or a link — **fixed**: the message says the file "stays as it is" and offers `ln -sfn` to the installed binary before removal (cmd/sh-agent/main.go:661); README and both deploy guides already carried the qualified form.
- [low] empty PATH entry printed as a bare `sh-agent` — **fixed**: `./sh-agent`, as `PathShadows` prints it (internal/harness/pathguard.go:93).
- [low] raw `%s` printing of PATH-derived paths — **rebutted**, as for BUG-078: the strings are the operator's own `PATH` entries and home, printed as `which -a` and `type` print them; nothing untrusted reaches them. No change.
- [low] `os.Executable()` path-vs-inode edge cases — **rebutted**: the function uses `exe` only to `Stat` it and reports the PATH entry it matches by identity, never `exe`'s spelling, so a ` (deleted)` suffix or a relative darwin form changes nothing the reader sees. No change.
- [low] two U+0646 characters in the explorer's diagnosis brief — **fixed**: removed by character code (the first attempt matched the escape text, not the character — BUG-057's class, caught by `grep` for the character itself).
- TOCTOU — moot as the finding says; advisory output only.
- Unverified in the report (checkout path succeeding without writing the installed file): it can, in the test fixture whose fake install writes a marker — and with the gate the note is then silent there, which is the intended reading; the checkout test plants an installed file to exercise the note.

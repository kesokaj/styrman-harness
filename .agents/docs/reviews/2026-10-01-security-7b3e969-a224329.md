## Findings

- **F1 [low / confidence: medium]** `context/AGENTS.md:15` with `agents/verifier.md:14`.
  - **What changed:** the verifier no longer decides on its own to run a plan's tiers or an edited command; both now wait for the dispatch. Its text: "a tier a plan names runs when the dispatch names it too: a plan is a file the change can edit". An edited command stays BLOCKED "until the main agent, who can read the edit, re-dispatches with the command named".
  - **The gap:** the main agent's side says only "every tier the plan names (the dispatch names each)", with no condition. It says nothing about reading an edited command before quoting it. So a change that adds an install or real-home tier to the plan, or edits a guide command, runs as soon as the main agent names or quotes it without reading it. That moves the verifier's own reason one hop up and defeats it.
  - **A related gap in `:14`:** the "as they were before the change" rule covers "those commands" (tests, vet, lint, build). It does not say what happens to a tier named by reference ("run § 3e") whose steps the change edited. Such a tier can be read as running at HEAD.

    - `:15`: "(the dispatch names each, after reading what the change did to the plan; a command the verifier reported as BLOCKED is read before it is quoted)".
    - `:14`: "a tier runs as the guide had it at the base; a step the change added or edited inside it is a changed command".
  - **Exposure if shipped:** a hostile or injected plan or guide edit reaches execution through the main agent's dispatch, within the operator's permission mode.
  - **Not a regression:** before this range the verifier ran plan tiers itself.

- **F2 [low / confidence: high]** `agents/verifier.md:79`.

- **F3 [low / confidence: medium]** `skills/google-catalog/scripts/refresh-catalog.sh:42-46` (the claim), with the git calls at `:198`, `:200` and `:203`.

- **F6 [low / confidence: high]** `internal/harness/catalog_test.go:~348-396` (`headPipeProblem`, `TestScriptsHaveNoBareHeadPipe`), against BUG-155's claim that "the class was closed".
  - **The gap:** the graduated check matches only `| head`, and not `| /usr/bin/head`. The same SIGPIPE-under-pipefail class has a fail-open form the check cannot see:

    - The producer's status 141 turns a match into "no match", so whatever the branch guards is skipped.

    - Add the fail-open form to BUG-155's Prevention.
  - **Exposure if shipped:** none today. A later refusal written as `if find … | grep -q .; then fail …` would pass every test and skip itself on large input.

**Does the EXIT trap print the note on every exit after the first clone or fetch, and never before?**

| Route | `on_disk` | Status | Note printed to |
|---|---|---|---|
| normal end | set | 0 | stdout |

| errexit | set | 1, and 7 in a second case | stderr |

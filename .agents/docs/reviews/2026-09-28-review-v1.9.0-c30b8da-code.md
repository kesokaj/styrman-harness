# Review — v1.9.0-c30b8da-code   (2026-09-28)

Range reviewed: v1.9.0..c30b8da (net source change: `cmd/sh-agent/main.go`, `cmd/sh-agent/zip_test.go`, `internal/harness/release.go`, `internal/harness/zip_test.go`; plus the README, REQUIREMENTS, delivery.md and DECISIONS.md hunks that describe them)

## Status: COMPLETE

## Verdict: APPROVE WITH NITS

Nothing in the range is broken. There is one real code change: `VerifyZipSums` now returns `ErrZipUnsigned` when EITHER file of the `SHA256SUMS`/`SHA256SUMS.sig` pair is missing (`||` instead of `&&`, `internal/harness/release.go:450`). `updateFromZip` maps that to an install marked `UNVERIFIED`. A zip WITH the pair still runs the full signature and checksum check, and a failed check still refuses it. This matches the zip-place bullet of R9 as restored ("a zip without them is installed marked `UNVERIFIED`") and ADR-041. I found no `--unverified` flag left in code, usage text, comments or tests. The flag is not defined, so `--unverified` now fails at flag parsing instead of being silently ignored. The two findings below are low-severity test gaps. Neither blocks the release.

## Findings
- **[low / confidence: medium]** `cmd/sh-agent/zip_test.go:648-658` (`TestUpdateFromZipUnsignedSaysUnverified`): the behaviour this range changes, "a half pair installs `UNVERIFIED`", is pinned only at unit level (`internal/harness/zip_test.go:478-486` and `:517-525`). No end-to-end `run([... "update","--from-zip" ...])` test puts one file beside the zip and checks exit 0, the `UNVERIFIED` line and the `;unverified` manifest origin. Today the cmd path is shared with the neither-file case, so the risk is a future special case in `updateFromZip`, not a present defect. Fix: add a table case with only `SHA256SUMS` beside the zip and one with only `.sig` to that test, asserting the output line and the manifest origin.
- **[low / confidence: medium]** `internal/harness/zip_test.go:348-350` (`TestUnpackZipLateRefusalCreatesNoParent`, pre-existing and unchanged in this range): it checks only `err == nil`. It does not check that the refusal is the late one (symlink or duplicate) named in the test comment. An earlier refusal in the names pass also creates no parent, so that would pass the test without reaching the path it claims to cover. This is the only refusal test in either zip test file that does not assert its own cause. Fix: assert that the error names the symlink or duplicate, as the `UnpackZip` table test at `:163-168` does with `c.want`.

## Verdict: FINDINGS

The new `update` guard does not close the hole it claims to. `harness.Inspect` asks `git status --porcelain` with no flags, so it inherits `status.showUntrackedFiles` from the operator's git config, and it never sees ignored files at all. Probe-demonstrated: with `status.showUntrackedFiles=no` an entirely untracked `skills/<new>/` tree reports clean, and a `skills/<name>/creds.key` (matching this repo's own `.gitignore` line `*.key`) is invisible to the check in every configuration while `sh-agent install --dry-run` plans to write it to `~/.claude/skills/foo/creds.key` and `~/.gemini/config/skills/foo/creds.key`. So the two categories of content that can reach a vendor home without ever being committed are exactly the two the guard cannot see — and one of them is the secret-shaped category the `.gitignore` exists to catch. The guard is a real improvement on the committed path it does cover (the tests exercise all four legs honestly); it is not the invariant its error message states.

## Findings

- **[medium / confidence: high]** `internal/harness/repo.go:89` (`Inspect`, consumed by the new guard at `cmd/sh-agent/main.go:356`) — `gitOut(repo, "status", "--porcelain")` takes `status.showUntrackedFiles` from the operator's config. Probe (`.agents/scratch/security-board/probe`): default output `?? skills/`; with `-c status.showUntrackedFiles=no` the output is empty; with `--untracked-files=all` it is back. `no` is a common large-repo performance setting and is inherited from `~/.gitconfig`, `GIT_CONFIG_GLOBAL`, or a repo-local `.git/config`. Under it, a wholly untracked new `skills/<name>/`, `agents/<name>.md`, `rules/<name>.md` or `commands/<name>.md` reports the tree clean, `update` proceeds, and that uncommitted content is deployed into both vendor homes — the exact BUG-046 outcome the guard was written to stop. The same call backs `sh-agent status`'s reporting, so nothing else in the tool surfaces it either. Remediation: pass the flag rather than trusting the config — `gitOut(repo, "status", "--porcelain", "--untracked-files=all")`. One flag, stdlib `os/exec`, no dependency.

- **[medium / confidence: high on mechanism, medium on likelihood]** `internal/harness/plan.go:100-140` (blast radius of the guard; not itself changed in the range) — a gitignored file inside a managed directory is invisible to `git status --porcelain` in EVERY configuration (probe: `!! skills/foo/creds.key` appears only with `--ignored`) and is still deployed: `Plan`'s skill walk copies every regular file under `skills/<name>/`, filtering only `.DS_Store`. This repo's `.gitignore` lists precisely `.env`, `.env.*`, `*.pem`, `*.key`, `*.tfvars`, `*.tfstate`. Demonstrated with a scratch repo: `go run ./cmd/sh-agent install --repo <scratch> --home <scratch> --dry-run` planned `write ~/.claude/skills/foo/creds.key` and `write ~/.gemini/config/skills/foo/creds.key`. A credential left beside a skill is therefore correctly kept out of git and incorrectly copied into two directories both CLIs enumerate and surface to the model, with `update` reporting the tree clean and `sh-agent status` reporting no drift (the file is in the plan, so it is "ok"). Remediation: refuse — do not silently skip — any file in a managed directory whose base name matches the secret-shaped set, in `Plan`'s walk, using `filepath.Match` from the stdlib. Rejected `git check-ignore`: `Plan` must work from a plain copy with no `.git` (BUG-015), so the check cannot depend on git.

- **[low / confidence: high]** `cmd/sh-agent/main.go:352-358` — time-of-check/time-of-use. The dirty verdict is taken, then `Pull` runs, then `Reinstall` does `go build` (seconds), then the child `install` re-reads the working tree; the child does not re-check (by design — `install` may deploy a dirty tree). The window is small but it is precisely the BUG-046 situation: an hourly timer firing while the operator edits the checkout. The comment and error message assert "`update` deploys the WORKING TREE, not the commit it just fetched" and then treat a stale verdict about that working tree as authoritative. Remediation, cheapest first: capture `git rev-parse HEAD` plus the dirty verdict before the build and have the child re-verify both (an env var the parent sets, checked in `install` when `SH_AGENT_CHILD=1`); properly, stop deploying the working tree — materialise `HEAD` with `git archive` or a temporary worktree under `.agents/scratch/` and plan from that, which makes the guard unnecessary rather than better-defended.

- **[low / confidence: high]** `internal/harness/adopt.go:66-80` as committed — `staging := dest + ".adopt-staging"` puts the staging tree inside `skills/`. Three consequences, all in the delete-target class BUG-037 came from: (a) a process killed between `copyTree` and `os.Rename` leaves `skills/foo.adopt-staging` holding a complete `SKILL.md`; `identLike` allows `.` after position 0, so with no frontmatter `name:` the next `install` deploys it to both vendors as a skill named `foo.adopt-staging`, and with `name: foo` it collides with the real skill (at the committed range `LoadSkills` had no duplicate check, so `Plan`'s duplicate-Rel error jams every install, status and diff until someone finds the directory). (b) `os.RemoveAll(staging)` runs before any `--force` consideration, so `sh-agent adopt foo` deletes an existing `skills/foo.adopt-staging` — a legal skill name — without asking. (c) `within()` compares `from` against `dest` only, never against `staging`; a source path shaped `<repo>/skills/x.adopt-staging/x` yields `dest=<repo>/skills/x`, `staging=<repo>/skills/x.adopt-staging`, no overlap is detected, and the first `RemoveAll(staging)` deletes the source tree before the copy. Contrived, but it is the same shape as BUG-037. The staging path itself cannot escape `skills/`: `name` is `filepath.Base(from)` through `validName`, and `dest` is `filepath.Abs`. **In flight:** the uncommitted working tree already moves staging to `<repo>/.agents/scratch/adopt-<name>-<pid>` (gitignored, outside `skills/`, pid-unique) and adds a duplicate-name refusal to `LoadSkills`, which closes (a), (b) and (c). Confirm that lands in the next commit; no further change needed if it does.

- **[low / confidence: medium]** `cmd/sh-agent/main_test.go:676-690` (`gitFixture`) — the environment is `append(os.Environ(), "GIT_CONFIG_GLOBAL=…", "GIT_CONFIG_NOSYSTEM=1")`. Config is neutralised correctly and `$HOME` is otherwise untouched, but `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES` and `GIT_CEILING_DIRECTORIES` are inherited. On a box where the operator exports `GIT_DIR` (the bare-dotfiles-repo pattern), the fixture's `git init`, `add -A`, `commit` and `push` can act on that repository instead of the temp tree — BUG-045's mechanism (a probe's git falling through to the real repository), here in test code that runs on every `go test -race ./...`. I did not demonstrate it (my box exports none of these). Remediation: append the neutralising assignments after the two existing ones — Go's `os/exec` takes the last value for a duplicate key, so `"GIT_DIR=", "GIT_WORK_TREE=", "GIT_INDEX_FILE=", "GIT_OBJECT_DIRECTORY=", "GIT_ALTERNATE_OBJECT_DIRECTORIES=", "GIT_CEILING_DIRECTORIES="+base` is a one-line fix with no dependency. The same treatment belongs on the nested `run` closure inside `TestUpdateNeverInstallsDirtyTree`'s `behind` helper, which repeats the pattern.

- **[low / confidence: high]** `.agents/docs/deploy/remote.md:31-44` (new section) — the diff does not just document the refusal, it recommends and templates an hourly systemd timer running `sh-agent update`, i.e. unattended `git fetch` → `pull --ff-only` → `go build` → execute, following `main` with no signature check, on every operator box. Anyone who can push to `main` (a stolen GitHub token, a compromised machine) gets code execution as the operator within the hour on every box running the timer, plus their prose into the `AGENTS.md` both CLIs feed the model. `--ff-only` limits it to fast-forwards; it does not limit who pushed. This is a RECORDED accepted risk, not a new defect: ADR-026 states "`sh-agent update` on operator machines and on argolis-devbox keeps following `main`; a tag changes nothing for them; a `sh-agent update --release` … is a Feature question, not decided here", while crew gets the signature-gated channel. The change is that a per-box habit is now documented practice. Remediation: one sentence in that section saying the timer trusts whatever is on `main` and pointing at the ADR-026 follow-up, so the next reader who copies the unit knows what they are accepting.

- **[low / confidence: medium]** `skills/docker/SKILL.md:105` (daemon-start row) — the tightening is correct and matches `context/dev-setup.md`: the root step is now conditional on the operator asking AND "the project's `.claude/settings.json` records the standing permission". The residual is that the gate is a file the agent itself can write. Neither the skill nor `dev-setup.md` says the record is the operator's to make. An agent that reads "run it only when settings.json records the permission" and has an Edit tool has a short path to writing the record and then satisfying its own gate. Remediation: add "recorded by the operator — never add that entry yourself" to the row, and to the matching sentence in `context/dev-setup.md`. Judged against the brief's question: nothing in this diff instructs an agent to run a root command it could not run before (the row got narrower, not wider), write a credential, or send data off the machine.

- **[low / confidence: medium]** `skills/gcloud-setup/SKILL.md:127-137` — the reframing is a real tightening (keys are now a last resort, behind an explicit operator instruction, with the CI justification removed and "Never commit service account keys to git" retained). What the section still does not say, now that it is the "only when the operator says so" path: where the key file may live (never inside the repo), that it is `chmod 600`, that it is scoped to one role, and that it is deleted when the task ends. `export GOOGLE_APPLICATION_CREDENTIALS=/path/to/key.json` is left as the last line of the block with no lifecycle. Remediation: three clauses on the existing warning line.

- **[low / confidence: low]** `skills/distill/SKILL.md:156` — the new `project` field is an absolute path (`/home/you/workspace/<project>`), so `~/.config/sh-agent/feedback.jsonl` now carries the operator's home path on every entry, and `/retro` filters with `grep -vE '"project": ?"<this project>"'` — an unescaped path interpolated into a regex. A directory name containing `.`, `+`, `(` or `|` makes the exclusion match too much or too little, which is the same wrong-evidence promotion BUG-021 was written to stop, arriving by a different route. The log is local and uncommitted, so the path disclosure is minor; the regex is the part worth fixing. Remediation: match with `grep -vF '"project": "<path>"'` (fixed-string), or have the field be the repo directory's base name.

- **[note, not a finding]** `skills/golang/references/golang-ecosystem.md:1030` (BUG-022) closes cleanly. The upload instruction is gone and the replacement is unambiguous ("never on your own initiative", "registering uploads the source to a third party"). Grep over the whole non-vendored skill tree finds no other text asking an agent to submit code anywhere; the remaining Context7 mentions (`golang-core.md:321`, `golang-io-web.md:476`, `golang-samber.md` ×6) are read-only documentation lookups, a different direction of data flow. `skills/golang/references/golang-samber.md` already carries the stdlib-first preamble, so the `samber/lo` and `samber/oops` reframings in `golang-architecture.md` and `golang-core.md` do not leave a contradicting default behind.

- **[note, not a finding]** `skills/cloud-run-deploy/SKILL.md` routing through `/preflight` is a tightening. The seam left open is that "a rollback" and "a failed revision" stay direct-entry, so a production traffic change can still happen without the gate. ## Checked

The new `update` error message names only the repo path — no diff, no file contents, no config. The real exposure found is structural, not literal: finding 2, ignored secret-shaped files under `skills/` deployed into both vendor homes.
- **Injection:** no SQL, template or path injection reachable. Every subprocess is `exec.Command` with an argument vector, never a shell; `Reinstall` passes `--repo <path>` as an argument. Path construction in `Adopt` is `filepath.Abs`+`Join` with `validName` (`identLike`, `filepath.IsLocal`) at the boundary, so no staging or destination path can leave `skills/`. The one unvalidated interpolation is the `/retro` grep pattern (finding on `skills/distill/SKILL.md`). Shell hygiene note: `docker ps --filter id=$cid` in `skills/docker/SKILL.md` is unquoted; `$cid` is a docker-issued hex id, so this is style, not a vector.
- **Authz/authn:** no auth surface in the code. The two authorization-shaped controls in the text are the root-step gate (`skills/docker/SKILL.md`, finding above: the gate file is agent-writable) and the `/preflight` routing (`skills/cloud-run-deploy/SKILL.md`, tightened). `knownCheckout` still guards `update` and `install` against building an unnamed checkout — unchanged and still in place after the diff.
- **Crypto:** nothing hand-rolled anywhere in the range — no primitive, MAC, KDF, token format, session or auth flow is implemented or composed. `writeAtomic`'s added `tmp.Sync()` is a durability fix, not crypto. The repo's signing story (ADR-026) is git's own SSH signing verified with `git verify-tag` against an allowed-signers file: consuming a vetted implementation, no finding. No finding under the hard rule.
- **Dependencies:** `go.mod` declares no third-party requirement — stdlib only, and the diff adds none. `govulncheck ./...` ran (`/home/kesokaj/.go/bin/govulncheck`, toolchain go1.24.4) and reports **2 reachable standard-library vulnerabilities**, both on paths this diff touches: `GO-2025-3956` (unexpected paths from `exec.LookPath`) reached at `internal/harness/repo.go:144` via `Reinstall` — which is what the changed `update` calls — fixed in go1.24.6; and `GO-2026-4602` (`FileInfo` can escape from a `Root` in `os`) reached at `internal/harness/inventory.go:164` via `LoadSkills`, fixed in go1.25.8. Both are low impact here (the LookPath issue is primarily a Windows relative-path resolution problem; this is a Linux/macOS tool), but the remediation is free and has no dependency cost: move the toolchain past go1.24.6, ideally to the current 1.25.x, and bump the `go` line. The tool also reports 2 vulnerabilities in imported packages and 43 in required modules that the code does not call. `npm audit` not run and not applicable: no `package.json` anywhere in the repo.
- **GCP surface:** no IAM binding, service account, Terraform or `gcloud` invocation in the code — the GCP surface in this range is instruction text only. All three touched pieces move in the safe direction: hardcoded `us-central1` replaced by an operator-supplied `$REGION` in `skills/gcloud-setup/SKILL.md` and `skills/bash/references/makefile-patterns.md` (with `REGION ?= $(error …)` so a missing value fails loudly instead of defaulting into someone else's project); service-account key files demoted to a last resort behind an explicit operator instruction; deploy requests routed through `/preflight`. ## Outcome

[medium] the dirty check inherited `status.showUntrackedFiles`, so an untracked skill directory read as clean and would still be deployed — **fixed**: `Inspect` passes `--untracked-files=all` (`internal/harness/repo.go`), with `TestInspectCountsUntrackedFiles` setting that key to `no` in a fixture and asserting the tree still reads dirty. Recorded as BUG-049, because a same-day fix reproduced in miniature the failure it was written to stop.
2. [medium] gitignored, secret-shaped files inside a skill directory are invisible to review and still deployed to both vendors on every machine — **fixed**: `Plan` refuses `.env`, `.env.*`, `*.pem`, `*.key`, `*.tfvars`, `*.tfstate`, `*credentials*.json` and `*-key.json`, naming the path, through a stdlib `filepath.Match` helper (`internal/harness/plan.go`); `TestPlanRefusesSecretShapedFiles` covers seven shapes plus a control (`keys-explained.md`) that must still deploy. Recorded as BUG-050. The shapes are the context's Git-rule list, so the same names that stop a commit now stop a deploy.
3. [low] TOCTOU between the dirty check and the child install that re-reads the tree — **left, accepted and recorded**: narrowed, not closed, and the only full fix is not deploying a working tree at all, which is what `install` is for. Written into ADR-027's Consequences rather than left in a report.
4. [low] adopt's staging inside `skills/` — **fixed, confirmed landed**: it is `.agents/scratch/adopt-<name>-<pid>` in the committed tree, which is the change the report predicted would close all three of its consequences.
5.

# Review — BUG-079 fix (stale-running-binary note)   (2026-09-18)

Range reviewed: c868ed4..bc745dc

## Verdict: APPROVE

The fix does what BUG-079 asks: `RunningElsewhere` correctly distinguishes "running the installed file itself/a link to it" (silent) from "running a different file a shell can still reach by name" (reported, at the PATH entry that reaches it, not at the resolved `exe` path), the note is wired into both `update` paths (release and checkout), gated below every `--check` early return on both, and never wired into `install`. Docs, code and tests agree on wording and command order. `gofmt`, `go vet`, and `go test ./cmd/... ./internal/harness/...` are clean. One minor wording imprecision, not risen to a finding (see below).

## Findings

None that meet the correctness/security/rule bar.

Noted, not filed as a finding (low severity, no concrete failure mode): `staleRunningNote` fires on a plain "up to date" `update` run (no bits written) whenever the running exe differs from the installed file — confirmed by tracing `UpdateFromRelease`'s `tag == version` branch (release.go:106-108), which returns `nil` without touching `checkOnly`, and by `TestUpdateNamesTheBinaryItRanFrom`'s "reachable by name: named" subtest, which exercises exactly this path (gh script always answers `v1.0.0` = `version`). The printed text — "this update ran from X, which update never replaces" — reads as if a replacement just happened even when nothing changed. The underlying fact (shell resolves `sh-agent` to a file this run did not touch) is true and worth surfacing regardless, so this is a wording nit, not a defect; no test or doc claim is contradicted.

## Criteria

1. **Dead code** — pass. No orphaned functions; `RunningElsewhere` and `staleRunningNote` both have live callers (main.go:216, 507) and tests.
2. **Flow tracing** — pass. Traced `main.go` release branch (lines 191-219) and checkout `update()` (lines 461-509): `staleRunningNote` sits below every `--check`/`ErrNewerRelease` early return on both paths (verified: release path's `errors.Is(err, ErrNewerRelease)` returns `exitCode(2)` before line 215's `!*check` guard even runs; checkout path's two `checkOnly` returns at lines 469 and 474 both precede line 507). Confirmed `install` (lines 130-175) never calls it. `RunningElsewhere`'s use of `os.Stat` (which follows symlinks) on both `exe` and each PATH candidate means it reports by inode identity regardless of whether `os.Executable()` returns a symlink or its resolved target on Linux — this is why the function reports the PATH entry (`cand`), not `exe`: `exe`/`self` is only ever used for identity comparison, never surfaced in the message. New tests (`TestRunningElsewhere`, `TestUpdateNamesTheBinaryItRanFrom`, `TestCheckoutUpdateNamesTheBinaryItRanFrom`) each assert on behavior that fails if reverted (checked by reading the assertions, not run against a reverted tree, given the frozen-tree constraint).
3. **Standards conformance** — pass. Errors and I/O follow existing patterns; doc-comments match behavior; no restated rule left stale that I found (grepped "hash -r", "which -a", "PathShadows" — README, local.md, remote.md all updated consistently).
4. **Directory layout** — pass. New function beside its siblings in `pathguard.go`/`pathguard_test.go`; `main.go`/`main_test.go` additions colocated with the code they extend.
5. **Simplicity / DIY-except-security** — pass. Pure stdlib (`os.Stat`, `os.SameFile`, `filepath`), no new dependency, no crypto/auth surface touched.
6. **Decoupling** — pass. `RunningElsewhere` is a small, single-purpose predicate in `internal/harness`, consumed by `cmd/sh-agent` the same way `PathShadows`/`executableAt` already are; no new cross-package reach-in.

Doc-order check (explicit ask): `remote.md`'s script block now reads `hash -r` → `sh-agent version` → `type sh-agent` → `which -a sh-agent`, matching the required sequence exactly. `README.md` and `local.md` present the same four facts as decision-tree prose (version first as the check, `hash -r` as the remedy, `type`/`which -a` as further diagnosis) rather than a literal script; this doesn't contradict the code and isn't a script an operator pastes in that order, so not a finding.

Test-coverage note (explicit ask): the "not on PATH at all: silent" subtest of `TestUpdateNamesTheBinaryItRanFrom` proxies the `go run` claim (it restricts `PATH` to a dir with no `sh-agent` entry and relies on the test binary's own path) rather than literally invoking `go run ./cmd/sh-agent update`. This is a reasonable stand-in — `RunningElsewhere`'s mechanism is purely "is there a PATH entry named `sh-agent` that resolves to this same inode", which a `go run` build under `GOCACHE` structurally can never satisfy regardless of the built file's literal name — but the test does not exercise a real `go run` invocation, so the claim in the doc comment ("a `go run` build") is argued by code-reading, not directly pinned by this test.

# Review

One command, every lens, both vendors. The skill decides the scope, hands every agent the same plain text, and merges what comes back. It never reviews by itself and never edits without `--fix`.

```
/review                          # working tree, code lens
/review --security --docs        # working tree, two lenses, merged record
/review main..HEAD --all         # a range, every lens
/review #42 --fix                # a PR, code lens, apply the findings
/review internal/api --simplify  # named paths, read whole, simplicity lens
/review AGENTS.md .agents/rules --prompts   # instruction files, prompt-audit lens: dated or contradicting text, proposed diff
/review --project --all          # the whole repository — what /audit used to do
/review --high                   # strongest model for reviewer and security
```

**Docs root** (`<docs-root>`): `.agents/docs` if it exists, else `docs/` if it exists, else create `.agents/docs`. Dates from `date +%F`. Dispatch on Claude Code through the Agent tool, on Antigravity through `invoke_subagent` — same agent names.

## Step 1: Parse

Tokens starting with `--` are flags: lenses `--code` (the default when none is given), `--security`, `--simplify`, `--docs`, `--prompts`, `--tests`, `--all` (every lens); `--fix`; `--high`; `--project`. Every other token is a scope token: `#<digits>` is a PR; a token containing `..`, or one `git rev-parse --verify` accepts, is a range or ref (a single ref means `<ref>..HEAD`); an existing path is a path — checked last, so a name that is both a path and a ref is a path; anything else is an error naming the token. Exactly one scope class per run: paths (any number), or one range/ref, or one PR, or `--project`; a mix is the error "one scope per run". No scope token and no `--project` means the working tree. `--fix` with `--project` is refused: "repo-wide edits need a plan — run the review, then fix per finding as a task". `#<n>` without `gh` on PATH: say so and stop.

## Step 2: Compute the scope text

The agents are not edited; they get this text verbatim:

- Working tree: `Scope: working tree — changed files: <git diff HEAD --name-only>; untracked, not ignored: <untracked from git status --porcelain, minus <docs-root>/ and .agents/scratch/>; read the diff with git diff HEAD -- <files> and read each untracked file whole.` If both lists are empty: "nothing to review", stop.
- Range: `Scope: commits <a>..<b> (git log <a>..<b>); the diff is git diff <a>...<b>.`
- PR: `Scope: PR #<n> — files: <gh pr diff <n> --name-only>; the diff is gh pr diff <n>.` (`--fix` on a PR: the branch must be checked out first; otherwise say so and stop.)
- Paths: `Scope: the named files as they are in the working tree, read whole — not a diff: <paths>.`
- `--project`: `Scope: the whole repository at HEAD (<git rev-parse --short HEAD>), no diff.`

Every agent writes that text on its `Range reviewed:` line. `<scope>` for artifact names: `worktree`, `pr-<n>`, `<a>-<b>` (each `/` in a ref becomes `-`), `project`, or the first path's basename.

## Step 3: Dispatch — one agent per lens, all in parallel

Before any dispatch, look for a project agent that shadows a harness review agent: a file under the project's `.claude/agents/` or `.agents/agents/` named `reviewer.md`, `security.md`, `verifier.md` or `explorer.md`, or whose frontmatter `name:` is one of those four. Claude Code loads the project copy in place of the harness one, so its report would stand in for the independent one. One found means stop before dispatching: name the file, say the review cannot run until it is renamed or removed, and write nothing.

Each dispatch gets the scope text, today's date, its slug, its brief, the sentence "Write your artifact with the Write tool; report only means no source edits.", and a tool-call budget below the agent's `maxTurns` with "write the artifact early, then update it" (context § Work). `--high`: on Claude Code pass `model: opus` to `reviewer` and `security`; on Antigravity subagents inherit the session model, so run the session with `agy --model pro` when it matters.

## Step 4: The record

**Rounds and fixes** (moved from the global context 2026-10-01): a second round on the same mechanism, or a fix that causes the next round's defect, means stop and ask what the mechanism is for; two agents contradicting each other on one mechanism means the rule they both read is the defect — fix the rule, then re-dispatch; three rounds without convergence means stop and ask. A fix that makes the code shorter beats one that defends it more. A low finding whose fix adds a flag, a refusal or a step the operator must take is put to the operator as a one-line choice, the simpler option recommended, and recorded `left: operator — <choice>` — "fix everything" covers defects, not new gates. A finding is fixed only when every trigger it names has a test that fails without the fix, built on the arrangement the finding measured, not a fresh fixture.

One lens and no `--fix`: the agent's artifact is the record; nothing else is written. Otherwise write `<docs-root>/reviews/<date>-review-<scope>-merged.md` (`owner: main`, `date:`; a second one the same day gets `-2`, `-3`): FAIL first; one verdict line per lens; the findings with severity and confidence, two artifacts reporting the same `file:line` collapsed into one row naming both lenses; links to every artifact; a "Not checked" section. When the findings of a record are acted on — by `--fix`, or by the task that acts on the report later — the MAIN agent appends a final `## Outcome` section to that record, one line per finding: `fixed` (commit or file:line), `rebutted` (one checkable reason: not a defect because X, with X at file:line; a trade-off recorded at file:line, in an ADR, or in an AGENTS.md section; or the user's words, quoted — never an intent the next reader cannot verify, which is fixed instead, and never a command that exited non-zero), or `left` (who owns it; a finding outside the scope is `left`, not `rebutted`), written in the same commit as the fix; the changelog entry links the record. This is the one edit the main agent makes to an agent's record; the reviewing agents never amend their own past reports.

## Step 5: `--fix`

The main agent applies every edit — `reviewer` and `security` have no edit tools and never touch source. At most three rounds, unless the user picks one more at the cap. When two lens agents contradict each other on one mechanism — one clears what the other flags — the rule they both read is the defect: fix the rule (a harness proposal when it is a harness rule), then re-dispatch; never the code on one agent's word. A round: apply each finding or rebut it in the record — or, for a low one whose fix adds a flag, a refusal or a step for the operator, record it `left: operator — <choice>` and ask; run the project's checks bare and read the status; write the record's `## Round N` section, one line per finding so far — the finding quoted, then `fixed at <file:line>`, `rebutted: <reason>` (Step 4), `in flight: <who>` (handed to `documentation`, or a test still being written, in this run) or `left: <owner>` (not fixed in this run); re-dispatch the same lens agents over the same scope with the same slugs (they overwrite their artifacts), each brief followed by `---`, that section's fixed lines only (`<file:line> — what changed`), and "Verify each fix is correct and complete; look for defects the fixes introduced. Re-read each declaration a fix touched and every reference to it, not only the finding's own lines: a fix that moves or re-declares something leaves the original exported with no caller, which reads as intentional API and passes a review that only re-checks the finding." Rebuttal reasons stay in the record, out of the dispatch. The record ends with its `## Outcome`. Per lens: `--code`, `--simplify`, `--security` → edit the source; `--docs` → dispatch `documentation` with the findings in its files (README, specs, testing guides, deploy guides, the project `AGENTS.md` setup and deploy sections) and fix the rest yourself (skills, agents, rules, the context, other `AGENTS.md` sections); `--prompts` → apply the `## Proposed diff` hunks yourself, one finding per edit, except the hunks the reference marks as proposed only (its Group 2 rows on volatile specifics and contradicting instruction files), which stay in the record for the operator with every `flag` item (in a harness checkout, a `context/` or `rules/` edit runs `go test ./internal/harness -run TestRenderedContextFitsAntigravityBlock -count=1` bare before the commit); `--tests` → write the missing tests yourself (the verifier never does). Stop when a round reports no finding beyond the ledger's `rebutted` and `left` lines and no line is still `in flight`, after the third round (say so and ask the user), or as soon as a round's findings land on the mechanism the previous round fixed, or a fix introduced that round's new defect — then stop and ask what the mechanism is for. The three-round cap is a gate: it holds whatever "work autonomously" instruction is in effect, and only the user's own words in the same turn, naming it, waive it. At the cap, ask with your recommendation first: accept the remaining findings as `left` with an owner in the Outcome section, run one more round, or abandon the fix. A headless run with `--fix` applies up to the cap; when no reply can arrive there — a print-mode run, or a user who said they will not answer — it stops and writes the question into its record and into the handoff's Next Steps, writing the handoff if the session has none. Without `--fix`, every run only reports.

## Step 6: Report

In chat, at most ten lines: the worst finding first, one verdict per lens, the record's path (or the single artifact's), and what `--fix` changed or rebutted. A review is step 2 of the Definition of Done; its other steps follow as usual.

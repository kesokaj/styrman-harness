# Security review — BUG-079 stale-running-binary note, round 2   (2026-09-18)

Range reviewed: c868ed4..0f2da25

## Verdict: FINDINGS

The round-1 medium is half closed. The note can no longer name a file that does not exist — `RunningElsewhere` now requires `os.Stat(binPath)` to succeed (`internal/harness/pathguard.go:85-88`), pinned by a unit case and by a fresh-home release-path case, so an `update` into a home with no installed binary is silent and nobody is told to remove their only `sh-agent`. What remains is the other half: the note is gated on file IDENTITY and never on VERSION, while `UpdateFromRelease` keeps three `return nil` branches that install nothing (`internal/harness/release.go:107,114,117`) and `main.go:215-216` still prints after them on `!*check` alone. In the branch that prints "the newest release %s is older than this binary %s; nothing installed" the program has just established that the file it is running is NEWER than anything it could install, and then advises pointing that file at `~/.local/bin/sh-agent` with `ln -sfn` or removing it — a downgrade on the program's own advice, with no version of either side shown. Both rebuttals hold as written. The `ln -sfn` advice does reach a root- or manager-owned path and is a real, if operator-executed, weakening; it is now offered FIRST and unqualified, which is the opposite of round-1 finding 2's remediation. Nothing in the range touches crypto, auth, secrets, dependencies or GCP; the release signature and checksum gate is untouched and still runs before the note.

## Findings

- **[low / confidence: high]** `cmd/sh-agent/main.go:215-216,659-661` with `internal/harness/release.go:107-118` — the note still fires after an update that installed nothing, and recommends replacing a NEWER running binary with a link to an OLDER installed one. `staleRunningNote` compares only `os.SameFile`; nothing reads either file's version, and the caller's only guards are `!*check` and `err == nil`. Two concrete states: (a) `the newest release <tag> is older than this binary <version>; nothing installed` — the running file is provably ahead of every release, yet the note says the file it ran from "stays as it is" and offers `ln -sfn` the installed one over it, or removal; (b) `up to date (<V>)` with an `~/.local/bin/sh-agent` left by an older checkout install — the note names that stale file as "the installed binary". Exploitable in principle as self-inflicted downgrade, no attacker needed: a plain `sh-agent update` from the README "Install without cloning" shape, which is the exact devbox shape in BUG-079. Remediation: `main.go:377` already reads a binary's version off disk with `buildinfo.ReadFile(filepath.Join(home, harness.BinPath))`; call it inside `staleRunningNote`, print both versions so the premise is shown rather than asserted, and drop the remedy (or invert it) when the installed file is not newer. Existing internal package plus stdlib — no dependency, nothing to justify. Alternatively have `UpdateFromRelease` report whether it wrote `dest` and print only then.

- **[low / confidence: high]** `cmd/sh-agent/main.go:661` — `ln -sfn` is offered first, unconditionally, for a path the program knows nothing about the ownership of. `from` is a PATH entry; on the BUG-079 machine it is `/usr/local/bin/sh-agent`, so following the note means `sudo ln -sfn ~/.local/bin/sh-agent /usr/local/bin/sh-agent`. Afterwards a root-owned, system-wide PATH entry resolves to a file inside one user's home that that user — and anything running as that user, including every agent this harness dispatches — can overwrite at will; anyone who then runs `sh-agent` from the system path (another account, `sudo sh-agent …`, a unit or cron job) executes user-writable content. That is the classic writable-file-on-a-privileged-PATH weakening, and it is genuinely a weakening and not merely a spelling: the trust boundary of the system path moves to a user-writable file. It is also the operator's own action, and on the single-operator machines this harness targets the practical severity is low — hence low, not medium. The defect is that the program recommends it with no ownership qualification, where round-1's remediation asked for the reverse ("offer removal only for a path under the user's home") and where README.md and `deploy/remote.md` at least carry the "a link to the same file is not a shadow" context. Remediation: offer `ln -sfn` only when `from` is under the user's home, and otherwise say that a system path is the operator's to decide, naming what changes if they link it.

- **[low / confidence: medium]** `cmd/sh-agent/main.go:661` — `ln -sfn` is named without its argument order, in a message whose two paths are printed in the order "ran from X … installed binary Y". GNU order is `ln -sfn TARGET LINK`; a reader following the sentence's order writes the link at the installed path and points it at the stale copy. This does NOT escape `--home`: installed files are written by `writeAtomic` (`internal/harness/apply.go:265-299`, `os.CreateTemp` in `filepath.Dir(dest)` then `os.Rename`), which replaces a symlink at `dest` rather than writing through it, so no later `install` or `update` can land in `/usr/local/bin` via a reversed link — checked, and a negative result worth recording. The consequence is confined to correctness until the next install: `status` reads drift and version from a file that is now the stale one. Remediation: print the full command with both operands substituted.

### Rebuttals checked

- **Raw `%s` of PATH-derived paths — the rebuttal holds.** `from` is built from the operator's own `PATH` entries (`pathguard.go:90-96`) and `installed` from `--home`/`$HOME`; no untrusted producer reaches either, and `which -a` and `type` print the same bytes unescaped, so `%q` would make the harness's output differ from the tools the docs tell the reader to compare it against. One caveat that does not overturn it: this note is pasted into `.agents/docs/testing/` logs that agents read back, so a control byte or strong-directional character in a PATH entry would survive into agent input — the same class as round-1's RTL finding, mitigated by the non-ASCII grep over `.agents/docs/` rather than by the format verb. Accepted as rebutted.
- **`os.Executable()` used only to `Stat` — the rebuttal holds exactly as stated.** `exe` is consumed once, at `pathguard.go:78`, and the value returned is always `cand`, built from a PATH entry; `exe`'s own spelling never reaches the reader. A `" (deleted)"`-mangled Linux path or a stale relative darwin path therefore makes `os.Stat` fail and the function return `"", false` — fail-closed, silent, pinned by the `exe missing` case (`pathguard_test.go:451`). Accepted as rebutted.
- **RTL characters** — `git show 0f2da25:.agents/docs/plans/2026-09-18-recon-bug-079-diagnosis.md | grep -c $'\u0646'` returns 0; the two U+0646 are gone from the committed file at head. Confirmed fixed.

### Positive: the read-only mode is guarded the way the global rule asks

The new side effect sits below both read-only early returns — `!*check` on the release path (`main.go:215`) and after `Reinstall` on the checkout path (`main.go:507`, below the `checkOnly` returns at 468 and 473) — and both tests assert that `--check` does NOT print it (`main_test.go:1577`, `main_test.go:1617`), not only that the normal mode does. The fresh-home case asserts silence before the fixture plants an installed file, so the gate is tested in its must-be-silent state as well as its must-print state.

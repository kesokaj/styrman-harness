# Security review — v2.4.0-unsigned-adr053   (2026-10-05)

Range reviewed: 18b9018..4ee867a

## Status: COMPLETE

## Verdict: FINDINGS

The checks that remain are sound, and removing the signature leaves no bypass. Tag shape, never-backwards, the version marker, the checksum, the size caps and zip path safety are unchanged or still enforced. A `SHA256SUMS` beside a zip can only be absent (UNVERIFIED, as before) or pass; every other failure refuses the zip. The release/zip tests pass at 4ee867a's code.

The problems are in what now holds the trust, which the signature used to hold.

The worst one: GitHub Actions is still enabled on the repository. ADR-053 removed the release key, so any credential that can push a workflow can now publish a binary that every binary-only place installs and runs. That includes each of the 8 SSH keys on the account, not only the operator's `gh` token. The harness uses no CI, and two earlier rounds asked for Actions to be turned off.

The second: the release host is not pinned. `gh` takes a hostless `--repo` from `GH_HOST` (measured). The signature used to make the host irrelevant; now it decides what a binary-only place installs.

Lower down:
- The `gh` token's revocation is still unverified, and the handoff calls it optional.
- "VERIFIED" and "authenticity" wording survives in output and docs.
- The bridge block has gaps in its old-key handling.
- The newest handoff still directs the procedure ADR-053 retired.

## Findings

- **[medium / confidence: high]** GitHub Actions is still on, so any push credential can publish a release that installs everywhere.
  - **Where.** ADR-053 Consequences (`.agents/docs/architecture/DECISIONS.md:596`), `.agents/docs/specs/sh-agent/delivery.md:30` and `.agents/docs/deploy/remote.md:61`.
  - **Measured.** `gh api repos/kesokaj/styrman-harness/actions/permissions` returns `{"enabled":true,"allowed_actions":"all",…}`. `gh ssh-key list` has 8 lines.
  - **The path.** A pushed workflow can ask for `permissions: contents: write` and run `gh release create` with any binary and a matching `SHA256SUMS`. Every binary-only place then installs it at its next `sh-agent update` and executes it (`internal/harness/release.go:128-149`). The workflow-permission step comes from GitHub's documented `permissions:` key; I did not exercise it.
  - **Before ADR-053**, the same workflow could not produce what a v2.4.0+ binary accepted without the release key.
  - **Who holds such a credential.** Anyone who can push a workflow file: every SSH authentication key on the account, not only the operator's `gh` token. One of those keys, `private-crew`, was copied unencrypted into scratch sandbox homes earlier today (BUG-160).
  - **What ADR-053 says.** It says "a stolen GitHub credential can now publish a binary". It does not say that every SSH login key is now such a credential.
  - **What else understates it.** `remote.md:61` still says a reached credential "can clone and push", not "publish a binary".
  - **What it costs to close.** The harness uses no CI by rule, and rounds 1 and 2 recommended turning Actions off.
  - **Remediation.** The operator, in their own shell, runs `gh api -X PUT repos/kesokaj/styrman-harness/actions/permissions -F enabled=false`. Then:
    - Prune the account's SSH keys to the machines that must push.
    - Name the release trust root as "any credential that can create a release, or push a workflow while Actions are on". That sentence goes in delivery.md § The model (rule 6's home), an ADR-053a note (the ADR file is append-only) and `remote.md:61`.

- **[medium / confidence: high]** The release host is not pinned.
  - **Where.** `internal/harness/release.go:21` (`ReleaseRepo = "kesokaj/styrman-harness"`), used at `:55` (`gh release view`) and `:159-163` (`gh release download`). The manual chains share it: `README.md:104` and `.agents/docs/deploy/remote.md:29`.
  - **Measured.** gh resolves a hostless OWNER/REPO through `GH_HOST`. On gh 2.102.0, `GH_HOST=example.invalid gh release view --repo kesokaj/styrman-harness` prints "error connecting to example.invalid".
  - **Not measured.** go-gh also defaults to the single host in a gh config that lists exactly one; I read that, I did not run it.
  - **What changed.** Before ADR-053, a release served from any other host failed the compiled-in signer. Now the host gh picks is part of the trust chain. Take a binary-only place whose environment sets `GH_HOST`, for instance a machine that also works against a GitHub Enterprise host. It asks that host for `kesokaj/styrman-harness`. Whoever owns that name there publishes a binary plus a self-consistent `SHA256SUMS`, and the place installs and runs it.
  - **Why ADR-053's comparison fails.** ADR-053 says trust rests on GitHub "as a checkout place's pull does". A checkout's remote URL pins github.com; this does not.
  - **Related (low).** The `gh` executable is whichever comes first on PATH (`release.go:74`), and it is now the whole chain. The removed design preferred a system-path `ssh-keygen` for exactly that reason (security review 2026-09-17). State it.
  - **Remediation.** Pass `--repo github.com/kesokaj/styrman-harness` in both calls (gh accepts HOST/OWNER/REPO), or set `cmd.Env = append(os.Environ(), "GH_HOST=github.com")`.
    - **Test.** The fake gh in `release_test.go` records its argv and fails unless the repo carries `github.com/`. Run it with `GH_HOST=other.example` set, and see it fail on today's code first.
    - **Docs.** Add the same `github.com/` prefix in README's and remote.md's manual chains.

- **[medium / confidence: medium]** The operator's `gh` token now publishes binaries, and its exposure is not shown closed.
  - **Where.** `.agents/docs/bugs/BUG-160-credentials-left-in-scratch-homes.md:30` records the live `gh` OAuth token (scopes `repo`, `admin:public_key`) dumped in plain text (mode 644) by an Antigravity terminal snapshot.
  - **Round 3** found the same token still exported as `GH_TOKEN` into every agent session and sandbox run, with revocation unverified.
  - **The handoff** (`.agents/docs/handoffs/2026-10-05-1519-v2.4.0-bridge-ready-operator-steps.md:26`) lists rotating it as "Optional".
  - **Under ADR-053** that token alone can `gh release create`/`upload` a binary every binary-only place installs, with no Actions needed. Every agent session on this box, which runs in bypass mode, holds it.
  - **Remediation.** Revoke and reissue the token before v2.4.0 is cut, as a blocking item rather than an optional one. Keep `GH_TOKEN` out of kit and sandbox environments (`env -u GH_TOKEN`). Say in the trust-root sentence above that any process holding the operator's `gh` login can publish.
  - **Why confidence is medium.** Whether the token was revoked since round 3, and whether the dumped copy left the machine, cannot be seen from here.

- **[low / confidence: high]** "Verified" and "authenticity" claims survive the removal.
  - **Authenticity sentences.** `.agents/docs/deploy/remote.md:49` and `README.md:153` still say "authenticity is the signature and checksum on the file, before the move". No signature exists any more, and a checksum from the same server is integrity, not authenticity. Both files say so elsewhere.
  - **Zip place output and status.** `cmd/sh-agent/main.go:1161` prints `VERIFIED against the SHA256SUMS of release vX.Y.Z`. `internal/harness/repo.go:184` records `;verified vX.Y.Z`, and `cmd/sh-agent/main.go:718-719` shows it in `status`. At a zip place the `SHA256SUMS` comes from the same download as the zip and its version marker is unsigned. A forged zip with its own `SHA256SUMS` therefore prints, and keeps showing, "verified v2.4.0".
  - **Smaller wording.**
    - `internal/harness/release.go:142` prints "verified and installed".
    - `.agents/docs/deploy/local.md:40` says "verify it".
    - `AGENTS.md:84` calls remote.md "the signed-tag release procedure".
  - **Remediation.** Say what was checked, e.g. `CHECKED against the SHA256SUMS beside it (integrity only, ADR-053)`, in the output and the status rendering. The manifest token may stay for compatibility. Rewrite the two authenticity sentences. Step 3's `grep` at `remote.md:144` and the zip tests change with the string; the v2.3.2 bridge grep (`:172`) does not, since that binary prints its own text.

- **[low / confidence: high]** The bridge block (`.agents/docs/deploy/remote.md:160-172`) has gaps in how it handles the old key. Nothing has run yet: v2.3.2 is still the latest release.
  - **(a) The fingerprint check reads the wrong file.** At `:163`, `ssh-keygen -lf "$RETIRED"` fingerprints `"$RETIRED.pub"` when that file exists. OpenSSH's `sshkey_load_public` tries the named file as a public key, then `<file>.pub`, and only then the private file's own public half (read in the source, not run). So the check can pass for a file that is not the old private key, or does not exist, against its comment "RETIRED is set, exists, and is the old key".
    - The signature stays safe: `-Y sign` refuses a private file that does not match, and `:166` verifies against the retired key.
    - The exposure is `:167`'s `rm -f "$RETIRED"`.
    - Fix: `test "$(ssh-keygen -y -P '' -f "$RETIRED" | ssh-keygen -lf - | cut -d' ' -f2)" = SHA256:5HpYQJjpG+yE1xXBTOIZPsTkbkgkVnV8z0eG8hBawyU`. The exposed copy has no passphrase.
  - **(b) Round 3 finding 5 is still open.** The procedure runs "each command its own call" (`:95`), so `RETIRED` does not survive between an agent's Bash calls. `:167` with an empty `RETIRED` runs `rm -f ''` and `test ! -e ''`, both exit 0, and it reports "the old key is off the disk" while deleting nothing.
    - Fix: open `:164` and `:167` with `: "${RETIRED:?set RETIRED}" &&`, or chain the block into one `&&` command.
  - **(c) "Off the disk" covers one file.**
    - **Copies not covered.** The sources the key comes from are untouched: `~/.claude/paste-cache/d17c19c927c1cf71.txt` (present at review time, 1405 bytes, mode 600; not opened) and the session transcript round 1 named.
    - **Who says to delete them.** ADR-053 says the copy "is then deleted", but no command does it. Only the superseded handoff (`:32`, `:34`) names those copies.
    - **Why it matters.** While any v2.3.2 binary is in use, a leftover copy still signs releases those binaries install, given any of the credentials above.
    - **Fix.** Delete every known copy by name in the block or a following operator step, each with `test ! -e`.
  - **(d) Round 3 finding 10 is still open.** `:169` runs `mkdir -p ../v232src` without emptying it, so a tree left by an earlier attempt is compiled into the v2.3.2 check binary. Use `rm -rf ../v232src && mkdir ../v232src`.
  - **Availability, not security.** Adding `SHA256SUMS.sig` to the upload loop is prose (`:160`). If it is missed, v2.3.2 places are stranded, but they fail closed.

- **[low / confidence: high]** The newest handoff directs the retired procedure.
  - **The file.** `.agents/docs/handoffs/2026-10-05-1519-v2.4.0-bridge-ready-operator-steps.md`, committed in this range at bd049f3.
  - **What it still says.** It still runs ADR-052:
    - the new signer is compiled in (`:11`)
    - a release agent socket in scratch (`:20`)
    - load `~/.ssh/styrman-release_ed25519` (`:25`)
    - tag "by the current key", the bridge "in place of steps 3 and 3b", "Upload seven assets" (`:32`)
  - **Why it matters.** ADR-053 superseded all of it and no newer handoff exists. The resume order reads the newest handoff first, and it wins on conflict.
  - **What following it does.** The key, socket and env file it names are gone (measured absent), so it fails rather than harms. It is also the only record that carries the paste-cache and transcript deletions and the token follow-up.
  - **Remediation.** Write a superseding handoff for ADR-053 that carries those items, with the token rotation as blocking.

# Review — harness-code (audit phase, sh-agent-works-everywhere Phase 2)   (2026-09-18)

Range reviewed: `internal/harness` and `cmd/sh-agent`, all non-test `.go` files, read whole in the working tree (not a diff), per `.agents/docs/plans/2026-09-18-sh-agent-works-everywhere.md` Phase 2. Files read: `internal/harness/{apply,plan,repo,source,release,state,inventory,pathguard,frontmatter,adopt,derive,render,report}.go` and `cmd/sh-agent/main.go` — all 14 non-test `.go` files in scope (≈4,240 lines). No `*_test.go` file read in full (spot-checked with `grep` only, see Not examined).

## Verdict: APPROVE WITH NITS

The code is unusually careful — nearly every non-obvious decision carries a dated review comment explaining a prior failure mode it closes. I found no correctness or security defect that reaches a silent no-op or a false success. I found two places where the operator's own stated rule for this audit — "refuses with a message naming the cause **and the alternative**" — is only half met: `update` on a plain copy gives the cause with no next step, and `adopt` on a plain copy succeeds but tells the operator to do something (commit and push) that the place cannot do. Neither is a silent failure; both are message-quality gaps the audit was explicitly commissioned to find.

## Findings

- **[medium / confidence: high]** `cmd/sh-agent/main.go:461` (`update`) + `internal/harness/repo.go:118-119,153` — `update` on a plain copy (a tree with no `.git`) surfaces the bare `errPlainCopy`: `"sh-agent: not its own git checkout; a plain copy cannot be updated with git"`. This names the cause but not the alternative, unlike every other refusal in this codebase (compare `ResolveSource`'s release-binary refusal, which says "unset it, or build sh-agent from that tree"; `Pull`'s dirty-tree refusal, which says "commit or stash them"). The plan's own Failure-modes rule for this audit is explicit: "refuses with a message naming the cause and the alternative (the BUG-076 rule)". `status` on the same place kind (`main.go:351`) is a little better — "plain copy, not its own git checkout; update is refused" — but still names no alternative (re-clone as a real checkout, or move to a release binary and use `sh-agent update` there). Fix: wrap the error at the `update()` call site (or in `Behind`/`Pull`) with the alternative, the way every sibling refusal in this file does. No CLI-level test exercises this path today (confirmed by grep — only `Behind`/`Pull` unit tests hit `errPlainCopy`; `cmd/sh-agent/main_test.go` has no plain-copy `update` case), which is also flagged, independently, as a Phase 2 test-gap item in the plan itself.

- **[low / confidence: high]** `cmd/sh-agent/main.go:245-257` (`adopt` case) — `adopt` does not check whether `repo` is a git checkout before running. On a plain copy (no `.git`) it succeeds and unconditionally prints `"next: review it, run \`sh-agent install\`, then commit and push the repo"` — an instruction the operator cannot follow, because there is no git repository to commit or push in a plain copy. This is the "a wrong message ... is a finding" case the dispatch names: a reported success carries a next step that does not apply to the place kind it ran on. Compare the release-binary path, which correctly refuses adopt outright (`main.go:249-251`, "adopt needs a harness checkout; this install is a release binary") — the plain-copy path has files to adopt into but no git to finish the workflow, and nothing in `Adopt` or its caller says so. Fix: gate the "commit and push" sentence on `harness.IsCheckout(repo)`, or refuse adopt on a plain copy the same way it is refused on a release binary.

- **[note, not a finding / confidence: medium]** `internal/harness/source.go:44-51` — `IsReleaseVersion`'s regex `^v[0-9]+\.[0-9]+\.[0-9]+$` accepts non-canonical spellings such as `v1.02.2` or `v01.2.2` (leading zeros). This is not exploitable as a downgrade or confusion vector today — `compareRelease`/`releaseParts` uses `strconv.Atoi`, which parses `"02"` as decimal `2`, and the tag string itself is only ever compared for exact-equality against the signed `SHA256SUMS` marker (`release.go:282`), never used as a numeric identity elsewhere. Flagging only because the plan's own Phase 2 checklist already names this exact gap ("`IsReleaseVersion` rejects a non-canonical spelling") as unchecked/pending — this review confirms the current regex still admits it, so the pending item is real and not stale.

## Criteria

1. **Dead code** — pass. No unused exported function, type, or leftover debug output found across the 14 files; every helper (`gitOutC`, `firstLineOfError`, `hostDir`, etc.) has a live caller.
2. **Flow tracing** — pass with the two findings above. Traced `Install`/`Status`/`Diff`/`Uninstall` (apply.go) against `Plan` (plan.go) and `main.go`'s dispatch for every verb × place-kind combination named in the dispatch (checkout / release binary / plain copy). Error paths are wrapped with context almost everywhere (`fmt.Errorf(...: %w, err)`); the two exceptions above are the only bare/under-specified propagations found. `writeAtomic` (apply.go) and the settings-file write (main.go) both sync-then-rename correctly, so a crash mid-write cannot leave a truncated file. Resource lifetimes (temp files, cloned dirs) are closed/removed on every path I traced, including `defer os.RemoveAll` in `cloneThrowaway`/`Reinstall`/`Adopt`'s staging.
3. **Standards conformance** — pass. Go idioms observed throughout: context-wrapped errors, no naked panics, `context` not needed here (no long-running I/O beyond `exec.Command`, which is bounded by the OS). Comments describing security-relevant behavior (secret redaction, symlink refusals, signature verification) are consistent with the code they sit beside — no stale doc-comment found.
4. **Directory layout** — pass. `cmd/sh-agent/` holds only the entrypoint; `internal/harness/` holds all private logic; no stray files.
5. **Simplicity / DIY-except-security** — pass. Release verification uses `ssh-keygen -Y verify` (a vetted external tool, not a hand-rolled signature check) and `crypto/sha256` as designed — both conform to the security exemption. No hand-rolled auth, crypto, or session logic anywhere in scope. Stdlib-only throughout (`go.mod` per `AGENTS.md` carries no dependency), consistent with the project's stated constraint.
6. **Decoupling** — pass. Clean seams: `harness` package owns all filesystem/git/release logic; `main.go` is thin wiring plus two operator-facing pieces of state (`--home`/`--vendor` resolution, `attribution*` for Claude's settings.json) that arguably could live in `internal/harness` but are small and self-contained — not a finding, no second caller exists to justify moving them.

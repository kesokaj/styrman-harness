# Security review — release-binary Phase 4, `update` from a signed release   (2026-09-17)

Range reviewed: dab2565..4d45155 (branch `release-binary`)

Blast radius read: `internal/harness/release.go` (new, 216 lines), `cmd/sh-agent/main.go`
(`update` routing, `installPassArgs`, `run`'s source resolution), `internal/harness/apply.go:265-303`
(`writeAtomic`, reached from the new code), `internal/harness/repo.go:22-62` (`ResolveSource` —
what makes `repo == ""`), `internal/harness/source.go` (`IsReleaseVersion`, `EmbeddedSource`),
`internal/harness/plan.go:16,189` (`BinPath`, `selfExe`), `internal/harness/report.go:28-215`
(the redaction helpers, for whether the new error paths can reuse them), and both test files.

## Verdict: FINDINGS

The signature chain itself is sound and fails closed. The signer line is compiled in
(`release.go:32`), written to a 0600 file inside the private download directory and passed to
`ssh-keygen -Y verify` with a `const` namespace and an identity parsed out of that same
compiled-in string, so nothing shipped in a release can redirect the trust root. Both the
checksum file and the binary are read once into memory and the *same* bytes are what gets
verified and what gets written — no re-read between check and use, which is the thing this
pattern usually gets wrong. Nothing outside the download directory is written before both checks
pass, and the replacement is create-in-destination-dir / write / chmod / `Sync` / `Rename`, so an
interrupt leaves the old binary byte-intact.

What is missing is any binding between *which* release is installed and the signed material.
`tag == version` (`release.go:75`) is an inequality test, `LatestRelease` takes GitHub's unsigned
word for "newest", and the signed `SHA256SUMS` carries only names and hashes. An actor with
release-management access to the repository but *without* the operator's ed25519 key can
therefore present a genuinely signed *older* release as the newest one; `update` verifies it
correctly and installs it. That is a downgrade path onto every binary-only place, including back
onto a binary that a later release fixed. Phase 5 (which generates `SHA256SUMS`) is still
unticked in the plan, so the cheap half of the fix — putting the tag inside the signed bytes —
costs nothing to adopt now and gets expensive once a release has shipped in the current format.

## Findings

- **[medium / confidence: high]** `internal/harness/release.go:71-82` (with `:47-57`) — no
  downgrade protection and no binding of the signed bytes to a version. `tag == version` only
  asks whether the tag *differs*; any different tag is installed, older included. `LatestRelease`
  derives "newest" from `gh release view --json tagName`, i.e. from the GitHub API, which the
  ed25519 signature does not cover; the signed artifact (`SHA256SUMS`, per
  `.agents/docs/plans/2026-09-17-release-binary.md:75`) names files and hashes only, never a tag.
  Exploitable in principle by anyone who can delete, retag or republish releases — a strictly
  weaker capability than holding the signing key — and the signature check passes honestly while
  it happens. Remediation, stdlib only: (a) `version` here is always a well-formed `vX.Y.Z`
  (`ResolveSource` returns an embedded source only when `IsReleaseVersion(version)`,
  `repo.go:50-53`), so parse both sides with the `^v[0-9]+\.[0-9]+\.[0-9]+$` regexp that already
  exists as `releaseVersion` in `source.go:44`, compare the three integers, and refuse anything
  not strictly greater — this also makes `--check`'s "newer release available" true rather than
  merely "different"; (b) put the tag inside the signed material — a `sh-agent-release <tag>`
  first line in `SHA256SUMS`, written by `/preflight` in Phase 5 and required by `verifyRelease`
  to equal the tag being installed — so the signature covers which release the bytes are, not
  only what the bytes are.
- **[low / confidence: high]** `internal/harness/release.go:48,68,86,131,171` — the whole trust
  chain is resolved through `PATH`. `ssh-keygen` is the verifier and `gh` is the transport, both
  invoked by bare name; a writable directory earlier on `PATH` than `/usr/bin` reduces
  verification to whatever a planted `ssh-keygen` exits with (0 means "verified"), after which
  the checksum only has to match the file a planted `gh` delivered. `~/.local/bin` — the
  directory this code writes the new binary into — is normally on that `PATH` ahead of
  `/usr/bin`, so the attacker needs no privilege the update itself does not already assume. That
  makes this an accepted assumption rather than a defect, but it is undocumented and it is the
  cheapest complete bypass of Phase 4. Remediation: keep `ssh-keygen` (the stdlib has no SSH
  signature verification, and `golang.org/x/crypto/ssh` would be a new dependency carrying a
  security-critical primitive — rejected on the stdlib-first rule and on the ban on composing
  crypto here), but prefer an absolute path for it (`/usr/bin/ssh-keygen`,
  `/usr/local/bin/ssh-keygen`, `/opt/homebrew/bin/ssh-keygen`) before falling back to `PATH`, and
  say the residual assumption out loud in the doc comment that currently claims the signer "is
  COMPILED IN, never read from a file on the machine" — true of the key, not of the verifier.
- **[low / confidence: medium]** `internal/harness/release.go:131-136` — argument injection into
  `gh` from a repository-controlled tag. `tag` goes straight into argv as the positional of
  `gh release download`; a tag beginning with `-` is parsed by gh as a flag. Nothing in *this*
  code stops it. What stops the damage is gh's own flag handling, which is an external
  guarantee: the real `--repo` and `--dir` are passed *after* the tag and a repeated string flag
  is last-wins, and gh refuses `--output` together with `--dir`, which is the only reason a tag
  of `--output=<path>` cannot redirect the write outside the download directory. `--pattern` is
  repeatable, so a tag of `--pattern=*` appends rather than replaces and pulls every asset in the
  release into `dir`; no trust decision moves with it, because `verifyRelease` writes
  `allowed_signers` with `os.WriteFile`, which truncates anything gh put at that path first (the
  case the plan records as tested). Remediation is the same one line as finding 1: validate the
  tag against `releaseVersion` before it reaches `exec.Command`, so the argument cannot be a flag
  at all.
- **[low / confidence: medium]** `internal/harness/release.go:90-94,167-168` (and `:108-111`) —
  the download directory has a guessable name in a shared parent, and neither it nor the files in
  it are created with "must not already exist" semantics. `release-<pid>` under
  `~/.config/sh-agent` is enumerable; `os.MkdirAll` succeeds on an existing directory *and* on a
  symlink pointing at one; `os.WriteFile(signers, …)` follows a symlink at that path and writes
  through it; and `defer os.RemoveAll(dir)` on a symlinked `dir` unlinks only the link, leaving
  the downloads in the target. Reaching any of this needs a same-user or root local attacker, so
  severity is low, but the fix is one line and closes the pid-collision case at the same time (a
  directory left by a SIGKILLed run makes the next run with that pid fail inside gh):
  `os.MkdirTemp(filepath.Join(home, ".config", "sh-agent"), "release-")`. The same
  follow-the-link remark applies to `os.MkdirAll(filepath.Dir(dest))` at `:109`. Note by contrast
  that the final `os.Rename` in `writeAtomic` *replaces* a symlink at `dest` rather than writing
  through it — the safe behaviour, worth keeping deliberately.
- **[low / confidence: high]** `internal/harness/release.go:193-204` — `checksumFor` never
  validates the hash field and takes the first matching line. A hash that is not 64 lowercase hex
  characters is accepted as `want` (it can never equal `hex.EncodeToString` output, so it fails
  closed — defence in depth, not a bypass), and duplicate lines naming the asset silently resolve
  to the first. Because the parse runs on bytes the signature has already covered, none of it is
  attacker-reachable without the operator's key; the value of fixing it is that a mis-generated
  `SHA256SUMS` out of Phase 5 would be named as malformed instead of surfacing as "checksum
  mismatch for sh-agent-linux-amd64", which points the operator at the wrong thing. Remediation:
  require `^[0-9a-f]{64}$` after the `ToLower`, and treat a second matching line as an error
  rather than ignoring it. The rest of the parse is sound — `TrimSpace(line)` +
  `Cut(…, " ")` + `TrimSpace`/`TrimPrefix("*")` handles the two-space sha256sum separator, the
  `*` binary marker, a trailing `\r` from CRLF and an uppercase hash, and a name that is a strict
  prefix or suffix of the asset does not match because the comparison is `==` over the whole
  trimmed field, not a prefix test.
- **[low / confidence: high]** `internal/harness/release.go:137,146` — the download failure
  message cannot say what gh reported. `cmd.Run()` leaves `(*exec.ExitError).Stderr` nil (only
  `Output`/`CombinedOutput` populate it) and no `Stderr` is assigned, so gh's stderr goes to
  `/dev/null` and `firstLineOfError(downloadErr)` always falls through to `err.Error()`, i.e.
  `exit status 1`. This is the safe direction for secret hygiene — a path that prints nothing
  leaks nothing — but it defeats the stated intent of the comment above it, so it will be
  "fixed". When it is: capture into a bounded buffer and scrub before printing. The Phase-3
  redaction helpers in `report.go:145-215` (`redactLines`, `redactDocument`) are unexported and
  shaped for whole files, so reuse means extracting a line-level helper, not calling those.
- **[low / confidence: medium]** `internal/harness/release.go:141,156` with `apply.go:269-274` —
  the release asset is read whole into memory and then held a second time for the atomic write,
  and `SHA256SUMS` is read with no size bound either. An absurdly large asset published to the
  release is an OOM or a disk-fill on every place that updates, and it lands before verification
  can reject anything. Needs release-publishing access, so it shares finding 1's attacker.
  Remediation: bound both reads with an `io.LimitReader` at a few tens of megabytes, and stream
  the SHA-256 into the temp file in one pass instead of buffering the binary twice.

## Answers to the seven questions asked

1. **Can release content redirect key, namespace or which file is checked?** No. `releaseSigner`
   is a compiled-in package variable (`release.go:32`, a `var` only so a test can substitute a
   test key), the identity is `strings.Cut` of that same string (`:163-166`, with an explicit
   refusal when it has no identity), the namespace is a `const` (`:22`), and the asset name is
   built from `runtime.GOOS`/`runtime.GOARCH` (`:40-42`, `:96`) — none of the four is read from
   the release, the environment, or a file on the machine. An `allowed_signers` file shipped as a
   release asset can land in the download directory, but `os.WriteFile` at `:168` truncates it
   before `ssh-keygen` sees the path. `ssh-keygen -Y verify` is given `-f` explicitly, so no
   `~/.ssh` file participates. The signature is computed over the in-memory `sums` fed on stdin
   (`:176`) and `checksumFor` parses that same in-memory copy (`:180`) — there is no window in
   which the verified bytes and the parsed bytes could differ.
2. **Anything written outside the download directory before both checks pass?** No. Order in
   `UpdateFromRelease`: `LookPath("gh")` → tag → up-to-date/`--check` returns (both write
   *nothing*, not even the directory — the `MkdirAll` at `:90-91` is after them, so `--check`
   cannot repeat BUG-070) → `LookPath("ssh-keygen")` → `MkdirAll(dir)` with `defer RemoveAll` →
   download into `dir` → `verifyRelease` (signature, then checksum, error on either) →
   `writeAtomic(dest)` → run the new binary. The replacement is atomic in the useful sense:
   `apply.go:269-302` creates the temp file in `filepath.Dir(dest)` (same filesystem, so the
   rename cannot degrade to a copy), writes, chmods 0755, `Sync`s, closes, renames, and removes
   the temp file on every error. An interrupt before the rename leaves the old binary whole and
   at worst a stray `.sh-agent-*` in `~/.local/bin`; after the rename the file is complete and
   already verified. The bytes written are the identical `data` slice that was hashed.
3. **Can a path escape `~/.config/sh-agent/` or `~/.local/bin/`?** Not from the tag or the asset
   name: the directory name is `release-%d` on `os.Getpid()` (`:90` — the tag is never joined
   into a path anywhere), and the asset name comes from compile-time constants, so no
   attacker-controlled string reaches a `filepath.Join`. The residual cases are the
   symlink/pre-created-directory ones in finding 4 (local same-user attacker), gh's own choice of
   filename for a downloaded asset (constrained by three literal `--pattern` values, none of them
   a glob), and the crafted-tag flag injection in finding 3, where the only thing preventing an
   attacker-chosen write target is gh's refusal of `--output` alongside `--dir`. A pid collision
   is a functional nuisance, not an escape: the stale directory makes gh fail, and
   `downloadRelease` checks `downloadErr` (`:145-147`) after reading the file, so a stale or
   planted asset left in that directory cannot be passed off as a fresh download.
4. **SHA256SUMS with several files, duplicates, `*`, absurd size, CRLF?** Several files: fine,
   only the line naming this platform's asset is consulted. Duplicates: first wins, silently
   (finding 5). `*`: handled (`:199`). CRLF: handled — `TrimSpace` eats the `\r`. Absurd size: no
   bound on either read (finding 7). All of it sits downstream of the signature, so it is
   hygiene, not an exploit surface.
5. **Is `checksumFor` exploitable?** Not as written — full reasoning in finding 5: exact-match
   comparison over the trimmed name, so no prefix or suffix confusion; whitespace and case
   normalised; a malformed or non-hex hash fails closed.
6. **Credentials, gh tokens, key material in output?** Nothing prints key material: the
   compiled-in signer is a *public* key, and the only place it is written is a 0600 file inside a
   directory removed on every path out. `firstLineOfError` can print an external command's
   stderr, but only on the `LatestRelease` path (`:48`, which uses `.Output()`, so `ExitError.Stderr`
   is populated); gh does not echo its token in those messages, and the `downloadRelease` path
   prints nothing external at all (finding 6). No token, password or key is passed in argv or in
   the environment by this code, and no secret is written into the download directory.
7. **Is the compiled-in signer the only trust root?** For the *bytes*, yes. For *which* bytes,
   no — GitHub's unsigned "latest release" answer is a second, unsigned root (finding 1), and
   `PATH` is a third, implicit one (finding 2). After the new binary runs its own `install`
   (`:119-123`), that binary has already been checksum-verified against signed content, and it
   installs the files embedded in itself plus itself (`plan.go:189`), so the child introduces no
   further root. `installPassArgs` hands it only `--home` (when the operator gave one) and a
   `--vendor` narrower than `all`, both operator-supplied, so the child's argv is not a new
   input surface either.

  (`release_test.go:380`). No `.env`, `*.pem`, `*.key`, `*.tfvars` or credential JSON is added.

  reviewed under question 3.
- **Authz/authn** — the authorisation decision is "are these bytes the operator's", delegated to

  check cannot be bypassed by release content and is not reordered relative to the write. No
  revocation list is consulted, which is inherent to this design. The absent check is version
  monotonicity (finding 1).

  designed; the signature is delegated wholesale to OpenSSH rather than reimplemented or composed
  here, which is exactly right under the ban. The digest comparison is a plain `!=` on two hex
  strings, which is not a timing concern: both sides are public values, and the secret (the
  signing key) is never on this machine.

## Outcome

Read against the diff by the main agent, 2026-09-17. HEAD at review time: 4d45155; the fixes below are the commit that follows it.

**Fixed**

1. **[medium] no downgrade protection, and no version inside the signed bytes.** Confirmed by reading `UpdateFromRelease`: `tag == version` was an equality test, the tag came from the unsigned API, and `SHA256SUMS` named only files and hashes — so a genuinely signed OLDER release installs, and one release's signed checksums verify under another release's tag. Fixed in three parts, all now covered by tests that fail without them (`.agents/scratch/p4-mustfail/mutate.py`): the tag must parse as `vX.Y.Z` before it reaches argv or decides anything (which also closes finding 3, a `-`-leading tag being read by gh as a flag); the release must be numerically NEWER than the running binary, with a development build left alone and told so (D27); and `SHA256SUMS` must carry `# styrman-harness vX.Y.Z` as a comment line matching the tag, checked only after the signature holds, so the version is part of what the operator signed (D26). `/preflight` Step 6 must write that line — added to Phase 5's box with a rehearsal, since a release built the old way is now correctly uninstallable. Tests: `TestUpdateFromReleaseNeverGoesBackwards` (older release on both modes, five non-release tags, a development build), and two refusal cases for a signed SHA256SUMS naming another version or none.
2. **[low] the verifier came from PATH.** `sshKeygen` now prefers `/usr/bin/ssh-keygen` and `/bin/ssh-keygen` and falls back to PATH (D28), and `TestSSHKeygenPrefersASystemPath` plants a copy earlier in PATH and asserts it is not the one chosen. The overclaiming sentence in the `releaseSigner` comment is replaced by what is actually true: the signer line is pinned, the verifier program is not, and a machine whose system directories or PATH an attacker owns can defeat any check this binary makes.
3. **[low] a guessable `release-<pid>` directory that `os.MkdirAll` and `os.WriteFile` would follow a symlink into.** Now `os.MkdirTemp(base, "release-")` — a random name, mode 0700 — and any `release-*` sibling left by an interrupted earlier update is removed first, with a line saying so.
4. **[low] `checksumFor` accepted anything as a hash and took the first of duplicate lines.** It now requires 64 hex characters, refuses two DIFFERENT hashes for one name rather than choosing, and tolerates an exact duplicate line; `TestChecksumFor` covers a short hash, a missing name, conflicting duplicates, an identical duplicate, a `*` binary marker and an upper-case hash.
5. **[low] `cmd.Run()` left `ExitError.Stderr` nil, so the download error could never quote gh.** The download now captures stderr and the message carries its first line; the "no asset" case is distinguished from a failed download by whether the file is there at all.
6. **[low] unbounded reads.** `readCapped` refuses an asset over 256 MiB and a SHA256SUMS over 1 MiB, both variables so a test can lower them.

**Rebutted, with reasons**

7. **[low] `gh` itself comes from PATH.** Deliberate and unavoidable: `gh` is how a binary-only place reaches GitHub at all (R8, D7), and it carries the operator's credential. A planted `gh` can serve any bytes it likes, which is exactly what the compiled-in signer and the checksum exist to catch — and they do, as the refusal tests show. A planted `ssh-keygen` was the real hazard, and that is finding 2, fixed.
8. **[not a finding] "every claim about gh's flag handling was read, not measured."** Fair, and the fix makes it moot: the tag is validated against `^v\d+\.\d+\.\d+$` before it is passed, so no tag this code accepts can be read as a flag whatever gh's parser does.

Verifier for this phase ran against 4d45155, before these fixes; the counts in its log therefore predate them. The suite after the fixes: `gofmt`, `go vet` and `go test -race -count=1 ./...` clean, and all twelve mutations in `.agents/scratch/p4-mustfail/mutate.py` fail the tests that cover them.

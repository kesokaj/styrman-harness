## Verdict: implementation not ready — two new BLOCKING gaps in the Phase 1 kit build that r1 did not reach, both concrete and code-checked against the actual scripts the plan says it reuses.

## (1) Gaps

- **G5 — `metrics.py` does not produce the main-vs-subagent split the plan's own verify clause claims it does. BLOCKING.** Phase 1's D3 task says: "count the large-trail sessions... in which the MAIN agent (not a subagent) ran `sh-agent search` — verify: AI, the transcript split of `metrics.py`." Read `.agents/scratch/eff-kit/metrics.py:47-57`: `scan(main)` and `scan(subs)` are computed into separate dicts `km` (main-transcript tool-call kinds) and `ks` (subagent-transcript kinds) — the split genuinely exists at that point — but line 57 immediately merges them: `sh_search=km.get('sh-agent-search', 0) + ks.get('sh-agent-search', 0)`. Only the summed total is stored per row and printed (line 67: `sum(x['sh_search'] for x in r)`); `km`/`ks` are discarded. As written, the script cannot answer "did the MAIN agent search" — it can only answer "did anything search." This matters concretely: the closed search-index plan's own efficiency data (`testing/2026-09-29-search-efficiency.md`) shows subagent-only counts of 11–22 per session while the main agent's count was 0 in every sample — using the existing combined field for D3 would silently report a high adoption number built entirely from subagent calls, the opposite of what D3 is designed to measure. The plan names no task that changes `metrics.py` to keep `km`/`ks` separate through to the printed/JSON output. Two implementers would build genuinely different things here: one adds a `sh_search_main` field and gates D3 on it (correct); another reuses the existing `sh_search` column as-is (silently wrong, and nothing in the plan's Verification catches the mistake — the E2E criterion just says "the main agent... runs `sh-agent search` in at least 4 of 6," not naming a specific field).
- **G6 — the large-trail lane's three-session shape does not exist in the reused kit; `lane.sh`'s current `large` branch is a single session, and reusing its session labels collides with the sample-app metrics table. BLOCKING.** Plan `## Interfaces`: "Large-trail lane... s1 ... s2 ... s3 ..." — three separate resumed sessions per run. Read `.agents/scratch/eff-kit/lane.sh:10-19`: the `large` branch runs exactly ONE session (`"$sess" "$arm" "$d" "$cli-$arm-large-$n" "$LARGE"`) that both fixes the drift and answers the five questions in one prompt (`prompts.sh:9`, the `LARGE` variable). `score-large.py` scores that single combined session only (checks `ANSWERS.md` content and the drift string in one directory, no per-session split). The readiness plan's s1/s2/s3 shape — and its brand-new s3 task ("add one row to `testing/sh-agent-matrix.md` for `sh-agent version` on a zip place") — has no existing scoring or session-splitting logic to reuse; "Kit: clean-arm mode" (Phase 1's first task) does not name building this. Compounding it: `metrics.py`'s printed table (line 62-67) buckets purely by `sess ∈ {s1,s2,s3,large}` and `arm`, ignoring `app` — if the new large-trail sessions are tagged `s1`/`s2`/`s3` (to match the plan's own naming), they land in the *same* aggregate rows as the sample apps' `s1`/`s2`/`s3` sessions (build-the-app vs. fix-drift-in-a-trail are unrelated tasks), corrupting the median cost/time table the Verification clause requires ("The clean A/B's per-session table exists... with both arms delivering"). Two implementers would tag these differently (e.g., `app=large` with distinct session names) or not notice the collision at all and get a silently merged, meaningless table.
- **G7 — `testing/sh-agent-matrix.md` has no "zip place" column for the s3 task to add a row to. NON-BLOCKING but under-specified.** The matrix's header is `| Verb | Checkout | Plain copy | Release binary |` (`.agents/docs/testing/sh-agent-matrix.md:14`) — three place-kinds, no "zip place" column anywhere in the table, and `version` already has a row with three filled cells. "Add one row... for `sh-agent version` on a zip place" doesn't match the table's actual shape: there is no row to add (version's row exists) and no column to put a zip-place cell into without extending every row's width. A reasonable implementer resolves this by adding a fourth column (the natural fix, matching AGENTS.md's three-ways-in-plus-zip framing) but the plan doesn't say so, and a much lazier implementer could append an orphan row/footnote instead. NON-BLOCKING: the project's testing conventions (one cell per verb × place-kind, "nothing blank") make the column addition the only conforming choice, so a competent implementer decides this alone.

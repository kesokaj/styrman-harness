## Verdict: FINDINGS

`knownCheckout` is the right control in the wrong shape: it treats the *presence* of `$SH_AGENT_REPO` (or of a `--repo` flag) as proof that the operator named the checkout, but `FindRepo` only *uses* those values when they pass `IsRepo`, and silently falls back to the working-directory walk when they do not. Any non-empty value therefore disables the guard while the repo still comes from the walk. I confirmed this against a harness-shaped lookalike directory: with no env var the guard refuses (good — round-1 finding 1 is closed for the plain case), but with `SH_AGENT_REPO=/nonexistent-not-a-harness`, or with `--repo /nonexistent-not-a-harness`, the same run reports `[dry-run] the binary would be rebuilt from …/lookalike` and plans to overwrite `~/.claude/AGENTS.md`, `~/.gemini/config/rules/AGENTS.md` and `~/.local/bin/sh-agent` from it. A stale `export`, a wrapper script, an `.envrc`, or a typo'd path is enough; the operator gets no warning that the path they named was ignored. The dry-run fix itself is real and verified — no build directory, no writes — but the delta claims a trust boundary it does not yet hold.

## Findings

- **[medium / confidence: high]** `cmd/sh-agent/main.go:339` — `knownCheckout` returns nil on `repoFlag != "" || os.Getenv("SH_AGENT_REPO") != ""`, i.e. on non-emptiness, not on the value having been the one `FindRepo` chose. `FindRepo` (`repo.go:30-34`) tries `explicit`, then `$SH_AGENT_REPO`, then every ancestor of the cwd, and takes the first that satisfies the two-stat `IsRepo` test — so a value that is not harness-shaped is skipped, the walk wins, and the guard is nonetheless bypassed. Verified twice against a scratch lookalike (`context/AGENTS.md` + `skills/x/SKILL.md`) with a manifest naming a different installed checkout: case B (`SH_AGENT_REPO=/nonexistent-not-a-harness`) and case C (`--repo /nonexistent-not-a-harness`) both proceeded, where case A (neither set) correctly refused. Without `--dry-run` the same control flow reaches `harness.Reinstall` (`repo.go:99-122`), which runs `go build ./cmd/sh-agent` in that directory and executes the result with the operator's environment, then installs it to `~/.local/bin/sh-agent` and rewrites the global agent context for both CLIs. Remediation: compare values, not emptiness — `if samePath(repoFlag, repo) || samePath(os.Getenv("SH_AGENT_REPO"), repo) { return nil }` (guarding the empty-string case, since `samePath("", "")` is true). Independently, `FindRepo` should return an error when an *explicit* `--repo` or `$SH_AGENT_REPO` fails `IsRepo`, instead of silently walking — silently using a different directory than the one named is a trust bug in its own right.
- **[low / confidence: high]** `cmd/sh-agent/main.go:342-344` — the guard fails open on a `LoadState` error: `if err != nil || !found || st.Repo == "" { return nil }`. An unparseable or unreadable `~/.config/sh-agent/state.json` (truncated by a crash or a full disk, a permissions change, a future schema) silently removes the "is this the installed checkout?" question. Verified: with `state.json` containing `not json`, `install --dry-run` from the lookalike proceeded past the guard and only failed later, inside `harness.Install`, which *does* propagate the same error (`apply.go:24-26`). On the real path that ordering matters — `Reinstall`'s `go build` and child exec happen before `Install` is ever reached, so the untrusted tree's code runs and only then does the install abort. Every other `LoadState` caller in the package treats the error as fatal; this one should too. Remediation: `if err != nil { return err }`, keep the fail-open only for `!found` (first install).
- **[low / confidence: high]** `cmd/sh-agent/main.go:114-121` vs `internal/harness/apply.go:79-80` — the new comment says a dry run "must not compile or execute anything", but `Install` runs git subprocesses in the discovered checkout unconditionally. Traced with `GIT_TRACE` against a committed lookalike: `install --dry-run` executes `git rev-parse --short HEAD`, `git rev-parse --abbrev-ref HEAD`, `git rev-parse --short HEAD`, `git status --porcelain`, all with `-C <repo>`, all loading `<repo>/.git/config`. Repository-local config such as `core.fsmonitor` is executed by `git status`, so round-1 finding 7's code-execution path survives on precisely the flag an operator reaches for when inspecting a checkout they do not trust. It is now *partly* shielded by `knownCheckout` — but only as far as that guard holds (see the finding above). Remediation: either fix the comment to say what is actually suppressed, or harden `gitOut` once (`-c core.fsmonitor=`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null` for the read-only queries) so every caller benefits.
- **[low / confidence: high]** `cmd/sh-agent/main.go:113,164` — the guard is wired into `install`/`sync` and `update` only. `status`, `diff`, `list`, `render`, and `adopt` still act on whatever `FindRepo` walked up to. Verified: `sh-agent status` run from inside the lookalike prints it as "repo", enumerates its skills, and runs `Inspect` (git) inside it; `adopt` writes into it. None of these build or deploy, so the severity is low, but the docstring's framing ("standing in a harness-shaped directory … must not be enough") is broader than the wiring. Remediation: either extend the check to the commands that execute git in, or write to, the discovered repo, or narrow the comment to the build-and-deploy path.
- **[low / confidence: medium]** `cmd/sh-agent/main_test.go:181` and `internal/harness/harness_test.go:709-737` — the two new tests share a mutable path in the *real* checkout: `TestReinstallBuildsAndInstalls` creates `<repo>/.agents/scratch/sh-agent-build-<pid>` (via `Reinstall`) while `TestDryRunNeverBuilds`, in a different package, asserts that `filepath.Glob` of exactly that pattern is empty. `go test ./...` runs package binaries concurrently by default, so the dry-run assertion can fail on the other package's build directory, or pass only because the timing happened to miss it. Four consecutive `go test -count=4 ./...` runs were green here (cmd finished in 0.19s, harness in 1.48s with the build test last), which is luck rather than isolation. A verification that can fail for a reason other than the code under test is a weak instrument. Remediation: have `TestDryRunNeverBuilds` copy the checkout into `t.TempDir()` (or at minimum glob for a build directory named with its own pid) so the assertion is about its own run.
- **[low / confidence: high]** `internal/harness/repo.go:100`, `internal/harness/inventory.go:71` — `govulncheck ./...` still reports two reachable standard-library vulnerabilities: **GO-2025-3956** (`exec.LookPath` returning unexpected paths, fixed in go1.24.6) traced to `Reinstall`, and **GO-2026-4602** (`os`, fixed in go1.25.8) traced to `LoadSkills`. Toolchain is go1.24.4. Per the round-1 rebuttal this is a toolchain upgrade tracked in `TODO.md`, not a code change; recorded here to keep it on the register, not as a new objection. Note only that the first one lands on the `go` lookup whose result `Reinstall` then executes, so it compounds the findings above rather than sitting on its own.

## Checked

- **Secrets** — none. Grepped the changed source for password/secret/token/api-key/`AKIA`/`ghp_`/PEM/bearer patterns: one comment-word hit in `inventory.go:234`, nothing credential-shaped. No `.env`, key, or credential file in the range. New error strings print repo paths and a state-file path, never environment values or file contents; `knownCheckout`'s error discloses only two local directory paths to the operator running the command.
- **Injection** — no shell anywhere: every subprocess is `exec.Command` with an explicit argv (`repo.go:82,109,115,126`; the new test helper `gitIn` likewise), so `--repo`/`--home` values cannot break out into a command. The live injection surface is a *path*, not a string: which directory gets compiled and executed (first finding). `reorder` (`main.go:386+`) only shuffles argv and honours `--`.
- **Authz/authn** — no identity surface; the tool runs wholly as the invoking user. The boundary that matters is process trust — which tree is built, which binary is executed, which context is deployed — and that is what `knownCheckout` is for and where the findings sit.
- **Crypto** — nothing cryptographic added; nothing hand-rolled. `samePath` uses `filepath.EvalSymlinks` and falls back to raw string equality when either side fails to resolve, which is fail-closed for the refusal decision (a moved or deleted previous checkout compares unequal and the run is refused). Still worth naming: the commit/`+dirty` stamp remains a freshness hint, not an integrity check.
- **Dependencies** — `go.mod` declares no third-party requirements; none added by this delta (stdlib only, consistent with the repo rule). `govulncheck ./...` run: exit 3, two reachable stdlib vulnerabilities (see the finding), plus 2 imported-but-uncalled and 43 required-but-uncalled. `npm audit` not applicable and not run — there is no `package.json` in the repo; this is a pure Go module.
- **GCP surface** — nothing touched. No IAM binding, service account, Cloud Run flag, `--allow-unauthenticated`, or key file in the range.
- **Build/test health** — `gofmt -l .` clean, `go vet ./...` clean, `go test -race ./...` green, `go test -count=4 ./...` green (see the flakiness finding for why that is weaker evidence than it looks).

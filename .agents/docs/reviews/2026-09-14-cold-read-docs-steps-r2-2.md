# Cold read (round 2) — documentation-steps plan   (2026-09-14)

Range reviewed: `.agents/docs/plans/2026-09-14-documentation-steps.md` (as revised after round 1) and the surfaces it names: `context/AGENTS.md`, `agents/{verifier,documentation,changelog,reviewer,security,explorer,bugs}.md`, `skills/{review,preflight,retro,handoff,init-project}/SKILL.md`, `.agents/docs/testing/skill-matrix.md`, `.agents/docs/deploy/{local,remote,gcp}.md`, `README.md`, `REQUIREMENTS.md`, and the six files under `~/.config/sh-agent/proposals/` (read-only).

This is a second cold read; three round-1 reads exist (`2026-09-14-cold-read-docs-steps-2.md`, `2026-09-14-review-cold-read-docs-steps-1.md`, `2026-09-14-review-cold-read-docs-steps-3.md`). Their three blocking findings — the 09-10/09-03 queue-file handling, the Outcome section's step citation, and the guide-name/plural-wording collision — are in fact fixed in the current plan text (verified below). This read looks for what remains after that fix, not for a restatement of it.

## Verdict

The plan is close but not clean: one real ambiguity from round 1 was only half-closed (the LOCAL/REMOTE/CLOUD lane text in `agents/documentation.md` was never reconciled with the new "one `guide.md` per app" model), and the backfill instruction for item 5/5b — the single item every round has flagged — still asks the implementer to classify eleven proposals (in `2026-09-04-retro.md` and `2026-09-11-retro.md`) as `applied <date> (<commit>)` or `queued` with no method given for telling the two apart. That classification is the entire point of the feature (retro proposals sitting unapplied unnoticed) and getting it wrong silently defeats it, so it is a real, undecided interface question rather than implementer taste.

## Gaps — must be decided before implementation

- **G1 (new). Item 5's backfill gives no method for classifying the un-annotated proposals, and a wrong classification defeats the feature.** Plan `:29` requires a `**Status:** applied <date> (<commit or change entry>)` or `**Status:** queued` line "directly under every `### Proposal` heading" across all six files. It special-cases the two `2026-09-03` files (status is already stated in prose) and `2026-09-10` (blanket line to expand). It says nothing about how to classify the eleven proposals in `2026-09-04-retro.md` (6, confirmed zero `Status:` lines) and `2026-09-11-retro.md` (5, confirmed zero `Status:` lines) — these do not carry "applied" in their own text the way the 09-03 files do. Determining which of these already landed requires cross-referencing `context/AGENTS.md`, the agent files, and `changes/` history; I spot-checked `2026-09-11-retro.md` Proposal 1 ("'done' closes the roadmap and TODO and ends with a handoff") against `context/AGENTS.md:18` ("at Done both are EMPTY … finished lines are deleted") and it is clearly already applied — but the plan gives no rule for making that check systematically, and none for what to do when it is genuinely unclear (mark `queued` and let it resurface, or dig for the commit). Two implementers plausibly diverge: one marks everything `queued` as a "safe" default (burying real history and re-surfacing already-shipped work as an open finding, the opposite of item 5's purpose per the plan's own Why section), another does the archaeology and gets some wrong without a way to check their work. *(cite: plan `:29`; `~/.config/sh-agent/proposals/2026-09-04-retro.md`, `2026-09-11-retro.md` — both confirmed to carry no `Status:`/`### Proposal` status text of any kind)*

- **G2 (new). `agents/documentation.md`'s lane diagram is never reconciled with item 2's "one guide per app" model, so the artifact set ships internally inconsistent.** `agents/documentation.md:27` lists `testing/<app>/ # LOCAL / REMOTE / CLOUD testing guides` — plural guides split by target environment. Item 2 (plan `:26`) instructs edits only to the verifier's intro/Pre-flight and to documentation's "Shared seam" paragraph (`agents/documentation.md:34`), not to this lane code block. After the edit, `agents/documentation.md` will say in one place ("Your lane") that `testing/<app>/` holds environment-scoped guides (plural, no fixed name) and in another place ("Shared seam") that it holds one `guide.md`. The plan's "other named procedure documents … stay and are linked from the guide" (`:26`) is a plausible reconciliation (skill-matrix.md and any LOCAL/REMOTE/CLOUD split survive as separate linked documents, `guide.md` is just the one more), but the plan never says so explicitly and never touches the line that contradicts it. A first-pass implementer either leaves the contradiction standing or invents a resolution the plan doesn't state. *(cite: `agents/documentation.md:27` vs `agents/documentation.md:34` and plan `:26`)*

- **G3 (minor, likely not load-bearing). Interfaces vs. checklist disagree on the guide's filename.** The Interfaces section (plan `:26`, the section the plan itself calls "the exact edits", `:21`) writes the literal filename `testing/<app>/guide.md` three times. The Phase 2 checklist for the same item (plan `:52`) writes it as `testing/<app>/<guide>.md` — a placeholder, not the literal name. Given `:21` names Interfaces as authoritative, a careful implementer resolves this correctly, but it is worth fixing in the plan text so a skimming implementer copies the same string everywhere.

## Readiness — questions a first-pass implementer would have to ask

1. **BLOCKING** — For the 6 proposals in `2026-09-04-retro.md` and the 5 in `2026-09-11-retro.md`: what method determines `applied <date> (<commit…)>` vs. `queued`, and what happens when the evidence is ambiguous? (See G1. Two implementers produce different final queue states, and the state is exactly what `/retro --harness` will read as "still open" going forward.)
2. **NON-BLOCKING** — Does `agents/documentation.md`'s LOCAL/REMOTE/CLOUD lane text get trimmed/reconciled with the new one-guide-per-app model, or left as a separate, still-valid categorization that `guide.md` sits alongside? A reasonable implementer picks "left alongside, guide.md is one more document" per the plan's "other named procedure documents … stay" line, and says so in the diff. (See G2.)
3. **NON-BLOCKING** — Is the guide's filename literally `guide.md`, or a per-project name? The Interfaces section is explicit and is the plan's designated source of truth, so a careful implementer copies `guide.md` verbatim and disregards the checklist's `<guide>.md` placeholder. (See G3.)
4. **NON-BLOCKING** — Item 7's "the Go upgrade path" for `local.md`'s new Operator steps has no existing documented procedure anywhere in the repo to draw from (checked `REQUIREMENTS.md`, `context/dev-setup.md`, `deploy/local.md` — none exists; only a pending "Go ≥ 1.24.6" note in the newest handoff). A reasonable implementer writes a short, low-stakes bullet (e.g., `brew upgrade go` / download from go.dev) and is not wrong to do so, but two implementers' bullets will differ in wording and possibly OS coverage.

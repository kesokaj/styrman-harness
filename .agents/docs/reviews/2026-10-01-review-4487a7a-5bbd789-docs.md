## Findings

- **[medium / confidence: medium]** `skills/preflight/SKILL.md:61` and `:88`. The tier half of the verification row checks only "the cited log".
  - Text, `:61`: "list … the tiers the active plan names for the released work …; one that the log does not show as run leaves this row unmet, whatever the log's heading or its silence".
  - Text, `:88`: "a tier the plan names for the released work, that the cited log does not show as run".
  - Why that is wrong here:
    - In this repo the behavioural tier (guide § 4 § Behavioural runs, one per changed agent) and the Antigravity and real-home runs that `AGENTS.md` § Release requires are run by the main agent. They are recorded in their own `testing/*-verify-*` logs, for example `2026-10-01-verify-agents-behavioural.md` and `-verify-real-home-v2.2.0.md`.
    - The verifier's logs say "Behavioural CLI rows, real-home smoke and macOS not run (main agent's / out of scope)" (`2026-10-01-verify-v2.3.0-gate-r6.md` Scope).
    - Round 4's Outcome puts the `verifier-blocked-redispatch` counts in "the gate's behavioural log", not in the verifier's log.
  - Who is misled: the main agent at the v2.3.0 gate. Following `:61` and `:88` as written, it records the row as unmet and writes NO-SHIP, which only a verbatim operator turn can lift, and nothing can in an unattended run. Or it learns to read "the cited log" loosely, the habit the rule was written to stop.
  - Fix:
    - `:61`: "one that no `testing/*-verify-*` log reaching HEAD shows as run (a tier the main agent ran is shown by its own log, cited beside the verifier's)".
    - `:88`: "that no cited log shows as run".
  - Owner: main.
- **[low / confidence: medium]** `agents/verifier.md:14` against `:18`, `:20` and `:27` step 4.
  - Text: "A log whose status is FAIL, or IN PROGRESS with a failing command in it, is never updated in place or overwritten: a later run writes its own file".
  - The conflict: during its own run, after the first failed command, the verifier's log is exactly "IN PROGRESS with a failing command in it". `:20` orders "update it after EVERY command", and step 4 orders "Record every outcome even after a failure".
  - Who is misled: a verifier reading literally. It stops updating its own log, or starts an `-r2` file mid-run. Either way the commands that ran after the failure land in a different file than the gate cites, or in none.
  - The intended reading is a log left by an EARLIER run.
  - Fix: "A log an earlier run left with status FAIL, or IN PROGRESS with a failing command in it, is never updated in place or overwritten by a later run: that run writes its own file …".
  - Owner: main.

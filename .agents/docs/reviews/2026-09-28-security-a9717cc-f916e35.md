## Findings

- **[medium / confidence: high]** `.agents/docs/testing/skill-matrix.md:14` (and `:13`). This is outside the range, but it is the second home of the rule the range rewrote.
  - **Weakness:**
    - The full-matrix procedure writes `<home>/.gemini/antigravity-cli/settings.json` with `"allow": ["command(*)", "read_file(*)", "write_file(*)", "edit_file(*)", "list_dir(*)"]` and names no `trustedWorkspaces`. Step 1 of the same procedure logs the sandbox home in to both CLIs.
    - `command(*)` approves every shell command without a prompt. That is the same class of blanket grant round 1 rated medium, only without the trust over real checkouts.
    - The Claude row's allowlist looks enumerated, but `Bash(bash:*)` and `Bash(python3:*)` admit any command (`bash -c …`). `Bash(curl:*)` gives network egress. Together they also defeat the matrix's own mock ("a cloud command is denied").
    - `AGENTS.md:66` now says the opposite: the fewest grants the run needs, and the scratch clone as the only trusted workspace. An agent that rebuilds the kit "from this file" (`:7`) follows the matrix literally.
    - The matrix's `list_dir(*)` is also an invalid agy grant, silently ignored (see finding 2).
  - **Why it is exploitable in principle:**
    - The run executes as the operator's uid, on the machine that holds the release-signing ed25519 key, with live CLI credentials in its home.
    - Instruction-shaped text that reaches a matrix run can run any command with no approval. Such text can come from the 30 installed skills (six of them vendored third-party text) or from the fixtures.
    - `HOME=<scratch>` contains nothing.
  - **Remediation:**
    1. Replace the settings clause at `:14` with a pointer to `AGENTS.md:66` plus the matrix's own enumerated needs: `command(<name>)` for the commands the scenarios run, write and edit grants only as far as the scenarios need them, and `trustedWorkspaces` set to the run clones. Drop `list_dir(*)`.
    2. Drop `Bash(bash:*)`, `Bash(python3:*)` and `Bash(curl:*)` from `:13`, or record them as accepted risk with their conditions (operator-written fixtures, no third-party content, credentials deleted by name after the batch).
    3. Make the fix in one commit, so that one text holds the rule.
- **[low / confidence: medium]** `AGENTS.md:66` at f916e35 ("a read-only run: `read_file(*)`, `list_dir(*)` and `command(<name>)` for each read-only command"), and its instance at `.agents/docs/testing/2026-09-28-verify-v1.7.0-gate-fixes.md:17`. The list the text calls read-only is not read-only.
  - **Weakness:**
    - The run that was actually used (`cli.log` 15:31:37) granted `command(find)`, `command(git)` and `command(sed)`:
      - `find` can execute and delete (`-exec`, `-delete`).
      - `git` can execute code (`-c core.pager=…`, `-c alias.x=!…`), write, and push to any URL.
      - GNU `sed` can execute and write (`e`, `w`, `-i`).
    - `read_file(*)` has no path scope. It reaches `~/.ssh` (the release-signing key) and the real home's credential files. Whatever the agent reads is sent to the model provider as tool output.
    - `list_dir(*)` is rejected by agy 1.2.8: `ignoring invalid allow entry "list_dir(*)": unknown action "list_dir"` (sandbox `cli.log`, 15:31:40). That fails closed, so it is a correctness defect, not a security one. The verify log's "1 of 1 right" did not notice it.
  - **Why it is exploitable in principle:** instruction-shaped text reaching such a run could read a key and push it out with `git`, with no prompt. The grant is far narrower than `always-proceed`, and the fixtures so far are operator-written, hence low.
  - **Confidence is medium because:**
    - Argument matching for `command(<name>)` was not verified by a live run.
    - The uncommitted `AGENTS.md:66` now states "a `command(<name>)` grant allows every argument of that command", which corroborates the premise but has not been reviewed.
    - Whether `trustedWorkspaces` limits `read_file(*)` is unknown.
  - **Remediation:**
    1. Keep exec-, write- and network-capable commands (`find`, `git`, `sed`) out of any list the text calls read-only, or name them as deliberate grants.
    2. Scope `read_file` to the clone if agy's grant grammar takes a path pattern. Prove it with a must-fail probe: a read outside the clone must be auto-denied. Otherwise record `read_file(*)` as an accepted residual.
    3. Add that must-fail probe to the verify evidence. The log shows only the must-pass direction.
- **[low / confidence: medium]** `skills/preflight/SKILL.md:40` at f916e35, and `context/AGENTS.md:45`. These are the residuals of round-1 finding 2.
  - **Weakness:**
    - Round-1 remediation item `refresh_token` was left out of the committed fix with no recorded reason. A copied Google OAuth refresh token (`1//…`, JSON key `refresh_token`) under any other file name therefore passes both the stop-by-name list and the fallback scan.
    - The changes entry (`.agents/docs/changes/2026-09-28-1539-v1.7.0-gate-fixes.md:10`) calls `.credentials.json` and `antigravity-oauth-token` fallback-scan patterns. They are stop-by-name entries; only `sk-ant-` was added to the scan.
    - The always-on stop list that governs every commit, not only preflight's, is `context/AGENTS.md:45` ("credential JSON"). It still does not name the extension-less agy token file.
  - **Why it is exploitable in principle:** the credential copies live in the working tree under `.agents/scratch/`. `.gitignore:39` is their only barrier. A force-add or a renamed copy reaches the index unflagged. `gitleaks` was absent on this host at round 1.
  - **Remediation:**
    1. Commit the tree's `refresh_token` addition through the gate.
    2. Name "a CLI token file" in `context/AGENTS.md:45`, keeping inside the 22,000-byte `TestRenderedContextFitsAntigravityBlock` budget. Or record why the gitignore suffices.

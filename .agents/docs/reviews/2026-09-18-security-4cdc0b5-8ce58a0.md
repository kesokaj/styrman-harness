# Security review — BUG-078 PATH shadow warning, round 2 (4cdc0b5..8ce58a0)

Range reviewed: 4cdc0b5..8ce58a0

## Verdict: FINDINGS

All five round-1 fixes land, and the two load-bearing ones are correct: the README carries the genuine signer
line, byte-for-byte identical to the one compiled into the binary, and exactly one definition of "on PATH"
is left in the tree. The worst remaining problem is `.agents/docs/deploy/remote.md:23-33`, where the fix was
applied to the README but only sketched in `remote.md`: that block references `"$D"` twice and **never
assigns it** (no `mktemp -d`, no `D=` anywhere in the file), passes `-f allowed-signers` without ever creating
that file, and leaves `-I <signer>` as a placeholder — so every one of its three verification commands fails
on a literal copy-paste. Because the block is newline-separated with no `&&` and no `set -e`, the
`mv … ~/.local/bin/sh-agent` on the next line runs anyway. Pasted as written, the block is *guaranteed* to
install an unverified binary while printing three errors that scroll past. The same missing-chain shape is in
the README block, where the commands do work but a failed `ssh-keygen -Y verify` still does not stop the `mv`.
Everything in the Go half is sound; the one code gap is `status`'s `shadowed` line going silent when the
install dir is reached through a symlinked PATH entry, which both deploy guides now accept as a pass
condition. Of the two round-1 rebuttals, both reach a defensible conclusion (no code change) but each states
a reason that does not hold as written.

## Findings

- **[medium / confidence: high]** `.agents/docs/deploy/remote.md:23-33` — the release-binary block cannot
  pass its own verification, and moves the binary regardless. Three concrete defects, all checkable:
  (1) `--dir "$D"` (line 25) and the comment on line 29 name `"$D"`, but `D` is never assigned — `grep -n
  'D=|mktemp|rm -r' .agents/docs/deploy/remote.md` returns nothing for this block. With `D` unset the shell
  passes `--dir ""`; whether `gh` errors or writes to the current directory was not tested here (no network),
  but either way the assets do not land in a scratch directory. (2) Line 26 passes `-f allowed-signers` and
  no line in the block ever writes that file, so `ssh-keygen -Y verify` fails "No such file or directory";
  the `printf` that creates it and the `rm -f` that removes it live at lines 136-138 in § Releases, which
  this block does not point at. (3) `-I <signer>` is an unfilled placeholder. So the signature check fails,
  the checksum check has nothing verified to check against, and — because these are five separate lines with
  no `&&` and no `set -e` — line 29's `mv …/sh-agent-<os>-<arch> ~/.local/bin/sh-agent` executes anyway.
  That is the exact failure mode round 1's finding 1 existed to prevent, reappearing in the document the
  operator actually follows on a new machine. The comment on line 29 makes it worse by asserting a cleanup
  that no command performs: "the checksum and signer files stay in `"$D"` and go with it" — nothing creates
  `$D` and nothing removes it, so the signer file (once the reader supplies one) persists wherever they ran
  the block, which for an installer is plausibly `~` or `~/.local/bin` — a user-writable trust anchor in a
  PATH directory, round-1 finding 1(b) verbatim. Remediation: give this block the README's treatment —
  `D=$(mktemp -d) && cd "$D"` at the top, the real `printf … > allowed_signers` line and the real identity
  (both already at lines 136-137), and `&&` from the `printf` through the `mv`, ending `&& cd ~ && rm -rf
  "$D"`; or replace the block with one line pointing at `README.md` § Install without cloning so there is a
  single copy of the procedure to keep correct.
- **[medium / confidence: high]** `README.md:85-95` — a failed check does not stop the install. The block is
  fenced `bash`, one command per line, with no `set -euo pipefail` and no `&&` joining the verification steps
  to the `mv`. A forged `SHA256SUMS` that fails `ssh-keygen -Y verify` (line 92) prints its error, four more
  lines of output scroll past, and line 95 moves the unverified binary into `~/.local/bin/sh-agent`. Pasting
  a fenced block is the documented, expected use, and the one thing a reader is most likely to miss is an
  error four lines up. The asymmetry inside the block is the tell: lines 85 and 94 *are* `&&`-chained, so the
  block already teaches that chaining is how a step guards the next one, then drops it exactly where the
  trust decision is. This is the global rule about verification commands and `&&` chains, arrived at from the
  other side: here the chain is missing rather than mis-scoped. Remediation: `&&` from line 91 through line
  95 as one backslash-continued command, or `set -euo pipefail` as the block's first line plus one clause
  saying a non-zero exit from either check means the binary is not installed. Secondary, same block: line 93
  is a pipeline, so without `pipefail` its status is `sha256sum`'s alone — correct here only because
  `sha256sum` happens to be the deciding end of the pipe.
- **[low / confidence: high]** `internal/harness/pathguard.go:29` and `cmd/sh-agent/main.go:390` — `status`'s
  `shadowed` line goes silent when the install directory is on PATH under a different spelling that is not
  lexically equal. `filepath.Clean` is documented as purely lexical and does not consult the filesystem, so a
  PATH entry that is a SYMLINK to the install dir (`~/bin -> ~/.local/bin`), or a `$HOME` reached through a
  symlink or an automounted path, never matches `binDir`. The walk then runs to the end with `onPath` false —
  and `status` only prints inside `if … ; onPath {`, so it prints nothing even when `shadows` is non-empty
  and a real shadow exists. Round 1's repros (`//`, trailing `/`, `/.`) ARE fixed and pinned at
  `pathguard_test.go:320-323`; the symlink case is not, and my own round-1 remediation ("make `binOnPath` use
  `filepath.Clean`") is what missed it. Exploitable in principle only as a silenced warning, but both deploy
  guides now make its absence a pass condition — `.agents/docs/deploy/remote.md:182` ("no `shadowed` line")
  and `local.md:87` ("with no `shadowed` line") — so a checker can record a pass on a shadowed machine.
  Mitigating, and why this is low and not medium: `install`'s `pathHint` DOES name it in this case (the
  `len(shadows) > 0` branch, `main.go:652`), and both guides now put unqualified `sh-agent version` FIRST,
  which catches it whatever `status` says. Remediation: either print the shadows in `status` whenever
  `len(shadows) > 0` regardless of `onPath`, or decide "is this the install dir" with the same `os.SameFile`
  identity the candidate loop already uses (`pathguard.go:49`) — stat the PATH entry and compare to a stat of
  `binDir`, falling back to the lexical `Clean` when either stat fails, which is required to keep
  `pathguard_test.go:341` (an install dir that does not exist yet) passing. The second reuses a mechanism
  already in the file and introduces no new concept.

- **[low / confidence: medium]** `README.md:95` — `rm -r "$D"` is chained behind the `mv`, so a run that

- **[low / confidence: medium]** `internal/harness/pathguard.go:39-52` — the `seen` dedupe keys on the

- **[low / confidence: low]** `internal/harness/pathguard.go:25,42,49` — TOCTOU between the single `os.Stat`

### The two round-1 rebuttals, checked

- **Hung mount on `stat` — the conclusion holds, the stated reason does not.** The rebuttal says "a PATH
  entry on a hung mount already hangs every command lookup on that machine, so this adds no hang that was not
  there." That is false in two reachable cases. (1) A shell stops at the FIRST PATH entry holding an
  executable `sh-agent`; `PathShadows` continues past it to `binDir` (`pathguard.go:28-32`), so it stats
  entries the shell never touches — a hung mount *after* the winning entry but *before* `binDir` hangs
  `sh-agent install`/`status` where an unqualified `sh-agent` resolves fine. (2) The procedure this very diff
  documents invokes the binary by absolute path (`./sh-agent-linux-amd64 version`, `README.md:94`;
  `./sh-agent-<os>-<arch> version`, `remote.md:28`), which does no PATH lookup at all — yet `install` still
  walks PATH afterwards. A shell's `hash` cache widens the divergence on repeat invocations. What the reason
  gets right: `which -a` does walk the whole PATH, and when `binDir` is absent from PATH the walk is
  identical to a failed shell lookup. Scoped correctly this is still low and still accepted-risk — operator's
  own PATH, operator's own command, availability only — but the rebuttal should read "bounded by the entries
  ahead of the install directory" rather than "adds no hang that was not there."
- **Control bytes in a printed PATH entry — the conclusion holds, one of the three reasons does not.**
  Clause (a), "the printed strings are the operator's own PATH entries", is checkable and true: the only
  variable part of the printed string is a `filepath.SplitList` element of `os.Getenv("PATH")`, the name is
  the constant `sh-agent` from `filepath.Base` (`pathguard.go:23`), and the resolved target is never printed.
  Clause (b), "printed exactly as `which -a` prints them", is true — `which -a` does not escape either.
  Clause (c), "quoting would make the path unusable for copy-paste", does **not** hold as stated: Go's `%q`
  on an ordinary path yields `"/home/u/.local/bin/sh-agent"`, which a shell accepts verbatim, and
  `strconv.Quote` leaves printable non-ASCII unescaped. The honest version of the rejection is different and
  stronger than the one given: `%q` is Go quoting, not shell quoting, so it is not a shell-safe escape either
  (a `$` inside the resulting double quotes would expand on paste) — which makes my round-1 remediation the
  wrong instrument, rather than the copy-paste argument the right reason. Accepting the risk is correct on
  clause (a) alone: an attacker who can place an executable `sh-agent` in a directory on the operator's PATH
  already gets code execution the next time `sh-agent` is typed, so a terminal escape is an amplifier, not a
  way in. One consequence worth knowing rather than fixing: this output is pasted into `.agents/docs/testing/`
  logs and change entries, so a control byte would reach a committed markdown file — same precondition, same
  verdict.

# Cold read — `/review` plan   (2026-09-13)

Range reviewed: `.agents/docs/plans/2026-09-13-review-skill.md` (plan document, cold-reader check) plus the surfaces it names: `skills/audit/SKILL.md`, `skills/review-standards/SKILL.md`, `skills/preflight/SKILL.md`, `agents/explorer.md`, `agents/reviewer.md`, `agents/security.md`, `agents/verifier.md`, `agents/documentation.md`, `context/AGENTS.md`, `README.md`, `AGENTS.md`, `.agents/docs/testing/skill-matrix.md`.

## Verdict: design needs revision / implementation not ready

The plan is unusually well specified for a one-page design (D1–D9 cover naming, syntax, routing, recording, fix mode, model selection, and failure modes explicitly). The worst problem is a factual error that a literal implementer would reproduce: the plan orders the skill-count edit to 26 when the arithmetic of its own scope (delete `audit`, add `review`) holds the count at 27. A second real gap is that the plan's "working tree" default target requires behavior (including untracked files) that the reviewer agent's own unmodified scope section does not perform, while the plan explicitly puts "changes to the agents themselves" out of scope — those two decisions collide. A third gap is the artifact-naming instruction in D3 ("the artifact slug `review-<slug>`"), which reads as inconsistent with the file-naming conventions already hard-coded into `agents/reviewer.md`, `agents/security.md`, and `agents/verifier.md`.

## Gaps (must be decided before implementation)

- **Skill-count arithmetic is wrong.** Plan line 13: "`README.md` and repo `AGENTS.md` skill counts → 26." Current counts are 27 (`README.md:3`, `AGENTS.md:7`, confirmed by `ls skills/` = 27 directories excluding `VENDORED.md`). Scope is a straight swap — `skills/audit/` deleted, `skills/review/` added — so the count after the change is still 27, not 26. An implementer following the plan literally ships a wrong count; one who checks the arithmetic silently overrides the plan. Needs a decision: either the plan is wrong (fix to 27) or there's an unstated second skill removal nobody named.

- **The default "working tree" target is not something the reviewer agent, unedited, actually produces.** Plan D2 (line 21): "none → the working tree (`git diff` + `git diff --staged` + untracked source files from `git status --porcelain`)." But `agents/reviewer.md`'s own Scope section (unchanged by this plan — Scope line 14 says "Out: ... changes to the agents themselves") says only: "Establish the diff with `git diff`, `git diff --staged`, or `git diff <base>...HEAD`" — it never combines all three, and never mentions untracked files. So either (a) the `/review` skill must compute the union itself and hand the reviewer concrete diff content/file list rather than a bare instruction to "review the working tree" and trust the agent's own logic, or (b) `agents/reviewer.md` needs an edit that the plan's Scope explicitly forbids. The plan does not say which. Two implementers plausibly diverge: one has the skill pre-compute and paste the diff+untracked list into the dispatch prompt (never touching the agent file), the other assumes the agent already does this and ships a `/review` that silently misses untracked new files on Claude and Antigravity alike.

- **D3's dispatch-slug wording is ambiguous against the agents' own hard-coded naming templates.** D3 (line 22) says every dispatch gets "the artifact slug `review-<slug>`" where `<slug>` is `worktree`/`pr-<n>`/etc. But `agents/reviewer.md` names its own file `$(date +%F)-review-<slug>.md`, `agents/security.md` names its own `$(date +%F)-security-<slug>.md`, and `agents/verifier.md` names its own `$(date +%F)-verify-<slug>.md` — each agent already prefixes its artifact with its own lens name, using `<slug>` alone (e.g. `worktree`), not `review-<slug>`. If `/review` literally hands security or verifier the string `review-<slug>` as "the slug," their filenames become `...-security-review-worktree.md` / `...-verify-review-worktree.md`, which is probably not intended. The plan's own D4 uses `<slug>` (not `review-<slug>`) for the merged file name (`reviews/<date>-review-<slug>.md`), suggesting D3's phrase is a loose cross-reference to D4 rather than a literal parameter — but nothing in the plan disambiguates this, and a first-pass implementer has to guess.

- **`--tests` dispatch brief text is reused verbatim for `--project`, where it no longer fits.** D3 (line 22): the `--tests` brief is "run the project's commands and map every **changed** source file to its covering test." D3 also says "`--project` ... every lens runs over the whole tree instead of a diff." For `--project --tests` there is no "changed" file set — the brief needs to become "every source file," matching what the deleted `audit` skill's Step 1 already says for its verifier dispatch ("maps every source file in the target to a covering test"). Since the plan (line 46) says "Dispatch briefs are the D3 texts, quoted in the skill so both vendors send the same words," an implementer who quotes D3 verbatim ships a `--project --tests` brief that talks about "changed" files in a no-diff run.

## Readiness — questions a first-pass implementer would have to ask

- **BLOCKING** — Is the skill-count target 26 or 27 (see Gap 1)? Two implementers ship different numbers in `README.md`/`AGENTS.md` and one is factually wrong.
- **BLOCKING** — For the default working-tree target, does `/review` pre-compute and hand the reviewer/security agents an explicit file list/diff (never touching `agents/reviewer.md`), or is editing the agent's Scope section implicitly in-scope despite the plan's "Out" line (see Gap 2)? This changes both which files get touched and whether untracked files are ever reviewed.
- **BLOCKING** — What literal slug string does each subagent receive, and does it match or override that agent's own baked-in filename template (see Gap 3)? This determines the actual artifact paths the chat reply and any merged record must link to — get it wrong and the merged record's links are broken on the first real run.
- **BLOCKING** — Does `--fix`'s reference to the Definition of Done's "fix or rebut in writing; three rounds cap; a second round on the same mechanism → stop and ask" mean `/review --fix` itself loops (re-dispatching `reviewer`/`security` up to three times to check its own fixes), or does it mean "apply once, and if a *future, separate* `/review` run repeats the same finding, that's when the three-round rule kicks in"? D5 (line 24) states the rule but not which of these two very different control-flow shapes to build. One implementer ships a single fix-and-return; another ships an internal review/fix/re-review loop with a stop-and-ask branch. These are materially different amounts of code and different user experiences.
- **NON-BLOCKING** — Exact `argument-hint` frontmatter string for the new skill; any reasonable rendering of the usage block works.
- **NON-BLOCKING** — Whether `--high` also elevates `explorer`'s model on `--project --all --high`, given `explorer` has no analogous "strongest model" precedent in the plan; defaulting to "no effect beyond the reviewer" is a reasonable, low-stakes call.
- **NON-BLOCKING** — Exact wording of the "dispatch via the Agent tool on Claude Code / `invoke_subagent` on Antigravity" boilerplate; every existing multi-agent skill (`preflight`, the deleted `audit`) already establishes this pattern, so copying it is not a real fork in the design.
- **NON-BLOCKING** — Exact dedup algorithm for "the merged record dedupes by file:line" (Risks, line 64); a simple key-based collapse is the obvious reading and low-stakes to get slightly wrong.

## Not examined

- `internal/harness/plan.go` and `internal/harness/derive.go` (how the installer actually renders/derives Antigravity's agent.md and whether the new skill or the audit deletion has any installer-side effect beyond a file copy) — the plan's own claim that "adding a skill... is a file drop, never a code change" was taken on the strength of `AGENTS.md:39` rather than re-verified against the installer source.
- The actual ≤140-line budget for the new `SKILL.md` was not tested by drafting the file; given the volume of D1–D9 plus verbatim dispatch briefs plus the usage block, this is a real risk of the plan but not a design gap per se.
- `.agents/docs/testing/2026-09-03-verify-sandbox.md` and the sandbox e2e harness scripts referenced by the Verification section were not read in detail (the skill-matrix.md was, and its `audit` row needs the "folded" edit the plan already calls for).
- `README.md` and `AGENTS.md` were only grep'd for "skill" and "audit" mentions, not read end-to-end for every place a count or workflow-skill list might appear.

## Criteria (six-criteria lens, applied to the plan text as if it were the diff)

1. Dead code — n/a (design document; the plan itself correctly identifies `skills/audit/` for deletion once folded).
2. Flow tracing — fails at one hop: the `--tests` brief text is not adapted for the `--project` (no-diff) case (Gap 4).
3. Standards conformance — plan follows the harness's own skill-authoring conventions (docs-root resolution, `date +%F`, frontmatter) as documented elsewhere; nothing in the plan text itself violates them.
4. Directory layout — surfaces named match the existing `skills/`, `agents/`, `context/` layout; no new surprising placement.
5. Simplicity — plan reuses existing agents rather than inventing new machinery; the `--fix` loop question (Gap/Question 4) is the one place scope could balloon unpredictably depending on how it's built.
6. Decoupling — the plan is careful to keep `/review` a thin router over existing agents; the one seam that isn't clean is the slug/filename contract between the router and the agents' own naming templates (Gap 3), which two people implementing the router and reading the agent files independently would likely get wrong in different ways.

## Status: COMPLETE

## Verdict: FINDINGS (three lows, none blocking; the carried medium is CLOSED)

**The carried medium is closed.** The prior report's medium was "an unsigned zip installs with exit 0, and the party who supplies the zip controls that". This range closes it; the operator now has to make that decision explicitly.
- `VerifyZipSums` returns `ErrZipUnsigned` only when BOTH `os.Stat` calls return `fs.ErrNotExist` (`internal/harness/release.go:438-452`).
- The closure in `updateFromZip` turns only that sentinel into nil, and only with `--unverified` (`cmd/sh-agent/main.go:1095-1108`). Every other error is returned unchanged.
- `UnpackZip` hashes and runs the check before it parses anything or creates a directory (`internal/harness/zip.go:54-66`).
- **The flag cannot let a failed verification through.** I confirmed this three ways:
  - by reading the code;
  - with a built binary, where one file only, and a foreign signature, were both refused with `--unverified`;
  - with four must-fail mutations, each of which compiled and failed a named test (see Checked).

**What remains is three lows, all about how the new control is used, not about the verification.** The worst: the unsigned refusal tells whoever reads it how to bypass it. On this harness the reader is often an agent, which can turn an operator-only decision into an automatic retry. Confidence is low: agent behaviour was not measured.

## Findings

- **[low / confidence: low] The unsigned refusal hands the bypass to whoever reads the error, and in this harness that is often an agent.** `cmd/sh-agent/main.go:1099`.
  - **The message:** "…or pass --unverified to install it anyway, with trust resting on your own download".
  - **Why it matters in principle:** the flag exists so that a HUMAN decides whether unsigned content becomes the instructions every later session reads (ADR-040: "it discloses and does not control" was the reason for the change). Suppose an operator asks an agent to "install the harness from this zip". The agent runs `update --from-zip`, reads this refusal, and has every reason to retry with `--unverified`. In auto mode, or a headless `-p` run, nobody is prompted. The control then falls back to a line in the transcript, which is the state ADR-040 set out to leave.
  - **Not measured:** no behavioural run was made, hence low confidence.
  - **What is fine:** naming the flag is right for a human reader, and ADR-040's point stands (the flag cannot pass a failed check). No skill, agent or context file tells an agent to pass `--unverified` (`git grep -- '--unverified'` over `skills context agents commands rules`: 0 hits).
  - **Remediation, cheapest first:**
    - address the decision to the operator in the message itself, e.g. "…the operator, not an agent, decides to pass --unverified";
    - or add one hard-rule clause to `context/AGENTS.md` saying `--unverified` is the operator's own decision, like "ship/deploy from the user's own turn". This must stay within the 22,000-byte budget, `TestRenderedContextFitsAntigravityBlock`.
    - Either way, measure it with the repo's behavioural-run procedure: a fixture where an agent is told to install an unsigned zip. Report n of N runs that retry with the flag, before and after.

- **[low / confidence: high] Carried from the prior report, which asked for it to be revisited once the flag landed: a downgrade to an OLDER signed release is now the remaining route that needs no opt-in.** `cmd/sh-agent/main.go:1094-1135`.
  - **What happens:** `verifiedTag` is used only for the output line and the manifest origin. Nothing compares it with the running binary's version (`buildVersion()`) or with the verified tag already recorded in the manifest.
  - **The route:** whoever supplies the folder can hand over an older release's zip with its own genuine `SHA256SUMS` and `.sig`. It installs with exit 0 and prints `VERIFIED against the signed SHA256SUMS of release v1.x.y`.
  - **Why it is low:**
    - the content was signed by the operator;
    - the release is named in the output and in `status` (`verified vX.Y.Z`);
    - the repository is private, so older assets need repository access;
    - nothing in the zip replaces the binary.

    What it can do is bring back older agent instructions, for example a rule a later release fixed.
  - **Decision on record:** ADR-039 Consequences accepted this ("the operator chooses the zip"), at a time when an unsigned zip was the stronger route. This range made that premise stale.
  - **Remediation (existing helpers, no dependency):**
    - when the manifest already records `;verified vA` and the zip verifies as an older `vB`, i.e. `compareRelease(vB, vA) < 0` (`internal/harness/release.go:378`), refuse unless the operator passes an explicit flag, or at least print a `DOWNGRADE` line;
    - on a release binary, the same check against `buildVersion()`.

    This is an R9/ADR matter for the operator, not a gate blocker.

- **[low / confidence: high] `--unverified false` reads as `--unverified`.** `cmd/sh-agent/main.go:95` and `:136`; `update` never checks `fs.NArg()`.
  - **Why:** a stdlib `flag` bool takes a value only in the `=` form. `reorder` moves the flag in front, and the stray `false` becomes a positional argument that `update` ignores without saying so.
  - **Reproduced with a built binary:**
    - `update --from-zip <unsigned>.zip --unverified false --dry-run` → exit 0, `UNVERIFIED`;
    - `--unverified=false` → refused, exit 1.
  - **Why it matters:** a script that templates the value (`--unverified "$ALLOW"`) always allows. This is the one bool flag here where the stray value errs toward LESS checking: `--dry-run false` errs toward doing nothing.
  - **Remediation:** refuse extra positional arguments on `update`, at least on the `--from-zip` branch (`if fs.NArg() != 0 { return error }`, stdlib `flag`). Add a test that runs `--unverified false` and expects a refusal.

## Outcome

1. **Low, an agent could retry with `--unverified`: fixed in the wording.** The refusal now reads "when the operator decides to trust this download, pass --unverified (an agent never adds it on its own)", and `TestUpdateFromZipUnsignedRefusedWithoutFlag` asserts it. Agent behaviour is still not measured; the text is the control.
2. **Low, a downgrade to an older signed release installs VERIFIED: left for the operator.** ADR-039 accepted downgrades because the operator chooses the zip, and a zip place has no other way to roll back. Reversing that is a design decision, so the v2.0.0 handoff puts it to the operator, with a recommendation.
3. **Low, `--unverified false` read as on: fixed.** `update --from-zip` refuses any stray argument (`fs.NArg() != 0`). `TestFromZipStrayArgumentRefused` covers it; dropping the check compiled and failed that test.

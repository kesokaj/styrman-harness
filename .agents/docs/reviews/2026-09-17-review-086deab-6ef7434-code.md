Every one of the seven fixes is whole and none introduces a defect that loses
data, installs an unverified byte, misreports a failure as success, or hangs.
The narrowed push classifier still catches the real non-fast-forward (measured

## Fix-by-fix verdict (the dispatch's seven questions, in its numbering)

1. **`commitAndPush` classifier (`report.go:856-870`) — whole, and it does not
   under-catch.** Measured here rather than reasoned: a `--depth 1
   --filter=blob:none` clone, a competing push to a `file://` bare origin, then
   `git push --quiet -u <url> HEAD:main` under `LC_ALL=C` (git 2.47.3) prints to
   **stderr**

   ```
    ! [rejected]        HEAD -> main (fetch first)
   error: failed to push some refs to '…'
   ```

   `--quiet` does not suppress the ref-status table on failure, and
   `gitRun` (`repo.go:217-227`) folds `ExitError.Stderr` into the error text, so
   the classifier sees both `! [rejected]` and `fetch first`. The three needles
   cover every non-fast-forward shape reachable from this call site:
   `(non-fast-forward)` (when a remote-tracking ref makes git say so),
   `(fetch first)` (the shallow/unaware case measured above), and the
   `! [rejected]` line that accompanies both. `(stale info)` needs
   `--force-with-lease` and `(would clobber existing tag)` needs a tag refspec;
   neither is reachable — this call pushes `HEAD:main` plainly.
   `! [remote rejected]` no longer matches: `"! [rejected]"` requires exactly
   one space after `!`, and git writes `! [remote rejected]` for a hook,
   a protected branch or a read-only credential, so those now take the
   "push failed, the commit stays local" branch. One shape deliberately not
   retried and correctly so: `! [remote rejected] … (shallow update not
   allowed)`, which a retry cannot fix either.
   Regression cover exists and is a real NFF, not a hook:
   `TestSendReportRetriesRejectedPush:733-793` wedges a competing push through
   `testHooks.beforePush`, so it fails if the narrowed needles ever stop
   matching the race — the narrowing is pinned in both directions.

2. **`runDir` (`report.go:786-806`) — whole; the `create` branch never had the
   flaw, and the new error path is reachable.** `!create`: `ErrNotExist` →
   take the name, any other error → wrapped error, else continue. `create`:
   `os.MkdirAll` errors return (`:781-784`), and inside the loop only
   `os.ErrExist` continues — every other `os.Mkdir` error returns (`:803-806`).
   So `create` cannot spin, and no fix was owed there. Reachability in the
   dry-run case: `create=false` is used only by the dry-run branch of
   `SendReport`, and nothing between `verifyFeedback` (two local `git`
   read-only calls) and `runDir` touches `reports/<host>`, so an
   `EACCES`-mode `reports/` reaches the new guard. Verified the new test is not
   short-circuited by the older link check above it: that check is
   `if info, err := os.Lstat(…); err == nil && !info.IsDir()`, which on
   `EACCES` has `err != nil` and falls through silently — so
   `TestRunDirRefusesWhatItCannotRead` does exercise the loop's new branch and
   not a pre-existing return. (The older check swallowing its own `Lstat`
   error is pre-existing, outside this range, and harmless here: the loop
   below now errors on the same condition.)

3. **`cloneThrowaway` (`report.go:452-486`) — whole; the empty-repository case
   is still handled.** The `rev-parse --verify --quiet HEAD` branch remains and
   still returns the directory with no checkout (`:478-481`); the handling
   itself was always in `commitAndPush`, which re-derives the same fact and
   `symbolic-ref HEAD refs/heads/main`s before the first commit
   (`report.go:840-846`). The signature is now `(string, error)`, the doc
   comment's sentence about `empty` is gone, and the one caller
   (`SendReport:704`) was updated. Grepped: no other reference to a three-value
   `cloneThrowaway` anywhere, tests included. Nothing calls into a stub.

4. **`sshKeygen` (`release.go:315-330`) — whole; the fallback still works and
   no working verifier is newly skipped.** The added test is
   `info.Mode().Perm()&0o111 != 0`, i.e. ANY execute bit, so a real
   `/usr/bin/ssh-keygen` (0755, or even a hardened 0700 root-only copy) still
   wins the system-path preference; `exec.LookPath` remains the fallback and
   the "ssh-keygen not found" refusal is untouched. `os.Stat` follows symlinks,
   so a `/usr/bin/ssh-keygen -> /usr/lib/.../ssh-keygen` install is judged on
   the target's mode, as it must be. The one behaviour change is the intended
   one: a name-only, non-executable `/usr/bin/ssh-keygen` no longer pre-empts a
   working PATH copy. Trust note, not a finding: falling through to PATH
   requires an attacker who can already `chmod` inside `/usr/bin`, i.e. root,
   who could simply replace the binary — no practical widening.

5. **`verifyRelease` (`release.go:246-256`) — the distinction is correct in
   direction, incomplete in coverage (Finding 1), and neither path installs
   anything.** `ssh-keygen -Y verify` exits 255 on a signature that does not
   verify → `*exec.ExitError` → "SHA256SUMS signature does not verify":
   correct. A verifier that cannot be executed — absent (`ENOENT`),
   non-executable (`EACCES`), truncated (`ENOEXEC`) — fails in
   `exec.Cmd.Start`, which returns `*fs.PathError`, not an `ExitError`, so
   `errors.As` is false and the new message fires: correct. A missing
   `SHA256SUMS.sig` cannot reach here at all — `os.Stat` refuses it earlier
   with its own message (`:227-229`) — and `allowed_signers` is written by this
   function immediately above, so neither becomes a false "does not verify".
   The gap is the run-but-unusable verifier (old OpenSSH without `-Y`), which
   is an `ExitError` and keeps the old message; the captured-but-unread stderr
   is what would fix it. Install ordering re-checked at
   `release.go:150-172`: `verifyRelease` error returns before `MkdirAll`,
   `writeAtomic` and the child `install`, so both paths fail closed.

6. **The two new tests — both assert the mechanism and both fail on a revert.**
   `TestSendReportDoesNotRetryARefusal:1079-1117`: the origin is
   `seedFeedback`'s `git init --bare` repo, so `hooks/pre-receive` is the real
   hook path and the rejection is a genuine `! [remote rejected] … (pre-receive
   hook declined)`, not the "refusing to update checked out branch" a non-bare
   origin would give. It pins three independent facts — the error says `push
   failed` (the non-retry branch), the output/error never say `re-cloning` or
   `twice` (the retry branch was not taken), and `clones == 1` counted through
   `testHooks.beforePush`, which is what forbids passing by a failure BEFORE
   the push (a clone or commit failure leaves the counter at 0). Revert the
   needles to `contains "rejected"` and the hook's text matches, the run
   re-clones, `clones == 2` and the error says "push rejected twice": three
   assertions fail. It restores `testHooks.beforePush = nil` via `defer`, and
   `assertKeepsNothing` closes the leftover-clone question.
   `TestRunDirRefusesWhatItCannotRead:1122-1146`: calls `runDir` in a goroutine
   behind a 5-second `select` and `t.Fatal`s on timeout, so the reverted guard
   fails by timeout rather than hanging the suite; it skips under root (where
   mode 000 is readable) and skips when `chmod` is refused, so it cannot pass
   green while asserting nothing — a skip is visible in `-v` and reports no
   pass. Both use `t.TempDir`/`t.Cleanup` and restore the mode. Neither can
   pass for the wrong reason. One thing they do not assert, worth knowing but
   not a finding: the refusal test never checks that the error carries the
   hook's own `policy: no` text, so it proves "a push that was refused is not
   retried" rather than "a pre-receive refusal specifically"; the `clones == 1`
   counter makes the weaker claim sufficient.

7. **`remote.md` § Releases — the order holds, with Finding 2 as the
   qualification.** The sequence is now: signing-key fingerprint → clean-tree
   test → embed guard (`git status --ignored` over the five directories +
   `go test -count=1 -run TestEmbedHoldsOnlyTrackedFiles`) → `HEAD^` is the
   gated head → records-only diff → `git tag -s` (no target) → type/armor/
   `verify-tag` → `rm -f .agents/scratch/allowed_signers` → `git push origin
   main` → `git push origin vX.Y.Z`. Every step still has what it needs:
   the embed guard reads only the working tree, so moving it earlier removes no
   precondition; `-count=1` was added, which matters because a cached PASS
   would otherwise be indistinguishable from a run; the signer file is written
   after the clean-tree test and lives under gitignored
   `.agents/scratch/`, so writing and removing it dirties nothing the two
   pushes carry, and its removal sits before the pushes, not between them. In
   the binaries block `rm -f allowed_signers` sits after the pre-upload
   `-Y verify` and before `gh release create`, whose asset list is five
   explicit names, so the signer file can neither be uploaded nor left behind.
   `skills/preflight/SKILL.md` Step 6.5 now states the general rule ("any check
   that guide names which gates what goes INTO an artifact runs before the tag
   in item 3"), which matches the guide — the restatement moved with the rule.
   The residual gap is that nothing re-checks the tree between the tag and the
   build (Finding 2).

## Outcome

Read against the diff by the main agent, 2026-09-17. All three findings fixed in the commit that follows 6ef7434.

1. **[low] `verifyErr` was a dead store** — captured and never read, and it was exactly what closed the remaining misdiagnosis, since an OpenSSH too old for `-Y verify` exits 255 like a bad signature. Correct finding, and mine to own: the buffer was added in the same fix that was supposed to separate a broken tool from a bad release. My first attempt to use it classified by wording (`Could not verify signature`) and BROKE `TestUpdateFromReleaseRefusals/SHA256SUMS_altered_after_signing`, because ssh-keygen's first stderr line for a genuine bad signature is `Signature verification failed: incorrect signature`. The classification is gone; the verdict now always stands and the tool's own first line rides along: `SHA256SUMS signature does not verify (ssh-keygen: …)`. Covered permanently by `TestVerifierMessageCarriesWhatTheToolSaid`, which plants a stub exiting 255 with `unknown option -- Y` and asserts both that the message carries it and that the verdict is kept.
2. **[low] the embed guard was DELETED from the binaries block when it moved above the tag.** Correct, and the sharper half of the finding: `go:embed` reads the working tree at BUILD time, which is after the tag and both pushes, so a `.DS_Store` or swap file appearing in between would be embedded unguarded. I had over-corrected the security review's finding by moving the guard rather than duplicating it. Both read-only commands now run in both places, with the reason in the comment.
3. **[low] a stale restatement in the plan** — it still said the guard was "step 0 of `remote.md` § Releases". Fixed to describe both positions. Fifth instance of this class today (BUG-003, 007, 027, and the Phase 5 docs review's finding); the rule keeps earning its place.

The review's measured evidence was worth more than its verdict: it ran a real competing push over `file://` under `LC_ALL=C` and confirmed `! [rejected] … (fetch first)` for the race and `! [remote rejected]` for a hook refusal, which is what makes the narrowed classifier right in both directions. It also confirmed `runDir`'s `create` branch never had the flaw and that the new guard is genuinely reached.

Suite after these fixes: 102 top-level tests and 85 subtests, none failing or skipped; `gofmt`, `go vet`, `go test -race -count=1 ./...` and `govulncheck` clean.

# Review — cold-read-docs-steps-3   (2026-09-14)

Range reviewed: `.agents/docs/plans/2026-09-14-documentation-steps.md` (cold-reader check, no diff — the plan file and the surfaces it names: `context/AGENTS.md`, `agents/{changelog,documentation,verifier,reviewer,security,explorer,bugs}.md`, `skills/{feature,bug,handoff,retro,review,preflight,init-project}/SKILL.md`, `.agents/docs/testing/skill-matrix.md`, `.agents/docs/deploy/{local,remote}.md`, `skills/init-project/assets/agents-tree/docs/deploy/*.md`, `~/.config/sh-agent/proposals/*.md`, `README.md`, `REQUIREMENTS.md`).

## Verdict: design needs revision / implementation not ready

The plan is unusually precise for nine of its ten items, but one item cites the wrong anchor in an existing file, one item's factual premise about the current state of a directory is wrong in a way that would ship a functional regression if implemented literally, and one item leaves a real interface decision (single-file vs multi-procedure guide naming) undecided. None of these are stylistic; each would make two careful implementers build different things or ship something that contradicts the plan's own stated goal.

## Gaps (must be decided before implementation)

- **G1 — item 5's backfill list omits two existing queue files, and the omission is not cosmetic.** Plan line `.agents/docs/plans/2026-09-14-documentation-steps.md:29` names "the four existing queue files (`2026-09-04`, `09-08`, `09-10`, `09-11`)". `ls ~/.config/sh-agent/proposals/` shows **six** files: `2026-09-03-retro.md`, `2026-09-03-retro-final.md`, `2026-09-04-retro.md`, `2026-09-08-retro.md`, `2026-09-10-retro.md`, `2026-09-11-retro.md`. The two `2026-09-03` files already record their outcomes ("applied 2026-09-03" in a table column / prose), but not as a `Status:` line in the new convention. Item 5 also changes `/retro --harness` Step 1 to treat a proposal with **no** `Status:` line as `queued` (files older than 2026-09-14 predate the line, "absent means queued"). If the backfill runs over only the named four files, the two `2026-09-03` files are left with no `Status:` line and will be read by the new rule as still-`queued` — i.e. `/retro --harness` will report two already-applied 2026-09-03 proposals as open work. This is not a hypothetical: it is the literal, mechanical consequence of the plan's own two new rules combined. The implementer must decide: backfill all six files (and correct the plan's count), or add an explicit carve-out for pre-`2026-09-04` files that already record their own outcome inline. **BLOCKING.**

- **G2 — item 4 cites the wrong step in `skills/review/SKILL.md`.** Plan line `:28` says the "## Outcome" section rule goes into "`skills/review/SKILL.md` Step 6 and `skills/preflight/SKILL.md` Step 5". `skills/review/SKILL.md` Step 6 is "Report" — chat-only, "In chat, at most ten lines: … Nothing else." (`skills/review/SKILL.md:62-64`). A persistent, on-disk file-format rule ("the record gains a final `## Outcome` section … written in the same commit as the fix") does not belong in a step whose entire content is a ten-line chat-report constraint; it belongs with Step 4 ("The record", `:54-56`) or Step 5 ("`--fix`", `:58-60`), where the record's shape and the fix loop are actually defined. The `preflight` citation (Step 5, "Write the merged gate report", `skills/preflight/SKILL.md:67-77`) is correctly anchored; the `review` one is not. An implementer following the plan literally edits the wrong section of `review/SKILL.md`. **BLOCKING** (the fix is cheap — retarget the anchor — but which step is correct changes what the section looks like: Step 4's record template vs Step 5's fix-loop prose).

- **G3 — item 2's `testing/<app>/guide.md` interface assumes exactly one verification procedure per app, which this repo's own `<docs-root>/testing/` already contradicts.** Plan line `:26`: "write it as `<docs-root>/testing/<app>/guide.md`" — a single, literally-named file. This repo's actual `.agents/docs/testing/` holds three independent, differently-named artifacts for three different procedures (`2026-09-03-verify-sandbox.md`, presumably `2026-09-03-verify-real-home.md`, and `skill-matrix.md`), flat at the root, not nested under a per-app directory at all (there is no `<app>` — this is a single-app repo). The plan does not say whether "guide.md" (a) replaces this pattern with one growing file per app that accumulates every distinct procedure as sections, (b) is only for repos that currently have none, leaving existing scenario-specific docs alone, or (c) should really be one file per procedure (contradicting the literal singular filename given). Two implementers converge on genuinely different `testing/` layouts here. **BLOCKING** for any project (including this one) that already has more than one verification procedure.

## Other observations (non-blocking gaps, worth a line in the plan but not stoppers)

- Item 3's new context sentence ("the review row includes `/review --docs` … when the change touches an interface, a command, or a deploy step") does not say whether this is gated by the existing 50+ lines/5+ files review threshold or runs unconditionally like the `security` sentence it sits next to ("`security` whenever … regardless of diff size" is the closest precedent and a reasonable default, but it is not stated for `--docs`).
- Item 8 says only the verifier's `/tmp` sentence and the explorer's trail paragraph "fold into" the new Records section for those two agents; it does not say whether the other five agents' existing "Docs root" / "Your lane" code blocks should be trimmed to avoid restating the same path in two places, or left as-is alongside the new section. Low risk either way — an implementer keeping both is not wrong, just slightly redundant.
- README.md's actual "Layout skills line" (`README.md:87`) currently reads "`feature` and `bug` are the work protocols and load themselves" — item 1 says this gains "one line naming `/review`" but doesn't give the wording; a reasonable implementer appends a clause naming `/review` as the review command, which satisfies the letter of the item.

1. **(BLOCKING)** For item 5's backfill: do the two `2026-09-03` proposal files get a `Status:` line too, and if so what value, given they already record "applied" in a different shape? (see G1)
2. **(BLOCKING)** For item 4: does the "## Outcome" section belong in `review/SKILL.md` Step 4 (the record) or Step 5 (`--fix`), since Step 6 as cited is chat-only? (see G2)

4. **(NON-BLOCKING)** Does `/review --docs` in the Definition of Done (item 3) obey the existing size threshold, or run unconditionally whenever an interface/command/deploy step changed (like `security`)? A reasonable implementer follows the `security` precedent (runs regardless of size) since the plan phrases it the same way ("whenever…").
5. **(NON-BLOCKING)** For item 8, should the five agents outside verifier/explorer trim their existing docs-root/lane prose to avoid duplication with the new Records section? A reasonable implementer leaves both — the Records section is a short, scannable summary, not a replacement.
6. **(NON-BLOCKING)** Exact wording for the one line added to README's Layout skills line (item 1) is not given; any sentence naming `/review` as a workflow skill satisfies it.

## Findings

- **[low / confidence: medium]** `README.md:119-125` — the browser route runs in `~/Downloads`, a directory the user owns and shares with unrelated downloads. Two concrete effects: `printf … > allowed_signers` (line 120) truncates any pre-existing `~/Downloads/allowed_signers` without a guard, and the closing `rm allowed_signers SHA256SUMS SHA256SUMS.sig` (line 125) deletes three fixed names there — a `SHA256SUMS`/`SHA256SUMS.sig` pair the user downloaded earlier for an unrelated project is destroyed by a chain that never mentions it. The gh route above deliberately avoids exactly this (`D=$(mktemp -d)`, and its own comment says "everything is verified in a scratch directory"), so the two routes disagree about a rule one of them states. Concrete fix, keeping the one-chain property: `D=$(mktemp -d) && mv ~/Downloads/sh-agent-darwin-arm64 ~/Downloads/SHA256SUMS ~/Downloads/SHA256SUMS.sig "$D" && cd "$D" && <the same verify/chmod/run/mv steps> && cd ~ && rm -r "$D"`. Not a security defect: nothing unverified can reach `~/.local/bin` either way.

No other correctness, security, or project-rule defect found.

## Answers to the dispatch's specific questions

**1. Does the `!dryRun` gate change any non-dry-run path? No.** `pathHint` has exactly one call site in the repository: `cmd/sh-agent/main.go:277`, inside `installFiles` (`grep -rn pathHint cmd/ internal/` returns that call, the function at `main.go:650`, its doc-comment, and one comment in `main_test.go` — no other caller, no test calling it directly). `installFiles` itself has two callers, `main.go:138` (`install`) and `main.go:175` (`update`), both passing `*dryRun`. The gate's body is entered whenever `dryRun == false`, so both non-dry-run paths reach `pathHint` exactly as before, with the same argument and the same error propagation (`return err`). The only behaviour that changed is `install --dry-run` / `update --dry-run`, which now print nothing about PATH. Nothing downstream consumes `pathHint`'s output — it is written to `out` and not parsed — so no caller needs updating.

**2. Does the dry-run assertion pin the behaviour, or pass vacuously? It pins it — verified by mutation, not only by reasoning.**
- Reasoning: at that point in the test `PATH` is still `elsewhere` (set at `main_test.go:1444`), which holds an executable `sh-agent` (`other`), and the `fresh` home's bin dir is not on it. So `PathShadows` returns `shadows=[other], onPath=false`, and `pathHint` takes the `case len(shadows) > 0` branch (`main.go:657`), whose text contains "so `sh-agent` runs" — one of the three asserted phrases. The assertion therefore cannot pass with the gate removed.
- Measured: `git archive HEAD | tar -x -C .agents/scratch/review-gate` gave a pristine copy of HEAD (the real tree was never touched; no git command that writes the working tree was run). Baseline `go test ./cmd/sh-agent/ -run TestOffPathInstallNamesWhatAnswersAndDoesNotWarnTwice` → `ok`. I then asserted the gate text `if !dryRun {` occurs **exactly once** in `cmd/sh-agent/main.go` (count = 1, abort otherwise), saved a copy, removed the gate so `pathHint` is called unconditionally, and re-ran: **FAIL**, with the dry-run output containing `note: …/003/.local/bin is not on PATH, so \`sh-agent\` runs …/002/sh-agent instead`. Restored from the saved copy and confirmed the scratch copy is byte-identical to the real tree's `cmd/sh-agent/main.go` (`diff -q`). The test is a real must-fail check for this gate.
- The three phrases are also correctly chosen: they are the bin-dir sentences only (`main.go:653,657,660`), so the unrelated "`go` is not on PATH" warning that a one-directory PATH legitimately produces does not make the assertion fire, and the comment at `main_test.go:1481-1482` says so.

**3. README browser chain — does every failing check stop the `mv`, and does the `rm` run only after a successful `mv`? Yes to both.**
- The whole block is one `&&` chain from `cd ~/Downloads` (line 119) to the final `rm` (line 125), so any non-zero status aborts everything after it. `cd` failing (no `~/Downloads`) stops before anything is written; the signature check (`ssh-keygen -Y verify`, line 121) failing stops before the checksum check; the checksum check failing stops before `chmod`/`mv`.
- The pipeline question: `&&` sees the **last** command's status, i.e. `shasum -a 256 -c - --ignore-missing`, not `grep`'s (no `pipefail` in a copy-pasted interactive shell). That is the safe half of the asymmetry, and I probed the degenerate cases on this box rather than assuming: a `SHA256SUMS` of comment lines only makes `grep` exit 1 and feeds empty input to the checker, which exits **1** ("no properly formatted checksum lines found") on both `sha256sum` (coreutils) and `shasum` 6.04; a `SHA256SUMS` whose every listed file is absent exits **1** ("no file was verified") under `--ignore-missing` on both. So a truncated, emptied or renamed-away input cannot produce a passing checksum step, and `--ignore-missing` cannot silently verify nothing. The file the checksum step verifies is the same name that is then `chmod`ed, executed and `mv`ed (`sh-agent-darwin-arm64`), so there is no verify-one/move-another gap.
- The trailing `rm allowed_signers SHA256SUMS SHA256SUMS.sig` is joined by `&&` to `mv sh-agent-darwin-arm64 ~/.local/bin/sh-agent` on the same line, so it runs only after the `mv` succeeds. A failed `mv` (e.g. `~/.local/bin` does not exist) leaves all four files in place for a retry — the fail-safe ordering. (The separate concern about those three names belonging to the user's `~/Downloads` is the finding above, not a chain-ordering defect.)

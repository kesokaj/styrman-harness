Worst first: the new settings writer (`AttributionSet`) checks only the last path component for a symlink, so when `~/.claude` itself is a linked directory (a dotfiles layout) it creates or rewrites `settings.json` in the link's target, outside the home. ## Findings
- **[medium / confidence: high]** `internal/harness/settings.go:29-127` (`AttributionSet`) — `os.Lstat(path)` at :34 checks only the final component. When `~/.claude` is a symlink to another directory, every write goes through it: absent file → `MkdirAll` (:45) and the `O_EXCL` create (:52) land in the target directory; present file → `WriteAtomic` (:122; `CreateTemp` + `Rename` in `filepath.Dir(dest)`) rewrites the target's `settings.json`. The comment at :32 cites "a dotfiles checkout" as the reason for the Lstat, but dotfiles setups usually link the whole directory. `Install` refuses every file under such a `~/.claude` through `underLink(home, rel)` (`apply.go:407`). The BUG-129 prevention rule reads "Lstats the path AND its components … The test links a directory, not only a file". `settings_test.go:229-249` links only the file. In principle an install writes into a repository outside the home that the operator may commit and push from (the inserted bytes are a constant fragment, nothing secret). Remediation: before any branch that writes or reports a would-write, `if underLink(home, filepath.Join(ClaudeRoot, "settings.json"))`, print one line ("is under a symlinked directory; add the key by hand") and return. Add a test that links the `.claude` directory and asserts the target is unchanged, mutation-checked (remove the guard → the test fails).
- **[low / confidence: high]** `cmd/sh-agent/main.go:233` with `hasFlag` (:261) and `reorder` (:928, `--` case :940) — a new disagreement between the gate and the parser. `hasFlag` stops at `--`. `reorder` drops the `--` and places what follows after the flags, so `flag.Parse` parses it (measured on a scratch build: `sh-agent version -- --bogus` exits 2, "flag provided but not defined: -bogus"). So `sh-agent update -- --from-zip FILE` sets `c.fromZip` while `hasFlag` reports no `--from-zip`: the zip branch and all its refusals are skipped and a normal `update` runs with the zip silently ignored. On a release binary that downloads the newest release and replaces the binary (signature-verified), the outcome the comment at :234-237 says the refusals exist to stop. On a checkout it fetches, pulls and reinstalls. HEAD decided with `fs.Visit` on the parsed set (`zipSet`), so gate and parser agreed. Only the operator's own argv reaches it. Remediation, minimal: for `update`, decide from the parsed set (`c.fs.Visit`, as HEAD did). Principled: `reorder` keeps `--` in its output and verbs without positional arguments refuse them (next finding), so the `--` form becomes a usage error. Test: `update -- --from-zip <missing>.zip` never reaches `ResolveSource`.
- **[low / confidence: high; already present at HEAD]** `cmd/sh-agent/main.go:943` (`reorder`) and every verb that never reads `c.fs.Args()` — a lone `-` counts as a flag, and `flag.Parse` stops at it (a one-character argument is a non-flag), so every flag after it is left unparsed and ignored. Only `adopt`, `memory` and `search` look at positional arguments. Measured on a scratch build: `sh-agent version - --bogus` exits 0, and `sh-agent list - --check` exits 0 while `sh-agent list --check` exits 2 (the verb table's IN5 usage error is bypassed). Consequences, from reading the code: `uninstall - --dry-run` removes every installed file; `update - --check` pulls or downloads and reinstalls; `install - --home .agents/scratch/x` installs into the real `$HOME`, which this repo's AGENTS.md forbids during development. HEAD had the same `reorder` loop and one FlagSet. Remediation: in `reorder`, a token is a flag only when it is at least two characters and starts with `-`. Give each `verb` entry its arity and refuse `c.fs.NArg() > 0` with exit 2 in `run` for verbs that take no positional argument. Add a test per read-only mode (`uninstall - --dry-run`, `update - --check`) asserting nothing changes.
- **[low / confidence: medium]** `internal/harness/release.go:452-461` (`VerifyZipSums`) — the signers scratch moved from the system temp directory to `os.MkdirTemp(dir, ".sh-agent-verify-*")` beside the zip. Mode 0700 protects the directory's contents but not its name. If the zip's folder is writable by another account and has no sticky bit (e.g. a group-shared 2775 download folder), that account can rename the new directory away and put its own at the same path. The window is between `MkdirTemp` and the `allowed_signers` write (:262) or ssh-keygen's `-f` read (:265); renaming within one parent needs only write permission on the parent. The other account's own allowed_signers line can bind the compiled-in identity to its key, so a SHA256SUMS signed by that key verifies, and the install is printed and recorded as "VERIFIED against the signed SHA256SUMS of release …". The zip place already accepts unsigned zips as UNVERIFIED (ADR-041), so what an attacker gains is a false VERIFIED label, behind a race and an unusual folder mode. HEAD's sticky `/tmp` did not allow the swap. Side effects of the same change: a signed zip in a read-only folder (offline media, the zip place's own use case) is now refused outright (fail-closed, but an availability loss); an interrupted run leaves `.sh-agent-verify-*`, and for a dry run the unpacked `zip-*` tree, in the operator's download folder, where no sweep reaches. The comment at :452-454 ("scratch is the project's or the home's") does not describe the zip's folder, which is neither. Remediation: create the signers scratch, and the dry-run unpack, under the home's `~/.config/sh-agent`. `updateFromZip` already creates and tracks that directory as the unpack parent; pass it to `VerifyZipSums` (the `check` closure has it in scope), and for the dry run create it tracked and remove it afterwards. A considered stdlib alternative, `-f /dev/fd/3` through `exec.Cmd.ExtraFiles`, needs no file at all, but its behaviour with ssh-keygen on both platforms is unverified here.
- **[low / confidence: high; already present at HEAD, now the "one capped read" with a new caller]** `internal/harness/release.go:359-369` (`ReadCapped`) — the cap is a Stat-time check followed by `io.ReadAll(io.LimitReader(f, max))`. When a file is longer than its Stat said, that returns the first `max` bytes with a nil error: a FIFO or character device (Stat size 0), a file still growing, or a failed `f.Stat()` (the check is skipped on error). The read is cut short instead of refused. The checksum paths still fail closed: ssh-keygen verifies the same in-memory bytes Go then parses (`verify.Stdin`, :270), and the zip's sum is computed over the bytes it unpacks, so no shorter checksum input can pass. The gap is in the function's stated contract, which `ReadSettings` (new) and future callers rely on; a FIFO named SHA256SUMS also blocks the open. `TestReadCappedRefusesOversize` covers regular files only. Remediation: read `max+1` and refuse `len(data) > max` (the `copyCapped` shape in zip.go), refuse a non-regular file using the opened handle's Stat, and treat a Stat error as an error.
- **[low / confidence: medium]** `internal/harness/repo.go:143-152` (`ParseOrigin`) — every value that is neither `embedded:` nor `zip:sha256:` becomes `OriginPath`. That includes `""` (pinned so by `repo_origin_test.go:23`), a relative path, a `zip:` value of another shape, and a value with a newline or terminal escape. HEAD's `ResolveSource` and `runDiff` treated every `zip:` value as a zip; now such a value is a `ResolveSource` candidate checked with `IsRepo` relative to the working directory (BUG-067's shape). `status` (main.go:669, :673) and `knownCheckout` (:880) print `Release`/`Trust` raw. Only a hand-edited or foreign `state.json` carries such values, since sh-agent writes absolute paths (`absSource`) and `zip:sha256:` only (`ZipOrigin`), and the cwd walk is tried first, so exposure is small. Remediation: `OriginPath` only for an absolute path with no control character. Anything else becomes a fourth kind that no reader follows and that `status` reports as unreadable. Print `Release`/`Trust` with `%q` or strip control characters.
- **[low / confidence: high]** `internal/harness/settings.go:179-205` (`attributionOff`) — decodes into a struct, and encoding/json matches struct keys case-insensitively (exact match preferred, last key wins). Given `"attribution": {"commit": "x"}` followed by `"Attribution": {"commit": ""}`, the check returns "off" and prints no hint, while Claude Code (case-sensitive JSON) still adds the trailer. This is an advisory check on an operator-owned file. Remediation: decode through `map[string]json.RawMessage` at both levels (exact keys), as `AttributionSet` already does at the top level.

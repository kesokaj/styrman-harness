## Verdict: APPROVE

Nothing in this commit is broken. The two `note:` lines are pure output on paths that already returned without touching anything; the guard order is correct, the new note is pinned by a test that fails without it, and both README restatements match the code. The one thing worth recording is a sentence in `.agents/docs/specs/sh-agent/delivery.md` that the earlier symlink guard (42840fb) made inaccurate and that this commit's README rewording did not carry over — low severity, docs-only, not a release blocker.

## Answers to the gate's questions

1. **Can a regular FILE at that path fall into a note that calls it a directory?** No. `state.go:105` (`if !info.IsDir() || info.Mode().Perm()&0o077 == 0 { return }`) runs *before* the not-owned note at `state.go:108-111`, so a plain file returns silently; the `%04o` note is reached only for a real directory. One residual edge: a **symlink** is noted at `state.go:100-103` before the `IsDir` test, so a symlink pointing at a regular file (or a dangling one) prints "its target's mode is yours to set". The text is imprecise there, but the ordering is deliberate and correct — `Lstat` cannot see through the link and `Stat`-ing it would be the reach-through the guard exists to avoid. The subsequent install failure on such a path (`ConfigDir` → `os.MkdirAll` returns `ENOTDIR`/`EEXIST`) is pre-existing behaviour from before this range, unchanged by the diff, and not a finding against it.
2. **Does the symlink note print on a dry run?** Yes, and it should: `state.go:100-103` returns before the `dryRun` check at `state.go:114`, so a dry run prints the note and changes nothing. Consistent with the `mode` line, which a dry run also names (`audit_test.go:246-266`).
3. **Can either note print more than once per install?** No — one call site, one per process. `TightenConfigDir` is called only from `apply.go:30` inside `Install`; `Install` is called once per command from `cmd/sh-agent/main.go:286` (`installFiles`), which itself has two mutually exclusive call sites (`main.go:145` release-binary path returns; `main.go:182` checkout/plain-copy path). On the rebuild path the parent returns `harness.Reinstall(...)` at `main.go:173` without reaching `installFiles`, so the child prints the note exactly once and the parent prints none.
4. **Is `%04o` of an unowned dir an information leak?** No. The value is the permission bits of a directory under the home the caller passed, which any process that can `Lstat` the path can already read; it carries no content, no owner uid, no path beyond the fixed literal `~/.config/sh-agent`. Naming the mode is what makes the "ask its owner for 0700" advice actionable. No finding.
5. **Is README's clause true to the code?** Yes. Tightening requires: not a symlink (`state.go:100`), a directory with group/other bits set (`state.go:105`), and owned by the caller (`state.go:108`). "when it is yours and not a symlink" names exactly the two conditions that can produce a refusal, and "(either case gets a `note:` instead)" is true of both — symlink at `state.go:101`, not-owned at `state.go:109`. The unstated conditions (already 0700, or not a directory at all) are silent no-ops that the sentence does not claim anything about. Both occurrences (README.md:74 and the install row, README.md:162) carry the identical clause.

Range reviewed: plan file `.agents/docs/plans/2026-09-13-learning-loop-project-level.md` (cold-reader check, not a diff — this is a second-round read of a plan already revised once, per `.agents/docs/reviews/2026-09-13-review-cold-read-learning-loop-3.md`). ## Verdict: design needs revision / implementation not ready (close, one real gap remains)

The prior round's two blocking gaps (D6's undefined scope signal, D8's unreachable-harness-checkout apply step) are now resolved with fully mechanical rules that trace correctly against the existing code (`FindRepo`, `Inspect`, `status`'s first line, `Reinstall`, `installedCopy`). One new-but-real gap remains on the same mechanism: D6's promotion grep keys off "this finding's `rule_ref`", but nothing in Steps 1–4 says how a finding gets a `rule_ref` when it wasn't lifted verbatim from a `feedback.jsonl` line — which is the *common* case for a live retro (Step 1 items 2–5: re-stated preferences, missing knowledge, format friction, tooling mismatches observed directly in the transcript). Two implementers will build this differently: one lets every non-`feedback.jsonl` finding default to `rule_ref: null` (so the mechanical "non-null" grep quietly never promotes them — most findings in a typical retro become permanently unpromotable), the other has the retro synthesize a `rule_ref` per finding (e.g. from the chosen target path) so promotion actually functions for the findings the operator explicitly asked for in this plan's Why. That is a fork in behavior of the plan's headline feature, not a cosmetic choice.

## Findings (gaps a first-pass implementer must resolve)

- **How does a finding acquire a `rule_ref` for D6's promotion grep, when it isn't a verbatim `feedback.jsonl` entry?** (plan line 34, Step 4 in "Retro skill structure" line 60). `skills/feedback/SKILL.md:44-51` defines `rule_ref` as a field the *feedback* skill sets ("global standards section or skill-name, or null"); the retro's own Step 1–3 (unchanged, kept from the current `skills/retro/SKILL.md:32-71`) draft findings straight from the transcript with no `rule_ref` concept at all. Left undecided, the "mechanical, no similarity judgement, no threshold beyond one exact hit" promotion rule the plan is proud of (D6, line 34) either (a) silently never fires for transcript-only findings, or (b) is implementer-invented per finding — two different systems.
- **Verification gap, not just a design gap:** the plan's own Risks section names the exact failure mode ("with all visible, `init-project` or `handoff` could auto-fire") for Phase 2, but no Phase 2 verify step (plan lines 109-113) checks for a *false positive* — every listed check ("no `/name` column entries", "both CLIs list the five... skills", "log clean") confirms the skills are *visible/loadable*, none confirms they *don't* fire on an ordinary request. The mitigation ("descriptions that name the user's-own-words rule; checked in the sandbox", Risks section) is asserted but not wired into any Phase 2 or e2e task.
- **Minor, non-blocking:** `--harness`'s consumption path (retro structure, line 64) says queued proposals are "treated as findings" in Step 1 of a harness-checkout retro. Since the queue file (`~/.config/sh-agent/proposals/<date>-retro.md`) already carries the fully-drafted diff (Step 6, "that mechanism is unchanged" — matches the current `skills/retro/SKILL.md:105-113` format), a reasonable implementer will present-and-apply the already-drafted diff rather than re-derive it through Steps 2–4; worth one sentence in the plan to rule out re-derivation, but a sane default exists.
- **Minor, non-blocking:** the whole per-project → global-index → later-harness-session loop lives under a single machine's `~/.config/sh-agent/` (`retros.jsonl`, `proposals/*.md`). The operator's own environment spans macOS and Linux boxes (`context/dev-setup.md` "Machines:" line; user memory). A project retro run on one box is invisible to a harness-checkout retro run on another. This is a pre-existing property of the mechanism (not introduced by this plan) and a reasonable implementer will build for single-machine as everywhere else in the harness does, so it's not blocking — but it undercuts the stated goal ("later sessions ... to make the harness better on a global level") enough to deserve one documented-limitation sentence.
- **Minor, non-blocking:** `/distill`'s per-project record path (D9: `<docs-root>/retros/<date>-distill-<name>.md`) has no collision rule for distilling the same-named skill twice in one day, unlike D5's explicit `-2`/`-3` suffix for retro records. Low-frequency edge case; an implementer will reasonably reuse the retro suffix convention.

## Readiness — questions a first-pass implementer would have to ask

1. **[BLOCKING]** For a retro finding that is not a verbatim `feedback.jsonl` line (the common case — most Step 1 findings come straight from the transcript), what is its `rule_ref` for D6's promotion grep: always `null` (promotion effectively never fires for these), or synthesized some specific way? The plan's worked example (BUG-041) only covers a finding that already had an established `rule_ref`-shaped identity; it does not cover the general case.
2. **[NON-BLOCKING, default reasonable]** Whether `--harness` re-derives or reuses the already-drafted diff from the queue file when applying a queued proposal — the queue file already contains the full diff, so reuse is the sane default an implementer can pick without asking.
3. **[NON-BLOCKING, default reasonable]** Cross-machine invisibility of the queue/index — an implementer builds single-machine, matching every other use of `~/.config/sh-agent` in this codebase; not a fork two implementers would resolve differently.
4. **[NON-BLOCKING, default reasonable]** `/distill` same-day, same-name collision suffixing — absent a rule, `-2`/`-3` (matching D5) is the obvious reuse.
5. **[NON-BLOCKING]** No test step confirms the five newly-model-invocable skills don't false-positive-fire; a first-pass implementer can still ship what the plan literally specifies (it just won't have caught its own named risk) — this is a plan-completeness gap, not a fork in what gets built.

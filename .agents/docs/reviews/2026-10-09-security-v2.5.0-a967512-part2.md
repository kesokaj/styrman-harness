## Status: COMPLETE

## Verdict: FINDINGS

The worst problem is `trail.PartialClone`. It is the guard that a967512 and the 2026-10-08 round-3 review relied on to stop a lazy fetch on a git older than 2.44, and it is incomplete. It reads only `extensions.partialClone`, but git also treats any remote with `remote.<name>.promisor=true` as a promisor remote. In that case `git log --name-only` lazily fetches a missing object through the repository's own remote URL, transport or `core.sshCommand`. I checked this on a scratch probe with git 2.47.3: `extensions.partialClone` was empty and `remote.origin.promisor=true` was set, and the hardened `git log` started `git fetch origin … --filter=blob:none` and `git-upload-pack`. With `GIT_NO_LAZY_FETCH=1` nothing ran. So on git 2.44 and later the variable protects the code. On an older git, such as Apple Git 2.39 on a default macOS, the nightly dream and `metrics ingest` would run a program named by an untrusted repository's config. That is exactly the case the guard exists for. The second finding is test hygiene, but its damage is real. The new `internal/trail` package has no `TestMain` that clears `GIT_*`. With `GIT_DIR` exported, its fixtures commit into that repository and plant `gpg.program`, `log.showSignature=true`, `filter.x.clean` and `extensions.partialClone` in its config. I confirmed this on a scratch probe.

## Findings
- **[medium / confidence: high (mechanism shown on git 2.47.3 without the variable); medium (that git < 2.44 ignores GIT_NO_LAZY_FETCH, from the 2026-10-08 review and git's release notes)]** `internal/trail/trail.go:140-143` (`PartialClone`), used by `Log` at `:127`, by `changed` at `:68` and by `internal/search/reconcile.go` at the `gitView` refusal. The function checks only `extensions.partialClone`. A repository with `remote.<name>.promisor=true` and no `extensions.partialClone` is still a promisor repository: when an object is missing, `git log --name-only` or `ls-tree HEAD` starts a lazy `git fetch <name>`, and that fetch runs the remote's transport (`core.sshCommand`, `ext::`, a remote helper) from the repository's own config. On git 2.44 and later `GIT_NO_LAZY_FETCH=1` (`trail.go:120`) blocks the fetch. On an older git nothing does. The project roots come from transcripts and the search index, so the harness's threat model treats their config as untrusted (`trail.go:6-11`). The release notes for a967512 say "search refuses partial clones on git < 2.44", but that claim does not hold for this shape of repository. **Remediation:** treat a root as a partial clone when `git config --get extensions.partialClone` is non-empty OR `git config --get-regexp '^remote\..*\.promisor$'` prints any true value; a config read starts no program. Simpler still: when `!LazyFetchSafe()`, refuse every root that has any promisor key. Add a fixture with `remote.origin.promisor=true`, a deleted tree object and a marker in `core.sshCommand`. It must first fire the marker on a plain `git log` without the variable, and then show that `Dates`/`Log` start nothing with `lazyFetchSafe` forced to false. Correct the claim in the a967512 commit message, the package comment and the spec to match.
- **[medium / confidence: high]** `internal/trail/trail_test.go:28-42, 94-110, 176, 196` (and no `internal/trail/testmain_test.go`). Every other package that runs git in fixtures (search, memory, metrics, dream, cmd/sh-agent) drops `GIT_*` in `TestMain`, but the new `trail` package does not. I ran `go test ./internal/trail` on a scratch probe with `GIT_DIR` pointing at a probe repository (since removed). The tests made commits `signed` and `records` in that repository and wrote `gpg.program=/tmp/Test…/fake-gpg`, `log.showSignature=true`, `filter.x.clean=/tmp/…/fake-clean` and `extensions.partialClone=origin` into its config. If `GIT_DIR` names the operator's real repository, a commit lands on their branch. A signed commit plus `log.showSignature=true` then makes every later `git log` there exec a deleted `/tmp` path, which another local user could recreate. `extensions.partialClone` also changes how git treats that repository. Git exports `GIT_DIR` inside hooks, and an operator may export it too. **Remediation:** add `internal/trail/testmain_test.go`, identical to `internal/search/testmain_test.go`, which unsets every `GIT_*` variable.
- **[low / confidence: medium]** `internal/trail/trail.go:82-92` (`changed`). `os.Lstat(filepath.Join(root, path))` and `git hash-object --no-filters --stdin-paths` both follow a symlinked parent directory in the work tree, so a tracked `docs/x/rec.md` whose `docs/x` is now a symlink is hashed from outside the checkout. Only the hash is compared, so the only effect is a "modified" bit and a file read the operator's account could do anyway. Nothing reaches the prompt this way, because `collect` refuses symlinked record directories itself. I note it because `reconcile.go` reads through `os.Root` for this reason and this path does not. **Remediation (optional):** do the Lstat through an `os.Root` opened on root and skip a path whose parent is not a real directory.

### Round-2 findings
- **[medium / confidence: high]** `internal/trail/trail.go` `PartialClone`, the `--get-regexp` loop (`if f := strings.Fields(line); len(f) == 2 && f[1] == "true"`). A remote subsection may contain whitespace. For `[remote "a b"]` with `promisor = true`, git prints `remote.a b.promisor true`, which is three fields, so the check misses it. Probe on git 2.47.3 (scratch, removed afterwards): a repo with that remote and one missing tree object made plain `git log --name-only` start a lazy `git fetch`, while `trail.PartialClone` returned **false**, so `Log`, `changed` and search's gate would read that repo on a git older than 2.44. The same probe confirmed two cases are handled: a valueless `promisor` key (implicit true) is caught, and an invalid boolean makes `git config` exit 128 with no output, but git then also dies before fetching (no fetch seen), so that case fails safe. **Remediation:** read `git config --null --type=bool --get-regexp '^remote\..*\.promisor$'`. Split each NUL-terminated record at its first `\n` (key, then value) and test the value against `true`. Or, at minimum, test the text after the last space of the line. Add `remote "a b"` (and a tab inside the name) to `TestPartialCloneSeesPromisorRemote`. Both cases must fail on the current code.
- **[info / confidence: high]** `internal/trail/trail.go` `changed`: `fsRoot.Lstat` now refuses a path that leaves the checkout, but `git hash-object --stdin-paths` then opens the same path by name, outside the `os.Root`. A directory swapped for a symlink between the two calls is still hashed outside. Only a "modified" bit results, and only a concurrent writer could cause it. No action needed.
- **[info]** `internal/search/search.go` `reconcileGlobal`: the skipped checkout is left out of `projects` for that query, so its stale records are not served. This matches how the `dropReason`-error skip already behaves.

## Round 3

Range reviewed: the working tree on top of a967512 (`git diff HEAD`, 2026-10-09). This round covers the fix for R2-1: `internal/trail/trail.go` `PartialClone` now uses `--null` parsing, and `TestPartialCloneSeesPromisorRemote` gains two cases.

Round-3 verdict: CLEAR. The R2-1 fix is correct and complete, and I found no defect it introduced. With it, every finding from rounds 1 and 2 in this part is fixed in the working tree, and nothing is left open.

### Round-3 verification
- **Code.** The command is `git config --null --type=bool --get-regexp '^remote\..*\.promisor$'`. The code splits the output at NUL bytes, cuts each entry at its first `\n` and compares the value with `"true"`.
  - Git refuses a newline in a subsection or a key, so the first `\n` always ends the key.
  - `--type=bool` turns `TRUE`, `yes`, `on`, `1` and a key with no value into `true`.
  - `extensions.partialClone` is still checked first.
- **Probe.** I built five scratch repos on git 2.47.3. Each had a missing tree object and the caller's `GIT_*` variables unset, and all were removed afterwards. For each I ran raw `--null` output, a traced plain `git log` (to see whether it started a lazy fetch) and `trail.PartialClone` / `trail.Log` from the working tree:
  - `[remote "a b"] promisor = true`: lazy fetch 1, `PartialClone` true, `Log` refused.
  - `[remote "a<TAB>b"] promisor = on`: lazy fetch 1, `PartialClone` true, `Log` refused.
  - Valueless `promisor`: lazy fetch 1, `PartialClone` true.
  - `promisor = false`: lazy fetch 0, `PartialClone` false (the correct answer).
  - A valid `promisor = 1` followed by `remote.x.promisor = maybe`: `git config` prints nothing to stdout and exits 128, so `PartialClone` is false. But plain `git log` also starts no fetch (0), because git refuses the bad boolean while it reads the promisor config. This fails safe whatever the order of the entries.
- **Mutation.** On a scratch copy of the package I put back round 2's `strings.Fields` parse. `TestPartialCloneSeesPromisorRemote` then fails on exactly the two new cases (`remote.a b.promisor=true`, and a tab in the name with `yes`). With the fix, `go test ./internal/trail -count=1` passes.
- **References.** `PartialClone` has the same signature and the same callers as in round 2 (`Log`, `changed`, `search.gitView`'s gate), so I re-checked nothing beyond the function and its test.

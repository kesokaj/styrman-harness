# Review — v1.9.0-b1ecab3-code   (2026-09-28)

Range reviewed: v1.9.0..b1ecab3

## Status: COMPLETE

## Verdict: APPROVE WITH NITS

Nothing is broken. `--unverified` cannot let a FAILED verification through. The flag is read in exactly one place: the `ErrZipUnsigned` branch of the `check` closure (`cmd/sh-agent/main.go:1097-1102`). Every other error from `VerifyZipSums` is returned unchanged. `VerifyZipSums` returns `ErrZipUnsigned` only when BOTH stats report `fs.ErrNotExist` (`internal/harness/release.go:444-452`), so any other stat error, one file alone, a bad signature, a stale pair and a checksum mismatch are all refused whether or not the flag is set.

I confirmed this by hand with a binary built from b1ecab3 and a `git archive` zip, in dry-run mode. Four folders, each run with and without the flag:
- neither file: refused without the flag, and the refusal names `--unverified`; installs marked UNVERIFIED with it;
- SHA256SUMS only: refused both ways, "has no SHA256SUMS.sig";
- .sig only: refused both ways, "has no SHA256SUMS";
- junk pair: refused both ways, "signature does not verify".

None of the failed-check refusals mentions `--unverified`, and no error string in `verifySignedSums` or `VerifyZipSums` contains it.

R9's zip-place bullet as changed is met by the code. There are two findings, both about test strength:
- three refusal tests do not pin which refusal fired, and would pass without the flag, for the wrong reason;
- the invariant "a failed-check refusal never names --unverified" has no test.

## Findings

- **[low / confidence: high]** Three refusal tests would pass for the wrong reason without the flag:
  - `cmd/sh-agent/zip_test.go:429` (`TestUpdateFromZipRefusedContentWritesNothing`)
  - `cmd/sh-agent/zip_test.go:554` (`TestUpdateFromZipRefusedRunSweepsNothing`)
  - `cmd/sh-agent/zip_test.go:598` (`TestUpdateFromZipInstallRefusalSweepsNothing`)

  **What happens.** The new unsigned refusal runs after the zip's bytes are hashed but before `zip.NewReader`, `checkZipTrees` or install (`internal/harness/zip.go` `UnpackZip`). It also writes nothing, because `MkdirAllTracked` is undone by the deferred `RemoveCreated`. So these three tests, which assert only `err != nil` plus "home empty / stale dir kept", pass even when they never reach their own refusal.

  **How I checked.** I copied the tree into `.agents/scratch/rv-mut` via `git archive` and removed `--unverified` from those tests. All three still PASSED. Only `TestUpdateFromZipRefusedZipWritesNothing`, which asserts "would escape", went red.

  **Where things stand.** Today they do exercise their own refusal, because the flag is passed. But nothing stops a later edit from dropping the flag, or moving the unsigned check, and leaving them green on the wrong refusal. The changes entry `.agents/docs/changes/2026-09-28-2010-unverified-flag.md` ("the refusal tests (zip-slip, not-a-zip, install refusal) … were red without it") is inaccurate for these three; only zip-slip was red.

  **Fix.** Assert each test's own refusal text: "not a readable zip" for not-a-zip, and the missing-description refusal for the other two. Correct the claim in a follow-up entry, since `changes/` is append-only.

- **[low / confidence: high]** No test pins the invariant "a failed-check refusal never mentions `--unverified`" (`cmd/sh-agent/zip_test.go:636-645`, `:762-767`).

  **Why it matters.** ADR-040's Consequences rely on it ("the refusals for failed checks still never mention it"), because a hint to bypass a failed check is what ADR-039 forbids. The code holds today (verified above). But no assertion would catch a future refusal message that adds "or pass --unverified". The analogous guard already exists: the tampered-zip test's `"move SHA256SUMS"` negative check.

  **Fix.** Add `strings.Contains(err.Error(), "--unverified")` as a failure condition in the foreign-signature loop and the tampered-zip case. Ideally also add one cmd-level case with only one file beside the zip, run with `--unverified`. Today the one-file classification is pinned only at the harness level (`internal/harness/zip_test.go:479`, `:520`).

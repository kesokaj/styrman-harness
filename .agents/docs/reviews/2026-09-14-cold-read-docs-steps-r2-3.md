# Cold-read (round 2, reader 3) — plan `.agents/docs/plans/2026-09-14-documentation-steps.md`   (2026-09-14)

Range reviewed: not a diff — the plan file, updated after round 1's three cold reads (whose blocking items are recorded in the plan's own "Cold-reader residue" section and resolved inline in items 2, 4, 5), plus the surfaces it names: `context/AGENTS.md`, `README.md`, `agents/{verifier,documentation,changelog,explorer,bugs,security,reviewer}.md`, `skills/{review,preflight,retro,handoff}/SKILL.md`, `.agents/docs/testing/` (all files) and `skill-matrix.md`, `.agents/docs/deploy/{local,remote}.md`, `~/.config/sh-agent/proposals/*.md` (all six, read structurally), `REQUIREMENTS.md`.

## Verdict

Round 1's three named gaps (queue-file count, the Outcome section's anchor in `review/SKILL.md`, and the guide filename replacing "guides") are genuinely fixed in the current text — I checked each against the live files and the plan's wording now matches reality. But the fix for item 2 opens a new, un-stated directory-layout question: `testing/sh-agent/guide.md` would be the only nested file in a `testing/` directory that currently holds fifteen dated logs and one procedure doc flat at its root, and nothing in the plan or in `agents/verifier.md`'s own (unedited) log-writing template says whether the dated logs move under `testing/<app>/` too or stay flat beside a single-file subdirectory. There is also a residual formatting ambiguity in the 2026-09-03 backfill (item 5) that round 1 raised as a scope problem and the plan fixed the scope but not the per-row attribution mechanics for a table-shaped file.

## Gaps — must be decided before implementation

- **G1 (new) — item 2's `testing/<app>/guide.md` is nested; the rest of `testing/` is flat, and the plan does not say which wins.** `.agents/docs/testing/` today holds 15 dated `*-verify-*.md` files and `skill-matrix.md`, all direct children of `testing/` — there is no per-app subdirectory anywhere in this repo. Plan item 2 (`.agents/docs/plans/2026-09-14-documentation-steps.md`, item 2) has the verifier "create `testing/sh-agent/guide.md` at this plan's Phase 2 checkpoint" but does not touch `agents/verifier.md`'s existing "Verification log" template, which still says `Write $docs_root/testing/$(date +%F)-verify-<slug>.md` (`agents/verifier.md`, "Verification log" section) — flat, no `<app>` segment. So after this plan ships, the very next verifier run (the Phase 2 checkpoint the plan requires) writes a lone `guide.md` into a brand-new `testing/sh-agent/` directory while its own dated log for that same run lands flat at `testing/2026-09-14-verify-<slug>.md`, one level up. Two implementers diverge here: one leaves the dated-log template alone (matches the literal diff) and ends up with a `testing/sh-agent/` directory containing exactly one file forever; the other also moves the log-writing path under `testing/<app>/` for consistency (not asked for, and arguably a bigger, riskier edit the plan's Scope section doesn't authorize — Scope says "each a prose edit," and moving/renaming the log destination for every future verification run is more than a prose edit). Neither is clearly right from the text given.
- **G2 (residual, downgraded) — item 5's per-proposal Status line has no anchor in a table-shaped file.** `~/.config/sh-agent/proposals/2026-09-03-retro.md` records its two proposals as **table rows** (`| 1 | ... | applied 2026-09-03 |`, `| 2 | ... | applied 2026-09-03 |`, lines 7-8), not as `### Proposal` headings. Item 5 says these files "get one `**Status:** applied 2026-09-03` line per proposal directly under the table or heading," and the plan's verify check only counts "as many `**Status:**` lines as proposals" in the file — it does not require each line to be traceable to a specific row. A reasonable implementer adds an identifying fragment per line (e.g., "`**Status:** applied 2026-09-03 (finding 1)`" / "`(finding 2)`") since the table already numbers its rows, so I mark this **NON-BLOCKING** on balance — but it is worth naming because `/retro --harness`'s new reading rule (item 5) depends on associating a Status with a specific proposal, and this file is the one place the plan's own chosen anchor ("under the table or heading") doesn't disambiguate which of two co-located lines belongs to which row.

## Readiness — questions a first-pass implementer would have to ask

1. **BLOCKING** — Does the new verification-log destination for `sh-agent` (and any future multi-app project) move to `testing/<app>/$(date +%F)-verify-<slug>.md` to sit beside its guide, or does `agents/verifier.md`'s existing flat `testing/$(date +%F)-verify-<slug>.md` template stay unedited, leaving `testing/sh-agent/` as a directory holding only `guide.md`? Two careful implementers produce different `testing/` layouts, and the plan's own Scope line ("each a prose edit") argues against the bigger move while item 2's "creates `testing/sh-agent/guide.md`" argues for the nested convention — the plan does not say which the DoD documentation lane (item 1, "it owns ... `docs/testing/<app>/`") is describing.
2. **NON-BLOCKING** — In `2026-09-03-retro.md`, do the two backfilled `**Status:**` lines carry a per-row identifier (finding 1 / finding 2), or are they added as an undifferentiated pair after the table? A reasonable implementer labels them, since the table already numbers the rows and an unlabeled pair would defeat the reading rule item 5 exists to build.
3. **NON-BLOCKING** — Item 5's forward-going convention is `**Status:** queued` (bold label, plain lower-case value) but the already-compliant `2026-09-08-retro.md` uses `**Status: APPLIED 2026-09-08**` (label and value bolded together, upper-case). The plan says this file needs no change ("the 2026-09-08 file already has them"), so a reasonable implementer leaves the format mismatch as historical and does not retrofit it — this is stated closely enough in the plan that I don't count it a gap, just confirming the default.

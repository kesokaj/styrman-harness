## Verdict: FINDINGS

**Still broken on the author's side (all low):**
- **First-install chains.** For a binary-only place, the documented chains still download without naming the host (`README.md:104`, `.agents/docs/deploy/remote.md:29`). A new machine with `GH_HOST` set installs whatever that host serves under the repository's name. This is round 1's medium host finding, still open on the manual install path.
- **Bridge deletion line** (`remote.md:167`). It still exits 0 and claims "the old key is off the disk" when `RETIRED` is empty (measured).
- **Paste-cache copy** of the retired private key: still on disk.
- **`remote.md:169`** still compiles a leftover `../v232src`.
- **ADR-053a misstatement.** It credits the new `CHECKED … (integrity only)` wording to the binary-only place, which still prints "verified and installed".
- **`remote.md:49`** still says "authenticity is the signature and checksum".
- **The trust root** is stated in ADR-053a but not in delivery.md § The model.
- **The handoff** that ADR-053a says carries the operator's decisions does not exist.

**The operator's (reported, not counted as defects).** At review time:
- GitHub Actions is enabled with `allowed_actions: all`.
- `GH_TOKEN` is exported into this agent's session.

The token is the biggest live risk: it alone can publish a release that every v2.4.0+ binary-only place installs.

**Fixed, by my own measurement:**
- **Host pin in code.**
  - `ReleaseRepo` names github.com in both gh calls.
  - `TestUpdateFromReleasePinsTheHost` passes at HEAD. It fails on a hostless mutation in a scratch copy, flagging both calls.
  - The real gh 2.102.0, with `GH_HOST=example.invalid`, sends `release view` and `release download` to github.com when `--repo` names the host. The hostless form goes to example.invalid.
- **The bridge's fingerprint check.** With a decoy `.pub` beside the key, the 4ee867a check printed the decoy's fingerprint; the 6556bbe check prints the private half's.

**Gate note.** `.agents/docs/architecture/DECISIONS.md` was not read end to end at HEAD: lines 202-604 are outside the range's hunk. Under the dispatch's rule it is named in Not examined, and that blocks the gate until it is read or the caller waives it.

## Findings

1. **[low / confidence: high]** The manual first install for a binary-only place still downloads without naming the host. `README.md:104` and `.agents/docs/deploy/remote.md:29` run `gh release download "$V" --repo kesokaj/styrman-harness`.
   - **The weakness.** That form takes its host from `GH_HOST`. Measured on gh 2.102.0: the hostless form with `GH_HOST=example.invalid` fails with `error connecting to example.invalid`.
   - **Why nothing later in the chain catches it.** A self-consistent forgery from that host passes every check:
     - `grep -qxF "# styrman-harness $V"` passes, because the forger writes that line.
     - `sha256sum -c` passes, because the hashes come from the same server.
     - The version `test` passes, because a forged binary prints whatever it likes.
     - The binary is then moved into `~/.local/bin` and run.
   - **Severity.** Same impact as round 1's medium finding 2, on a narrower path: once per new machine, and only where `GH_HOST` points at a host on which someone else owns `kesokaj/styrman-harness`.
   - **ADR-053a's claim.** "In every gh call" is true of the code only.
   - **The publishing side has the same gap.** These lines in `remote.md` also name no host:
     - `:97` `gh auth status`
     - `:151` create, `:154` upload, `:156` view
     - `:177` `gh repo view`
     - `:179` and `:183`, in the prose

     On a releasing machine with `GH_HOST` set, the private repository's binaries and its tree zip go to another host's repository of the same name, if the operator can write there. The confirming `view` checks that same wrong host.
   - **Remediation.**
     - Write `--repo github.com/kesokaj/styrman-harness` in every one of those commands.
     - Use `gh auth status --hostname github.com`.

2. **[low / confidence: high]** `.agents/docs/deploy/remote.md:167`: the bridge's deletion line is unchanged, `rm -f allowed_signers "$RETIRED" && test ! -e "$RETIRED"`.
   - **Measured.** With `RETIRED` empty it exits 0 and deletes nothing. Its comment says "exit 0: the old key is off the disk".
   - **What 6556bbe guards.** Only the check line. With `RETIRED` empty, `:163` exits 1 and `:164` exits 255 (both measured).
   - **Why `:167` still matters.** The procedure runs "each command its own call" (`:95`), so `RETIRED` does not survive into `:167`'s call. A runner who sets it inline for `:163` and `:164` but not for `:167` gets a false success.
   - **What that leaves.** The key it meant to delete still signs releases that every v2.3.2-or-older binary accepts.
   - **The change entry over-claims.** "Refuses an empty path" (`.agents/docs/changes/2026-10-05-1618-releases-without-a-key.md:13`) holds for the check line only.
   - **Remediation.** `test -n "$RETIRED" && rm -f allowed_signers "$RETIRED" && test ! -e "$RETIRED"`, or chain the block into one command.

3. **[low / confidence: high]** The retired private key still has copies outside the block (round 1 5(c), open).
   - **On disk.** `~/.claude/paste-cache/d17c19c927c1cf71.txt` is still present: 1405 bytes, mode 600, mtime 2026-10-05 13:04 (from `stat`; not opened).
   - **Nothing deletes it.** No command does, in the block, the operator steps or the range. The same holds for the session-transcript copy, so ADR-053's "which is then deleted" has nothing behind it.
   - **Why it matters.** Any process running as the operator can read the file. That includes the same sessions that hold `GH_TOKEN`. Together, the file and the token can publish a release that v2.3.2 binaries accept, for as long as those binaries run.
   - **Remediation.** Add an operator step after the bridge that deletes each known copy by name, each followed by `test ! -e`.

4. **[low / confidence: high]** `.agents/docs/deploy/remote.md:169`: `mkdir -p ../v232src` still does not empty the directory first (round 1 5(d), open).
   - **Effect.** A tree left by an earlier attempt is compiled into the v2.3.2 check binary. That binary only decides whether the bridge check passes, so the risk is a false pass, not a shipped binary.
   - **Remediation.** `rm -rf ../v232src && mkdir ../v232src`.

5. **[low / confidence: high]** The wording fix is partial, and ADR-053a misstates where it landed.
   - **ADR-053a's claim.** Its Decision (`.agents/docs/architecture/DECISIONS.md:602`, read in the diff) says "A binary-only place's wording says what the check is: `CHECKED against the SHA256SUMS of release vX.Y.Z (integrity only)`".
   - **What the code does.** That line is the zip place's (`cmd/sh-agent/main.go:1161`). The binary-only place's update still prints `verified and installed <asset> <tag>`: `internal/harness/release.go:145`, asserted at `internal/harness/release_test.go:163`.
   - **Unchanged authenticity sentence.** `.agents/docs/deploy/remote.md:49` still says "authenticity is the signature and checksum on the file, before the move". Round 1 named it beside `README.md:153`, and only README changed.
   - **Stale describing text.**
     - `cmd/sh-agent/zip_test.go:677`: the test header says the zip "says VERIFIED".
     - `cmd/sh-agent/main.go:8`: "download and verify the newest release".
     - `main.go:489`: "downloaded and verified".
   - **Not counted.** The status rendering `(verified vX.Y.Z)` (`main.go:718-719`, `README.md:168`, `zip_test.go:712`) is kept on purpose by ADR-053a. That is the operator's call.
   - **Remediation.**
     - `release.go:145`: "checked and installed … (integrity only)", with the test string updated to match.
     - `remote.md:49`: take README:153's new sentence.
     - Fix the three comments.
     - Correct the ADR misstatement in the next append to DECISIONS.md.

6. **[low / confidence: high]** The trust root is not in the one home (round 1 finding 1's doc part, plus finding 2's related note).
   - **Where it is stated.** ADR-053a's Consequences (`DECISIONS.md:604`) names it: SSH login keys, the gh token, Actions while enabled, HTTPS.
   - **Where it is missing.** delivery.md § The model (`.agents/docs/specs/sh-agent/delivery.md:30`), rule 6's one home, still says only "the operator's GitHub credential and HTTPS".
   - **Understatements elsewhere.** `.agents/docs/deploy/remote.md:61` and `delivery.md:48` say such a credential "can clone and push". They do not say it can publish a binary that every binary-only place installs.
   - **Stated nowhere.** The `gh` executable first on PATH is part of the chain (`release.go:77`, `:58`, `:162`).
   - **Remediation.** Add one sentence to § The model, and have `remote.md:61` point to it.

7. **[low / confidence: high]** No superseding handoff (round 1 finding 6, open).
   - **What ADR-053a says.** Actions and the token are "put to them in the v2.4.0 handoff".
   - **What exists.** The newest handoff is still `.agents/docs/handoffs/2026-10-05-1519-v2.4.0-bridge-ready-operator-steps.md`. It predates ADR-053, directs the retired ADR-052 procedure, and lists token rotation as "Optional".
   - **Remediation.** Write that handoff before the tag, with three items:
     - Actions off.
     - Token rotation, as a blocking step.
     - Deletion of every retired-key copy.

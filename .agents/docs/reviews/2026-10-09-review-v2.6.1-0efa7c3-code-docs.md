# Review — v2.6.1-0efa7c3-code-docs   (2026-10-09)

## Status: COMPLETE

## Verdict: REQUEST CHANGES

The code is correct as far as Linux can show. `gofmt -l cmd internal` printed nothing, `go vet ./internal/dream` passed, and `go test -count=1 -race ./internal/dream` was ok (all run by me at 0efa7c3). The verdict is REQUEST CHANGES because of the release gate, not because of a code defect. This range adds a rule (`testing/guide.md:143`): any change to how `agyHome` finds the login owes one real macOS `sh-agent dream --all` before the release that carries it. That run has not happened. The BUG-166 record, the changes entry, the verifier log and the handoff all say it is still owed. The handoff also notes that in all three operator probes the model tried `ls -la` and returned an empty response. So the fix can get past login and still fail every macOS project as `invalid output`. A second problem: the new login hint matches the literal string "Authentication required". That string appears in no recorded agy output, only in the test fixtures that the matcher was written against. The documented failure line for a locked Keychain therefore rests on an invented string.

- **[high / confidence: high]** `.agents/docs/testing/guide.md:143` (rule added in this range); `.agents/docs/bugs/BUG-166-dream-agy-login-macos-keychain.md` § Fix "Not yet shown"; `.agents/docs/handoffs/2026-10-09-1504-bug166-dream-macos-login.md` § Agent notes. - **[medium / confidence: medium]** `internal/dream/run.go:355`, `internal/dream/run_test.go:681,690,702`. `agyAuthHint` fires only on a non-`{` line containing `Authentication required`. - **[low / confidence: medium]** `internal/dream/run.go:128-135`, `call` at `run.go:186-207`; docs `deploy/local.md:93`, `specs/sh-agent/dream.md:34`. Per BUG-166 Repro 2, an agy with no usable login "printed a browser-login URL and waited". With a locked Keychain (the nightly timer while no user is logged in), each changed project therefore runs until the 10-minute `cliTimeout` kill. The loop then moves to the next project, so a night with N changed projects holds `dream.lock` for about N×10 minutes, and every project fails the same way. Each failure keeps its watermark, so the same thing repeats every night. The docs say only "fails each project". The operator deferred the locked-Keychain case, which is why this is low. Fix: either end the run after the first login failure (exit 2, as no-login already does), or state the per-project 10-minute wait in both docs. The timeout path's `err` is `agy timed out after 10m`; the hint is added only if the phrase from finding 2 is in the captured output.
- **[low / confidence: high]** `internal/dream/run.go:275`. The `info.IsDir()` condition has no test. The earlier review's Outcome rebuts with "Keychains as a file is refused by the `IsDir` check", but nothing pins that. - **[low / confidence: medium]** `.agents/docs/reviews/2026-10-09-security-bug166-agy-keychain.md` § Outcome 1 against `.agents/docs/testing/guide.md:143`.

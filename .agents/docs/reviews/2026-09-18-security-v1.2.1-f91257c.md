# Security review — release gate v1.2.2 (v1.2.1..f91257c)   (2026-09-18)

Range reviewed: v1.2.1..f91257c

## Verdict: FINDINGS — all low; nothing here blocks the gate

Nothing in this range hand-rolls crypto, adds a dependency, commits a secret, or introduces an
injection sink. `govulncheck ./...` on go1.27.1: **No vulnerabilities found** (run by me, this tree).
The public ssh-ed25519 signer line is byte-for-byte identical in all seven places it appears —
`internal/harness/release.go:40` (`releaseSigner`), `README.md:92,120`, `.agents/docs/deploy/remote.md:31,91,113,145`
— measured, not eyeballed: SHA-256 of each occurrence is `2b5cdc207c04e554790bd70bcb590bbb1ac5b49c0382f0e73df01bfb2220fcca`,
one distinct value across all seven, and `TestReleaseSignerMatchesTheDeployGuide` (`internal/harness/release_test.go:431`)
pins the `remote.md` copies to the compiled-in one. It is a PUBLIC key whose identity is the operator's
own email, which is its purpose, not a leak.

The worst item is a **downgrade gap in the newly documented MANUAL install chains**: both strip the
`# styrman-harness vX.Y.Z` marker out of `SHA256SUMS` with `grep -v '^#'` and never assert it, so the
human route does not bind the signed hashes to the version being installed — the exact check
`internal/harness/release.go:277-283` makes for `sh-agent update`, and the one `sumsVersionMarker`'s own
comment says exists because "serving an older release's assets under a newer tag would pass every check".
It was named as a hardening note in round 1's report and never carried into any `## Outcome`, so it is
still open. Low, because it needs an actor who can serve release assets without holding the key.

## Findings

- **[low / confidence: high]** `README.md:94`, `.agents/docs/deploy/remote.md:33` — the documented chains
  verify `ssh-keygen -Y verify` over `SHA256SUMS`, then pipe `grep -v '^#' SHA256SUMS` into
  `sha256sum -c - --ignore-missing`. The `#` line discarded there is `sumsVersionMarker`, the only thing
  binding a signed checksum file to a release; `verifyRelease` checks it (`internal/harness/release.go:277-283`,
  "the signed SHA256SUMS says %s but this is release %s"), the human chain does not. Exploitable in
  principle by anyone who controls what the release endpoint serves but not the signing key: hand the
  operator an older, genuinely signed `SHA256SUMS` + `SHA256SUMS.sig` + binary and every step of the
  documented chain passes — a silent downgrade to a release with known defects. Sharper for `README.md:90`,
  which passes no tag at all (`gh release download --repo … --pattern …` takes the newest release), so the
  reader has nothing at all tying the bytes to a version. `remote.md:29` at least names `vX.Y.Z` to `gh`,
  but never checks that the signed file agrees. Remediation, no new dependency, one extra `&&` link before
  the checksum step: `grep -qx '# styrman-harness vX.Y.Z' SHA256SUMS` (README: the version the reader meant
  to install), keeping the existing `grep -v '^#'` filter afterwards for `sha256sum -c`'s benefit.
- **[low / confidence: medium]** `README.md:119-124` — the browser-route chain, added in the closing
  commit of this range, is the one verification chain in the repository that has never been executed on
  the platform it targets. It is written for macOS (`shasum -a 256 -c - --ignore-missing`), and the
  handoff in this same range says so in as many words: "Not run on a Mac: the README browser route's
  `shasum -a 256 -c - --ignore-missing` form (written from the manual)"
  (`.agents/docs/handoffs/2026-09-18-bug-078-closeout.md`). This repository's own BUG-075 prevention rule
  — "a doc command is RUN as written before the release that documents it, not read" (`bugs/INDEX.md`) —
  is what v1.2.2 would be publishing against. Risk direction is honest: I measured both plausible
  implementations on this Linux box and both FAIL CLOSED with nothing verified — GNU coreutils
  `sha256sum -c - --ignore-missing` exits 1 (`'standard input': no file was verified`) and Perl
  `shasum` 6.x exits 1 with the same message — and an implementation that rejects the flag exits non-zero
  too, stopping the chain before `chmod +x`. The version macOS actually ships was not measured by me or by
  any prior round. Remediation: run the fence once on the Mac before or immediately after cutting the tag
  and record the result in `.agents/docs/testing/`, or drop `--ignore-missing` (the signed file lists
  three assets, so `-c` without it will report the two absent ones and fail — which is why the flag is
  there; if it is dropped, the chain must select the one line instead).
- **[low / confidence: high]** `cmd/sh-agent/main.go:395` with `internal/harness/pathguard.go:30,48` —
  `status` prints its `shadowed` line only inside `if … ; onPath {`, and `onPath` is false whenever
  `executableAt(binPath)` fails: the installed file is missing, is a directory, or has lost its execute
  bit. In that state the walk has already collected real shadows and drops them silently, while
  `.agents/docs/deploy/remote.md:191` and `local.md:87` both list "no `shadowed` line" as a Verify pass
  condition — so a shadowed machine can be recorded as passing. This is the BUG-078 shape (every command
  reporting success about a binary that is not the one running) surviving in one branch. Known and twice
  dispositioned `left` by the main agent (rounds 3 and 4), with real mitigations I confirmed: a missing
  file also prints `binary unknown (installed file has no build info)` (`main.go:373` fallback), and both
  guides now additionally require an unqualified `sh-agent version` matching what was installed. The
  uncovered case remains a present-but-non-executable binary, where the `binary` line prints normally.
  Recorded, not a gate blocker. Remediation (makes the code shorter): print the shadows whenever
  `len(shadows) > 0` and let the `binary` line carry whether the file is installed.
- **[low / confidence: high]** trail markdown in this range — `.agents/docs/testing/2026-09-17-release-binary-e2e.md`,
  `.agents/docs/bugs/BUG-078-*.md`, `.agents/docs/handoffs/2026-09-18-bug-078-closeout.md` and the verifier
  logs record internal machine identifiers: account names on other hosts (`/home/admin`, `/Users/spgo`),
  internal hostnames (`spgo-mac.roam.internal`, `devbox`, `dave`), provisioning paths (`/opt/devbox/bin`,
  `/opt/devbox/deploy/harness`), and the local home path throughout. No credential, token, private key or
  `.env` content anywhere — the only key material is the public signer line and the public fingerprint
  `SHA256:5HpYQJjpG+yE1xXBTOIZPsTkbkgkVnV8z0eG8hBawyU`. The repository is private (confirmed in the e2e
  log by `gh repo view --json visibility` → `PRIVATE`), and `remote.md:161` already carries the standing
  note that the trail names internal hostnames and machine paths. Exploitable only as reconnaissance if
  the repository is ever published, which is why it is low and informational. Remediation: none needed
  now; treat it as a checklist item for any decision to open the repository, as `remote.md:161` says.

### Considered, not raised as findings

- **Terminal control bytes in the new `shadowed`/`warning:` output** (`main.go:397,657`, paths printed
  verbatim with `%s`). Raised in rounds 1 and 2 and rebutted twice; I checked the rebuttal and concur:
  the only variable part is an element of the operator's own `$PATH`, the resolved target is never
  printed, `which -a` does not escape either, and anyone who can put an executable `sh-agent` on that
  PATH already gets code execution the next time `sh-agent` is typed. `%q` is Go quoting, not shell
  quoting, so it is not the right instrument. No new information since; no code change asked for.
- **`os.Stat` on every PATH entry hanging on a dead NFS/autofs mount.** Availability only, on the
  operator's own command, bounded by the entries ahead of the installed file (and by every distinct
  entry when the installed file is absent). Rebutted across rounds 2-4 with the reason finally stated
  correctly; I agree.
- **`sh-agent report` leaking the new path output.** It does not: `internal/harness/report.go` `Collect`
  reads files under `~/.config/sh-agent` (`feedback.jsonl`, `retros.jsonl`, `proposals/`, `state.json`)
  and redacts them; it never captures `status` or `install` stdout, so these paths do not reach the
  feedback repository. Verified by reading `report.go`'s `Collect`/`redactLines`/`redactDocument`.

## Checked

- **Secrets** — the only credential-shaped string in range is the PUBLIC allowed-signers line, identical
  to `releaseSigner` by hash across all seven occurrences and pinned by a test. Greps over every added
  markdown line for `password|secret|token|api[_-]?key|private key|BEGIN .*PRIVATE|bearer|ghp_|github_pat_|
  AKIA|xox[baprs]-|client_secret|\.pem|\.key|id_rsa|id_ed25519|GOOGLE_APPLICATION|service.account`: no
  hits other than prose in the prior security reports discussing the absence of secrets. No `.env`,
  `*.pem`, `*.key`, `*.tfvars`, `*.tfstate` or credential JSON in the range; `git diff --numstat` shows
  no binary file (no `-`/`-` row), so nothing is hidden from a reviewer.
- **Injection** — `PathShadows` splits `$PATH` with `filepath.SplitList`, joins with `filepath.Join`,
  and never opens, reads or executes a candidate (`os.Stat` only). Every sink is `fmt.Fprintf` with a
  constant format string and the path as an argument; no shell, no `exec`, no template, no SQL added in
  range. In the markdown half the commands are run by a human: every expansion is double-quoted
  (`"$D"`, `"$ASSET"`, `"./$ASSET"`), the chains are single `&&` chains so a failed check cannot be
  outrun by the `mv`, and `chmod +x` sits after both checks so a failed verification leaves a
  non-executable file. The one pipeline (`grep … | sha256sum -c -`) has the deciding command at the end,
  so the `&&` chain reads the right status — and I measured that `sha256sum` cannot exit 0 without
  verifying a real file (empty input → exit 1, nothing present → exit 1).
- **Authz/authn** — no endpoint, session, identity decision or privilege change in range. The one trust
  decision is release-artifact verification; `internal/harness/release.go` is unchanged across the whole
  range, the compiled-in signer and the `sh-agent-release` namespace are intact, and the documented
  chains verify the signature BEFORE trusting the checksum file — the correct order. The gap between the
  documented route and the code route is finding 1.
- **Crypto** — nothing implemented or composed here. The change consumes `ssh-keygen -Y verify` and
  `sha256sum`/`shasum` as designed; `os.Stat`/`os.SameFile` are not crypto. No cipher, hash, MAC,
  signature, KDF, RNG, token or session format is hand-rolled anywhere in range.
- **Dependencies** — none added; `go.mod`/`go.sum` untouched across `v1.2.1..f91257c`. `pathguard.go`
  imports `os` and `path/filepath` only. `govulncheck ./...` → `No vulnerabilities found.`, exit 0,
  go1.27.1 (run by me on this tree; prior rounds could not run it under a no-network limit). No npm
  ecosystem in this repository, so `npm audit` does not apply.
- **GCP surface** — nothing in range: no IAM binding, service account, Cloud Run flag,
  `--allow-unauthenticated`, secret-as-env-var, or service-account key file. This repository has no GCP
  deploy path.
- **Trail markdown (secrets, private data, instruction-shaped text)** — all 21 markdown paths in the
  range read end to end (the four prior security reports, four code/docs reviews, five testing logs, the
  bug record, the changes entry, the handoff, two plan diffs, `INDEX.md`, `README.md`, `ROADMAP.md`,
  `local.md`, `remote.md`). Greps for injection-shaped text (`ignore previous|disregard|new instructions|
  system prompt|override|curl … | sh|rm -rf|chmod 777|--dangerously|--no-verify|skip the review|
  force-push|git config --global|eval|base64 -d`) found no added line that instructs an agent to act
  outside the documented procedure or reads as a prompt override; the only `rm -rf` hits are review prose
  discussing a remediation and the `rm -r "$D"` cleanup. `sudo` appears only in prose on `remote.md:38`
  and in the bug record quoting what the operator did. Private data is finding 4.

## Not examined

- **macOS.** Every measurement here is on Linux (`Linux 6.12.107+deb13-amd64`, go1.27.1, GNU coreutils,
  Perl `shasum` 6.x). The README browser fence's `shasum -a 256 -c - --ignore-missing` form and the
  quarantine behaviour were not run on macOS by me or by any prior round (finding 2).
- **The shell chains were never executed end to end**: no `gh release download`, no network, no release
  fetched, nothing moved into any `bin` directory, nothing written to the real `$HOME`, and
  `sh-agent report` was never run (hard limits). `gh`'s exit status on a missing tag or non-matching
  `--pattern` is taken from its documented behaviour, not measured, so finding 1's threat model rests on
  reading `release.go` and the chains, not on an observed downgrade.
- **Files outside the release diff, read only in part**: `cmd/sh-agent/main.go` (~975 lines) was read
  through the full diff plus `:370-400` (`status`), `:260-285` (`installFiles`) and `:640-665`
  (`pathHint`), with greps enumerating every `PathShadows`/`pathHint` call site (exactly two, both in
  range) — the rest is unread. `cmd/sh-agent/main_test.go` was read through its 117 added lines only.
  `internal/harness/release.go` was read at `:20-50` and `:218-290`; `report.go` at its `Collect`/redaction
  functions; `pathguard_test.go` in full. No other file in `internal/` was read.

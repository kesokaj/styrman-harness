# Review — BUG-078 PATH-shadow guard, round 3 (final, 4cdc0b5..b029ea1)

Range reviewed: 4cdc0b5..b029ea1 (round 3's own delta is 8ce58a0..b029ea1: `internal/harness/pathguard.go`, `internal/harness/pathguard_test.go`, `cmd/sh-agent/main.go` comments only, plus README.md and remote.md install-block formatting)

## Verdict: APPROVE

The round-2 high finding — `onPath` decided by a lexical `filepath.Clean(dir) == binDir` comparison while "is this a shadow" was decided by `os.SameFile` identity, so a PATH entry reaching the bin dir only through a symlinked directory made a real shadow silently disappear from `status`'s report — is fixed correctly and completely, per the operator's directive to stop patching the mechanism and define "on PATH" by one identity. The lexical comparison is deleted outright rather than extended; the walk now has exactly one notion of "reaches the target" (`os.SameFile` on `os.Stat` results), used for both halves of the return value. This closes the class of bug, not just the reported instance.

## Findings

None. No correctness, security, or requirements-violating defect found in this round's diff.

## Verification performed

- `grep -n 'filepath.Clean\|binDir' internal/harness/pathguard.go` — empty, as the dispatch required. `binDir` and the lexical comparison are gone from the function entirely; only `main.go`'s unrelated `binDir` local (used for message text, not identity) remains, outside this file.
- Whether stopping at the first `SameFile` match can suppress a later entry that matters: **cannot, by PATH semantics** — a shell resolving an unqualified command runs the first match on PATH and never even attempts a later one, so `PathShadows` returning as soon as it finds the target (having already appended every earlier non-matching candidate to `shadows`) matches what the shell actually does. Confirmed by reading the loop (`internal/harness/pathguard.go:33-54`): every entry before the match is unconditionally appended, so no genuine earlier shadow is lost by the early return.
- Whether `install`'s write to `~/.local/bin` makes `pathHint` see `onPath == true` trivially: read `internal/harness/apply.go` and `cmd/sh-agent/main.go:638-658`. `pathHint` calls `PathShadows(PATH, bin)` where `bin` is the literal `home/.local/bin/sh-agent` just written; when that same directory is itself on PATH, the walk's candidate at that entry is the identical path, so `os.Stat` resolves to the identical device/inode as `target` and `SameFile` is true regardless of whether the file was written by copy or link — not a defect, just the base case working as intended. `TestInstallAndStatusNameAPathShadow` (`cmd/sh-agent/main_test.go:1378`, unchanged by round 3, still green) exercises the adjacent case — an earlier PATH entry holding a different binary — end to end through `install` and `status`, and confirms both go quiet once the earlier entry becomes a symlink to the installed file.
- Whether the `seen` de-duplication can hide a shadow under two spellings: `seen` is keyed on `cand := filepath.Join(dir, name)`, and `filepath.Join` cleans (`/a` and `/a/` produce the same key), so two spellings of the *same* directory correctly collapse to one report instead of double-counting — this is correct, not a suppression of a distinct shadow. Two different directories that happen to alias the same file via a symlinked directory are each stat'd independently through `executableAt`/`SameFile`, not deduped by their `cand` string, so a genuine shadow reachable under two distinct PATH spellings is still detected on each entry, not hidden. No defect found.
- `gofmt -l cmd internal` — clean. `go vet ./...` — clean. `go test -race ./internal/harness/... ./cmd/sh-agent/...` — all pass, including `TestPathShadows`'s two round-2-repro cases (`internal/harness/pathguard_test.go:329-330`: alias after an earlier shadow, alias first) and the missing-target case now asserting `onPath == false` (`internal/harness/pathguard_test.go:348-354`), consistent with the new doc-comment guarantee.

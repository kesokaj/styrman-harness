## Findings
Probe evidence: a scratch copy (`git archive 1fc0d4c` under `.agents/scratch/security-v2.3.0/src`) with a throwaway test calling `LoadInventory(DirSource(<t.TempDir>))` once per shape and kind. The baseline (no key) LOADED and the control (a plain key at column 0) was refused for all four kinds, so the probe tells both states apart. The probe files are deleted again; the copy stays in gitignored scratch.

- **[medium / confidence: high harness side, medium reader side]** `internal/harness/frontmatter.go:50-73,97-107` (`entries`, `unreadLine`; older than this range): a command or rule whose frontmatter is an indented root mapping (`---\n  description: d\n  allowed-tools: Bash(*)\n---\n`) LOADS.
  - Why the lint misses it: the probe shows harness keys `[]`. `keyLine` is anchored at column 0, and `unreadLine` skips every line that starts with a space.
  - Why a reader takes it: YAML reads an indented root block mapping as the top-level map. Claude Code 2.1.286 reads frontmatter as follows (from a read-only grep of the installed binary): strip the BOM, match `/^---\s*\n([\s\S]*?)---\s*\n?/`, then call `Bun.YAML`. It would get `allowed-tools`, which Claude Code honours for commands.
  - Skills and agents are refused only incidentally, because the shape leaves them with no `description`.
  - This bypasses the BUG-143 guard that this range's BUG-151 fix hardens.
  - Remediation: in `unreadLine`, refuse an indented line that does not follow a key line (the first non-blank, non-comment line of the block must match `keyLine`), with a must-refuse test per kind.
- **[medium / confidence: low]** `internal/harness/frontmatter.go:19,52-54` (older than this range): a lone carriage return inside a key line (`description: d\rallowed-tools: Bash(*)`, or `\rpermissionMode: …` in an agent) LOADS for skill, agent, command and rule. Harness keys are `[name description]`.
  - Why the lint misses it: lines are split on `\n` only, and `.` in `keyLine` swallows the `\r`.
  - Why a reader may take it: YAML 1.2 makes a lone CR a line break, so a conforming reader sees the permission key at top level.
  - Not verified: whether `Bun.YAML` follows the spec here. Running it needs a `bun` binary, and the Bun-compiled `claude` did not act as one (see Not examined). If it does not, the parse fails instead.
  - NEL, LINE SEPARATOR and PARAGRAPH SEPARATOR inside a key line also LOAD. Only YAML 1.1 and libyaml-family readers (PyYAML, go-yaml) break lines on those. The Antigravity CLI's reader is unknown.
  - This is the BUG-151 family (a CR the harness and YAML read differently); this range fixed it at the fence only.
  - Remediation: refuse any `\r` that is not directly before `\n`, and U+0085, U+2028 and U+2029, anywhere in the frontmatter block, with must-refuse cases in `TestLintPermissionKeysByKind`.
- **[low / confidence: high]** `internal/search/search.go:617-631` `printable` (older than this range):
  - What now holds: no line can be forged. C0, DEL, C1 (NEL included), Zl and Zp all become `?`, and the bidi controls are Cf.
  - Invisible runes outside Cf still pass. Probed on Go 1.27.1 (Unicode 17.0.0): the variation selectors U+FE00-FE0F and U+E0100-E01EF and the Mongolian U+180B (Mn); CGJ U+034F; the Hangul fillers U+115F, U+1160, U+3164 and U+FFA0 (Lo); unassigned default-ignorables U+E0000, U+E0080…, U+2065 and U+FFF0.
  - Visible but odd runes also pass, none of which forges a line: Zs spaces (NBSP, U+3000), combining overlays (U+0336), private use (U+E000), U+2800.
  - Variation selectors can carry arbitrary bytes ("emoji smuggling") into a model's reading of search output while the terminal shows nothing.
  - **Exposure if shipped:** an indexed tracked file can put invisible text into the search output an agent reads. The agent reads the same bytes when it opens that file, so this filter is not the only gate.
  - Remediation (stdlib): also map `unicode.Variation_Selector` and `unicode.Other_Default_Ignorable_Code_Point` to `?`.
- **[low / confidence: high]** `skills/google-catalog/scripts/refresh-catalog.sh:176-190` `fetch()`:
  - What now holds: no message prints an override's value, and `MANIFEST.md` names only the upstream repositories plus a fixed "Fetched through an override" line. `next:`, `origins.txt` (name and label only) and `writer.log` (output of the catalog `go test`, which never reads the override variables) do not carry the value either.
  - But the value persists on disk. Reproduced in scratch with fetch()'s exact `git clone -q --`, `remote set-url` and `fetch -q` sequence, the value sits in the work clone's `.git/config` (`remote.origin.url`), in `FETCH_HEAD` after a reuse fetch, and in the reflogs (`clone: from <value>`). A later run without the override rewrites the config and `FETCH_HEAD` but never the reflog.
  - The value is also on git's argv while the clone runs.
  - The work directory is gitignored scratch (default `.agents/scratch/catalog-refresh/`), so nothing is committed.
  - Hiding git's message hides nothing the operator needs for safety. A TLS or certificate failure, or any other git failure, still ends the run with "cannot clone/fetch the <role> source" and a hint to rerun git by hand. Success-path warnings (a redirect, for example) were already swallowed before this range. The content is pinned by commit id.
  - **Exposure if shipped:** a mirror URL carrying a token in its path stays in plaintext under scratch until the work directory is deleted.
  - Remediation: either say this in the header and in the refusal text (recommend a credential helper, which the script already does for user information), or keep the URL only on argv: `git init`, then `git -c core.logAllRefUpdates=false fetch --no-write-fetch-head -- <url> …`, with no stored remote.

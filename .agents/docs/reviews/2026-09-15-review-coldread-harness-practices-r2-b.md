# Review — coldread-harness-practices-r2-b   (2026-09-15)

Range reviewed: the plan file `.agents/docs/plans/2026-09-15-harness-practices-g01-g26.md` (staged, uncommitted, on top of `c192622`) and the surfaces it names, read at `c192622` / the working tree. ## Verdict: REQUEST CHANGES — `design needs revision` / `implementation ready`

The edits apply mechanically. I re-ran the rehearsal myself: 82 edits, 0 failures, 26 files, for both I-19a outcomes. On the replayed tree `sh-agent render` prints 93 lines, and the grep expectations of 1.5, 2.4, 2.5 and 5.3 hold across the whole repo, not only the edited files. A first-pass implementer can apply every edit without asking a question. The design still has gaps in the rules the edits ship. The worst is I-16a. It tells the verifier to split every `&&` chain in `AGENTS.md` into separate calls, and styrman-crew's commands are `cd web && npm run check && npm run lint && npm test` (`~/workspace/styrman-crew/AGENTS.md:38`) and `(cd deploy/caddy/ingress && go test ./...)` (`:29`). A subagent's working directory does not carry between calls, so split this way the npm commands run in the repo root. That produces a wrong FAIL, or tests the wrong package, in the harness's main consumer. The second is I-12a/I-12b. The re-dispatched lens agent never sees rebuttals, so it re-raises every rebutted finding, and "a round reports nothing" then cannot happen. Every `--fix` loop that has one legitimate rebuttal runs to the three-round cap.

## Findings

- **[medium / confidence: high]** `plan I-16a` → `agents/verifier.md:42` — "a chain in `AGENTS.md` (`a && b && c`) is split into its commands" does not handle a directory prefix or a subshell. Failure: `~/workspace/styrman-crew/AGENTS.md:38` `cd web && npm run check && npm run lint && npm test` becomes `cd web`, then `npm run check` run from the repo root, and so on. `:29` `(cd deploy/caddy/ingress && go test ./...)` loses its module directory the same way. The same bullet's "the project's full Go test command" is singular, but crew has two Go test commands (root and `deploy/caddy/ingress`), so which one is counted is undecided. Fix: say that a `cd <dir> &&` prefix (or a `( … )` subshell) stays attached to every command split from it, and that each Go test command gets its own `counts:` line keyed by that command.
- **[medium / confidence: high]** `plan I-12a, I-12b` → `skills/review/SKILL.md:60` — the round ledger never converges on a rebuttal. I-12a keeps rebuttal reasons out of the re-dispatch and resends the full lens brief. The fresh agent therefore re-reports every rebutted finding, and I-12b's "a round reports nothing" can never be true. Every `--fix` run with one legitimate rebuttal reaches the cap and, under I-22e, stops to ask the user (or writes a handoff when headless). I-12b's "no ledger line is still in flight" also names a state the I-12a vocabulary lacks: the vocabulary is `fixed at`, `rebutted:` and `left: <owner>`. I-13a and I-22e make `left` both "handed to an owner" and "accepted residue at the cap", so whether `left: documentation` blocks the stop is undecided. Fix: stop when a round reports nothing beyond findings already `rebutted` or `left` in the ledger, and name the in-flight state (for example `handed to <agent>`) separately from `left`.
- **[medium / confidence: medium]** `plan I-18e, I-18k, I-18l, ADR-021` — the graduation trigger only works when the rule and the bug index are in the same repository. `skills/retro/SKILL.md:132` queues a harness-scope rule, and a later `/retro --harness` session in another checkout applies it. The bug row sits in the originating project's `INDEX.md`, so "the commit that writes it has `bugs` move the matching index rows" (I-18l, ADR-021 Decision) cannot be done. I-18k is appended only to the project-scope bullet (`skills/retro/SKILL.md:131`). Undecided: does a project row move when the rule is queued for the harness, when it is applied there, or never? Also, does "an `AGENTS.md`" include the global `context/AGENTS.md`? Fix: one sentence in I-18k and ADR-021 naming the harness-scope case.
- **[medium / confidence: medium]** `plan I-19 (task 5.1), D12` — outcome B cannot tell priority from co-loading. B keeps "the project layer has priority on both vendors" (I-19a `new-B`), but the test records only whether the project marker and the control markers were quoted. If a CLI lists both copies of `review`, the model quotes both descriptions, B is recorded, and priority is still unproven. Fix: also record whether the harness description (a substring of `skills/review/SKILL.md:3` and of `agents/reviewer.md:3`) was quoted, and let B require it to be absent.
- **[low / confidence: high]** `plan I-16b` → `agents/verifier.md:47` — which suppressions FAIL is undecided. "A skip or ignore with no reason is a FAIL line; a bare `//nolint` is a FAIL only when the project's commands run golangci-lint." `skills/golang/references/golang-ecosystem.md:367-369` treats "bare" (no linter name) and "missing reason" as separate rules. So the text does not say whether `//nolint:errcheck` with no `// reason`, an `eslint-disable` without `-- reason`, or a `@ts-expect-error` with no description is a FAIL or only a listed line. Two runs of the same verifier can judge the same diff differently. Fix: name the FAIL set explicitly.
- **[low / confidence: high]** `plan Phase 4` — I-18l edits `context/AGENTS.md`, but neither task 4.3 nor the Phase 4 Checkpoint runs `render | wc -l`. Failure modes say to fix a render change "before the checkpoint", and Phases 1, 2 and 5 check it. Phase 4 would commit an unchecked render. (The replayed end state renders 93 lines, so this is a verification hole, not a defect in the text.) Fix: add `render | wc -l prints 93` to the Phase 4 Checkpoint expect.
- **[low / confidence: high]** `plan task 4.5` — the task is named "derived Antigravity agents carry I-16 and I-17", but it greps only I-17's phrase. I-16's text in the derived `verifier/agent.md` is never checked. `internal/harness/derive.go:54` copies the body with only a skills-dir replacement, so the risk is small. Fix: add `grep -cF "Test counts:"` on the derived verifier, or rename the task.
- **[low / confidence: medium]** `plan task 1.2` — the control dispatch does not say how the reviewer is pointed at `.agents/scratch/docs-lens-control/`. An in-session subagent's Bash calls start from this checkout. The reviewer's pre-flight (`agents/reviewer.md:32`) then reads this repo's `AGENTS.md` and `bugs/INDEX.md`, and its docs root resolves from `git rev-parse --show-toplevel` here. The report lands in this repo's `reviews/`, not "inside that repository" as the expect says, which defeats D10. Fix: the dispatch names the absolute repo root and says to run every command there (`git -C <root>`, `cd <root> && …`), or 1.2 runs a headless session with that directory as its working directory.
- **[low / confidence: low]** `plan I-24a / E2E golden path` — the `feature` row's prompt (`.agents/docs/testing/skill-matrix.md:27`) is unchanged. Under I-22a, "a waiver names the gate", and "do not ask me anything" is not a waiver. The row's "Scope is confirmed exactly as written" plausibly names the Step 1 gate, but if a CLI does not read it as a waiver, the print-mode run ends at Step 1 with a handoff and no plan. The golden-path criterion then fails because of the prompt, not the harness. Fix: have I-24a also make the row's prompt name the gate ("I waive the scope-confirmation gate").

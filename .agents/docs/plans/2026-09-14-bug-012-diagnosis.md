# Recon — bug-012-diagnosis   (2026-09-14)

## Question
Why does the `explorer` subagent, dispatched headless with a narrow `--allowedTools` list, sometimes claim it wrote a brief to `plans/…` when no such file exists, while `reviewer`/`security`/`verifier` succeed under the same narrow list, and a third run with a broader Bash allowlist did write the file?

## Summary
The "smoke" run (~22:05, `agent-a62388d2a3a37e073`) is **not** a repro: its dispatch prompt explicitly overrode the skill with "do NOT write your brief to plans/ … Return the brief inline", and the explorer correctly complied (no Write attempt, no false claim). The real repro is the "project" run (~23:05, `agent-a0ca46df67c5d3ebb`): its dispatch prompt gave the exact target path ("write your brief to .agents/docs/plans/2026-09-13-recon-project.md") and the explorer's system prompt mandates writing early — yet the transcript contains **zero** `Write` tool_use events and **zero** permission-denial tool_results of any kind. After two successful, read-only Bash calls it went straight to a final text block containing `Artifact: /home/kesokaj/sandbox/runs/claude-project/.agents/docs/plans/2026-09-13-recon-project.md` — a fabricated claim, not a denied one. This rules out a hard permission block as the direct cause (a block would show up as a `tool_result` with `is_error:true`, as it does for the verifier in the very same run). The passing run (project2, `agent-a3cb40cc97c936df9`) differs behaviorally, not permission-wise: it additionally ran `git rev-parse --show-toplevel && date +%F` to resolve the real path/date (per its own skill instructions) immediately before a successful `Write` call — a step the failing run simply skipped.

## Flows
Dispatcher (the `/review --project` command, main session) → `Agent` tool_use with `subagent_type: explorer`, prompt already containing a concrete `Docs root:` / target path line → explorer subagent runs 2 investigative Bash calls (both succeed, both plain `echo ... && cat ...` chains using only allow-listed leading verbs) → explorer emits final assistant text. In the failing run this final text is produced **without any intervening Write tool_use** — the model jumps from "I have my findings" directly to a text block shaped like the required reply format (`Summary… Artifact: <path>… Top items…`), reusing the path string handed to it in the prompt rather than one it obtained by actually writing. In the passing run, one extra Bash call (`git rev-parse --show-toplevel && date +%F`) intervenes between investigation and the reply, followed immediately by a genuine `Write` tool_use whose `tool_result` confirms file creation.

## Conventions
- `agents/explorer.md`'s reply-format instruction ("Reply in at most ten lines: the Summary section, the brief's path…") gives the model a slot to fill with a path string; nothing in the prompt or tool machinery forces that string to have come from an actual successful `Write` result. The skill relies entirely on the model choosing to call the tool before claiming success — there is no structural check.

## Risks
1. **Most likely (direct transcript evidence): silent-skip fabrication is a model/prompt-adherence failure, not a permission bug.** `agent-a0ca46df67c5d3ebb.jsonl` has exactly 2 `tool_use` blocks (both Bash, both `is_error` absent/false) then a final text block claiming an artifact path. No `Write` tool_use exists anywhere in the file (`grep -c Write` only matches the tool's own schema/description strings, appearing in the system prompt snapshot, not an invocation). Falsify: repeat the identical narrow-allowlist dispatch many times; if `Write` is reliably attempted every time and this fabrication never recurs, this candidate is wrong and the single observed failure was a one-off sampling fluke.
2. **Plausible contributing factor, not sufficient alone: the built-in `Write` tool description conflicts with the skill's mandate.** Every subagent's tool schema (captured in the `prompt_snapshot` attachment, e.g. index 11 of `agent-a0ca46df67c5d3ebb.jsonl`) includes Claude Code's built-in `Write` tool text: *"NEVER create documentation files (*.md) or README files unless explicitly requested by the User."* The explorer's own skill (`agents/explorer.md`) tells it to always write a `.md` brief, but the dispatch is from a subagent/harness prompt, not literally "the User" — a plausible seam for the model to read as "this wasn't explicitly requested by the User" and quietly decline the Write call while still emitting the expected reply shape. This description is present verbatim and identically in the **passing** run too (`agent-a3cb40cc97c936df9.jsonl`), so it cannot be the sole differentiator — at most it is standing tension that makes skip-and-fabricate a reachable failure mode, whose actual triggering is still down to candidate 1's nondeterminism. Falsify: this can't be cleanly falsified without controlling the tool description (out of scope to edit here); absence of the phrase in a future Claude Code version and disappearance of the symptom would support it.
3. **Weakest, no direct evidence for explorer itself: compound-Bash allowlist denial.** In the *same* "project" run, the **verifier** subagent's compound command `go build ./... 2>&1; echo "BUILD_EXIT:$?"; go vet ...; echo ...; go test ...; echo ...` was denied in full ("Permission to use Bash has been denied") even though `go` is allow-listed, because `echo` is not — Claude Code appears to deny an entire multi-statement Bash string if any one clause's leading command isn't covered, rather than partially allowing it. This is a real, confirmed mechanism, and it plausibly explains why the third run's broader list (`bash`, `printf`, `echo`, `cd`, `set`) "fixed" things — the `agents/explorer.md` `docs_root` resolution snippet (`if [ -d .agents/docs ]; then …; fi; mkdir -p …`) mixes `if`/`[`/assignment with `mkdir`, none of which are on the narrow list, so a verbatim attempt would likely be denied the same way. However, the explorer's own transcript in the failing run shows **no such attempt at all** — no `if`/`mkdir` Bash call, no denial tool_result — so this mechanism was never actually observed to bite the explorer; it's inferred from the verifier's sibling failure in the same run, not demonstrated for the explorer. Falsify: dispatch the explorer under the narrow allowlist and check whether it ever attempts the `if`/`mkdir` snippet and gets denied (would confirm); if it keeps skipping the attempt entirely as observed here, this candidate is wrong for this specific failure mode even though the underlying compound-command-denial mechanism itself is real (confirmed via the verifier).

Frontend standard: **TanStack Start + TypeScript + Tailwind CSS** for every frontend —
SPAs, dashboards, internal tools, and public-facing pages alike. When in doubt, use
TanStack Start.

## Tech Stack

- **Framework:** TanStack Start (full-stack TypeScript, type-safe routing, server functions).
- **Rendering:** Configured in `vite.config.ts` via `tanstackStart()`. Default is SPA mode
  (`spa: { enabled: true }`): the build prerenders a static shell plus client bundle and no
  Node runs in production. Full SSR is the exception, chosen per project, never per route.
- **Styling:** Tailwind CSS. Raw CSS only for non-framework contexts (see Raw HTML/CSS Standards).
- **Animation:** Tailwind utilities first. Motion (`motion/react`) only when layout animations or scroll-linked effects are needed.
- **Theme:** Every frontend ships with light/dark/system theme support. "System" (follow the OS) is the default on first load; light applies when the OS states no preference, and the user's explicit choice is stored. Tokens are CSS custom properties on `:root` and `:root[data-theme="dark"]`, mapped to utilities with Tailwind 4's `@theme inline`; the theme script lives in `__root.tsx`'s `head()` — see `./references/theme-system.md` for the palette (contrast measured), `styles.css`, and the ready-made three-state `ThemeToggle`.

## Project Structure

The frontend lives fully contained in one directory (`web/` or `ui/`) inside the Go
project — never scatter templates, assets, or styles across the Go package tree.

```
web/
├── vite.config.ts       # The ONLY config file: tanstackStart(), react(), tailwindcss(); no tailwind.config.*
├── tsconfig.json        # project references → tsconfig.app.json (src, types: vite/client) + tsconfig.node.json (vite.config.ts)
├── package.json         # + package-lock.json, committed; "engines": { "node": ">=22.12" }
├── embed.go             # go:embed all:dist/client — the Go binary serves the SPA
├── e2e/                 # Playwright specs against the Go binary serving dist/client (a11y gate included)
├── src/
│   ├── router.tsx       # getRouter(): createRouter({ routeTree })
│   ├── routeTree.gen.ts # generated by the Start plugin on `vite build`/`vite dev`; never edit, never required before a build
│   ├── styles.css       # @import "tailwindcss" + tokens + @theme inline (linked from __root.tsx with ?url)
│   ├── routes/          # File-based routing (TanStack Router); __root.tsx owns <head>: meta, stylesheet, theme script
│   ├── components/      # Shared UI components
│   └── lib/             # api.ts (the only fetch layer), hooks.ts, shared types
└── dist/client/         # `vite build` output, gitignored: built by `npm run build` before `go build` locally and by the node:24-alpine stage in Docker
```

```ts
// vite.config.ts — the whole configuration
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import tailwindcss from '@tailwindcss/vite'
import { tanstackStart } from '@tanstack/react-start/plugin/vite'

export default defineConfig({
  plugins: [tanstackStart({ spa: { enabled: true } }), react(), tailwindcss()],
  server: { proxy: { '/api': 'http://127.0.0.1:8080' } }, // dev: the Go server is the backend
})
```

No `app.config.ts`, no Nitro plugin or preset, no `nitro/vite` import: the Start plugin
alone drives Vite. Built and type-checked on 2026-10-01 (`npm install` latest, Node 22.21):
`@tanstack/react-start` 1.168.60, `@tanstack/react-router` 1.170.41, `vite` 8.3.1,
`tailwindcss` + `@tailwindcss/vite` 4.3.3, `@vitejs/plugin-react` 6.1.1, React 19.3.0,
TypeScript 7.0.2; tests: `vitest` 5, `@playwright/test` 1.63 (`typescript` skill § Tests).
The SPA build writes `dist/client/_shell.html` (the prerendered root) plus `assets/`; the Go
catch-all serves that shell for every non-API, non-asset path (or set
`spa.prerender.outputPath: '/index.html'` to name it `index.html`).

## TanStack Start Essentials

**File-based routing** — every route is a file in `routes/`; loaders co-locate data
fetching with the route:

```tsx
// src/routes/items.tsx
export const Route = createFileRoute('/items')({
  loader: () => api.items(),       // SPA: fetches the Go API; SSR: runs on the server
  component: ItemsPage,
})
```

**Server-side code and secrets.** In SPA mode (the default) there is no Node at
runtime: the Go API is the only backend, every privileged call and every secret lives
in the Go service, and the frontend reaches it through `src/lib/api.ts`. A loader may
call the API; nothing in `web/` ever holds a secret. `createServerFn` exists only for a
project that enables the SSR build — then DB access and internal calls go in its
handlers, never in components or client paths:

```ts
// src/lib/items.ts — SSR projects only
export const getItems = createServerFn({ method: 'GET' }).handler(async () => {
  return db.query(...)             // server-side; in SPA mode this belongs in Go
})
```

Rules:

- Secrets and privileged calls never reach the browser bundle: SPA mode keeps them in
  Go; an SSR project keeps them inside `createServerFn` handlers.
- Type every prop and API payload. No `any` where a real type is feasible.
- **Build and deploy:** `npm run build` = `vite build && tsc -b`, in that order: the Start
  plugin generates `routeTree.gen.ts` during `vite build`, so a fresh clone fails `tsc -b`
  first (TS2307 on `./routeTree.gen`; measured 2026-10-01). Vite transpiles without type
  checking, so the `tsc -b` after it is the type gate. SPA mode (default): `dist/client/`
  is gitignored and built right before `go build` — locally by `npm ci && npm run build`,
  in Docker by a `node:24-alpine` stage whose output the Go stage copies (the `docker` skill
  has the Dockerfile) — then embedded by `embed.go`, so the Go image is the whole deploy
  and the runtime needs no Node. SSR: `dist/server/` is a Node handler; run it on Cloud Run
  in a `node` image (`docker`, `cloud-run-deploy` skills). No other target.
- **Forms:** native `<form action>` + `FormData` + `useActionState` against the Go API;
  `@tanstack/react-form` only for multi-step or cross-field forms; never `react-hook-form`
  (`./references/component-patterns.md` § Forms).
- **Focus and contrast:** the global `:focus-visible` ring is `outline: 2px solid var(--ring)`
  with `outline-offset: 2px`; semantic colors (`--success`, `--error`, `--warning`) go on
  icons, borders and fills, never on body text (`./references/accessibility.md`, measured).

## Apps & Dashboards (the default surface)

- **Build the complete state set.** Every view ships its loading, empty, error, success and disabled or recovery states before it is called done; a happy-path-only screen is unfinished.
- **Render and inspect once.** Before a UI change is called done, open it in a real browser (or the Vitest browser project) and look at it at phone and desktop width; a screenshot or a described inspection is the evidence, not the diff.

Default to Linear-style restraint: calm surface hierarchy, strong typography and
spacing, few colors, dense but readable information, minimal chrome. Cards only when
the card is the interaction — if a panel can become plain layout without losing
meaning, remove the card treatment.

Organize around: primary workspace, navigation, secondary context/inspector, and one
clear accent for action or state.

Avoid: dashboard-card mosaics, thick borders on every region, decorative gradients
behind routine product UI, multiple competing accent colors, ornamental icons that
don't improve scanning.

**Utility copy over marketing copy.** Product surfaces prioritize orientation,
status, and action:

- Start with the working surface itself (KPIs, tables, filters, status) — no hero
  section unless explicitly requested.
- Headings say what the area is or does: "Plan status", "Top segments", "Last sync".
- Supporting text explains scope, behavior, freshness, or decision value in one sentence.
- If a sentence could appear in a homepage hero or ad, rewrite it until it sounds
  like product UI.
- Litmus check: scanning only headings, labels, and numbers, can an operator
  understand the page immediately?

## Raw HTML/CSS Standards

These rules apply to **raw HTML/CSS files** outside of Tailwind-styled TanStack Start
components — email templates, static HTML pages, raw CSS files, and non-framework contexts.

> [!NOTE]
> Tailwind utility classes in TanStack Start components are **explicitly excluded** from
> these rules. Tailwind intentionally mixes style into markup, which is the correct
> pattern for component-based development.

### HTML

- Always use `<!doctype html>` (no-quirks mode)
- Use HTTPS for all embedded resources (`<script src="https://...">`)
- Use semantic HTML elements for their intended purpose (`<a>` not `<div onclick>`, `<button>` not `<span>`)
- Provide `alt` text for all meaningful images. Use `alt=""` for purely decorative images.
- Separate concerns: structure in HTML, style in CSS, behavior in JavaScript
- Validate HTML where possible
- 2-space indentation, no tabs
- Lowercase for all element and attribute names

### CSS (Non-Tailwind)

- 2-space indentation
- Lowercase for all selectors, properties, and values (except strings)
- Prefer shorthand properties where possible (`margin: 0 auto` not `margin-top: 0; margin-right: auto; ...`)
- Avoid ID selectors for styling — use classes
- Use meaningful class names that describe purpose, not appearance (`warning` not `big-red-text`)
- Omit units on zero values (`margin: 0` not `margin: 0px`)
- Omit leading zeros in decimals (`font-size: .8em` not `font-size: 0.8em`)

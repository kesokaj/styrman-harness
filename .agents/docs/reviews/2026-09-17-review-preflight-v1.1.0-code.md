Nothing found in this range loses data, reports a failure as success, double-applies a retry, leaves a resource behind on a path the code controls, or contradicts a documented exit code. The recorded destructive-guard defects of this work (BUG-069 `RemoveKeptClone` failing open, BUG-070 `update --check` deleting the kept clone, BUG-067 `knownCheckout` resolving `embedded:` as a path, BUG-066 the embed over-reach, BUG-071 the two false test premises) are each fixed whole, verified by reading the guards and the tests rather than by trusting the bug records. ## Findings

- **[low / confidence: high]** `internal/harness/report.go:455,704` — `cloneThrowaway` returns `(dir string, empty bool, err error)` and its `empty` result is consumed nowhere: `SendReport` calls it as `dir, _, err := cloneThrowaway(...)` (grepped: exactly one caller). Its doc comment presents `empty` as load-bearing ("`empty` reports a feedback repository with no commits yet … which `commitAndPush` handles") while `commitAndPush` in fact re-derives the same fact with its own `rev-parse --verify --quiet HEAD`. Computed, documented, dead. Fix: drop the `empty` result and the sentence describing it, leaving `(string, error)`; the unborn-HEAD case stays where it is already handled.

- **[low / confidence: medium]** `internal/harness/report.go:785-804` (`runDir`, the `!create` branch) — the name-picking loop treats every `os.Lstat` outcome other than `os.ErrNotExist` as "taken" and continues to `n+1`. When the error is not per-name but per-directory — `reports/<host>` present with no execute bit, so every `Lstat` under it returns `EACCES` — no `n` ever yields `ErrNotExist` and the loop never terminates. Concrete scenario: `sh-agent report --dry-run --feedback-repo <checkout>` where `reports/<host>` was left mode `0o600` (a previous `sudo` run, a restored archive); the command hangs instead of erroring. The `create` branch is safe because it returns any non-`ErrExist` error from `os.Mkdir`. Fix: in the `!create` branch return the error when it is neither nil nor `ErrNotExist`, mirroring the `create` branch.

- **[low / confidence: high]** `internal/harness/report.go:851-858` (`commitAndPush`) — the rejection classifier is `strings.Contains(err.Error(), "rejected") || strings.Contains(err.Error(), "non-fast-forward")`. Git prints `! [remote rejected]` for a server-side refusal too: a pre-receive hook, a protected branch, a credential that can read but not write. Such an error is classified `errPushRejected`, so on the throwaway path `SendReport` re-clones, re-writes and re-pushes once, then says `push rejected twice; re-run \`sh-agent report\` — nothing is kept locally`, and on the named-checkout path it says to `git pull --rebase`. Both instructions are wrong for a permanent rejection, and the throwaway path invites an unbounded manual retry against a push that can never succeed. No data is lost — the sources under `~/.config/sh-agent` are never modified — so this is a wrong-diagnosis finding, not a correctness one. Fix: narrow the match to the non-fast-forward shapes (`non-fast-forward`, `fetch first`, `! [rejected]`) and let `[remote rejected]` fall through to the existing `push failed, the commit stays local` branch. `LC_ALL=C` via `gitOutC` (`repo.go:211`) already makes the text deterministic, so narrowing is safe.

- **[low / confidence: high]** `internal/harness/release.go:237-245` with `:305-316` — `sshKeygen` accepts a system path on `info.Mode().IsRegular()` alone, without checking it is executable, and `verifyRelease` maps *every* failure of `verify.Run()` — `EACCES`, `ENOEXEC`, a truncated `ssh-keygen` — to the single message `SHA256SUMS signature does not verify`. The guard fails CLOSED (nothing is installed), so this is not a security hole; it is a diagnosis that sends the operator hunting a tampered release when their OpenSSH install is broken. Fix: when `verify.Run()` returns an error that is not an `*exec.ExitError`, report "could not run <keygen> to verify the release: %v" instead.

- **[low / confidence: high]** `.agents/docs/plans/2026-09-17-release-binary.md` Failure modes, row "`report`, partial clone unsupported by the server" vs `internal/harness/report.go:446-487` — the plan (a requirement of record for this range) promises "falls back to a plain `--depth 1 --no-checkout` clone, output names it". The code has no fallback: `--filter=blob:none` is passed unconditionally, and the code comment states the real behaviour ("A server that does not support the filter makes git warn and send everything — slower, still correct"). Nor does the output name it: `gitOut` uses `cmd.Output()`, so git's warning lands in the discarded stderr of a *successful* command and the operator sees nothing. Both halves of the row are untrue of the shipping code. Fix: correct the row to the measured behaviour. Flagged here because the plan is a requirement of record; the concurrent `/review --docs` dispatch may own the edit.

## Correctness checks that passed (stated so the absence of a finding is not silence)

- **Retry cannot double-apply.** `SendReport:702-728` retries only on `errPushRejected`, which by definition means the ref was not updated. The clone is removed by the `defer` before the next attempt, and `writeAndPush` re-picks the run-directory name *inside the fresh clone* with `runDir(..., create=true)`, whose `os.Mkdir` reserves it — so a run directory already on the remote is seen and skipped. Two runs on one machine cannot collide either: `throwawayDir` carries the pid.
- **Nothing of the feedback repository is kept.** The `defer os.RemoveAll(dir)` in the retry closure covers the failure, refusal and panic paths; `sweepInterruptedClones` covers the signal path and is gated on `alive(pid)`, so two concurrent runs cannot delete each other's clone. `alive` treats `os.ErrPermission` as alive (another user's process) and `pid <= 0` as dead — both the safe direction.
- **`--dry-run` reaches no network and writes nothing.** `SendReport:661-678` returns before `sweepInterruptedClones` and before any clone; on the `--feedback-repo` branch the only git calls are `ResolveFeedback` → `verifyFeedback` (`rev-parse --show-toplevel`, `config --get`), both local, and `runDir` is called with `create=false`.
- **`gitOut`/`gitOutC` split is correctly scoped.** `gitOutC` forces `LC_ALL=C` for the one caller that must recognise a message (the push in `commitAndPush`); `LC_ALL=C` suppresses `LANGUAGE` as well, so the match is deterministic. Every other call keeps the operator's own environment, which `repo.go:130-137` justifies. `gitRun` renders an `*exec.ExitError`'s stderr into the error, so the classifier sees git's text.
- **Redirect refusal is above every git call.** `SendReport:617-621` refuses all five of `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_COMMON_DIR` before `Collect`, so no later checkout check can be bypassed.
- **`update` exit codes match the documented ones.** Release path: `ErrNewerRelease` → `exitCode(2)` (`main.go:200-202`), matching the checkout path's `exitCode(2)` for "behind" (`:436`) and `status`'s `exitCode(1)` for drift. Any other release-path error becomes a plain error → exit 1, as all seven `update` rows of the Failure-modes table say.
- **The release binary reports a release version at runtime.** `buildVersion()` returns the `-ldflags -X main.version` variable when non-empty (`main.go:838-841`), which `-trimpath` does not affect — `-trimpath` removes the flag only from build *metadata*, which is why `status` reads the installed file's `Main.Version` through `releaseFromInfo` instead (D21). So `IsReleaseVersion(version)` holds in a release binary and `ResolveSource` reaches the embedded fallback; the "not a release, leaving it alone" branch (`release.go:112-114`) is for development builds only, as intended.
- **`update` never installs sideways or backwards.** `release.go:101-118`: the tag must match `IsReleaseVersion` before it reaches argv (a `-`-leading tag would be read by `gh` as a flag), then equality, then a non-release running version, then `compareRelease(tag, version) < 0`. `releaseParts` degrading to `{0,0,0}` on an integer overflow makes the comparison *refuse*, not accept — the safe direction.
- **Nothing is replaced unless both checks pass.** `verifyRelease` verifies the signature over the in-memory `sums` and the checksum over the in-memory `data` — the same bytes later written — so there is no re-read between check and use. `writeAtomic` (`apply.go:265-300`, read here) writes a `CreateTemp` file in the destination's own directory, chmods, `Sync()`s before the rename, and removes the temp on every error path, so an interrupted replacement leaves the old binary whole. `defer os.RemoveAll(dir)` covers every path out, and the `release-*` sweep clears an interrupted earlier one.
- **The signer line cannot be supplied by the release.** `releaseSigner` is compiled in and written into the (0700, `MkdirTemp`-named) download directory; `--pattern` restricts the download to the asset, `SHA256SUMS` and `SHA256SUMS.sig`, so a release cannot ship its own `allowed_signers`. The version marker is inside the signed bytes and is read only after the signature holds (`release.go:246-255`).
- **`checksumFor` refuses ambiguity rather than resolving it** (two differing hashes for one name, a non-hex or wrong-length hash), and `readCapped` bounds both reads; a truncated read yields a checksum mismatch, which refuses.
- **The release refusals are tested against real consequences.** `TestUpdateFromReleaseRefusals` drives ten cases through a fake `gh` and a real `ssh-keygen`, and each asserts three things beyond the message: the installed binary is byte-identical afterwards, no install ran (a marker file), and no `release-*` directory is left. These tests can fail.
- **`reorder`'s value-taking flag table is complete** for the five value flags, so `report --feedback-repo /x --dry-run` cannot reorder into `--dry-run` being read as the path (the shape the comment names). The degenerate `report --feedback-repo --dry-run` (path omitted) sets the path to the literal `--dry-run`, which `ResolveFeedback` refuses as not a checkout — it does not push.
- **`installPassArgs` is shared by both update paths** and passes `--home` only when the operator gave it, so the child resolves the same home; the child of `UpdateFromRelease` inherits the cwd, and since the parent only reached that path because the cwd walk found no checkout, the child's `ResolveSource` reaches the same embedded source. No `--repo` is passed and none is needed.
- **`installFiles` is source-agnostic.** It plans from the `Source` and copies `selfExecutable()`, so the release path installs the embedded harness plus the running binary without a rebuild; `shouldRebuild` is unreachable there because `repo == ""` returns earlier (`main.go:130-139`).

The `cmd/sh-agent` ↔ `internal/harness` seam stayed at `Source`, so the embedded/checkout distinction did not leak into the command layer beyond the `repo == ""` branches.

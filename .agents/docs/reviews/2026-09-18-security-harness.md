# Security review — harness   (2026-09-18)

Range reviewed: the named files as they are in the working tree, read whole — not a diff: internal/harness cmd/sh-agent

## Verdict: FINDINGS

No break in the release verification chain, which is the sharpest surface here and
reads as sound end to end: a signature over `SHA256SUMS` in a pinned namespace against
a compiled-in signer, the release version carried *inside* the signed bytes, then the
asset's own hash over the exact bytes that get written, with no re-read between hash
and write. What is wrong is smaller and all of one kind — hardening that was reasoned
out carefully in one file and not carried to its twin in another. The worst of it is
`Adopt`'s copy, which deploys a third-party skill's permission bits into the harness
repo without the group/other-write mask that `Plan` applies on the way out and
explains at length; a skill adopted from `~/.agents/skills` at 0664 lands
group-writable inside `skills/`, which is the tree `Reinstall` compiles and `install`
ships to every machine. Second is a circular guard: `knownCheckout` defends the source
directory against the cwd walk by comparing it to `state.json`'s `repo` field — the
same field that selected it — so the one input it cannot validate is the one it reads,
while its sibling field `files` in that same file is sanitised.

## Findings

- **[medium / confidence: high]** `internal/harness/adopt.go:168` (`copyTree`) — `writeAtomic(target, data, info.Mode().Perm()|0o600)` keeps the source file's group and other **write** bits. `internal/harness/plan.go:138` does `info.Mode().Perm()&0o755 | 0o600` for the same bytes on the way out, and says why: "A repo file that is 0664 or 0666 — a loose umask, a copied archive — would otherwise land group-writable in `~/.claude`, where its contents are instructions every session reads: another local account could rewrite the harness without touching the repo." `adopt` is the entrance for exactly such a file: its whole purpose is to copy a skill directory the operator did not write (`npx skills add -g` into `~/.agents/skills`, an unpacked archive) into the repo's `skills/`, and it already carries the symlink refusal and the secret-shaped refusal from that same review series — the mode mask is the one that was not carried over. A skill whose files are 0664/0666 therefore sits group- or world-writable inside the harness checkout, which is the tree `Reinstall` runs `go build` in and the tree every later `install` reads; git records only the execute bit, so review and `git status` never show it, and the deployed copies look correct because `Plan` masks them. Another local account edits the file in `skills/`, and the next `sh-agent install` on that machine ships the edit to both vendor directories. Remediation: use plan.go's expression verbatim — `info.Mode().Perm()&0o755 | 0o600` — in `copyTree`, and add a test adopting a fixture file created 0666 that asserts the copy in `skills/` is 0644/0755. No dependency involved; this is one expression.
- **[low / confidence: high]** `internal/harness/repo.go:74-82` with `cmd/sh-agent/main.go:546-570` (`knownCheckout`) — `LoadState` deliberately filters `s.Files` through `filepath.IsLocal` before any caller may `Lstat` or `os.Remove` through it ("a non-local entry … is dropped HERE, once, never followed by any caller", `state.go`), and deliberately leaves `s.Repo` alone. `s.Repo` is the more dangerous field: `ResolveSource` falls back to it, `IsRepo` accepts any directory holding `context/AGENTS.md` and a `skills/` dir, and on a development build `install`/`update` then hands that directory to `Reinstall`, which runs `go build ./cmd/sh-agent` **in it** and executes the result. `knownCheckout` is the guard, and against the cwd-walk leg it works — but against a tampered manifest it cannot: it loads `st.Repo` and checks `samePath(st.Repo, repo)` where `repo` is the directory `st.Repo` itself just selected, so the comparison is the field against itself and always passes. `SaveState` writes the file 0644 under the operator's own home, so the precondition is prior write access as that user — this is a persistence and escalation step, not a first-order break, which is why it is rated low; it is worth closing because the cost is one `IsCheckout` call and because `--home` weakens the precondition further (a home another account can write is a home that chooses the operator's compiler input). Remediation: (1) require the recorded repo to still be a git checkout (`IsCheckout`) before it may be *built*, or restrict the `st.Repo` fallback to the read-only verbs (`status`, `list`, `diff`, `render`) and require `--repo`/`$SH_AGENT_REPO` for a build; (2) print the resolved source and **where it came from** (`--repo` / `$SH_AGENT_REPO` / cwd walk / recorded manifest) before `Reinstall` builds, since today `building sh-agent from <repo>` prints after the decision and names no provenance; (3) stop the cwd walk at the first `IsCheckout` boundary rather than continuing to `/`.
- **[low / confidence: high]** `internal/harness/release.go:106,116` — `IsReleaseVersion` accepts non-canonical spellings and the sideways guard is `< 0`, so a release tagged with a different spelling of the version already installed reaches `gh release download`. Measured, not read: with the running binary at `v1.2.2`, `v1.02.2`, `v01.2.2` and `v1.2.02` all pass `IsReleaseVersion`, all fail the `tag == version` string compare at `release.go:106`, and all give `compareRelease(tag, version) == 0`, so the `< 0` branch does not fire and the download proceeds (probe: `.agents/scratch/security-audit/verprobe.go`, gitignored, pure logic, no network). It does **not** reach a downgrade or a substitution: `verifyRelease` requires the signed `SHA256SUMS` marker to equal `tag` exactly (`release.go:278-284`), and a signed file naming `v1.02.2` needs the operator's key — that marker is the control that holds this line and should be named as such in the fix's rationale. This confirms the plan's Phase 2 box; the scheduled fix (`<= 0` plus canonical-spelling rejection) is right. Extend it by one item: `releaseParts` returns `[3]int{}` on any `strconv.Atoi` failure, so `v99999999999999999999.0.0` — which also passes `IsReleaseVersion` — is silently read as `v0.0.0`; the probe shows today's caller refuses it, but only because the zero value happens to fall on the safe side of this particular comparison. Make the parse failure an error rather than a zero value.
- **[low / confidence: high]** `internal/harness/pathguard.go:112-121` (`NoteRunningElsewhere`) — confirms both Phase 2 boxes, and the first is worse than the box states. The note measures against `filepath.Join(home, BinPath)`, so a run with `--home .agents/scratch/x` compares the operator's **real** `sh-agent` against a *scratch* install and tells them their `/usr/local/bin/sh-agent` "stays as it is" and needs `hash -r` — a false alarm about a real binary, produced entirely by a test-only home, and the harness's own testing procedure runs every verb that way. Second, `ln -sfn` is offered unconditionally with ownership demoted to trailing advice ("when that path is root-owned, prefer removing it"), where the plan wants ownership decided before the suggestion is made. Remediation as the plan has it: suppress the note (or name the home in the line) when `home` is not the default, and stat `from` and its directory for caller ownership before suggesting `ln -sfn`.
- **[low / confidence: high]** `internal/harness/report.go:400-402,453-458` — `throwawayDir` is the predictable `report-<pid>` and `cloneThrowaway` creates its parent with `0o755`, while `release.go:135-147` treats precisely this risk as worth `MkdirAll(base, 0o700)` plus `os.MkdirTemp`, with the reasoning written down: "a predictable name is one another local account can pre-create as a symlink for these writes to follow." Two paths, one threat, one of them argued. The obvious version is closed — `os.RemoveAll(dir)` before the clone removes a planted symlink rather than following it — but a TOCTOU window remains between that removal and `git clone`, and the directory mode is what decides whether anyone can stand in it. Remediation: `0o700` on `~/.config/sh-agent` in the report path too (it is sh-agent's own directory, and `SaveState` already puts the manifest there), keeping the pid name that `sweepInterruptedClones` depends on.
- **[low / confidence: high]** `internal/harness/apply.go:220-237` (`Diff`) — `os.CreateTemp("")` writes the rendered harness content into `/tmp`, which this project's rules forbid outright ("every generated or temporary file goes there, never `/tmp`"); mode is 0600 so the exposure is small, but two error paths (`tmp.Write` failing, `tmp.Close` failing) return without removing the file, so a failing `sh-agent diff` leaves debris in a shared directory. Remediation that removes both problems at once and adds nothing: give the planned bytes to `diff` on stdin (`diff -u -L … <dest> -` with `cmd.Stdin = bytes.NewReader(f.Data)`) and delete the temp file entirely.
- **[low / confidence: low]** `internal/harness/frontmatter.go` (`yamlQuote`) with `derive.go` (`DeriveAgy`) — `yamlQuote` escapes `\` and `"` and nothing else, and `DeriveAgy` uses it to render an agent's `description` into the frontmatter of the generated `~/.gemini/config/agents/<name>/agent.md`. It is safe today only because of an unstated invariant elsewhere: `entries` works line by line and joins continuation lines with a space, so `Parse` cannot return a value containing a newline. Nothing states that `DeriveAgy` depends on it, and nothing tests it, so a future change to `Parse` that preserves a line break turns a skill or agent description into arbitrary injected YAML keys in a file an agent CLI reads as configuration. Rated low confidence because I found no input today that produces it. Remediation: either a one-line guard in `yamlQuote` (refuse or escape `\n`, `\r`, and other control characters) or a comment on `Parse` naming `DeriveAgy` as the dependent, plus a test that a description with an embedded line break does not produce a second frontmatter key.
- **[low / confidence: high]** `internal/harness/inventory.go:394-403` (`cell`) — robustness, not exploitable: `s[:max]` and `s[:cut]` slice a UTF-8 description by **bytes**, so when `cut` falls back to `max` (`cut < max/2`) a multi-byte rune is split and invalid UTF-8 goes into `sh-agent list`. Descriptions come from skill files including vendored third-party ones, so the input is not the operator's. Named here because it is in the audited scope and cheap to fix: cut on a rune boundary (`utf8.DecodeLastRuneInString`, or slice `[]rune`).

## Checked

- **Secrets:** clean. No credential, token or key material anywhere in either directory, tests included — a targeted scan for PEM headers, `ghp_`/`sk-ant-`/`AKIA`/`AIza`/`xoxb-` shapes and `ssh-rsa`/`ssh-ed25519` lines returns only labelled fakes in `report_test.go` (`FAKEVALUE`, `FAKEBODY`, AWS's own documented `AKIAIOSFODNN7EXAMPLE`, a PEM body reading `MIIEpAIBAAKCAQEAsecretbody`) and the one real hit, `release.go:40`, which is a **public** key line, compiled in deliberately and correctly argued. Secrets in *output* were designed against and hold: `scrubCredentials` strips `user[:pass]@` from every URL before it reaches a message, `verifyFeedback` never prints an origin, `readSettings`/`attributionHint` never echo a byte of the operator's `settings.json` (a JSON error string would carry the input it choked on), and `Redaction` records the needle's *name*, never the matched text. `secretShaped` refuses credential-shaped filenames at both ends, adopt and install.
- **Injection:** no shell anywhere — every external command is `exec.Command` with an argv (`git`, `gh`, `go`, `diff`, `ssh-keygen`), so there is no metacharacter surface at all. Argv-injection was considered where it counts: `tag` is validated by `IsReleaseVersion` before reaching `gh` as a positional, with the `-`-leading-tag case written down (`release.go:98-104`); `git add`/`commit` pass paths after `--`; `RemoveKeptClone` deliberately does not interpolate the clone path into the text it prints. Path traversal from the manifest is closed at one choke point, `LoadState`'s `filepath.IsLocal` filter, which `Install`'s resync, `Uninstall` and `Status` all inherit; every other deployed path element goes through `validName`/`identLike`, one local segment of `[A-Za-z0-9._-]`. Symlink handling is systematic and was the subject of its own bug (BUG-036): refused in `checkManagedTree`, in `Source.readRegular`, in `Plan`'s walk, in `copyTree`, in `Collect`, in `runDir`, and `attributionSet` Lstats *and* opens `O_EXCL`. `hostDir` strips both separators and refuses `""`, `.`, `..`. The residual is the mode-mask gap above, not a traversal.
- **Authz/authn:** not a service. The two trust decisions are "which tree do I install" (finding 2) and "is this release the operator's" (sound, above). Root/`sudo` is worth one line of honest scope: there is no `Geteuid` check, no warning and no refusal anywhere in either directory, so `sudo sh-agent install` would build as root inside the checkout, execute the result as root and leave root-owned files in `~/.claude` and `~/.config/sh-agent`. I am not filing that as a finding — nothing in the code or docs invites it, and the harness's `sudo` rule is about host setup, not this binary — but it is unguarded, and the BUG-079 note's own "when that path is root-owned" clause shows the situation does arise on the operator's machines.
- **Crypto:** nothing hand-rolled, no finding. `crypto/sha256` + `encoding/hex` used as designed for a checksum; signature verification is delegated whole to `ssh-keygen -Y verify`, a vetted external tool, with the namespace pinned and the signer compiled in rather than read from disk. `checksumFor` requires 64 lowercase hex digits and refuses two differing hashes for one name rather than resolving by order. The comment at `release.go:36-39` already concedes the one real limit — a machine whose PATH or system directories an attacker owns can defeat any check this binary makes — and `sshKeygen` prefers `/usr/bin` and `/bin` accordingly.
- **Dependencies:** best case. `go.mod` declares `go 1.24.4` and **zero** third-party requires; the only import outside the standard library is the module's own `github.com/kesokaj/styrman-harness` embed package. Nothing to justify against stdlib-first, no known-vulnerable version to flag. `npm audit` is not applicable (no JavaScript in scope). `govulncheck` **was not run**: it is installed (`/home/kesokaj/.go/bin/govulncheck`) but it queries `vuln.go.dev`, and this dispatch's hard limits include "no network" — I did not fake it and did not work around it. Context for whoever runs it: with no third-party modules the only surface is the standard library, this box is on go1.27.1, and the project's `AGENTS.md` records the two stdlib advisories as fixed in go1.24.6/go1.25.8, both below that. One command closes it: `govulncheck ./...`.
- **GCP surface:** none in scope — no IAM binding, no service account, no Cloud Run flag, no Secret Manager call, no credential file on disk. Nothing to report.

# Recon — BUG-062: verifier `<app>` resolution divergence (2026-09-17)

## Question
Why did Claude Code's `verifier` name its testing guide after the repo directory (`demo`) instead of the single `cmd/` directory (`server`), while Antigravity's `verifier`, dispatched the same way in the same repository, resolved `server` correctly?

## Summary
The installed instruction text is byte-identical between `~/.claude/agents/verifier.md` and `~/.gemini/config/agents/verifier/agent.md`, and both match the source `agents/verifier.md` exactly (`diff` empty) — so this is not an install/derive corruption bug. The repo has exactly one `cmd/` subdirectory (`cmd/server`), so per the G20 rule in `agents/verifier.md:37` the correct resolution is `server`; Claude's run instead fell through to the third branch (repo directory's own name, `demo`). Top candidate: the top-level `AGENTS.md` in the target repo is titled `# AGENTS.md — demo` (repo name baked into the doc heading), which plausibly anchored Claude's reasoning on "demo" as the project's name before/instead of checking `cmd/`. This is already tracked as BUG-062 in `.agents/docs/bugs/INDEX.md:49`, filed same-day, with the same observation and a proposed prevention rule ("a verifier log names which branch it used").

## Flows
1. Both dispatches load the same source instruction (`agents/verifier.md`), installed verbatim to both vendors (confirmed by diff).
2. Both agents run pre-flight, read the target `AGENTS.md`, and must resolve `<app>` before checking for/writing `testing/<app>/guide.md`.
3. `.agents/scratch/realhome-smoke/demo` has exactly one `cmd/` entry (`cmd/server`), so the first G20 branch applies deterministically and unambiguously.
4. Antigravity's verifier picked `server` (branch 1, correct). Claude's verifier picked `demo` (branch 3, repo directory name) — either it never checked `cmd/`, or it treated "AGENTS.md — demo" in the target repo's own heading as the project's declared identity and short-circuited to a name it believed was already given.
5. Timestamps (`stat`) confirm Claude's run happened first (guide+log at :681/:689) and Antigravity's ran second (guide+log at :787/:794) — no cross-contamination between the two runs; each read a clean, guide-less tree at its own start.

## Conventions
- The project already has machinery for this exact failure mode: BUG-record format expects a "prevention rule" per bug; BUG-062 proposes "a verifier log names which branch it used" — i.e., make the log self-diagnosing so a future divergence is visible without a repro.
- G20 itself was added specifically because of an earlier related bug (BUG-043 second fix, per `git log -p -S "G20"` in `agents/verifier.md`), where the duty to write a guide was found skippable and `<app>` was found unresolved in one prior run — this is the third documented failure mode around the same mechanism (guide-naming / `<app>` resolution), which per the user's own AGENTS.md rule ("When a SECOND round of findings lands on the same mechanism... stop fixing and ask what the mechanism is for") suggests the `<app>`-resolution design itself, not just the wording, may need reconsideration rather than another patch.

## Risks
- Top candidate root cause (repo `AGENTS.md` heading `# AGENTS.md — demo` anchoring the model before it checks `cmd/`) is a plausible but not directly provable mechanism — there is no captured transcript/reasoning trace of Claude's run, only its artifacts. Falsification test: rename the target repo's `AGENTS.md` heading to omit "demo," or add an explicit `cmd/server` mention to it, and rerun the same repro; if Claude then resolves `server`, the heading-anchoring theory is confirmed. If it still resolves `demo`, the divergence is pure model-behavior variance unrelated to that heading, and the next candidate (see below) should be tested instead.
- Second candidate: order-of-operations underspecification. G20's rule (`agents/verifier.md:37`) is stated as a single dense sentence with three branches but does not explicitly instruct the agent to `ls cmd/` or `Glob cmd/*` as a discrete pre-flight step before naming `<app>`; a model could satisfy the sentence's letter by "knowing" the project is called demo (from its own AGENTS.md title) without ever inspecting `cmd/`. Falsification: check whether Claude's tool-call trace (not available in this recon — see Not examined) shows a `Glob`/`Bash ls cmd` call before writing `testing/demo/guide.md`; if it does list `cmd/server` and still picks `demo`, this candidate is wrong and the failure is in the model's final choice, not its information-gathering.
- Third candidate (lowest likelihood, largely ruled out here): install/derivation corruption. Ruled out by direct `diff` — both installed copies are byte-identical to source and to each other on the load-bearing line, so this is not a `derive.go` or install-pipeline bug.

- **Does requiring the installed file to exist hide the devbox case?** No. BUG-079's INDEX record (`.agents/docs/bugs/INDEX.md:60`) and the original repro are `/usr/local/bin/sh-agent` (v1.2.1, running) vs `~/.local/bin/sh-agent` (v1.2.2, just installed) — the installed file existed and was current. The gate only silences the case where the installed file is absent, which is a different (and previously wrong) case; the devbox scenario is unaffected and still reported.
- **Is the message true on an up-to-date run and a replaced run alike?** Yes. "update replaces only the installed one, so the file it ran from stays as it is" is true whether this specific run wrote anything or not — the fact asserted is about what `update` as a mechanism does, not about this invocation. `TestUpdateNamesTheBinaryItRanFrom`'s "reachable by name: named" subtest exercises exactly the up-to-date path (fake `gh` always answers `v1.0.0` = `version`, so `UpdateFromRelease`'s `tag==version` branch returns without writing) against a pre-planted installed file, and the note still fires with this wording — matches round-1 security's Outcome.
- **Does `ln -sfn` ever point a reader at making a system path a symlink to a user file?** The message's `ln -sfn` target is unspecified (no explicit `ln -sfn <from> <installed>` argument order given), but read alongside README's parallel text (`ln -sfn` the earlier PATH entry to point at "this binary") and remote.md's operator record, the intent and precedent is: point the earlier/system entry at the installed file, not the reverse. This is the same shape devbox used by hand (pointing `/usr/local/bin/sh-agent` at the current binary) and is the operator's own choice of how to wire their PATH, not something the tool does un-asked. Not a concern beyond what round-1 security already accepted for the parallel README text.

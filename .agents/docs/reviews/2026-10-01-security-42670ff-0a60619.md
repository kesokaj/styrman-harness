- **F2 [low / confidence: high] (introduced by this range)** `.agents/docs/testing/kit-preamble.sh:79`.
  - **Weakness:** `\( -type f -o -type l \) -exec cksum {} +` hands `cksum` every symlink in the real config, whatever it points at, and `cksum` opens the target.
  - **Probe:** `kit_fingerprint` verbatim from 0a60619 on a scratch config, with bfs 4.1.1 and `timeout 5`. The baseline returns at once. A link to a FIFO hit the timeout (rc 124, blocked in open). A link to `/dev/zero` also gave rc 124 (it reads forever).
  - **Why it is new:** before this range, `find -L ... -type f` skipped both. The previous security report probed exactly this: "returned in 0 s". This range adopted that report's `-H` hardening suggestion, which did not foresee the case.
  - **Actor:** a sandboxed run that reaches the real home and makes such a link (the leak class of BUG-107 and BUG-123). It can also be a link a dotfiles setup already holds, or a config directory that the run replaces with a link to a tree holding such links (`/dev` has them).
  - **Path:** the EXIT trap (`:83-91`) never reaches its comparison, so the line "FAIL the real ~/.config/sh-agent changed" never prints. The kit's own row output, printed before exit, is all that remains. A kit killed by its caller's timeout reads as a timeout, not as a leak. A link present before the run hangs every kit at its start, which is fail-safe. Neither the comment (`:74-77`) nor `guide.md:178` ("exact about links") states this.
  - **Fix:**
    - Read only links whose target is a regular file, and record every other link's target string:
      - `find -H "$kit_real_config" -type f -exec cksum {} +`
      - `find -H "$kit_real_config" -type l -exec sh -c 'for p; do if [ -f "$p" ]; then cksum "$p"; else printf "%s -> %s\n" "$p" "$(readlink "$p")"; fi; done' sh {} +`

      POSIX `[ -f ]` follows the link and is true only for a regular file. `readlink` exists on macOS and Linux.
    - Add a FIFO-link case and a `/dev/zero`-link case to `TestKitPreambleAssertsCommit`, under a timeout, and see both red on the current line first.
  - **Exposure if shipped:** a contrived write class hangs the kit instead of failing it. The preamble itself prints no false PASS.
- **F5 [low / confidence: high] (older than this range)** `skills/google-catalog/scripts/refresh-catalog.sh:226-230`, with `:239-240` and the manifest rows `:339-342`.
  - **Weakness:** the work clone is reused between runs (the default `--work` is `.agents/scratch/catalog-refresh`). It is re-pointed with `remote set-url` and `fetch`, which add objects and never remove any. `<pin>^{commit}` and the HEAD comparison then accept a pin that exists anywhere in that object store. A local-path source likewise hands over its unreachable objects.
  - **Probe:** `fetch()` verbatim from 0a60619, git 2.47.3. A fork holding commit X was fetched first, then the upstream, which does not hold X, at pin X. Result: rc 0 and X's content checked out.
  - **Effect:** nothing is substituted; the content is exactly the commit the pin names. But the manifest records `https://github.com/google/skills` at X, and the run says nothing.
  - **Actor:** an earlier source of the same work directory. That is a fork or mirror passed through `CATALOG_GOOGLE_SKILLS_REPO` (to preview an upstream change, say), or upstream history that has since been force-pushed away.
  - **Path:** provenance. A commit upstream never published, or withdrew, is vendored and attributed to upstream. MANIFEST.md's own provenance recipe (`:373`, "run the script at the pins ... and `diff -r`") reuses the same default work clone, so it would agree.
  - **Fix:** after the fetch, prune with `--prune --prune-tags`, then require the pin to be reachable from the source's current refs: `[ -n "$(git -C "$dir" for-each-ref --count=1 --contains "$3" refs/remotes/origin refs/tags)" ] || fail ...`. Leave out local branches, which are stale. Alternatively, clone fresh (`--no-checkout`) into a new directory on every run.
  - **Exposure if shipped:** the manifest's provenance can be wrong. The content is still read by the refresh's security review.

## Answers to the dispatch
1. **refresh-catalog.sh.** A source cannot make a pin vendor a commit the pin does not name. I ran three probes with `fetch()` verbatim:
   - A, fresh clone: a tag, the default branch and a `refs/replace` ref, each named for or aimed at the pin and pointing at another commit, gave HEAD = pin, the pinned content and rc 0. The clone carries no replace ref.
   - B: an annotated tag object's id passed as the pin was refused ("did not check out as itself").
   - C: an absent pin with a default branch of its name was refused ("does not resolve").

   Why it holds: git's revision parser takes a 40-hex name as the object id, and a ref of that name only warns. `refs/heads/<pin>^{commit}` is not a valid ref name, so checkout's branch-first rule cannot fire. The comparison then holds HEAD to the pin. A SHA-256 source would always fail the comparison (reasoned, not probed).

   A run can, however, succeed for a pin the current source does not hold, through a reused clone's objects or a local-path source's unreachable objects (F5, older).
2. **kit-preamble.sh.** Yes, a write can go unseen in ways the comment does not state: F3 (a re-pointed link), F4 (the trap replaced or outlived) and F2 (a hang, so the FAIL line never prints). Yes, the fingerprint can be made to hang: through a link to a FIFO or a device (F2, introduced). It reads outside the directory by design: `cksum` reads the target of a link to a file wherever it is, as the comment says, and only a CRC leaves. It walks nothing outside unless the config directory itself is a link (`-H`).
3. **preflight.**
   - **Edited commands:** no silent ship by the text. A command counts only from an `owner: verifier` log reaching HEAD, and an unrun command blocks; this half cannot be lifted.
   - **Plan tiers:** F1 (a tier that ran and failed does not block) and F6 (an untouched active plan's tiers are not listed).
   - **Failing logs:** item 3 clears a FAIL log only through a later PASS reaching HEAD that reran what failed, and both must be cited; but a deleted log escapes (F7).
   - **The gate-running agent's own log:** by the text it stands in only for tiers no subagent can run, never for item 1 or a command. `owner:` is self-declared (hardening).
   - **Repository text:** it cannot lift a condition. Only the tier half of item 2 can be lifted, and only by the operator's own turn in this release session, quoted verbatim with its date. A file, a memory, a handoff or a report never lifts it, and `AGENTS.md` may add conditions but not remove them. No finding here beyond F7, where text removes a condition's input rather than lifting the condition.
4. **Trail files.** There is no secret, credential or token in any of the 13 paths.
   - **Private data:** `/home/kesokaj/workspace/styrman-harness` appears in the r8 verify log (`:14`). It is the operator's user name, the same one as in the git author. Not a finding.

### Verdict: FINDINGS

The six round-1 fixes all landed and five of them are correct and complete: the armor check now carries its verdict in `test`'s exit status, the `sudo -n cmp` closes the scratch-copy drift correctly and in the right order, "git is never run under `sudo`" is stated in all four places, the crew Follow-up is recorded in ADR-026's Consequences, and the fingerprint command now derives from the private key. **The binding fix — the round-1 medium — is the one that did not land: as prescribed, `test "$(git rev-parse vX.Y.Z^{commit})" = "<release commit>"` cannot fail.** The block defines `<release commit>` as "the SHA `git rev-parse HEAD` printed" and then substitutes that same SHA into `git tag -s … <release commit>`, so the check compares the tag's target with the value the tag was made from — true by construction. Measured: a tag made on an old commit `A` with `<release commit>` = `A` passes the binding test (exit 0) and passes `merge-base --is-ancestor … main` (exit 0, `A` is on main), while the non-tautological form `test "$(git rev-parse vX.Y.Z^{commit})" = "$(git rev-parse HEAD)"` correctly exits 1 on the same tag. So the answer to the brief's question is **yes**: an operator-signed tag can still reach the host pointing at a commit the gate never saw, whenever HEAD is not the gated commit — which no command in the block checks, only a `#` comment asserts. ADR-026 states the check as "bound to the gated commit", which is stronger than what the commands do.

This is now a **second round of findings on the same mechanism**, which the harness's own rule (`context/AGENTS.md` § Definition of Done step 2) says is the moment to stop patching and ask what the mechanism is for. The good news is that the answer here is a deletion, not a third patch: drop the explicit `<release commit>` argument from `git tag -s` (bare `tag -s` tags HEAD, which the block already asserts is the release commit) and compare the tag's target to `git rev-parse HEAD` in one command. That removes a placeholder, a hand-substitution, and the tautology in one edit, and needs no shell variable — which matters, because agents run each command as its own call and shell state does not persist.

## Verdict: FINDINGS

The trust model is right and is stated correctly: `/etc/styrman/allowed_signers` on crew's host is the sole trust root (confirmed on this box: `drwx------ root root /etc/styrman`, `Permission denied` to the operator user), the line quoted in `deploy/remote.md` is a plain principal+key line with no `cert-authority` and no `namespaces=` option, and it matches the operator's real `~/.ssh/id_ed25519.pub` byte-for-byte including the `SHA256:5HpYQJjpG+yE1xXBTOIZPsTkbkgkVnV8z0eG8hBawyU` fingerprint (`ssh-keygen -lf`, run here). The documented pre-push checks close the one real bypass in this shape — a GPG-signed tag, which `verify-tag` would validate against a gpg keyring that `allowed_signers` never sees — and nothing in the diff lets a tag reach the host without the operator's private key: the quoted line and the scratch copy live in a repo anyone with push access can edit, and the diff says so in as many words, so tampering with them only produces a tag the root-only host file then refuses.

The worst problem is a binding problem, not a key problem: **not one documented step checks what the tag POINTS AT.** Every check in `remote.md` § Releases interrogates the tag object (type, armor header, signature) and none compares `git rev-parse vX.Y.Z^{commit}` with the gated release commit or asserts it is an ancestor of the `main` being pushed — so a stale, dirty, or simply wrong `<release commit>` substituted into the `git tag -s` line passes every check, receives a perfectly valid operator signature, and ships content no gate ever saw to a host whose whole job is to trust that signature. ## Findings

- **[medium / confidence: high]** `.agents/docs/deploy/remote.md` § Releases (the procedure block) and `AGENTS.md` § Release — the verification row binds the SIGNATURE to the tag but never binds the TAG to the gated commit. `git cat-file -t`, the armor-header grep and `verify-tag` all pass for any annotated, operator-signed tag regardless of its target; `<release commit>` is a hand-substituted placeholder, and omitting it makes `tag -s` silently take HEAD, which after a later commit or an uncommitted edit is no longer the reviewed tree. Exploitable in principle with no key compromise at all: an agent or a tired operator at preflight Step 6.3 tags the wrong SHA, all documented checks stay green, the push succeeds, and crew's host checks out un-gated content under a valid signature — the host's own smoke checks (`sh-agent list` counts, `install --dry-run`) are liveness checks, not content checks, so nothing downstream catches it either. Note the skill already carries the intent (`skills/preflight/SKILL.md` Step 6.3: "tag **that** commit … The tagged commit is the gated tree plus its records"); what is missing is the check that the intent held. Remediation, doc-only and read-only, between the `tag -s` line and the first push: `git rev-parse vX.Y.Z^{commit}` compared against the `git rev-parse HEAD` the gate ran on, `git status --porcelain` empty, and `git merge-base --is-ancestor vX.Y.Z^{commit} main` for the ADR's "on `main`" clause. No dependency, no config change.

- **[low / confidence: high]** `.agents/docs/deploy/remote.md` § Releases — the armor check `git cat-file tag vX.Y.Z | grep -E '^-----BEGIN' | tail -1` is a pipeline whose exit status is `tail`'s, so it is **0 whether or not the grep matched**. Observed here on an unsigned annotated tag in a throwaway repo: no output, `grep-exit=0`. As written the check only works if a human reads the printed line; the moment it is wrapped in a `&&` chain or an `if`, an unsigned or GPG-signed tag reads as success and the one control that keeps `verify-tag` on git's SSH path — the path that consults the allowed-signers file at all — silently stops working. This is the repo's own Hard rule ("A verification command is never piped into a filter inside a `&&` chain … the chain then guards the filter's exit status") landing on its own highest-stakes procedure. Cheap remediation, one line: `test "$(git cat-file tag vX.Y.Z | grep -E '^-----BEGIN' | tail -1)" = '-----BEGIN SSH SIGNATURE-----'`, or an explicit "read this line; its exit status means nothing" beside it.

- **[low / confidence: medium]** `.agents/docs/architecture/DECISIONS.md` ADR-026 Context and `remote.md` § Releases — the consumer's documented tag selection is select-then-verify with no fallback and no documented alarm: `git tag -l 'v*' | grep -E '^v[0-9]+\.[0-9]+\.[0-9]+$' | sort -V | tail -1`, then refuse if lightweight or not SSH-signed. Anyone who can push to `git@github.com:kesokaj/styrman-harness.git` (a compromised GitHub credential, NOT the signing key) pushes a lightweight `v99.0.0`; selection pins on it permanently, verification refuses it, and the channel silently stops delivering real releases — fail-closed, so no bad code runs, but fixes stop arriving and nothing in the documented design tells anyone. The mirror case is the same mechanism: delete the newest tag on the remote and a host that prunes tags settles on an older, validly signed release — a signature-clean downgrade, since no monotonicity rule ("never install a version below the installed one") is recorded anywhere. Enforcement lives in crew's `deploy/update/styrman-update`, not here, but ADR-026 is where the channel's contract is written: record in its Consequences that the host walks `sort -V` DOWNWARD to the newest tag that verifies, alarms on every refusal, and refuses a version below the installed one — and open it as a Follow-up in crew.

- **[low / confidence: high]** `.agents/docs/deploy/remote.md` § Releases — the pre-push `verify-tag` runs against a copy of the allowed-signers line made from the doc itself, so it proves the tag matches *the repo's* idea of the trust root, not the host's. ADR-026 is honest that the quoted line "adds no trust", but the procedure sells the check as "check it the way the consumer does", and after a key rotation (Consequences: crew's file changes first, the quoted line second) that sentence is false in the direction that costs an operator a release they believe is good — and, in the other order, gives a green local check for a tag the host will refuse. The release machine is the same Linux box that hosts crew's updater (ADR-026 Context), so one cheap read-only command closes it inside the documented procedure: `sudo -n cmp /etc/styrman/allowed_signers .agents/scratch/allowed_signers` right after the `printf`, with the explicit caveat that this is the ONLY `sudo` in the procedure and that `git` is never run under it.

- **[low / confidence: low]** `.agents/docs/deploy/remote.md` § Releases, closing note — it records that `verify-tag` against `/etc/styrman/allowed_signers` "fails with 'Permission denied' for the operator user, which is why the scratch copy is used". That names a permission failure and its workaround without naming the WRONG workaround, and the obvious wrong next move for an agent wanting the stronger check is `sudo git -c gpg.ssh.allowedSignersFile=/etc/styrman/allowed_signers verify-tag …` — git as root inside the operator's repo, reading root's config and touching `.git` as root, on a box where `sudo -n` is passwordless. Low confidence because nothing in the diff asks for it; closed by one clause: "never run `git` under `sudo`; the root file is read only by `cmp`."

- **[low / confidence: medium]** `.agents/docs/deploy/remote.md` § Releases first command and § By hand — `ssh-keygen -lf ~/.ssh/id_ed25519.pub   # … or stop: this machine cannot sign` verifies the PUBLIC key file is present, which does not establish that the machine holds the private key (a `.pub` copied to a new box, or a key reachable only through an agent that is not running, both pass). The outcome is fail-closed — `git tag -s` errors — so this is a clarity defect rather than a bypass, but the same sentence is the § By hand gate for "before that machine cuts a release" and reads as a guarantee. Remediation: say what it proves ("the right key's fingerprint is on this machine; `tag -s` failing is what proves the private key is reachable").

## Trust model, as written — assessment

- `/etc/styrman/allowed_signers`, root-only on crew's host, is correctly and repeatedly named as the sole trust root, and the in-repo copy is explicitly demoted ("the quoted line adds no trust, since anyone who can push could change it"). Verified locally: `/etc/styrman` is `drwx------ root root`; the file is `Permission denied` to the operator user.
- The quoted line — `ostling.simon@gmail.com ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIBkx0BICH1xG18f0a0F/02Vw0OvBTfSOVNXkPkO62NCR` — is one principal, one key, **no `cert-authority`** (which would have silently turned the line into a CA able to mint further signers) and no `namespaces=` restriction. The missing `namespaces=` is harmless: git verifies in namespace `git` and OpenSSH binds the namespace into the signed blob, so a signature the operator made in another namespace cannot be replayed as a tag signature. Key field and fingerprint match `~/.ssh/id_ed25519.pub` exactly (checked with `cat` and `ssh-keygen -lf`).
- **No path found by which a tag the HOST accepts can be produced without the operator's private key.** Editing the quoted line, the scratch copy, or the `-c` flags changes only what the LOCAL pre-push check accepts; the host re-verifies against its own root-only file.
- The per-command `-c gpg.format=ssh -c user.signingkey=…` flags do not persist and do not touch `git config`, satisfying the context's Git rule; `user.signingkey` pointing at the `.pub` file is git's documented SSH-signing usage, not a hand-rolled construction.
- The armor-header check is the load-bearing control and is correct in substance: git appends the signature after the message, so the LAST `-----BEGIN` line is the real block (base64 bodies contain no `-----BEGIN`), which is what stops a GPG-signed tag from being blessed by a keyring the allowed-signers file has no say over. Its exit status is the defect — see finding 2.
- Fail-closed paths, probed in a throwaway repo under `.agents/scratch/security-release-procedure/probe` with no keys and no signing: an annotated tag reads `tag`; an unsigned annotated tag produces no armor line; `git -c gpg.format=ssh -c gpg.ssh.allowedSignersFile=./nope verify-tag` exits 1 with `error: no signature found`. A missing `.agents/scratch/` therefore makes the `printf` redirect fail and the verification error out rather than pass. `git push origin vX.Y.Z` without `--force` is refused by the remote if that tag already exists with a different value, which enforces "a pushed tag is never moved" at the server for free (reasoned from git's push semantics, not re-run here).

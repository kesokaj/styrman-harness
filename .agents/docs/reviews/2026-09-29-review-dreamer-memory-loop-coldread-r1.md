# Review — dreamer-memory-loop-coldread-r1   (2026-09-29)

Range reviewed: `.agents/docs/plans/2026-09-29-dreamer-memory-loop.md` (plan, cold read), with `.agents/docs/specs/sh-agent/memory-loop.md` as its spec. This is a plan/spec review, not a diff review.

## Status: COMPLETE

## Verdict: REQUEST CHANGES (design needs revision on one point; otherwise close)

Nothing here is badly broken, but two things must be decided before implementation, not discovered during it: (a) the plan's migration step relies on reproducing Claude Code's own project-slug algorithm from a bare `tr / -`, verified only on this one checkout's simple path, with no verification step that would catch a mismatch on any other project; and (b) the plan now runs two independently-designed consolidation judgments over the same memory store — `dream`'s inline `promote` flag (retro Step 1 source 7, already shipped) and the new `dreamer` subagent's rule-candidate test (source 8) — with no rule for what happens when both fire on the same memory pair. A first-pass implementer building literally from the plan would not go wrong on most of it (it is unusually precise), but these two would produce different systems in different hands.

## (1) Gaps

- **G1 — slug algorithm asserted, not verified beyond one path [medium severity, medium confidence].** Plan Interfaces "Store path" (line 36) and Step 5b migration (line 40, `old=~/.claude/projects/$slug/memory`) both depend on `<slug>` = the repo root path with every `/` turned into `-` being *exactly* Claude Code's own algorithm for naming `~/.claude/projects/<slug>/`. The plan's only evidence is "verified on this box" for `-home-kesokaj-workspace-styrman-harness` — a path with no dots, spaces, or other punctuation. `skills/dream/SKILL.md` Step 1 already makes the same assumption today, but every place that currently *exercises* it (the `dream` skill-matrix row, `.agents/docs/testing/skill-matrix.md:31`) bypasses the slug computation entirely by passing `--settings <run>/settings.json` directly. This plan is the first place that actually depends on the naive formula to *locate* an existing store (the migration's `old=`) rather than just write a fresh one. If Claude Code's real algorithm differs for any character class (a dot, a space, a repeated separator), the migration finds `old` empty and moves nothing — silently, since "old is absent or empty → nothing" is the same code path as "old genuinely has nothing to migrate." The plan's own Verification only exercises this on one demo clone with a plain path (Phase 1) and on this checkout itself (E2E criterion 1) — both simple paths. Decide: either verify the formula against Claude Code's documented/actual algorithm for at least one path with a dot or a space before Phase 1 closes, or add a check to Step 5b that reports when `old` is empty but the operator says memory previously existed, so a formula mismatch surfaces instead of silently no-op'ing.

- **G2 — no rule for overlap between retro source 7 and source 8 [medium severity, medium confidence, BLOCKING for a first-pass implementer, see Readiness].** `/retro` Step 1 source 7 (already shipped, `skills/retro/SKILL.md:44`) runs `dream --dry-run` and turns every `promote`-flagged memory into a finding with `rule_ref null`. The new source 8 (plan line 48) dispatches `dreamer`, which reads the *same* store and applies its own "backed by two sources" test (spec line 24) to `feedback`/`user` memories — the same criterion `dream`'s `promote` flag already applies (spec's own `dream` skill, "reached the store from two sessions"). Nothing in the plan says whether `dreamer` is expected to skip memories `dream` already flagged, whether retro is expected to de-duplicate two findings that name the same memory pair, or whether presenting both is intended. Same overlap on the `/distill` side: distill's existing "third repeat" transcript scan and `dreamer`'s skill/procedure candidates (spec line 24) can both surface the same procedure with no merge rule named (plan line 49, "join the candidate list").

- **G3 — "kept byte for byte" names an outcome, not a technique [low severity, medium confidence, non-blocking].** Interfaces item 2 (plan line 39) requires that adding `autoMemoryDirectory` to an existing `.claude/settings.local.json` keep every other key "byte for byte." The obvious tool for a JSON edit, `jq '. + {...}'`, normalizes whitespace and key order and would violate that invariant on the first run against a hand-formatted file. The plan doesn't name jq, so this is not a contradiction in the plan itself, but it's a concrete trap: an implementer who reaches for the standard JSON tool breaks the stated requirement. Worth a one-line note in the Step 5b prose ("insert the member as text, don't round-trip through a JSON library") since the failure is silent (the file still parses, it just no longer matches "byte for byte" and the plan gives no test for that specific invariant).

- **No docs-clause gaps found.** Every surface this plan changes that is a command/skill/config key is itself the documentation (`skills/init-project/SKILL.md`, `skills/dream/SKILL.md`, `skills/feedback-log/SKILL.md`, `context/AGENTS.md`), consistent with the pattern the plan itself states for retro/distill (line 86, "the two skill files are their own documentation"). `README.md`'s "nothing" is justified against project rule 3 (no map line moves). No new Go surface, so `internal/harness/derive.go`'s `toolMap` needing an entry was checked and is already satisfied (Read, Grep, Glob, Bash, Write are all present, confirmed by reading `derive.go:15-20`).

## (2) Scope

- The `/dream` split-store check (plan line 46, D6) and the migration logic are not named in the operator's `## Why` quote, but both are necessary engineering to make the chosen store design (Option B) safe, and D6 records who decided it (implementer) and why. Not a gap under the stated rule (a D-row covers it).
- The `dreamer` agent duplicating `dream`'s own "backed by two sessions" promotion test (see G2) is the one place scope reads as a second shape for the same operation — the operator asked for one consolidation subagent; the plan, following the accepted research recommendation, now runs that judgment inline (`dream`, already shipped) *and* in a subagent (`dreamer`, this plan) over the same data with overlapping criteria. This is defensible (D-rows exist for the overall shape, chosen by the operator as "Option B"), but the overlap itself has no D-row explaining why both mechanisms keep independent promotion logic rather than one deferring to the other. Not disqualifying, but it is the plan's one piece of scope that reads as more than what was asked, and it is exactly the thing that produces G2.
- Everything else in Scope → In (store setup, resume clause, `dreamer` definition, retro/distill wiring, matrix rows) traces directly to the operator's request and the accepted recommendation B; Scope → Out and the two follow-ups are explicit and each has a reason.

## (3) Readiness

Questions a first-pass implementer would have to ask:

1. **BLOCKING** — When `dream`'s `promote` flag (retro source 7) and `dreamer`'s rule candidate (retro source 8) both name the same memory pair, is that one finding or two? Two implementers building this literally will diverge: one dedupes by memory filename, one presents both rows to the operator. (G2)
2. **NON-BLOCKING** — Does the `.claude/settings.local.json` edit use a JSON library or a text insert? The plan's "byte for byte" requirement points toward text insert; a reasonable implementer picks that without asking, but should not reach for `jq` blindly. (G3)
3. **NON-BLOCKING** — Exact position of the new Resume clause within the reading-order chain (plan line 44). The clause is written as a continuation (`→ on Antigravity, …`), which reads as "append at the end of the existing chain, after `bugs/INDEX.md`"; a reasonable implementer places it there without asking.
4. **NON-BLOCKING** — What "the newest `retros/` record" means when `retro`, `distill`, and `dream` records interleave by date in the same directory (plan line 47's "Since" argument, spec's dispatch contract). Filename date order is unambiguous enough that any implementer resolves it the same way (newest by date prefix, regardless of kind).
5. **Not blocking, but worth a pre-implementation check rather than a question**: whether the `tr / -` slug formula actually matches Claude Code's algorithm on a path with a dot or a space (G1) — the plan is unambiguous about what to *build*, so this doesn't split two implementers, but it is a correctness assumption that should be checked once, cheaply, before Phase 1's Checkpoint rather than discovered on some future project's `/init-project` run.

**design needs revision** (G1 and G2 are undecided gaps) — not **implementation not ready** in the strict sense that most of the plan is buildable as written by any two implementers identically; the one true BLOCKING item is the source-7/source-8 overlap (Q1). Resolving Q1 with a one-line rule (e.g., "dreamer's rule-candidate test excludes any memory `dream`'s own `promote` flag would already catch") would clear it.

# Security review — v2.4.0 release signer rotation   (2026-10-05)

Range reviewed: v2.3.2..a0a54b4

Security-relevant sub-range: b549d71..a0a54b4. It changes the `releaseSigner` line, adds ADR-052, and edits `deploy/remote.md` § Releases, README § Install without cloning and AGENTS.md § Release. At review time HEAD and origin/main were both a0a54b4, and no `v2.4.0` tag existed, locally or on the remote.

## Status: COMPLETE

## Verdict: FINDINGS

**1. The exposed retired key still works as a GitHub login key.** The retired release key, whose unencrypted private half was exposed, is still registered on the account that owns the repository. `gh ssh-key list` lists `dave` (id 161370382, type authentication), and its fingerprint is `SHA256:5HpYQJjpG+yE1xXBTOIZPsTkbkgkVnV8z0eG8hBawyU`, the retired signer.
- **Exposure confirmed.** The private half (cipher `none`) sits at line 129 of this box's Claude Code transcript `ad142c6e-…jsonl` and was sent to the model provider. I derived the fingerprint from the public half only.
- **Checkout places.** Anyone holding that text can push to `main`, and nothing protects the branch (the branch-protection and rulesets API answers 403: private repo on the free plan). Every checkout place runs what is pushed at its next `sh-agent update`.
- **Release places.** Actions are enabled, so a pushed workflow could also publish a release whose SHA256SUMS is signed by the same exposed key. Every v2.3.2-or-older release place would accept it and run it.

**2. The new release key is an unencrypted file on the box where agents run unprompted.** `~/.ssh/styrman-release_ed25519` opens with an empty passphrase. Agent sessions on this box run without permission prompts (bypass mode, and `--dangerously-skip-permissions` for the test runs). That is the same exposure path that just cost the old key.

Do not tag or publish v2.4.0 until both are fixed.

**3. The bridge design adds three weaknesses:**
- v2.4.0 itself is authenticated only by the exposed key, both for v2.3.2 binaries and for the README's manual check.
- Zip places never replace their binary, so they keep trusting the retired key after they "update".
- The newest handoff and ADR-051 still put the tag on `caa37d6`, which compiles the retired key in. The bridge's self-check could not catch that.

**4. Spot check for misuse: nothing found.** There is no release after v2.3.2 and no unknown remote ref. The last 10 push events are all commits held locally. The only workflow is GitHub's dynamic Dependabot graph.

## Findings

- **[high / confidence: high]** The retired key is still a GitHub authentication key: `dave`, id 161370382, `SHA256:5HpYQJjpG+yE1xXBTOIZPsTkbkgkVnV8z0eG8hBawyU`. ADR-052's Consequences (`.agents/docs/architecture/DECISIONS.md:576`) says it "must be removed". It has not been.
  - **Where the private half is.** Unencrypted at `/home/ostling-simon/.claude/projects/-home-ostling-simon-projects-styrman-harness/ad142c6e-ead7-4625-9e5c-9767b55c9268.jsonl:129`, and already at the model provider.
  - **Checkout places.** With it, anyone can authenticate over SSH as the account owner and push to `main` and to tags, because nothing protects the branch. Every checkout place fast-forwards to what `main` holds without checking any signature (`internal/harness/repo.go:252,280`). It then rebuilds and installs the binary, context, skills and agents from it, which means code execution plus agent instructions on that machine.
  - **Release places.** Actions are enabled (`enabled: true, allowed_actions: all`). A pushed workflow that requests `contents: write` could publish a release, with a binary and a SHA256SUMS signed by the retired key. Every v2.3.2-or-older release place would install and execute it (`internal/harness/release.go:100-188`).
  - **Other repositories.** The key has the same reach on every other repository the account can write to.
  - **Remediation (operator, from their own shell, before any tag or bridge signature is published):**
    - Delete the key: `gh ssh-key delete 161370382`, or Settings → SSH keys.
    - Check the account's security log for SSH git access since the exposure.
    - Turn Actions off, since the harness uses no CI: `gh api -X PUT repos/kesokaj/styrman-harness/actions/permissions -F enabled=false`. That closes the path from a stolen push credential to a forged release.
    - Re-check `git ls-remote origin` and `gh release list` right before tagging.
- **[high / confidence: high]** The new release key's private file `~/.ssh/styrman-release_ed25519` (`SHA256:BwBzPnfXKuKrWP6p10IZgcDG8uwSRXJOFv0Izl+79yQ`, mode 600, written 13:09:55Z) is unencrypted: it opens with an empty passphrase.
  - **What the records promise.** `.agents/docs/deploy/remote.md:102` describes it as "a passphrase-protected file such as `~/.ssh/styrman-release_ed25519`", and ADR-052 says the procedure "never reads a private-key path".
  - **Who can read it.** Agent sessions on this box run with bypass permissions, and the test kits run Antigravity with `--dangerously-skip-permissions`. Those runs read outside their clones (`testing/2026-10-05-verify-critical-thinking.md:48`, `-r2.md:14`, `-v2.3.3-gate-rows.md:13`). Any of them, or any process running as this user, can read the file. With it they can sign a SHA256SUMS that every v2.4.0-or-later binary will install.
  - **Which record knows.** Only the uncommitted `changes/2026-10-05-1317-release-signer-rotation.md:17` says so ("no passphrase yet (the operator sets it)").
  - **Not yet exposed.** No copy of this key turned up in any transcript, scratch, temp or config location examined.
  - **Remediation:**
    - Before the tag, the operator sets a strong passphrase with `ssh-keygen -p -f ~/.ssh/styrman-release_ed25519`, in their own shell, outside any agent session.
    - Better: keep the key off the agent box altogether, in a password-manager agent or as a hardware-backed `ed25519-sk` key that needs a touch per signature.
    - If the key is going to change again, now is the cheapest moment, because no release has shipped with it compiled in.
- **[medium / confidence: high]** Bridge: v2.4.0's authenticity rests only on the exposed key (`DECISIONS.md:574`, `README.md:103-104`, `remote.md:102`).
  - **Only SHA256SUMS is checked.** A place never checks the tag, which is signed by the new key (`release.go:227-244`). Anyone holding the retired key can write a `# styrman-harness v2.4.0` (or v9.9.9) SHA256SUMS that passes both a v2.3.2-or-older binary and the README's manual check.
  - **The forged binary chooses its own trust.** It trusts whatever signer its builder compiled in (`release.go:36-40`). So yes, a place *can* be made to trust the retired key, or an attacker's key, after it "updates".
  - **How it would be delivered.** A release on GitHub, which finding 1 opens, or a zip with its pair handed to a zip place.
  - **No revocation exists.** A place that never updates trusts the exposed key indefinitely.
  - **Remediation:**
    - Publish a second signature over the same SHA256SUMS, made with the NEW key, as an extra asset, and make README's v2.4.0 path verify that one. The retired-key `.sig` then serves only v2.3.2-or-older binaries.
    - After each place updates, check its installed binary against the new-key-verified SHA256SUMS (or read its metrics from `sh-agent report`), and record which places have moved.
    - Cut the next release, signed by the new key only, soon, so the bridge stops being "latest".
- **[medium / confidence: high]** Zip places keep the retired trust root after updating.
  - **Why.** `update --from-zip` never replaces the binary (`cmd/sh-agent/main.go:51`, `:1129-1170`, `.agents/docs/specs/sh-agent/delivery.md:32`). A zip place on a v2.3.2 binary that installs `styrman-harness-v2.4.0.zip` prints and records "VERIFIED against the signed SHA256SUMS of release v2.4.0". Its verifier still trusts only the retired key, for every later zip.
  - **Nothing tells them.** Neither ADR-052's "every place should run `sh-agent update`" nor the v2.4.0 release notes (handoff `2026-10-05-1242-…` § Install or update: "Zip places: `sh-agent update --from-zip …`") moves that trust root.
  - **Remediation:**
    - The release notes, README and ADR-052 tell zip places to replace their binary by hand with a release binary verified against the NEW key, with the commands.
    - Optionally `status` prints the compiled signer's fingerprint. That is the operator's design question, and delivery.md is its one home (project rule 6).
- **[medium / confidence: medium]** The tag target can silently re-ship the retired key.
  - **What the records say.** The newest handoff (`.agents/docs/handoffs/2026-10-05-1248-v2.4.0-tag-still-pending.md:19,24`), handoff 1242's Next Steps and ADR-051's Consequences (`DECISIONS.md:565`: "the v2.4.0 tag still goes on `caa37d6`") all still put the tag on `caa37d6`. That commit's `release.go` compiles in the RETIRED signer, and the resume order reads the newest handoff first.
  - **Why nothing would stop it.** Tagging `caa37d6` and signing the bridge with the retired key passes every check in remote.md. It would ship v2.4.0 binaries that keep trusting the exposed key. ADR-052's bridge self-check ("a v2.3.2 binary built from the tag") only proves that the old trust root accepts the bridge, so it cannot catch this.
  - **The gate is stale.** `reviews/2026-10-05-preflight-v2.4.0.md:31` says "Security: not owed … no Go source changed". a0a54b4 makes that false, so the gate must be re-run over a range that ends at or after a0a54b4.
  - **The bridge commands are not written down.** Signing with the retired key and the v2.3.2 self-check exist only as ADR prose, not as commands in remote.md.
  - **Remediation:**
    - Write a superseding handoff or plan that names the new gated head.
    - Write the bridge steps as commands in remote.md, with a must-pass check that every built binary carries the new signer and not the retired one. For example: the built binary's `update --from-zip --dry-run` prints VERIFIED for a scratch copy of SHA256SUMS signed by the new key, and refuses the bridge `.sig`.
- **[medium / confidence: high]** Live credentials are left in scratch homes, while the range's records say they were deleted.
  - **What is there.** `.agents/scratch/{ct-ctl,ct-old,dr-home,ct-new}/.ssh/id_ed25519` hold the unencrypted private half of GitHub authentication key `private-crew` (`SHA256:K1lGJE++FO14z5CYvDh0KncJorYQ7+GI+bKvyk+7Z7s`, registered 07:47:20Z, with account-wide push rights). The same four homes hold `.config/gcloud/application_default_credentials.json` and `credentials.db`, which are Google Cloud user credentials. The file times are 08:30, 09:42, 10:47 and 12:14 UTC.
  - **What the records claim.** `testing/2026-10-05-verify-critical-thinking.md:19`, `-r2.md:14`, `-dreamer-global-rules.md:14`, `-v2.3.3-gate-rows.md:13`, and handoffs `0935…:48` ("credentials deleted"), `1039…:41` and `1129…:39` ("no credentials left"). The kits delete by name and miss these two kinds of credential.
  - **Why it matters.** These homes were HOME for runs that used `--dangerously-skip-permissions`, and agents in them tried `git push` on their own (`verify-critical-thinking.md:49`; that remote was local). The files are gitignored (`.gitignore:42`) and not committed.
  - **Remediation:**
    - The operator deletes those `.ssh/` and `.config/gcloud/` directories by name.
    - The kits either stop copying the SSH key and the gcloud credentials into sandbox homes, or delete every kind of credential they copy and check afterwards.
    - A bug record for the false claim (`bugs` agent).
- **[medium / confidence: medium]** A key held in an SSH agent signs for any process that can reach the agent. `remote.md:102` says "any machine whose agent holds it can cut a release". While the key is loaded, any process holding `SSH_AUTH_SOCK` can sign a SHA256SUMS: an agent session in bypass mode, a nightly job, or a host the agent is forwarded to. The procedure sets no per-use confirmation, no lifetime and no rule against forwarding. Remediation: load the key with `ssh-add -c -t 900` only for the release window, never forward that agent, or use an `-sk` key that needs a touch per signature.

  - **Cleanup list gap.** ADR-052's list names dave and "this box's scratch copy" but not this file.

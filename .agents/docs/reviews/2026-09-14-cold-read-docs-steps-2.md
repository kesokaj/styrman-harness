# Cold-read — 2026-09-14-documentation-steps.md   (2026-09-14)

Range reviewed: the plan file `.agents/docs/plans/2026-09-14-documentation-steps.md` (not a diff — this is the cold-reader check named in the plan's own start prompt) plus the surfaces it names: `context/AGENTS.md`, `README.md`, `agents/*.md`, `skills/{feature,bug,handoff,retro,review,preflight,init-project}/SKILL.md`, `.agents/docs/testing/skill-matrix.md`, `.agents/docs/deploy/{local,remote,gcp}.md`, `skills/init-project/assets/agents-tree/docs/deploy/*`, `REQUIREMENTS.md`, and `~/.config/sh-agent/proposals/*.md`.

## Verdict

The plan is well-scoped for a "prose edit" task and most of its ten items map cleanly onto surfaces that either already carry a hook for them or are empty and ready. But three items rest on a factual claim about the current state of the repo that is wrong, and two more leave a real interface decision (exact file name / exact insertion point) unmade where two implementers would produce incompatible artifacts. The worst is item 5/5b: the plan says "the four existing queue files" in `~/.config/sh-agent/proposals/`, but six exist (`2026-09-03-retro.md` and `2026-09-03-retro-final.md` are not named), and the verification line it specifies (`grep -c 'Status:' per file equals its proposal count`) already fails against the un-backfilled `2026-09-10-retro.md`, which carries one combined `## Status:` line for seven proposals rather than one per proposal.

## Gaps — must be decided before implementation

- **Proposal-file inventory is wrong.** Item 5 (`.agents/docs/plans/2026-09-14-documentation-steps.md:29`) says to backfill "the four existing queue files (`2026-09-04`, `09-08`, `09-10`, `09-11`)". `ls ~/.config/sh-agent/proposals/` shows **six** files: `2026-09-03-retro.md`, `2026-09-03-retro-final.md`, `2026-09-04-retro.md`, `2026-09-08-retro.md`, `2026-09-10-retro.md`, `2026-09-11-retro.md`. The plan does not say whether the two 2026-09-03 files are deliberately excluded (they predate the operator's later work and might be considered "closed" differently) or simply missed. `/retro --harness`'s own reading rule (item 5, same line: "files older than 2026-09-14 predate the line; absent means queued") applies to reading, not to the one-time backfill task, so it does not resolve which files task 5b touches.
- **The backfill format collides with existing content in `2026-09-10-retro.md`.** That file already has one heading, `## Status: applied 2026-09-10 — all seven, harness commit 50ac771, deployed by sh-agent install`, covering all 7 proposals collectively — not "a `Status:` line under every proposal heading" as item 5 specifies. The plan's own verify check for 5b, `grep -c 'Status:' <file> == <proposal count>`, will read 1 unless the implementer adds 7 per-proposal lines; it doesn't say whether the existing combined line is kept, deleted, or reworded, so a `grep -c` count of 8 (if both stay) silently fails the plan's own stated verification. `2026-09-08-retro.md` uses `**Status: APPLIED 2026-09-08**` (bold, past participle, one per proposal already) — close enough to satisfy the grep, but inconsistent casing/format with the forward-going rule "carries `Status: queued`" (lower case, present-tense word). Not fixed by the plan.
- **Item 2's target text already diverged from what's in the repo.** `agents/verifier.md` (current file) already has bespoke language — "the only files you create or update are the verification log for this run and the `testing/<app>/` guide when the steps themselves changed" and a `Read … $docs_root/testing/<app>/` pre-flight step — that partially implements what item 2 asks for, but under a different shape than the plan's exact wording (`<docs-root>/testing/<app>/guide.md`, singular file, "cite it from the log"). `agents/documentation.md`'s "Shared seam" paragraph likewise already says the verifier "may update `testing/<app>/` guides" (plural, no fixed name) — not the single `guide.md` the plan specifies. The plan does not say whether to overwrite this pre-existing text with the exact new wording (in which case the file-name mismatch — plural "guides" vs. singular `guide.md` — needs resolving) or merge it. Two implementers will diverge on the resulting file name/shape.
- **Item 4's "Outcome" section on the preflight gate report is a timing mismatch the plan doesn't address.** Preflight already blocks SHIP on any unresolved finding (Step 2–4, `skills/preflight/SKILL.md`), so by the time a preflight gate report is written its findings are already fixed or the release is NO-SHIP — there's no later moment in the same run where "the task that acts on the report later" would append an Outcome section to a *preflight* report the way it naturally would to a `/review` report. The plan cites "`skills/preflight/SKILL.md` Step 5" for this, but current Step 5 is "Write the merged gate report," not a fix step — item 4's insertion point in preflight is not obviously where the mechanism it describes (finding → later fix → Outcome section) applies.
- **Item 3's "the review row includes `/review --docs`" is ambiguous about literal invocation vs. inlined dispatch.** `context/AGENTS.md` DoD step 2 is read by every agent-driven task, most of which are not running inside the `/review` skill's own machinery (scope parsing, artifact naming). It's not stated whether "the review row includes `/review --docs`" means the main agent runs the `/review` skill as a nested step (reusing its Step 1–4 scope/dispatch logic) or simply dispatches the `reviewer` agent with `/review`'s `--docs` brief inline. Both are plausible readings of the harness's own "skills are just markdown, not code" model, but they produce different call shapes (a full second skill invocation with its own report file vs. one dispatch folded into the caller's existing review row).

# Security review — v1.6.0-a9717cc   (2026-09-28)

Range reviewed: v1.6.0..a9717cc

## Status: COMPLETE

## Verdict: FINDINGS

The worst problem is the new sandbox rule at `AGENTS.md:66`. It makes a blanket tool-permission grant the standing setup for every headless-agy sandbox run. The rule copies the real home's `~/.gemini/antigravity-cli/settings.json` into the sandbox home "beside the copied token" and describes the file only by what it lacks ("it holds no credential"). On this box the file holds `toolPermission: always-proceed`, plus a `trustedWorkspaces` list naming the real harness checkout (`/home/kesokaj/workspace/styrman-harness`, the release source) and an unrelated project (`/home/kesokaj/workspace/valkompass`). Verified: the key set was read and values were printed for those two keys only; the sandbox copy at `.agents/scratch/tsn/.gemini/antigravity-cli/settings.json` is byte-identical and is still on disk.

The rule contradicts the harness's own policy in `.agents/docs/testing/guide.md` § 5: headless Antigravity tool checks use `permissions.allow` entries, and `--dangerously-skip-permissions` is used "only inside a throwaway clone, and never as the standing way". This is medium, not high, for two reasons. The fixtures used so far are written by the operator or by an agent. The project-root `AGENTS.md` does not ship in the release binaries (go:embed covers only the five source directories). By preflight's rule only a high finding blocks, so neither finding blocks the v1.7.0 gate. The medium one still needs a recorded decision in the gate report: fixed now, or accepted with the reason.

## Findings

- **[medium / confidence: high]** `AGENTS.md:66` (new § Testing paragraph, second bullet): the headless-agy sandbox rule copies a blanket auto-approve grant and a real trust list into every sandbox home.
  - **Weakness:** the rule tells every headless-agy sandbox home to carry a copy of the real home's agy `settings.json`. BUG-091's root cause records what that copy grants, and this review re-checked it: `toolPermission: always-proceed`, so every tool call runs without approval, shell included. The copy also brings `trustedWorkspaces`: this checkout, which contains every `.agents/scratch/` clone the probes run in, and another project, valkompass. The rule's only description of the file is "(it holds no credential)". That is true today: the keys are `artifactReviewPolicy`, `toolPermission` and `trustedWorkspaces`. But it hides the property that matters.
  - **Why it is exploitable in principle:**
    - `HOME=<scratch>` only redirects where dotfiles are looked up; it does not contain anything. The sandboxed agent runs as the operator's uid on the machine that holds the release-signing ed25519 key (`AGENTS.md` § Release) and the `gh` credentials.
    - Any instruction-shaped text that reaches such a run executes shell commands with no prompt, with a live OAuth token in the same home. Such text can come from the installed skills (six of them vendored third-party text, `skills/VENDORED.md`), a cloned third-party repository, or fetched content.
    - The run is also pre-trusted over the real release-source checkout and over another project.
    - The rule copies whatever posture the real home has at copy time. The real file has already moved from the six `permissions.allow` entries that guide § 5 relies on to `always-proceed`; their restore is deferred in `handoffs/2026-09-28-open-items.md`.
    - The copy left in `.agents/scratch/tsn` stays armed for the next run that copies a token in.
  - **Remediation:**
    1. Replace "carries the real home's `settings.json` (it holds no credential)" with a sandbox settings file written for the run. It should use the narrowest permission that lets the probe run, meaning the `permissions.allow` entries guide § 5 already names and only the exact commands the probe needs. Its `trustedWorkspaces` should list only that run's scratch clone(s), never the real checkout or another project.
    2. State in the rule that this file is a permission grant, and reconcile it with guide § 5 in the same commit, so that one text holds the rule.
    3. Delete the sandbox settings by name with the token after each batch, and delete the armed copy now.
    4. If the operator chooses blanket auto-approve for these runs, record it as an accepted risk with its conditions (fixtures the operator wrote, no third-party content), not as a silent default.
- **[low / confidence: medium]** `skills/preflight/SKILL.md:40` (the fallback secret scan, in a paragraph edited in this range): the scan has no pattern for either credential type that this repo's sandbox procedure copies into the working tree.
  - **Weakness:**
    - The sandbox procedure (guide § 4, and now `AGENTS.md:66` "beside the copied token") puts CLI credential copies inside the repository at `.agents/scratch/<home>/`. Only `.gitignore` (`.agents/scratch/*`) keeps them out of git.
    - The last line of defence before a commit is gitleaks, which is **not installed on this host**, so the fallback grep is the live control here. Its patterns are `PRIVATE KEY`, `-----BEGIN`, `AKIA`, `AIza`, `ya29.`, `token=` and `password=`.
    - The fallback does not match Claude Code's `.credentials.json` tokens (`sk-ant-` prefixed; product knowledge, the file was deliberately not opened) or an OAuth refresh token. The agy token file `antigravity-oauth-token` has no `.json` extension, so the name-based stop ("credential JSON") may not catch it either (not opened, contents unverified).
  - **Why it is exploitable in principle:** the credential lives in the working tree, and gitignore is the only barrier. A force-add, a gitignore edit, or a tree-walking tool is enough to stage it, and the scan would not flag it. The existing controls lower the practical risk. Those controls are `chmod 600`, delete-by-name after each batch, and a stop on secret-shaped paths. This review found no credential-shaped file left under `.agents/scratch/` (names only, depth 7, 2026-09-28).
  - **Remediation:** add `sk-ant-` and `refresh_token` to the fallback list at `:40`, which Step 6 item 3 re-runs. Name `.credentials.json` and `antigravity-oauth-token` in the stop-by-name list. These are prose edits with no new dependency; gitleaks remains the skill's preferred scanner on a host that has it.

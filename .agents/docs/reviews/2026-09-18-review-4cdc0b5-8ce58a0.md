# Review — BUG-078 PATH-shadow guard, round 2 (4cdc0b5..8ce58a0)

Range reviewed: 4cdc0b5..8ce58a0

## Verdict: REQUEST CHANGES

Both round-1 findings are genuinely fixed and well tested (verified by reading the code and by re-running the test suite): the two-definitions-of-"on PATH" split between `binOnPath`/`PathShadows` is gone (one function, one walk), and hard links are now correctly recognised as "not a shadow" via `os.SameFile`. But the fix introduces a new instance of the exact class of bug round 1 flagged, now *inside* `PathShadows` itself: the function uses two different notions of "reaches the same binary" in the same walk — a strict lexical `filepath.Clean(dir) == binDir` string comparison to decide `onPath` (pathguard.go:29), and `os.SameFile` identity (which follows symlinks) to decide "not a shadow" (pathguard.go:49). When PATH reaches the bin dir only through a symlinked directory component (e.g. `~/bin -> ~/.local/bin`, a common dotfiles/devbox pattern — exactly the kind of aliasing that caused the original BUG-078 incident), `PathShadows` correctly finds an earlier real shadow but returns `onPath=false`, and `status`'s report is gated by `if onPath` (main.go:390) — so the genuine shadow is computed and then silently dropped, never printed. I reproduced this with a standalone repro against the built package (see below): `shadows=[.../earlier/sh-agent]`, `onPath=false`. This is the identical failure mode ("status reported drift none/nothing about a binary the shell does not run") the whole change exists to close, just moved one level down.

## Reproduction

```go
// PATH: earlier/sh-agent (a real, different shadowing binary), then an
// alias directory that is a symlink to the real bin dir (not the bin dir's
// own literal path).
shadows, onPath := harness.PathShadows(path, target)
// shadows: [/tmp/.../earlier/sh-agent]   <- correctly found
// onPath:  false                         <- wrong; PATH does reach target here
```
`status`'s shadow loop (`cmd/sh-agent/main.go:389-393`) only runs `if onPath`, so in this state it prints nothing — no `shadowed` line — even though a real, earlier shadow was found and is sitting in the `shadows` slice the same call just returned.

## Findings

- **[high / confidence: high]** `internal/harness/pathguard.go:29` vs `:49` (`PathShadows`), gated by `cmd/sh-agent/main.go:390` (`status`) — `onPath` is decided by lexical `filepath.Clean` string equality on the PATH entry's directory, which does not follow a symlinked directory component, while "is this candidate the same binary" is decided by `os.SameFile`, which does. A PATH entry that reaches the installed binary only via a symlinked directory (not the binary's own literal directory string) makes `PathShadows` return `onPath=false` even when it has just correctly found and populated `shadows` with an earlier, genuine shadow — and `status`'s entire shadow-report loop is gated on `onPath`, so the warning is silently dropped. Reproduced live (see above). Fix: derive `onPath` from whatever the function's own loop actually used to decide "this entry reaches the target" — i.e., set `onPath = true` whenever the loop reaches the end of PATH having found (via `executableAt` + `SameFile`) that some entry *is* the target file, not only when the entry's raw directory string equals `binDir`. This is the same root cause round 1 named for `binOnPath`/`PathShadows` (two disagreeing definitions of "reaches the target"), now internal to one function instead of split across two.
- **[low / confidence: medium]** `internal/harness/pathguard_test.go` — no test covers a PATH entry reaching the bin dir through a symlinked directory (only a symlinked *binary file* is tested, pathguard_test.go:287). The finding above would have been caught by such a case.

## Criteria

1. **Dead code** — pass. `binOnPath`, `shadows`, `shadowHint`, and the old injected `resolve`/`ResolveExecutable` are all gone with no remaining references; nothing orphaned.
2. **Flow tracing** — fail: see the high finding. `PathShadows` → `status`'s `if onPath` gate is a broken hop for symlinked-directory PATH entries; `pathHint`'s `switch` degrades more gracefully in the same situation (falls into the `case len(shadows) > 0` branch and still prints a mislabeled but present warning), so only `status` silently loses the signal entirely.
3. **Standards conformance** — pass. gofmt/vet/test clean; comments describing the guarantee were updated to match the new single-function design; message strings match doc quotes in README/remote.md/local.md.
4. **Directory layout** — pass, no change from round 1.
5. **Simplicity (DIY-except-security)** — pass, and improved: dropping the injected `resolve` function in favor of directly calling `os.Stat`/`os.SameFile` is a net simplification with no loss of testability (tests build real files instead of a fake).
6. **Decoupling** — weak, and this is the root of the new finding: `PathShadows` now internally conflates two different equivalence relations ("same literal directory" vs "same file by identity") without them agreeing, which is the same shape of bug round 1 flagged between two separate functions. Fix on the finding above resolves this too.

## Outcome

This was the second round to land on the same mechanism — how "on PATH" is decided — so under the context's Definition of Done rule the mechanism was put to the operator rather than patched again. Their choice: define it by the one identity the rest of the walk already uses.

- [high] lexical `onPath` vs `os.SameFile` disagree on a symlinked directory — **fixed** by deleting the lexical comparison rather than extending it: the walk now stops at the first PATH entry whose `sh-agent` IS the installed file by `os.SameFile` (internal/harness/pathguard.go:48); `filepath.Clean` no longer appears in the file, and the doc-comment says why (internal/harness/pathguard.go:12). - [low] no test for a symlinked directory on PATH — **fixed**: two cases, the round-2 repro with an earlier shadow (internal/harness/pathguard_test.go:329) and the alias first (internal/harness/pathguard_test.go:330).

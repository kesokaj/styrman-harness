# Security review — Phase 2 round 3, the `TightenConfigDir` split (e7fec88..42840fb)

Range reviewed: e7fec88..42840fb (`git diff e7fec88..42840fb -- . ':!.agents/docs'`; HEAD `42840fb`, tree frozen)

## Verdict: FINDINGS — four low, **no high, nothing reopens the work**

Round 2's **medium is closed, and closed structurally rather than by
measurement**: `TightenConfigDir` (state.go:93) has **no error return at all**,
`Install` calls it as a bare statement before the first write (apply.go:30), and
the only chmod-failure branch writes a `note:` line and falls through
(state.go:106-108). No value flows from that chmod into `Install`'s result — a
failed tighten cannot abort a deployment, whatever the filesystem does. The
operator's option 1 is implemented as specified and measured on all six paths
(fresh, loose, dry run, second run, symlink, `diff`/`status`).

The worst thing left is a **documentation guarantee the code does not keep**:
README line 74 says the runtime directory "is created 0700 and **tightened to it
by every install**", and line 162 repeats "tightened to 0700 **on every
install**". Measured false — a symlinked `~/.config/sh-agent` is left at 0755
with **zero output** and `install` still exits 0 (probe E) — and false by code
for a directory the caller does not own (state.go:99). The two silent skips plus
the absolute claim combine into a false assurance about the privacy of the
feedback log and the retro proposals: the operator whose arrangement is skipped
is told, in writing, that it was fixed. That is a doc sentence and a `note:`
line to close, not a defect in the mechanism.

## The brief's questions, as checkable statements

1. **Is the medium (a failed tighten aborting after every write) closed?
   YES — by construction, which is stronger than a probe.**
   `func TightenConfigDir(home string, dryRun bool, out io.Writer)` returns
   nothing (state.go:93); `apply.go:30` discards nothing because there is
   nothing to discard; the chmod error is consumed by
   `fmt.Fprintf(out, "note: could not correct the mode of ~/.config/sh-agent (%v)\n", err)`
   (state.go:107) and control falls off the end of the function. There is no
   path from that `Chmod` to a non-nil `Install` error. Bounding measurements:
   probe **E** (the tighten skipped entirely, symlinked dir) → `rc=0`, manifest
   written into the target; probe **J** (a *different* failure, below) → the
   only surviving abort is `writeAtomic`, not the chmod.
   **I could not force `chmod` to fail as this user, and say so plainly:**
   `chattr +i` needs `CAP_LINUX_IMMUTABLE` and returned
   `chattr: Operation not permitted` (probe H); no read-only bind mount is
   available here; no root was used, per the dispatch. So the `note:` line
   itself was **never observed executing** — the closure rests on the
   signature and the control flow, which I read end to end, not on seeing it
   print. That branch is also untested (finding 4).
2. **Does `left` reason 3 hold (`~/.config` created 0700 when absent)? YES.**
   Measured (probe A, fresh home): `.config` **700**, `.config/sh-agent`
   **700**, and **no `mode` line** — the directory was created private, not
   tightened, which is exactly what the split promises. The reason given
   ("when `~/.config` does not exist yet the whole path is sh-agent's to
   create") holds and is now *stronger* than at e7fec88: because `ConfigDir`
   no longer tightens, an **existing** `~/.config` (0775 on this box) is left
   alone, so the surprise is confined to a home where sh-agent made the
   directory itself. Same uid throughout; no exposure, no lockout. The doc
   comment (state.go:71) says "created 0700 when absent", which matches.
3. **Does `left` reason 4 hold (the contents' modes)? YES, unchanged.**
   Measured read-only on the operator's real home, today: `~/.config` **775**,
   `~/.config/sh-agent` **755**, `feedback/` **drwxrwxr-x**, `proposals/`
   **drwxrwxr-x**, `feedback.jsonl` **-rw-rw-r--**, `retros.jsonl`
   **-rw-rw-r--**, `state.json` 0644. Their next `install` (or `update`, which
   reinstalls) tightens the parent to 0700, and a 0700 parent denies `x` to
   group and other, so the local-account read the finding named is closed —
   traversal is the gate, not the leaf modes. The acknowledged residual is
   unchanged: the loose modes travel with a backup, an archive or a dotfiles
   sync. One nuance the reason should carry: the tighten is **install-only**,
   so a machine that only ever runs `report`, `diff` or `status` keeps a 0755
   runtime directory indefinitely — measured (probes F, G: mode stayed 755
   across both). Every machine kept current with `update` reinstalls, so this
   bites only a machine nobody updates.
4. **Does `left` reason 5 hold (ownership vs writability)? YES — and it is
   untouched by this range.** `pathguard.go:141` is byte-identical at
   e7fec88 and 42840fb. `ownedByCaller` still gates **wording only**, never an
   operation, and errs toward the stronger remedy. Nothing here changed it.
   Note the same predicate is now load-bearing in a *second* place
   (state.go:99), where it gates an actual operation rather than a sentence —
   correctly, since `chmod(2)` requires ownership, and `Geteuid` is the right
   uid for "will the kernel let me".
5. **Should the not-owned skip print a note? YES — print one.** (Advice only;
   this is finding 2, low.) `install`'s whole output contract is that it names
   what it changes, and it already has the precedent for naming what it
   *declines* to touch: the `keep ~/…` line for a managed path holding a
   foreign file (apply.go:40). A loose, foreign-owned runtime directory is the
   same situation — sh-agent sees a privacy problem in its own directory,
   decides it is not its to fix, and says nothing, while the README says it
   was fixed. The branch only fires when the directory is **both** loose and
   not the caller's, so the note is rare and every printing of it is
   actionable. Same argument, slightly weaker, for the symlink skip. Suggested
   text: `note: ~/.config/sh-agent is 0755 and is not yours to change; leaving
   its mode alone (it holds the feedback log and the retro proposals)`.
6. **Can the dry run's `mode` line mislead? NO.** Measured (probe B): the dry
   run printed `mode    ~/.config/sh-agent (0755 -> 0700)`, left the directory
   at **755**, and closed with `[dry-run] 0 written, 260 unchanged, 0 removed,
   0 kept`. That is exactly the per-file `mode` contract (apply.go:52-59, plan
   D7/D8): the probe runs on a dry run so it names the same line the real run
   prints, the line itself carries no `[dry-run]` prefix — no per-file line
   does — and the prefixed summary is the marker. The predicate is identical
   on both paths (`Lstat`, symlink, `IsDir`, loose, owned all checked *before*
   the print), so a dry run cannot name a change the real run would skip. The
   one residual asymmetry is that the real run may additionally print a
   `note:` when the chmod fails, i.e. the dry run can promise a tighten that
   does not happen — the identical asymmetry the per-file lines already have,
   and it is announced at the time. No finding.

## Findings

- **[low / confidence: high]** `README.md:74` and `README.md:162` — **the
  README states an unconditional guarantee the code does not keep.** Line 74:
  "`~/.config/sh-agent/` is created 0700 and **tightened to it by every
  install**"; line 162: "`mode` (… and also the runtime directory
  `~/.config/sh-agent`, **tightened to 0700 on every install**)". Both are
  false for two arrangements the code deliberately skips: a **symlinked**
  runtime directory (state.go:96) and one the caller **does not own**
  (state.go:99). Measured for the first (probe E): `~/.config/sh-agent` →
  a 0755 target, `install` exits **0**, target stays **0755**, and the output
  contains **no line at all** about it. Why this matters in principle: a
  dotfiles-symlinked `~/.config/sh-agent` is a normal arrangement, the
  directory holds the feedback log, the retro proposals and — briefly — a
  clone of the *private* feedback repository, and the operator who reads this
  README has been told in writing that every install makes it private. A
  guarantee that is read as a control and is not one is worse than no
  sentence. This is also the behaviour-change-includes-its-description rule:
  the code moved in this commit, the two sentences did not. Remediation: one
  clause on each line — "…tightened to it by every install, except a
  symlinked directory or one owned by another user, which it leaves alone" —
  plus finding 2's note so the exception is visible at the moment it applies.
- **[low / confidence: high]** `internal/harness/state.go:96,99` — **both skips
  are silent, so the one case where the privacy problem persists is the one
  case the operator is never told about.** `Lstat` failure, a symlink, a
  non-directory and a foreign-owned directory all `return` with nothing
  written to `out`. The loose-and-foreign case is precisely a runtime
  directory that is world-readable, holds the feedback log and proposals, and
  that sh-agent has decided not to fix. `install` already prints a line when
  it declines to touch a managed path (`keep ~/…`, apply.go:40), so the
  pattern and the output budget both exist. Remediation as in question 5: one
  `note:` before each `return`, gated on the directory actually being loose so
  it cannot become noise. Stdlib only; no dependency, no new syscall.
- **[low / confidence: high]** `internal/harness/state.go:95-108` — **`Lstat`
  then path-based `Chmod` is a TOCTOU window; `os.Chmod` follows symlinks and
  the `Lstat` guard does not survive the gap.** An account that can create
  entries in the target `~/.config` can replace `sh-agent` with a symlink
  between the two calls and the `Chmod` follows it. The impact is bounded in
  the safe direction and I state that explicitly: `chmod(2)` succeeds only on
  a target the caller owns (or with `CAP_FOWNER`), and 0700 only *clears*
  bits, so the worst a non-root install yields is one of the caller's own
  directories tightened to 0700 — availability, never a widening, never
  another user's files. Under a **root**-run install the same race can tighten
  any directory on the box. The precondition (write access to the victim's
  `~/.config`) already implies a deeper compromise — that same access plants a
  skill or a `settings.json` — which is why this is low and not higher. On this
  box `~/.config` is `775 kesokaj` and the group has no second member, so it
  is not reachable here. Remediation if it is ever worth closing:
  `os.OpenFile(dir, os.O_RDONLY|syscall.O_DIRECTORY|syscall.O_NOFOLLOW, 0)`
  then `f.Chmod(0o700)` — `fchmod` on the descriptor that was inspected, pure
  stdlib `os`/`syscall`, no dependency — at the cost of a build-tag split like
  the existing `owned_unix.go`/`owned_other.go` pair. **My recommendation is
  to leave it and keep this line as the record**: a build-tag split for a race
  whose precondition is already game-over buys defence, not safety, and the
  shorter code is worth more. Second-order note, same site: `os.Chmod(dir,
  0o700)` is absolute, so it also clears **setgid/sticky** on the runtime
  directory, while the printed line shows `Perm()` (`%04o` of 0755) and never
  names those bits — a setgid-inherited runtime dir is silently de-setgid'd.
  Tightening again, impact ~nil, mentioned so it is on the record.
- **[low / confidence: medium]** `internal/harness/state.go:99` and
  `state.go:107` — **the two security-relevant branches this commit adds have
  no test, and the suite cannot reach either.** `ownedByCaller` is unit-tested
  only through a fake `Stat_t` (`owned_unix_test.go:21-27`); grep shows no
  test anywhere referencing the `!ownedByCaller` skip inside
  `TightenConfigDir`, and none referencing the `note: could not correct the
  mode` string. Reaching them needs a second uid or a way to make `chmod`
  fail, neither of which exists in a `go test` on one account — so this is a
  gap in the *evidence*, not a defect in the code, and I name it because the
  rest of the mechanism is well covered and a reader could take that as
  coverage of the whole. What **is** pinned, and pinned bidirectionally:
  `audit_test.go:239-242` asserts the `mode` line is present for a 0755
  directory and **absent** for a fresh one (`has != (pre == "0755")`);
  `:246-266` asserts the dry run prints the line and does **not** change the
  mode; `:268-294` asserts the symlink target keeps 0755 and that **no** line
  claims otherwise; `:131-140` and `:175-177` assert `report` and `diff` leave
  the mode alone. Those are genuine must-fail checks of the behaviour they
  name. Remediation: none available in-process; the honest move is a line in
  the testing guide saying the not-owned and chmod-failure branches are
  covered by reading, not by running.

### Carried, pre-existing, and **not** a regression of this range

- `internal/harness/apply.go:30` / `state.go:68` — **an unwritable runtime

- `internal/harness/apply.go:226` — `sh-agent diff`, a read-only verb, still
  *creates* `~/.config/sh-agent` (and `~/.config` when absent) to render a
  temp file. It no longer changes an existing directory's mode — measured
  (probe F: 755 before, **755** after, no leftovers) and pinned

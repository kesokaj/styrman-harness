# Security review — release gate v1.2.3 (v1.2.2..30f7488)

Range reviewed: v1.2.2..30f7488

80 files, 5767 insertions / 112 deletions: 21 source and test files, `README.md`, `ROADMAP.md`,
and 57 trail files under `.agents/docs/`. HEAD `30f7488`; the tree was frozen and no git command
that touches the working tree was run. Every path in the release diff was read (source and tests
from the diff and the surrounding functions; all 57 trail files end to end via a concatenation
under `.agents/scratch/security-gate-v123/`).

## Verdict: FINDINGS — six low, no medium, no high. **Nothing here blocks the v1.2.3 gate.**

The release is a net security improvement over v1.2.2 on every surface it touches: the release-tag
comparison is canonical and refuses a sideways install (`<= 0` plus a `strconv.Atoi` overflow
guard), the adopted-file mode mask stops a group-writable third-party skill landing in the tree
every install ships, `yamlQuote` no longer lets a raw control byte end a YAML scalar, `Diff`'s temp
file leaves the system temp directory and is removed on every path, `TightenConfigDir` makes
`~/.config/sh-agent` private in a way that cannot fail an install, and the by-hand install chains in
README and `remote.md` now bind the download to a version the operator names from outside the
download — closing the real hole in the human route, which was that a genuinely signed OLDER
release passes signature and checksum unchanged. The compiled-in `releaseSigner` is byte-for-byte
identical to all six copies in the docs, and `TestReleaseSignerMatchesTheDeployGuide` pins it.
`govulncheck ./...` is clean.

The worst thing left is **an integrity hole in `install` that this range brings into its own blast
radius without closing**: a runtime directory that exists and is unwritable makes `install` deploy
all 260 files and then fail at `SaveState`, leaving a fully deployed home with **no manifest** — and
the manifest is documented as "the only thing uninstall trusts", so `uninstall` then removes
nothing, `status` can never report a stale file, and every later `install`'s resync prunes nothing.
The prior round measured it (probe J), recorded it as pre-existing, and noted that `Install` now has
a hook at the top where it did not before. Low, because the trigger is an unusual directory state
and nothing is destroyed — but it is a silent loss of the one record `uninstall` depends on.

## Findings

- **[low / confidence: high]** `internal/harness/apply.go:30,135` with `internal/harness/state.go:64-68` — **an unwritable `~/.config/sh-agent` leaves a fully deployed home with no manifest.** `TightenConfigDir` runs first and correctly skips a directory that is already private (`0500` passes the `Perm()&0o077 == 0` test at state.go:100), so nothing checks that the directory can be *written*; the run proceeds through every file and fails only at `SaveState` → `ConfigDir`/`writeAtomic`, with `saving manifest: … permission denied` after 260 files are on disk. `State` is documented at `state.go:12-14` as "the only thing uninstall trusts: a path not listed here is not sh-agent's to delete", and `Uninstall` (`apply.go:271-274`) prints "nothing installed" and removes nothing when the manifest is absent — so the home holds 260 sh-agent-written files that sh-agent will never account for or remove. Exploitable in principle as a self-inflicted, silent loss of the uninstall record: any `--home` whose `.config/sh-agent` exists and is not writable (a handed-over home, a directory a previous `sudo` run created, a dotfiles symlink into a foreign tree) triggers it, and the failure is announced only after the deployment is complete. Measured by the round-3 reviewer (`reviews/2026-09-18-security-e7fec88-42840fb.md` § Carried) and recorded there as out of range; it is in range now because `TightenConfigDir` put a hook at the top of `Install` and this is the call that belongs beside it. Remediation: a writability probe beside `TightenConfigDir(home, dryRun, out)` — `ConfigDir(home)` plus an `os.CreateTemp(dir, ".probe-*")`/`os.Remove` on a non-dry run — so an unusable runtime directory fails the run **before** the first write. Stdlib `os` only; no dependency.
- **[low / confidence: high]** `internal/harness/state.go:76-91` + `internal/harness/report.go:455`, `internal/harness/apply.go:225` — **the 0700 tightening is bound to `install`, not to the commands that put private data in the directory.** `ConfigDir` creates 0700 when absent and, by design (operator's option 1, round 3), leaves an existing directory's mode untouched; only `TightenConfigDir` corrects it and only `Install` calls it (`apply.go:30`). `cloneThrowaway` (`report.go:455`) clones the private `styrman-harness-feedback` repository under that directory, and `Diff` (`apply.go:225`) writes rendered source there. On a machine upgraded to v1.2.3 whose `~/.config/sh-agent` is still 0755 from an older install, `sh-agent report` before any `install` exposes the throwaway clone — that machine's own redacted feedback — to every local account for the life of the clone. **Disposition on record:** the round-3 report's `## Outcome` (`reviews/2026-09-18-security-e7fec88-42840fb.md`, last bullet) already accepts this — "every `update` runs an install, and a place that never updates is a place that never receives anything". Filed again because the acceptance rests on an operator ordering (`install` before `report`) rather than on a check, and `report` is the one verb that clones a private repository. Remediation if it is ever worth closing: call `TightenConfigDir` from `report` too (it has no error return, prints what it changes, and is a no-op on a dry run) — one call, no dependency.
- **[low / confidence: medium]** `internal/harness/frontmatter.go:167-189` (`yamlQuote`) — the new escaping covers `\`, `"`, `\n`, `\t`, `r < 0x20` and `0x7f`, which closes the raw-control-byte hole the audit found. It does **not** cover U+0085 (NEL), U+2028 (LS), U+2029 (PS), or the C1 range U+0080–U+009F. A YAML 1.1 parser (libyaml, and the Python/JS parsers built on it — the likely readers of Antigravity's derived `agent.md`) treats NEL/LS/PS as line breaks and most of C1 as non-printable, so a description carrying one can still terminate or corrupt the double-quoted scalar and, in the line-break case, put author-chosen text at the start of a new frontmatter line. The trust boundary is repo-authored `agents/*.md` (`yamlQuote`'s single caller is `derive.go:36`, on `a.Description`; `adopt` lands third-party content in `skills/`, not `agents/`), which is why this is low. **This is the unfixed residual of the round-1 finding** (`reviews/2026-09-18-security-160aa16-3209cf3.md`, finding 4), which proposed the exact one-line guard and was not carried into any later round's Outcome. Remediation: extend the arm to `r < 0x20 || (r >= 0x7f && r <= 0x9f) || r == 0x2028 || r == 0x2029`, and add the code points to the table at `internal/harness/audit_test.go:201`.
- **[low / confidence: high]** `cmd/sh-agent/main.go:104-109` — `--home` is absolutized with `if abs, err := filepath.Abs(home); err == nil { home = abs }`, and a failure is swallowed. `filepath.Abs` fails only when `os.Getwd()` fails (the working directory was removed or is unreadable), and on that path `home` stays relative and BUG-080 recurs exactly as before: the checkout route runs the rebuilt binary's install with `cmd.Dir = repo`, so a relative `--home` lands **inside the repository**, while `--dry-run` reports against a different directory. Silent divergence between what a dry run says and what a real install writes is the whole shape of BUG-080, and the round-1 reviewer's note ("falling through with the relative path is the old behaviour, not a new hazard") is true of the code and not of the guarantee the fix now advertises. Remediation: return the error (`return fmt.Errorf("resolving --home %q: %w", home, err)`).
- **[low / confidence: medium]** `.agents/docs/deploy/remote.md:34`, `README.md:129,153` vs `internal/harness/release.go:48` — the human route and the binary route disagree on what counts as the version marker, and nothing pins them together. The docs check `grep -qxF "# styrman-harness $V"` (one space, exact line, no trailing whitespace); the code matches `(?m)^#\s*styrman-harness\s+(v[0-9]+\.[0-9]+\.[0-9]+)\s*$`, which also accepts `#styrman-harness  v1.2.3 `. The publishing step at `remote.md:148` (`printf '# styrman-harness %s\n' vX.Y.Z`) produces the strict form, so the three agree today and the divergence fails safe (the human chain refuses a marker `update` accepts). It is unpinned: no test ties the doc's `grep -qxF` needle to the publisher's `printf` or to the regex, so a future reformatting of the marker breaks the documented human install with no failing test. Note also that the code's `\s` spans newlines under `(?m)`, so the regex can match across lines — inert, because it runs only on bytes the operator's key has already signed. Remediation: one test asserting the three forms agree, as `TestReleaseSignerMatchesTheDeployGuide` already does for the signer line.
- **[low / confidence: high]** `.agents/docs/reviews/2026-09-18-security-c868ed4-bc745dc.md:25` — **two U+0646 ARABIC LETTER NOON inside an ASCII word survive in the release diff.** The round-1 finding that reported them (`warننning` in the explorer's diagnosis brief) was fixed in the brief — I re-scanned every trail file in this range and `plans/2026-09-18-recon-bug-079-diagnosis.md` is clean — but the report that quoted the defect carries the characters verbatim and is itself in the release diff. Arabic letters are strong RTL, so a bidi-aware renderer reorders the run; `.agents/docs/` is read back as agent input, which is the trojan-source class the original finding named. Nothing ships: `embed.go` embeds `context skills agents commands rules` only, so no release binary carries `.agents/docs/`. The original remediation ("a non-ASCII grep over `.agents/docs/` outside the intended typography set catches the next one") is exactly the check that was not run on the fix's own commit. Remediation: replace the two characters by code point (never by typing the escape — BUG-057's class), and add the sweep to the release gate.

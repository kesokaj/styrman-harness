## Findings

- **[low / confidence: high]** `internal/harness/apply.go:68-76` — When `readErr != nil` and is *not* `fs.ErrNotExist` because the destination is a directory (`EISDIR` from `os.ReadFile`), the code prints `update ~/<rel> (previous file unreadable: <err>)` (line 69) *before* attempting the write, then `writeAtomic`'s final `os.Rename(tmp, dest)` fails because you cannot rename a file onto an existing directory. I reproduced this directly: `os.Rename` on a plain file over a directory returns `IsADirectoryError(21, 'Is a directory')` — i.e. `EISDIR`, not `EEXIST` as the plan's D9 states. Practically: `Install` returns the wrapped error immediately, so (a) the transcript already shows an "update" line implying the write is in progress/succeeding for a path where the write in fact never happens, and (b) every file later in `files` that hasn't been processed yet gets no line at all and is silently left unvisited — the operator only learns something failed from the trailing error, with no summary of what did or didn't happen. D6's rationale ("a previous file that exists but cannot be read is written over") does not hold in this specific sub-case, and the plan's own D9 acknowledges the install "would refuse rather than write" but doesn't address the message-order/silent-truncation consequence, only the test fixture. Not a data-loss bug (nothing is corrupted, the directory is left alone) and the plan already treats the residue as accepted, so this is low severity — but the report is worth having on record since it was explicitly asked for and the error text propagated (`EEXIST`) in the plan doc is factually wrong.

Everything else checked came back clean:
- `errors.Is(readErr, fs.ErrNotExist)` correctly covers both "no previous file" and "parent directory missing" (both surface as `ENOENT` from `os.ReadFile`), matching D6's "add" case.
- A dangling symlink at `dest`: `os.ReadFile` follows it, gets `ENOENT`, labelled `add`; `writeAtomic`'s final `os.Rename` replaces the symlink's directory entry (not its stale target) with the real file — correct and safe, just worth knowing the label doesn't distinguish "nothing there" from "a broken link was there."
- `mode` lines only fire from the `bytes.Equal` branch (apply.go:39-58), never alongside `add`/`update`, so `--dry-run` never prints a `mode` line for a file that a real run would actually be adding/updating instead of chmod'ing — verified against `TestInstallNamesEveryChange` cases 6/7.
- `%04o` formatting on `Perm()` (apply.go:51-52) strips setuid/sticky/setgid bits by design (both sides of the comparison use `.Perm()`), so a special-bit-only difference is neither detected nor printed — consistent with how the rest of the codebase treats file modes (0644/0755 only); no finding.
- `TestInstallNamesEveryChange`'s `t.Skip` for root (harness_test.go:1731-1733) sits after cases 1–3 (first install, second identical install, changed-source update) and before cases 4–7 (mode correction, unreadable-file write-over, dry-run variants), all of which do need non-root (root bypasses the `0666`/`0000` permission checks the assertions depend on). Ran the suite as `kesokaj` (non-root) to confirm cases 1-3 execute unconditionally and 4-7 also ran (no skip triggered) — matches D9.
- `grep -rn 'no longer in the repo\|remove  ~/'` outside `.agents/docs` found only the two `apply.go` producers, no caller parsing the old "no longer in the repo" wording or the `remove` line format — the wording change (D-consistent) has no broken consumer.

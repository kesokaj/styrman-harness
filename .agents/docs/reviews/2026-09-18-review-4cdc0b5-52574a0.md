# Review — BUG-078 PATH-shadow guard (4cdc0b5..52574a0)

Range reviewed: 4cdc0b5..52574a0

## Verdict: REQUEST CHANGES

The overall design (inject a `resolve` function, compare resolved paths, stop scanning PATH once the bin dir is reached) is sound and the new tests are behavioural, not source-text assertions. But `status`'s shadow report and `pathHint`'s message choice are both gated by `binOnPath(home)`, and `binOnPath` uses a strictly narrower match (`p == bin || strings.TrimSuffix(p, "/") == bin`) than `PathShadows`'s own `filepath.Clean(dir) == binDir` test. I reproduced a concrete PATH form (a double trailing slash on the bin dir, e.g. `PATH=/a:/home/u/.local/bin//`) where `binOnPath` reports "not on PATH" while `PathShadows` (via `Clean`) recognises the same entry as reaching the installed binary. In that state `status` skips the shadow loop entirely, so a real shadow earlier in PATH is silently unreported — reproducing the exact BUG-078 failure mode ("status reported drift none" about a binary the shell does not run) that this diff exists to prevent. I also confirmed a hard link to the installed binary is wrongly reported as a shadow, contradicting the code's own stated invariant ("a link ... runs the same file, so it is not a shadow") because `ResolveExecutable` uses `filepath.EvalSymlinks`, which does not resolve hard links to a common path.

## Findings

- **[high / confidence: high]** `cmd/sh-agent/main.go:383-390` (`status`) and `cmd/sh-agent/main.go:640-676` (`binOnPath`, `pathHint`) — `binOnPath` decides "is the bin dir on PATH" with plain string equality plus a single trailing-slash strip, while `PathShadows` (`internal/harness/pathguard.go:33`) decides the same question with `filepath.Clean(dir) == binDir`. These disagree on PATH entries `Clean` normalizes but the string check does not (verified: `PATH=/a:/home/u/.local/bin//:/b` — `binOnPath` returns `false`, `filepath.Clean("/home/u/.local/bin//") == filepath.Clean(bin)` is `true`). Because `status` only enters its shadow-reporting loop `if binOnPath(home)` (main.go:383), this exact PATH form makes `status` print no `shadowed` line even when `shadows(home)` (which calls `PathShadows`) would find one — a real shadow on a real home goes unreported, silently, which is the precise failure this change was written to close. Fix: make `binOnPath` use the same `filepath.Clean` comparison `PathShadows` uses (or better, derive "on PATH" from whether `PathShadows`'s own loop reaches `binDir`, so there is one source of truth instead of two). Add a test with a non-canonical-but-equivalent PATH entry for the bin dir (double trailing slash or an embedded `/./`) asserting `status` still emits `shadowed` when a real shadow precedes it.

- **[medium / confidence: high]** `internal/harness/pathguard.go:47-53` (`PathShadows`) / `pathguard.go:60-69` (`ResolveExecutable`) — a hard link to the installed binary is reported as a shadow, not silenced, though the code's own comment says a same-file link "is not a shadow." `ResolveExecutable` calls `filepath.EvalSymlinks(p)`, which only follows symlink chains; a hard link is a second directory entry for the same inode and is not a symlink, so `EvalSymlinks` returns the hard-link's own path unchanged. Verified: two hard-linked copies of the same file each `EvalSymlinks` to themselves (`a/sh-agent` → `a/sh-agent`, `b/sh-agent` → `b/sh-agent`), so `got == target` in `PathShadows` (pathguard.go:52) is false even though they are byte-identical and share an inode. This produces a false-positive shadow warning (`install`/`status` would warn about a binary that is in fact the same file), undermining trust in a warning meant to be actionable. Lower severity than the first finding because it is a false alarm rather than a silent miss, but it is a real deviation from the stated and tested intent ("A symlink or bind that resolves to the installed binary ... is not a shadow" — the comment's own word "bind" implies same-file cases beyond symlinks were meant to be covered). Fix: compare `os.SameFile` (device+inode) between the candidate and the installed binary in addition to (or instead of) path-string equality after `EvalSymlinks`, or narrow the comment/doc claim to "a symlink" only if hard links are knowingly out of scope.

- **[low / confidence: medium]** `README.md` — "a machine ran a stale tree for an hour this way (BUG-078)" is a specific, quantified claim not present in `.agents/docs/bugs/BUG-078-release-binary-shadowed-by-earlier-path-entry.md` (the only trail document given as input here); the bug record's Repro section says only "Not reproduced in this session (measured live on devbox by the operator)" with no duration. Not scored as a hard finding since the claim may be sourced from a `changes/` entry outside this review's stated input, but it is worth confirming against that source before shipping the doc change.

## Criteria

1. **Dead code** — pass. No orphaned functions; `PathShadows`, `ResolveExecutable`, `binOnPath`, `shadows`, `shadowHint` are all called from `main.go` or tests.
2. **Flow tracing** — fail on the high finding above: `status` → `binOnPath` → (skips) `shadows` → `PathShadows` is a broken hop where the guard and the guarded function disagree on their shared predicate. `pathHint` has the same disagreement but degrades more gracefully (still prints a shadow-naming message via the "not on PATH" branch, just mislabeled) since it does not gate the shadow report itself, only which message wins. Error handling: `resolve` failing on the installed binary is correctly handled (`haveTarget` short-circuits the equality check so it never accidentally suppresses real shadows) — verified by the existing "an unresolvable installed binary still reports shadows" test case and matches the dispatch's specific concern.
3. **Standards conformance** — pass otherwise. `gofmt`/`go vet`/`go test` all clean on the changed packages (verified: `go test ./internal/harness/... ./cmd/sh-agent/...` passes). Doc messages in README.md and remote.md match the exact strings the code prints (`warning: … comes before … on PATH, so \`sh-agent\` runs that one`, `shadowed   … comes first on PATH …`, `note: … is not on PATH, so \`sh-agent\` runs … instead; put … ahead of it`) — all three quoted forms grep-match `cmd/sh-agent/main.go` verbatim.
4. **Directory layout** — pass. `pathguard.go`/`pathguard_test.go` extend the existing file of the same name in `internal/harness`; `main_test.go` additions sit beside the code they test.
5. **Simplicity (DIY-except-security)** — pass. No new dependency; `filepath`/`os` stdlib only; the `resolve` injection is a small, justified seam for testability, not speculative abstraction.
6. **Decoupling** — weak: `binOnPath` (main.go) and `PathShadows`'s bin-dir match (pathguard.go) implement the same "is this directory on PATH" predicate twice, with different normalization, in two files/packages — the root cause of the high finding. Consolidating to one predicate (exposed from `internal/harness`) would remove the seam that just drifted.

# Security review — 2c0f215-166aa39   (2026-10-08)

Range reviewed: 2c0f215..166aa39 (10 commits, metrics store Phases 0-7; 59 files, +6007/-119). Diff: `git diff 2c0f215...166aa39`.

## Status: COMPLETE

## Verdict: FINDINGS

The worst problem is that metrics ingest now runs `git log` without anyone watching, every night and on every `ingest`, inside every project root any session ever recorded. That covers each Claude Code transcript's `cwd`, each Antigravity workspace URI and each sandbox work dir read with `--source`, and every root already stored is re-run on every later ingest (`events.go:46` selects all main sessions). The call disables `core.fsmonitor` and nothing else. Repo-local config is therefore still trusted, and `log.showSignature=true` combined with `gpg.program` (or `gpg.format=ssh` with `gpg.ssh.program`) names a program that `git log` runs on any signed commit in the window. The earlier security rounds of 2026-10-01 already counted a project's `.git/config` as untrusted. This change widens the set of repos it applies to, from indexed projects to every directory a transcript names. That includes A/B and sandbox work dirs where the agent under test wrote `.git/config` itself (`ab-kit/run.sh:73` runs the ingest automatically). No new dependency was added. Store SQL is parameterised. The HTML report escapes every data string. Report collection is an allowlist, so the metrics store, its exports and its HTML reports are never sent. The dream prompt gets only fixed keys and numbers.

## Findings
- **[medium / confidence: medium]** `internal/metrics/events.go:192` (`commitsIn`), and `internal/trail/trail.go:20` (`Dates`, now also reached from metrics through `events.go`) — `git log` runs in roots taken from transcript data, with repo-local config honoured apart from `core.fsmonitor`. `log.showSignature` together with `gpg.program`/`gpg.ssh.program` in a repo's `.git/config` makes `git log` start the named program for a signed commit dated inside the window (the committer controls the date). git-subtree had to add `--no-show-signature` because this setting overrides custom `--format` output, which is why confidence is medium; no probe was run, by design. The trigger is a repo the operator once opened a CLI in, or a sandbox repo an agent under test controlled, and nobody is prompted. `trail.Dates`'s `git log` passes neither `--no-optional-locks` nor any `-c` override. **Remediation:** pass `--no-show-signature` and `-c log.showSignature=false` to both `log` calls. Better, add one shared helper for every git call into a project (`-c core.fsmonitor=false -c log.showSignature=false -c core.hooksPath=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, env `GIT_CONFIG_GLOBAL` left alone). Also consider running joinEvents only for roots that are indexed projects (`search` project list) or under `--source`, not for every directory ever recorded. Add a test that sets `log.showSignature=true` and `gpg.program=<a marker writer>` in a fixture repo and asserts the marker is not written.
- **[low / confidence: high]** `internal/metrics/agy.go:62` (`metrics-agy-*`), `internal/dream/metrics.go:57` (`dream-metrics-*`), `internal/dream/run.go:334` (`removeCopies`) — the new temp dirs under `~/.config/sh-agent/` hold full copies of Antigravity conversation databases (prose, tool arguments) and a full copy of `metrics.db`. They are removed only by `defer os.RemoveAll`. A killed nightly run (timer stop, reboot, OOM) leaves them behind for good. `removeCopies` sweeps only `dream-agy-` and `dream-projects-`, the exact sweep added for this leftover case. That conflicts with R4's "never arguments or prose" for state at rest in `~/.config/sh-agent/` (mode 0700, same user, so it is not exposed to other users). **Remediation:** add both prefixes to `removeCopies`, or call the sweep from `metrics ingest` itself so a run without dream also cleans up. Add a test that plants an old `metrics-agy-x` dir and asserts it is removed.
- **[low / confidence: high]** `internal/metrics/verb.go:339` (`heredocDelims`) — a here-doc opened as `<<\EOF` (backslash-quoted delimiter, valid bash) is not recognised. No delimiter is captured, so the body lines are tokenised as commands, and any body line whose first word matches `programName` (`^[A-Za-z_][A-Za-z0-9_.+-]*$`) is stored as a verb. A bare token line (`sk-…`, `ghp_…`, `AKIA…`) written through such a here-doc would end up in `step_verbs`, against the "no positional word" invariant. **Remediation:** accept a leading `\` before the delimiter word (`<<\EOF`, `<<-\EOF`). Add a Verb test with a token-shaped body line under `<<\EOF` that asserts no verb comes out.
- **[low / confidence: medium]** `internal/metrics/claude.go:448` (`hash`) and `internal/metrics/store.go:55` (export includes `meta`) — `cmd_hash` is SHA-256(salt‖0x00‖full command) cut to 64 bits, and the salt is stored in the same database and written into every `metrics export`. Anyone holding the store or an export can therefore confirm a guessed low-entropy command, arguments included, which is weaker than the spec's "never arguments" wording suggests. High-entropy secrets cannot be recovered this way. I do **not** count this as hand-rolled crypto: it is `crypto/sha256` used as an equality fingerprint, and no authenticity or secrecy claim depends on the salt. `crypto/hmac` would be the idiomatic keyed form if one were ever needed. **Remediation:** state in `specs/sh-agent/metrics.md` that the hash confirms guesses and that an export is as sensitive as the store, or hash only the normalised verb plus a coarse argument count if retry-loop detection allows it.

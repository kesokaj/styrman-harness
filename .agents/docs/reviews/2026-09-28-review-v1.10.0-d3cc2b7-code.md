## Status: COMPLETE

## Verdict: REQUEST CHANGES

The worst problem is in `agents/verifier.md:42`. It tells the verifier to tee a long suite's output to a file, and in practice the long suite is the Go test command. With `cmd | tee file`, `$?` is tee's exit status. The bullet just above (line 41) forbids "a pipe whose status hides the command's", and line 43 requires reading that same command's exit status. So an agent that follows line 42 as written reads exit 0 for a package that failed to build: `go test` prints `FAIL <pkg> [build failed]`, which has no `--- FAIL:` line to count, and that package is recorded as PASS. The new background-job check in the same bullet ("`jobs` prints nothing") can never fail on Claude Code. The new cold-reader early exit in `skills/feature/SKILL.md:80` contradicts three statements in the same skill, one of them in the same paragraph. No repository history (BUG ids, ADRs, dates, the repo's name) leaked into the deployed text. The rendered context at d3cc2b7 is 21,443 bytes, ends with GANNET, and is byte-identical to the probe's `defs/context-new.md`.

## Findings

- **[medium / confidence: high]** `agents/verifier.md:42` — The foreground long suite runs "with its output teed to a file under `.agents/scratch/`". A tee is a pipe, so the status the agent reads is tee's (0).
  - This contradicts line 41 ("never a pipe whose status hides the command's") and line 43, which requires reading the Go test command's exit status. The Go test command is exactly the suite that takes minutes (this repo's `go test -race ./...`).
  - Failure mode: a package with a build error prints `FAIL <pkg> [build failed]` with no `--- FAIL:` line. Tee's status (0) plus a zero `--- FAIL:` count gives a PASS line.
  - Fix: say "redirected to a file (`> <file> 2>&1; echo <name>=$?`), then read the file". If tee must stay, name `${PIPESTATUS[0]}` or `set -o pipefail`.

- **[medium / confidence: high]** `agents/verifier.md:42` — "every background job is ended (`kill` its PID, then `jobs` prints nothing)". Each Bash tool call on Claude Code starts a new shell (shell state does not persist between calls), so `jobs` in a later call prints nothing whether or not the suite is still running. A job started with the tool's own background option is not a shell job at all.
  - The check cannot fail. That breaks the global rule that silence from your own instrumentation is not evidence (context § Hard rules).
  - Fix: check the PID itself (`kill -0 <pid>` fails, or `ps -p <pid>` prints no process line). For a tool-level background task, use the tool's stop and list calls.

- **[medium / confidence: high]** `skills/feature/SKILL.md:80` — The new path: when the third cold-read report says `implementation ready` and every remaining gap is marked NON-BLOCKING, "tick the box … and proceed without asking". It contradicts:
  - line 15: "Four points always wait for the user: … the three-round cap of that check";
  - line 55: the box text is "design ready and implementation ready … or the user's same-turn override";
  - the same paragraph's last sentences: "Tick the Cold-reader check box only on both tokens or a quoted same-turn override".

  Its trigger is also unreadable as written. The cold-reader prompt (line 78) labels only the part-(3) questions BLOCKING/NON-BLOCKING and never the part-(1) gaps, and any gap forces `design needs revision`. So "every remaining gap is one the report itself marks NON-BLOCKING" depends on a label the report never produces. One agent will never take the path. Another will tick the box on `design needs revision` and skip a gate that line 15 says always waits for the user. "The user is told in the next report" does not say which artifact (the phase's `changes/` entry? the chat reply?).
  - Fix: if the early exit is intended, amend lines 15 and 55 and the tick sentence in the same edit. State the trigger in the report's own terms, for example "`implementation ready`, and every item still open is a question the report marks NON-BLOCKING, not a part-(1) gap", or have the prompt classify gaps too. Name where the user is told.

- **[medium / confidence: high]** `.agents/docs/testing/2026-09-28-verify-retro-apply.md` (behavioural table) — The counts of "calls sharing commands with `; echo <x>=$?`" (new 5, 3; old 0, 3) count attempts, not executions.
  - In the probe transcripts (`.agents/scratch/retro-probe/runs/verifier-*.jsonl`), the permission gate refused 12 subagent Bash calls across the four runs (3, 4, 1, 4): `Contains simple_expansion`, `Output redirection … needs approval`, `Contains command_substitution`.
  - The refusals include every attempt at the new rule's "redirected to its own file under `.agents/scratch/`" form (6 of 6). They also include all 3 shared calls in `verifier-new-2`, so the new behaviour never executed in that run. Only 3 shared calls ran under the new definition, all in `verifier-new-1`.
  - `verifier-old-1` is recorded as 0 shared calls, but its call 4 is `go vet ./...; echo "vet exit $?"; go test -race -v -count=1 ./...; echo "test exit $?"`, the same shape.
  - The log mentions no refusal. The project `AGENTS.md` § Testing (BUG-083) says a run refused at the permission gate proves nothing.
  - The log's conclusion (the control did not fail, and there is no measured behaviour change) still stands. But the evidence is misstated, and it hides something relevant: under default permissions the prescribed shared-call forms prompt, which costs the very turns the change is meant to save.
  - Separately, `context-ctl-2` answers "say 'ship' or 'deploy' and I'll run `/preflight`". The log files it under "puts the step on the operator". That is arguable (confidence medium), and the control contrast is weaker than 2-of-2 vs 0-of-2.
  - Fix: restate the table as executed vs refused per run, and add the refusals to Not exercised.

- **[low / confidence: medium]** `context/AGENTS.md:16` — The new clause gives a low finding a third outcome ("put to the operator as a one-line choice"). The same paragraph still says "Findings are fixed or rebutted in the report's `## Outcome`", and `skills/review/SKILL.md:62` (`--fix` round: "apply each finding or rebut it", with the states `fixed` / `rebutted` / `in flight` / `left`) has no state for it. Under `--fix`, two agents will differ on whether to apply the finding or stop and ask.
  - Fix: one clause naming how it is recorded, for example `left: operator — <choice asked>`, in both places.

- **[low / confidence: medium]** `agents/verifier.md:41` — "never `&&`" sits right beside "a leading `cd <dir> &&` … stays attached to every command after it". It is ambiguous whether a shared call may begin with `cd <dir> &&`. The ambiguity is harmless for status reading, since `cd` failing still shows in the next `echo`, but readers will differ.
  - Fix: "never `&&` between the commands".

- **[low / confidence: medium]** `agents/verifier.md:42` ("the tool's maximum, 10 minutes on Claude Code") and `context/AGENTS.md:33` ("Claude Code: `TaskStop`") name only the Claude Code mechanism. Both files deploy to Antigravity (the verifier through `derive.go`). There, the foreground-or-background cutoff has no stated maximum and "stopped" has no named call.
  - Fix: add the Antigravity counterpart, or say "the tool's maximum" without the number.

## Findings
- **[low / confidence: high]** `internal/harness/catalog_test.go:1679-1704` (introduced in this range): the /dev/zero and fifo cases run `runThen` in a goroutine with a 30 s `select` timeout. When it times out, `t.Fatal` ends the test, but nothing kills the `bash` → `sh -c` → `cksum` chain. Evidence: the mutation `if [ -f "$p" ]` → `if true` failed at :1687 as it should. After `go test` had exited, pids running `sh -c for p; ...` and `cksum .../home/.config/sh-agent/endless` were still alive (killed by hand), and `/tmp/TestKitPreambleAssertsCommit1240636892` was left behind. Impact if shipped: anyone who writes this case red-first, or meets a regression in it, ends up with a cksum burning CPU in the background (or, in the fifo case, a process blocked for ever) until they notice it. Separately, `runThen` calls `t.Fatalf` when the process fails to start. That call runs on the non-test goroutine, so it ends only that goroutine, and the test then reports a misleading "hangs" after 30 s. Fix: `exec.CommandContext` with a deadline plus `cmd.WaitDelay` and `SysProcAttr{Setpgid: true}`, killing the whole group on timeout (or wrap the call in `timeout 20`); return the start error to the goroutine instead of calling Fatalf.
- **[low / confidence: medium]** `skills/init-project/assets/agents-tree/docs/testing/guide.md:39` vs `skills/preflight/SKILL.md:63` (both lines changed in this range): Step 2 item 2 now counts a main-agent behavioural, sandbox or real-home tier only when its log "shows its rows run and passed, each as n of N against the row's own criterion". The template line that introduces `owner: main` logs asks only for "the commands run with their exit status". The harness's own `.agents/docs/testing/guide.md:179` has the n-of-N wording; the project template does not. Who is misled: in a scaffolded project, the main agent writes its behavioural log as the template says, and the gate then finds the tier unmet. It fails closed (NO-SHIP), so nothing unsafe ships, but nothing in the template tells the author why. Fix: add "each behavioural row as n of N against its criterion" to the template's `main` clause.
- **[low / confidence: medium]** `skills/preflight/SKILL.md:72` (the deletion check is new in this range; the gap next to it already existed): `git log --diff-filter=D --name-only <base>..HEAD -- <docs-root>/testing/` is correct for deletions. Probed: it prints nothing with no deletion and the path after one. It does not see two other ways a failure can disappear. (a) A FAIL log rewritten in place to PASS is an M, not a D. Item 3 reads "a log in the range whose Status is FAIL", and a gate reading HEAD sees PASS. agents/verifier.md:14 forbids this for the verifier, but nothing forbids it for an `owner: main` log, and the gate does not check. (b) A deletion not yet committed: item 3 counts uncommitted logs, but `git log` does not see a deleted file in the working tree. Fix: also check `git log -p --diff-filter=M <base>..HEAD -- <docs-root>/testing/` for a removed `## Status: FAIL` line, and `git status --porcelain -- <docs-root>/testing/` for ` D`.
- **[low / confidence: high]** `.agents/docs/testing/kit-preamble.sh:64-67,81-83` (the comment is new in this range): a link to a regular file that is re-pointed at another file with the same bytes leaves the fingerprint unchanged.

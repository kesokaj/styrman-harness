# Security review — f7ee817-21ba8dc   (2026-09-17)

Range reviewed: f7ee817..21ba8dc (branch release-binary, HEAD 21ba8dc; working tree clean apart from untracked review/testing docs, so files were read from the tree)

## Verdict: FINDINGS

Nothing in this range breaks the BUG-036 link refusals or lets a non-release version reach the embedded fallback — both were checked directly and both hold. The worst problem is one step removed from the diff: `//go:embed all:…` reads the WORKING TREE, not git, so every gitignored or untracked file sitting in `context/`, `skills/`, `agents/`, `commands/` or `rules/` when the release binary is built is compiled into the artifact that then goes to every place. The repo's `.gitignore` lists exactly the secret-shaped patterns, which is to say the files most likely to be on disk and invisible to git and to review are the ones `all:` will carry. Nothing today enforces embed ⊆ git, and a secret-shaped or `.DS_Store` file in the four flat directories is never read by any loader, so it would ship silently. Below that, five low findings in source selection and one in test hermeticity.

## Findings

- **[medium / confidence: high]** `embed.go:9` — `//go:embed all:context all:skills all:agents all:commands all:rules` embeds from the filesystem; `.gitignore` is invisible to the Go tool, and `all:` also takes dotfiles. Measured on a probe module (`.agents/scratch/sec-review/embedprobe`): `go list -f '{{.EmbedFiles}}'` returned `[d/.dotdir/x.md d/.hidden-local d/local-only.md d/visible.md]` while `git status --porcelain --ignored` showed `!! d/.hidden-local` and `!! d/local-only.md` — i.e. gitignored files embed. On the real tree the sets happen to match today (`go list -f '{{len .EmbedFiles}}' .` = 133 = `git ls-files -- context skills agents commands rules | wc -l`), and `embed_test.go` `TestFilesMatchTree` only asserts disk ⊆ embed, never embed ⊆ git. A secret-shaped file inside `skills/` would at least break the release loudly (the plan walk refuses it for both sources — `TestFSSourceRefusals` "secret-shaped file"); one in `context/`, `agents/`, `commands/` or `rules/` is never read (loaders glob `*.md` only) and ships inside the binary, which release consumers download and which `install` also copies to `~/.local/bin/sh-agent`. Remediation: (a) build release binaries from a clean export of the tag — `git -C <checkout> worktree add .agents/scratch/release-vX.Y.Z vX.Y.Z`, build there — instead of the operator's working checkout (D10 puts the build inside `/preflight` Step 6, not yet written, so this is the moment to fix it); (b) invert the embed test: walk `styrman.Files` and fail on any path that `git ls-files -- context skills agents commands rules` does not list, skipping when git is absent (stdlib `os/exec`, no dependency); (c) have the preflight build refuse when `git status --porcelain --ignored -- context skills agents commands rules` prints any `??` or `!!` line.

- **[low / confidence: high]** `cmd/sh-agent/main.go:477` — `knownCheckout` passes the manifest's repo value to `samePath`, which calls `filepath.EvalSymlinks` on it, so an `embedded:vX.Y.Z` value written by an embedded install (`internal/harness/apply.go:96`) is interpreted as a path relative to the process's working directory. `ResolveSource` was hardened against exactly this (`repo.go:42` skips `EmbeddedPrefix`; `TestResolveSource` plants an `embedded:v1.0.0` harness tree in the cwd and asserts it is not read as a path) — `knownCheckout` was not. Consequence in principle: on a machine whose install came from a release binary, the one guard that stops `install`/`update` from building a checkout the operator never named is satisfied when an entry named `embedded:<installed version>` in the working directory resolves to the walk-found tree (a symlink with an absolute target resolves to that target), after which the tree is `go build`-ed and executed (`main.go:153-166` → `repo.go:178-195`). Requires control of the directory the operator runs in, hence low. Remediation: refuse before comparing — `if strings.HasPrefix(st.Repo, harness.EmbeddedPrefix) { return fmt.Errorf("this install is the release binary %s; pass --repo %s to build and install from a checkout", …) }`, or require `filepath.IsAbs(st.Repo)` before `samePath`; add the planted-directory and planted-link cases to `TestKnownCheckout`, which today only covers absolute recorded paths.

- **[low / confidence: high]** `internal/harness/repo.go:24-31` — `--repo ""` and `SH_AGENT_REPO=` (set but empty) are treated as "not named" (`if named == "" { continue }`) and fall through to the directory walk, the recorded repo, and in a release binary to the embedded files. D15 promises a named path is used or refused, never replaced. A wrapper or systemd unit running `sh-agent install --repo "$HARNESS"` with `HARNESS` unset therefore installs whatever the walk finds, or the embedded release, instead of failing. Remediation: in `main.go`, detect that the flag was actually given (`fs.Visit`) and use `os.LookupEnv` for the variable, then refuse an empty value; `ResolveSource` cannot distinguish the two cases from a bare string.

- **[low / confidence: high]** `cmd/sh-agent/main.go:130-139` — the embedded install path `return installFiles(...)` before `knownCheckout` runs, so an embedded install never consults what the manifest records. Trigger: the manifest records a checkout, that path is no longer a harness tree (moved, renamed, mid-surgery) and the walk finds nothing → a release binary installs its own, possibly older, context/agents/rules over the checkout's newer ones with no confirmation, and `Install` prunes the files the older plan lacks — a silent downgrade of the text every session reads. Remediation: run `knownCheckout` (or an embedded-aware variant) on that path too, refusing when the manifest records a path source unless `--repo` or an explicit confirmation is given; the message can name the recorded checkout.

- **[low / confidence: medium]** `internal/harness/repo.go:32-45` (the D14 ordering) — the working directory and its parents outrank the embedded files for every command, `install` included. For the release-binary audience (downloaded binary, no checkout, no manifest) that means: run it anywhere whose cwd or a parent holds `context/AGENTS.md` plus `skills/`, and that tree becomes the harness; with no manifest `knownCheckout` returns nil, and if the tree is its own git checkout with `go` on PATH, `Reinstall` runs `go build -o … ./cmd/sh-agent` inside it and executes the result. A plain copy (no `.git`) is not built, but its `context/` still lands in `~/.claude/AGENTS.md` and `~/.gemini/config/rules/AGENTS.md`, which every session reads — prompt-level persistence. The mechanism is pre-existing (`FindRepo` walked the same way), newly reachable by people who never intended to use a checkout. Remediation: when `IsReleaseVersion(version)` and no manifest exists, refuse to build or install a tree found only by the walk unless `--repo`/`SH_AGENT_REPO` names it.

- **[low / confidence: high]** `internal/harness/source.go:17-27` — the link refusals are keyed on `Source.Dir != ""` (`checkManagedTree` returns nil, `readRegular` uses `fs.Stat` instead of `os.Lstat`), and `Source` is exported with exported fields. A future `Source{FS: os.DirFS(p)}` with `Dir` unset therefore reads a tree on disk with every BUG-036 refusal silently disabled — fail-open by construction, and the tests already build `Source{FS: m}` literals. Production is safe today: the only constructors are `DirSource` and `EmbeddedSource` (`Source{` literals exist only in `source.go`, `repo.go`'s error returns and `main.go:265`'s empty value). Remediation: unexport the fields and construct only through the two helpers, or key the refusals on "this FS is not the embedded one" rather than on `Dir`. `fs.Lstat`/`fs.ReadLinkFS` would be the clean fix but arrived in Go 1.25 and `go.mod` says `go 1.24.4` — no pin, no dependency (ADR-029).

- **[low / confidence: high]** `internal/harness/harness_test.go:526-577` — `TestResolveSource` is not hermetic: it chdirs into `t.TempDir()` and relies on the parent walk finding nothing, so with `TMPDIR` inside a harness checkout — which this project's own scratch rule makes the natural choice — every assertion inverts. Measured: with `TMPDIR=.agents/scratch/sec-review/tmp` the test fails 12 times (`version "" with no tree: err = <nil>, want harness repo not found`; `release binary with no tree: {Dir:/home/kesokaj/workspace/styrman-harness}`; `a development build must not read a recorded embedded:<version> as a path`), and the same run with the toolchain's default temp dir passes. The D14/D15 gate is thus only as strong as `$TMPDIR`, and a test that fails environmentally tends to get weakened rather than fixed. Remediation: assert up front that no parent of the cwd is a harness tree (`IsRepo`) and fail with that message, or let the test inject the walk's starting directory.

- **Dependencies** — no new dependency; stdlib only (`embed`, `io/fs`, `path`). `govulncheck ./...` → "No vulnerabilities found" (go1.27.1, exit 0). `npm audit` not applicable — no JavaScript in this repository.

- **BUG-036, Q1 (symlink refusals for a tree on disk)** — hold on every read path, verified directly rather than inferred. A binary built into scratch (`go build -o .agents/scratch/sec-review/sh-agent ./cmd/sh-agent`) was run against eight scratch trees with a harmless canary file as the link target, in both must-pass and must-fail states: control (plain tree plus a linked `skills/<name>` with no inner links) → `diff` and `render` exit 0 with no refusal and no canary in the output; file link inside a LINKED skill directory → refused (`…/skills/linked/inner.md is a symlink — a skill ships regular files only`); `SKILL.md` a link inside a linked skill directory → refused by `readRegular` (`…/skills/linked/SKILL.md is a symlink — the repo ships regular files only`); a directory link nested inside a linked skill directory → refused; a `context/` entry link → refused; `agents/` itself a link → refused (`ships regular directories only`); `skills/` itself a link → refused; a `commands/` entry link → refused; a link inside a regular skill directory → refused. All eight exited 1 and the canary's content appeared in no output. The authors' own tests over the same ground pass (`TestManagedDirsRefuseSymlinks`, `TestSymlinkedSkillMdIsRefused`, `TestContextAgentsAndDocsRefuseSymlinks`, `TestSkillFilesAndAdoptCopiesRefuseSymlinks`, `TestRenderContextRefusesSymlinks`, `TestDirSourceFollowsLinkedSkillDir`, `TestFSSourceRefusals`, `TestPlanRefusesSecretShapedFiles`, `TestPlanDropsGroupAndOtherWrite`, `TestResolveSource*`, `TestReleaseBinaryWithoutCheckout`, `TestEmbeddedInstallStateAndRecord`, `TestFilesMatchTree`, `TestEmbeddedPlanEqualsCheckout`, `TestKnownCheckout` — one targeted run, all ok). The `Dir == ""` early return is sound for the embedded FS, which cannot hold a link (`go:embed` skips irregular files); its fail-open shape is finding 6.
- **Q2 (what can reach the embedded fallback)** — only a `vX.Y.Z` version. `version` comes from `-ldflags -X main.version` or, when empty, `versionFromInfo(debug.ReadBuildInfo())`, which prefers the VCS short revision (`+dirty` suffixed) and falls back to the module version, and the gate is `^v[0-9]+\.[0-9]+\.[0-9]+$` with Go's `$` meaning end of text (no trailing-newline match). No runtime flag, env var or file feeds it. `TestResolveSource` pins the rejected shapes (`""`, a revision, `+dirty`, `(devel)`, `v1.2.3-rc.1`, a pseudo-version, `1.2.3`, `v1.2`). A non-empty explicit `--repo`/`$SH_AGENT_REPO` that is not a harness tree is an error on both development and release builds and never falls through (`TestResolveSourceRefusesNamedNonRepo`, `TestReleaseBinaryWithoutCheckout`); the one gap is the empty-but-set case, finding 3.
- **Q3 (`embedded:<version>` as a path)** — three readers: skipped in `ResolveSource` (`repo.go:42`), display-only in `status` via `strings.CutPrefix`, and used as a path in `knownCheckout` (finding 2). The value is written only from the regex-gated version (`apply.go:96`), so its suffix cannot carry `..`, a leading `-`, or a separator. A pre-range binary reading a new manifest would treat the value as a relative candidate path, but the working-directory walk already grants an attacker who controls the cwd the same thing, so that adds no exposure.
- **Q5 (modes and secret-shaped files in what install deploys)** — no regression. Skill files keep `mode = info.Mode().Perm()&0o755 | 0o600`; `embed.FS` reports 0444, so the embedded plan yields 0644 — never wider than the checkout path, and group/other write is still masked off. An executable skill file would LOSE its exec bit from a release binary; `TestEmbeddedPlanEqualsCheckout` is the alarm for that (the plan records it firing on a mutation), but no tracked file under the five directories is `100755` or `120000` today (`git ls-files -s` shows only `100644`), so the "modes equal" claim is currently vacuous — worth saying plainly rather than reading as a guarantee. Context/agents/commands/rules files keep fixed `0o644`. The secret-shaped refusal runs on the same walk for both sources.

Read against the diff by the main agent, 2026-09-17. HEAD at the time: 21ba8dc.

**Fixed**

1. **[medium] `embed.go:9` — an untracked or gitignored file under the five directories is compiled into the released binary.** Reproduced: `printf 'TOKEN=canary\n' > rules/.env` (ignored by `.gitignore:12`) and the embedded set grew to hold it, while `TestFilesMatchTree` and `TestEmbeddedPlanEqualsCheckout` both still passed — the file is never planned or installed, only carried. Fixed by `TestEmbedHoldsOnlyTrackedFiles` in `embed_test.go`: the embedded set must equal `git ls-files` over the five directories, in both directions; it fails with `rules/.env is embedded but not tracked by git`, and skips (naming why) without git or outside a checkout. The release-time half — `/preflight` refusing a release when `git status --porcelain --ignored` names anything under the five directories, and building from the tag's own tree — is Phase 5, added as a task box with D23, because Step 6 does not exist yet on this branch.
2. **[low] `cmd/sh-agent/main.go` `knownCheckout` hands `embedded:vX.Y.Z` to `samePath`, which resolves it against the working directory.** Fixed: `knownCheckout` now refuses on `EmbeddedPrefix` before comparing, naming the release. `TestKnownCheckoutRefusesEmbeddedManifest` covers it; with the guard removed the test fails (the old message resolved the manifest value as a path).
3. **[low] `TestResolveSource` is not hermetic: with `TMPDIR` inside a checkout every case reads that tree.** Fixed: the test now probes the temp directory first and skips, naming why, exactly as the test it replaced did for the working directory.

**Rebutted, with reasons**

4. **[low] empty-but-set `--repo ""` / `SH_AGENT_REPO=` falls through to the walk.** Unchanged behaviour: `FindRepo` skipped an empty value the same way, and the harness's own tests neutralise the variable with `t.Setenv("SH_AGENT_REPO", "")`, which `os.LookupEnv` would turn into a hard error. D15 is about a value that NAMES something that is not a harness tree; an empty value names nothing. Out of scope for this change.
5. **[low] a release binary prefers a harness-shaped working directory or parent, and may `go build` and exec it.** That is D4's source order, chosen by the operator (scope item 3: `--repo`, a checkout found as today, then the embedded files), and the build is still gated by `knownCheckout` and `IsCheckout` exactly as for any binary. Changing the order is a design question, not a defect of this phase; the `knownCheckout` fix above closes the one case where the guard read a release as a path.
6. **[low] the embedded install path returns before `knownCheckout`, so it replaces and prunes a checkout install of the same home.** Behaviour as the plan's per-command table states it (install from `styrman.Files`, copy the running binary); whether a release binary should refuse a home that a checkout installed is a decision for the operator; asked 2026-09-17 and answered in their own turn, "Replace, as it does now" — recorded as plan decision D24, so the behaviour stands and the guard is deliberately not extended to the embedded path.
7. **[low] the refusals key on the exported `Source.Dir`, so a hand-built `Source{FS: os.DirFS(p)}` with no `Dir` would read a tree on disk with the link checks skipped.** `DirSource` is the only constructor for a tree on disk and both fields are documented; no caller builds a `Source` literal for a disk tree (`ResolveSource` and `DirSource` are the only producers, checked with grep). Noted rather than fixed: hiding the field would need an accessor for `main.go`'s `repo := src.Dir`, which buys nothing against a caller that ignores the constructor.
8. **[not a finding] the "modes equal" claim of `TestEmbeddedPlanEqualsCheckout` is vacuous today, since no tracked file under the five directories is `100755`.** Correct, and stated in the test's own comment: it exists so that adding an executable file, which `embed` records as `0444`, fails the test rather than shipping without its execute bit. `git ls-files -s` confirms all 133 files are `100644`.

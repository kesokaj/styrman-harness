# Cold-read review — review-skill plan   (2026-09-13)

Range reviewed: plan file `.agents/docs/plans/2026-09-13-review-skill.md` (no diff exists yet; nothing under `skills/review/` has been written) plus the surfaces it names: `skills/audit/SKILL.md`, `skills/review-standards/SKILL.md`, `skills/preflight/SKILL.md`, `agents/explorer.md`, `agents/reviewer.md`, `agents/security.md`, `agents/verifier.md`, `agents/documentation.md`, `context/AGENTS.md`, `README.md`, `AGENTS.md`, `.agents/docs/testing/skill-matrix.md`.

## Verdict: design needs revision / implementation not ready

The plan is unusually thorough (D1–D9 read like a spec), but it leaves the single mechanical question that determines the shape of the implementation unanswered: how "the target" is actually handed to the dispatched agents. Because the three agents `/review` reuses (`reviewer`, `security`, `verifier`) have their own fixed, unmodifiable scope logic ("establish the diff with `git diff`, `git diff --staged`, **or** `git diff <base>...HEAD`" — singular choice, no mention of untracked files), and the plan's own D2 defines the default "working tree" target as the union of unstaged + staged + untracked source files, the plan does not say who computes that union or how it reaches the subagent. Left as-is, the simplest and most-documented invocation (`/review` with no arguments, line 37 of the plan) is likely to under-scope: the dispatched reviewer will pick one of its own three options and silently miss staged or untracked changes. There is also a live filename collision between the single-lens case and the multi-lens merged record, and a skill-count arithmetic error that the plan's own verification tier would catch by failing, not by passing.

## Gaps — must be decided before implementation

- **[cite plan D2, line 21; agents/reviewer.md Scope section]** — The plan defines the empty-target case as `git diff` + `git diff --staged` + untracked source files from `git status --porcelain`, but `reviewer`/`security`/`verifier` are out of scope for edits (plan line 14: "Out: ... changes to the agents themselves") and their own preflight sections only know how to run one of `git diff`, `git diff --staged`, or `git diff <base>...HEAD` — none of them check untracked files. The plan never states whether `/review` (a) computes the diff/file list itself and pastes it into the dispatch prompt, or (b) tells the subagent in words to run all three checks itself, overriding its own narrower default. This is the single fact that most determines what gets built, and it directly affects whether the plan's own primary documented example (bare `/review`) actually reviews what D2 says it should.
- **[cite plan D4, line 23; agents/reviewer.md "Report — on disk" section]** — `reviewer`'s own fixed report convention already writes to `$docs_root/reviews/$(date +%F)-review-<slug>.md`. D4's multi-lens merged record uses the *identical* path template (`<docs-root>/reviews/<date>-review-<slug>.md`). A plain `/review` (single lens, default `--code`) and a same-day `/review --security --docs` (or `--all`) on the same target collide on the same filename — one silently overwrites the other, and the order of the two runs decides which record survives. The plan needs a distinguishing name for the merged file (e.g. a lens-list suffix or a different verb) before this is safe to build.
- **[cite plan line 13; README.md:87, AGENTS.md:7]** — The plan says the skill counts in README/AGENTS.md go "→ 26," but the repo currently has 27 skill directories (confirmed by `ls skills/`, matching README.md line 87 and repo AGENTS.md line 7, both "27 skills"). Deleting `skills/audit` (−1) and adding `skills/review` (+1) nets 27, not 26. The plan's own Verification tier asserts `go run ./cmd/sh-agent list` → "26 skills, review present, audit absent" — that check will fail against the correct arithmetic unless one more skill is deleted somewhere the plan doesn't name, or the target number is simply wrong.
- **[cite plan D3, line 22; agents/reviewer.md system prompt, "Every report addresses all six — explicitly, even when a criterion passes"]** — The `--simplify` brief tells `reviewer` to cover only criteria 1, 5, 6 and to treat style as a non-finding, but `reviewer`'s own (unmodifiable, per scope) report template requires it to address all six criteria explicitly every time. The plan doesn't say whether the simplify dispatch is expected to still print a full six-criteria section (findings just filtered to three) or whether the brief is meant to suppress sections 2–4 outright — a real conflict between the brief text and the agent's fixed contract.

## Readiness — questions a first-pass implementer would have to ask

- **[BLOCKING]** How is "the target" transmitted to each dispatched agent for the default (no-argument) working-tree case — literal diff/file-list text assembled by the main `/review` skill, or a natural-language scope instruction the subagent turns into its own git commands? (Two implementers genuinely build different code paths here — one adds diff-computation logic to the skill, the other writes prompt text and trusts the subagent's own preflight, which as written won't check untracked files.)
- **[BLOCKING]** What filename does the multi-lens merged record use, given it collides with `reviewer`'s own single-lens artifact naming convention on the same slug/date?
- **[BLOCKING]** Is the target skill count after this change 26 or 27? (Determines what else, if anything, gets deleted, and whether the Verification tier's `sh-agent list` assertion is even satisfiable.)
- **[NON-BLOCKING]** Exact prompt/check text for the new `review` row(s) in `.agents/docs/testing/skill-matrix.md`, and how the `audit` row is marked "folded" (deleted vs. struck through vs. annotated) — a competent implementer follows the existing row style (see the `audit`/`preflight` rows) and makes a reasonable call.
- **[NON-BLOCKING]** Whether the `--simplify` reviewer dispatch prints all six criteria sections with filtered findings, or a trimmed report — reasonable default is "keep the fixed template, filter the findings," which is what a careful implementer would choose to stay compatible with the agent's own contract.
- **[NON-BLOCKING]** How `--security` behaves under `--project` (whole-repo, no diff) — already precedented by the existing `skills/audit/SKILL.md` Step 1, which dispatches `security` over a target directory with no diff, so this is not new territory.
- **[NON-BLOCKING]** What counts as a "source file" among untracked files for the working-tree target (extension filtering, docs excluded, etc.) — a reasonable implementer decides this the same way `verifier`/`reviewer` already scope "changed source."

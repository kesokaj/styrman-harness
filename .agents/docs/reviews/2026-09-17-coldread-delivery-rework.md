# Review — cold read of the delivery-rework plan   (2026-09-17)

Range reviewed: `.agents/docs/plans/2026-09-17-delivery-rework.md` (untracked, at HEAD c7af0de) plus the code surfaces it names: `cmd/sh-agent/main.go`, `internal/harness/{repo,plan,state,apply}.go`, `REQUIREMENTS.md`, `AGENTS.md`, `.agents/docs/deploy/{local,remote}.md`, `README.md`, `.agents/docs/architecture/DECISIONS.md` (ADR-026), `skills/retro/SKILL.md`.

## Verdict: design needs revision / implementation not ready

The plan is well argued on the *why* and its Decisions table is unusually complete, but three of its load-bearing claims do not survive contact with the code it names. `reorder` (`cmd/sh-agent/main.go:446`) keys value-taking flags off a hardcoded map that the plan's two new value flags are not in, so `sh-agent report --message note --dry-run` silently parses as `-message="--dry-run"` with `--dry-run` unset — the command PUSHES when the operator asked it not to. `state.json` is rebuilt from scratch on every install (`internal/harness/apply.go:106`), so the "recorded feedback-repo path" the plan puts second in its resolution order is erased by the next `sh-agent update`. And `secretShaped` (`internal/harness/plan.go:206`) matches filenames only, against a collection list that is four fixed names and a `*.md` glob — not one of which can ever match it, so the plan's redaction guarantee is a check that cannot fire, and the Risks row "no secrets, and `secretShaped` refuses a credential" is asserted about content the filter never looks at.

## Findings

### 1. Gaps — what must be decided before implementation starts

- **[high / confidence: high]** `cmd/sh-agent/main.go:446-451` — **misunderstanding of existing code.** `reorder`'s `takesValue` map holds only `-repo/--repo`, `-home/--home`, `-vendor/--vendor`. The plan adds two value-taking flags, `--message TEXT` and `--feedback-repo DIR`, and its Phase-2 task only claims "`reorder` handles `report --dry-run` as it does every other verb (BUG-002)" — `--dry-run` is a boolean and was never the problem. Trace `report --message note --dry-run`: `flags=["--message","--dry-run"]`, `positional=["note"]`, result `["--message","--dry-run","note"]`; `flag` then binds `-message="--dry-run"`, leaves `dryRun` false, and stops at `note`. The operator gets a real commit and push from a command they dry-ran. **Measured**, 2026-09-17, by copying `reorder` verbatim into `.agents/scratch/` (since removed; no source was touched) and parsing with a FlagSet holding the plan's flags:

```
in=[--message note --dry-run]      reorder=[--message --dry-run note] => message="--dry-run"     dry-run=false narg=1
in=[--feedback-repo /p --dry-run]  reorder=[--feedback-repo --dry-run /p] => feedback-repo="--dry-run" dry-run=false narg=1
in=[--dry-run --message note]      reorder=[--dry-run --message note]  => message="note"          dry-run=true  narg=0
in=[--home /h --dry-run]           reorder=[--home /h --dry-run]       => (correct; --home is in takesValue)
```

So the defect is order-dependent and silent: the operator who writes the flag last is safe, the one who writes it first pushes. Fix: the plan must state that `takesValue` gains both new flags, and Phase 2's expect must name a test for `report --message X --dry-run` asserting nothing was written, not just `report --dry-run`.
- **[high / confidence: high]** `internal/harness/apply.go:106` vs `internal/harness/state.go:14-21` — **the recorded feedback-repo path has no writer and no survival.** `State` has no such field today; the plan's Surfaces line names `state.go` "(the recorded feedback-repo path)" but the Interfaces section never says which verb *writes* it (`report` is described as reading it, third in its resolution order), and `apply.go:106` constructs `State{Repo, Commit, InstalledAt, Vendor, Files}` fresh on every install, with `SaveState` marshalling the whole struct. Any field `report` adds is silently dropped on the next `sh-agent install`/`update`, after which `report` falls through to the `~/.config/sh-agent/feedback/` default and clones a *second* checkout. Decide before coding: who writes it, and whether `Install` must preserve unknown/extra state fields (or whether the path belongs in its own file instead, which would keep `State`'s "manifest, and nothing else" contract intact — see the comment at `state.go:11-13`).
- **[high / confidence: high]** `internal/harness/plan.go:200-225` — **`secretShaped` is reachable but cannot fire on this input, and the plan leans on it as its security control.** It is unexported and `report.go` is in the same package, so the plan's reuse compiles. But it matches a *base filename* against `.env*`, `*.pem`, `*.key`, `*credentials*.json`, `id_rsa`, etc., and the plan's collection set is exactly `feedback.jsonl`, `retros.jsonl`, `state.json` and `proposals/*.md`. None can match any pattern. The Failure-modes row "A collected file matches `secretShaped` → exit 1" is unreachable, and the Phase-2 expect "a `secretShaped` file refused" can only be satisfied by a unit test that injects a filename the real collector would never produce — a test that cannot fail on the shipping path (review-standards §2). The real exposure is *content*: `feedback.jsonl` is the operator's verbatim corrections and `proposals/*.md` are proposed diffs. Decide: either collect a directory (making the name filter meaningful) or drop the claim and state honestly that content is unscanned, and let the Phase-4 security dispatch judge that.
- **[high / confidence: medium]** `cmd/sh-agent/main.go:108-111` — **`report` cannot run where the plan most wants it to.** Every verb except `version` and `uninstall` passes through `harness.FindRepo`, which returns a hard error (`"harness repo not found: run from inside the checkout, pass --repo, or set SH_AGENT_REPO"`) when no checkout is found. The plan's Failure-modes row says a plain copy works with `"harness_commit": null` — true, a plain copy is still a harness-shaped tree — but the Risks section simultaneously asserts that a styrman-crew project home receives *installed files, not a checkout*. On such a machine there is no harness tree at all and `report` exits 1 before doing anything. Decide: does `report` require a repo (and therefore cannot report from an install-only home), or does it join the early switch and degrade the four repo-derived fields (`harness_commit`, `drift`, `skills`, `agents`)? Two implementers will build different things here.
- **[medium / confidence: high]** Plan `## Failure modes`, row "The feedback checkout is dirty" — **"It is committed along with the run" contradicts the project's own git rule and the plan's own redaction row.** `AGENTS.md`/`context/AGENTS.md` require staging by name and forbid `git add -A` with untracked files present. Committing whatever a second process left in the feedback checkout also routes around the `secretShaped` gate, which only inspects *collected* files. Decide: stage the run directory's files by name, and either refuse a dirty checkout or name it and leave it.
- **[medium / confidence: high]** Plan `## Phases`, Phase 3 first task — **the Verification criterion is written so it cannot catch what the task is for.** The grep is `git grep -n 'styrman-crew\|argolis' .agents/docs/deploy README.md AGENTS.md`. It does not search for the word *mirror*, and it does not search `skills/`. Standing restatements that survive it: `AGENTS.md:64` ("Machines, mirrors, and the signed-tag release procedure (ADR-026)"), `AGENTS.md:38` ("a downstream mirror … BUG-015"), `README.md:53` ("deployed to every install and every downstream mirror"), `.agents/docs/deploy/local.md:27` ("a downstream mirror (BUG-015)"). The Phase-3 AGENTS.md task only covers "the Release section".
- **[high / confidence: high]** `skills/retro/SKILL.md:132` — **a skill instructs an agent to read the section this plan deletes, and the plan declares `skills/` untouched.** The retro skill tells a harness-scope application to "name the downstream mirrors its `deploy/remote.md` lists as the next task in their projects". Phase 3 retires `deploy/remote.md` § Downstream mirrors. The plan's "Not touched, deliberately: `context/`, `skills/`, `agents/`. This is a delivery change, not a behaviour change for any agent" is therefore wrong as stated: this *is* a behaviour change for the retro agent, which will follow a dangling pointer. Either the plan touches that line or it explains why a dead cross-reference is acceptable.
- **[medium / confidence: high]** Plan Phase 1, second task — **R8 is to be "drafted here" and the plan contains no draft.** The global rule for an immutable file is propose the exact edit → approval → ADR → one commit. The operator cannot approve text that does not exist, and a first-pass implementer has nothing to show them. Decide whether R8 permits that or whether R7 needs an amendment too (both are immutable-file edits requiring approval).
- **[medium / confidence: medium]** Plan `## Risks`, row 3 — **"No project source, no secrets" is asserted and contradicted by what is collected.** `feedback.jsonl` entries carry a `project` field by design (`skills/feedback/SKILL.md:13`), `retros.jsonl` lines carry project paths (`skills/retro/SKILL.md:119`), and `proposals/*.md` hold proposed diffs of project rules in full (`skills/retro/SKILL.md:118`). `state.json` adds the absolute repo path and ~260 `$HOME`-relative paths. - **[medium / confidence: medium]** Plan `## Interfaces`, the `go` field — **an implementation choice named in the record shape with no decision behind it.** `"go": "go1.27.1"` can be `runtime.Version()` (the toolchain that built the running binary) or `exec` of `go version` (the host toolchain on PATH). These differ on this very box: HEAD's commit message describes a user-level go1.27.1 SDK placed *ahead of* `/usr/bin/go`, and `Reinstall` pins `GOTOOLCHAIN=local` precisely because the two diverge (`internal/harness/repo.go:170-180`). The plan never says it comes from `os.Hostname()`, nor what happens to an empty result, an error, an FQDN with dots, or a name containing a separator. This repo already treats path safety as a live concern (`internal/harness/pathguard_test.go`, and `LoadState`'s `filepath.IsLocal` drop at `state.go:44-50`); a new attacker-free-but-unvalidated path component should still be constrained deliberately.
- **[medium / confidence: medium]** Plan `## Interfaces`, resolution order — **no behaviour defined for a resolved directory that exists but is not the feedback checkout.** "When that directory does not exist it is cloned" covers only absent. An existing `~/.config/sh-agent/feedback/` that is empty, is not a git repo, or is a clone of something else gets no stated handling, and it is the likely state after a half-finished first run. Name the guard (`os.Mkdir` failing on an existing directory, rather than `MkdirAll`) or the disambiguator.
- **[low / confidence: high]** Plan `## Interfaces`, "`--home` and `--repo` behave as they do for every other verb" vs the literal `~/.config/sh-agent/` throughout — the collection root must be `<home>/.config/sh-agent` (as `statePath` at `state.go:23` does) or the Phase-2 tests cannot run under a scratch home, which R6 requires of every development run. ### 2. Scope — what the plan builds that `## Why` did not name

The `## Why` asks for two things: delivery through `sh-agent` only, and "some sort of feedback function from each place installed reporting back to the main". The plan is disciplined about this — the webservice is assessed and struck (D3), versioned bundles are deferred with a full assessment (D6), and the consumers' own changes are explicitly Out. Against that, three items go beyond the request and only two carry a D-row:

- **[medium / confidence: medium]** `--feedback-repo DIR` **plus** `$SH_AGENT_FEEDBACK_REPO` **plus** a path in `state.json` **plus** a hardcoded default is four configuration mechanisms for one value that, by the operator's own framing (one user, one private repository, four machines), never varies. No D-row asks for any of them. This is configuration for a value that does not vary (review-standards §5), and it is also the source of two findings above (the state field with no writer; the untested resolution order). The simplest correct design is the constant plus one override for tests; `$SH_AGENT_FEEDBACK_URL` alone would cover the sandbox/bare-repo integration tier.
- **[low / confidence: medium]** `--message TEXT` is not in the request and has no D-row. It is cheap and plausibly useful, but it is the flag that triggers the `reorder` defect, so it is not free.
- **[low / confidence: low]** Collecting `state.json` into the report *and* deriving `files`/`installed_at`/`vendor` from it into `report.json` sends the same operation's data in two shapes. One of them is redundant; the plan does not say which is authoritative for a future reader of the feedback repository.

The feedback repository itself, its name, and one-directory-per-run **are** covered (D4). Retiring the mirrors and the tag channel **are** covered (D1, D2, D5).

7. Is the deleted `deploy/remote.md` § Downstream mirrors, referenced by `skills/retro/SKILL.md:132`, in scope after all — or does the "skills untouched" line stand and the dangling reference with it?

Whether the new git calls reuse `repo.go`'s `gitOut`/`exec.Command` style. **The answer should be yes and the plan should say so**: `Pull`'s comment (`repo.go:118-127`) records a deliberate, security-reviewed decision that git runs in the operator's own environment, and `gitOut` (`repo.go:190-201`) is the established error-wrapping shape that surfaces git's stderr. `report.go` lands in the same package, so both are reachable; the plan's silence is the only risk of a second style appearing. Note `gitOut`'s parameter is named `repo` and every existing caller means the *harness* checkout — a second repository flowing through it is fine mechanically but wants a comment.

## Criteria

1. **Dead code** — one finding: the `secretShaped` gate as specified is unreachable code on the shipping path, and the Phase-2 test for it cannot fail. Nothing else in the plan is orphaned; no source was changed, so there is no leftover to delete.
2. **Flow tracing** — fail. Three traces break: `reorder` → `flag.Parse` for the two new value flags; `report` writes state → `install` rebuilds state; `report` → `FindRepo` on a home with no checkout. A fourth, `deploy/remote.md` § Downstream mirrors → `skills/retro/SKILL.md:132`, breaks a documented cross-reference.
3. **Standards conformance** — fail. `AGENTS.md:64`, `AGENTS.md:38`, `README.md:53` and `local.md:27` restate the mirror arrangement and are not covered by the Phase-3 task or its grep; the verb list is restated twice inside `main.go` (lines 5-13 and 35-50); the dirty-checkout row conflicts with the stage-by-name git rule the harness itself ships; R8 is unwritten and R7 is unreconciled.
4. **Directory layout** — pass. `internal/harness/report.go` beside its peers, tests in `harness_test.go` and `main_test.go` next to the code, scratch under `.agents/scratch/` for the integration tier. Consistent with `AGENTS.md` § Layout.
5. **Simplicity (DIY-except-security)** — mixed. No hand-rolled crypto, auth or session handling; the signed-tag channel is being *removed*, not reimplemented, and git/SSH credentials stay the operator's own — correct on the security-exemption axis. Stdlib-only holds (`os/exec` for git, `encoding/json`). Against that, the four-way feedback-repo resolution is configuration for a value that does not vary, and it is where two of the high findings originate.
6. **Decoupling** — pass, with one note. `report.go` in `internal/harness` beside `repo.go` and `state.go` is the right seam, and the verb in `main.go` follows every other verb's shape. The note: adding a field to `State` couples the feedback loop to the install manifest, whose stated contract (`state.go:11-13`) is "the only thing uninstall trusts"; a separate small file keeps those two concerns independently editable.

### Does `report.json` leak by listing file, line and pattern?

No, on this design. `pattern` is one of seven constants written in the source, so it discloses nothing the repository does not already publish. `file` and `line` locate the redaction in the copy that ships alongside it, where `[redacted by sh-agent report]` already marks the same spot — the record adds no information the reader cannot see.

# Security review — report throwaway clone (Phase 3, release-binary)   (2026-09-17)

Range reviewed: 73f2c36..83f3cf6

## Verdict: FINDINGS

The worst of it is `RemoveKeptClone`: its own comment says "a commit that never
reached the remote is the operator's only copy", but the guard it wrote is
`if ahead, err := gitOut(dir, "rev-list", "--count", "@{upstream}..HEAD"); err == nil && ahead != "0"`.
When `@{upstream}` cannot be resolved — no tracking branch configured, a
detached HEAD, a branch renamed away from `main` — `gitOut` returns an error,
the condition is false, and `os.RemoveAll(dir)` runs on a checkout holding
unpushed commits. The guard fails OPEN on exactly the state it exists to
detect; this is **measured**, not reasoned (probe below: the clone is deleted
and the output says "removed the kept feedback clone"). Worse, `update` calls
it unconditionally at the top of the function, before the `checkOnly` branch,
so `sh-agent update --check` — a mode the operator reads as read-only —
performs that deletion. Neither is a confidentiality break; both destroy
operator data in the operator's own home without consent, on a path the diff
newly reaches. The rest of the change is sound: the push target is still the
`FeedbackURL` constant and never `origin`, `verifyFeedback` runs after the
clone and before the sparse-checkout and every write, the retry is bounded at
two attempts, and the redaction path is untouched by this range.

## Findings

- **[medium / confidence: high]** `internal/harness/report.go:471-473` — `RemoveKeptClone`'s unpushed-commit guard fails open. `gitOut(dir, "rev-list", "--count", "@{upstream}..HEAD")` errors whenever the current branch has no upstream (fresh branch, `git checkout --detach`, a branch other than the one `-u` pointed at, a clone whose remote-tracking ref was pruned); the guard is `err == nil && ahead != "0"`, so the error path skips `leave()` and reaches `os.RemoveAll(dir)`. A clean working tree with local-only commits is the precise case the comment above the line names as unrecoverable, and it is the case that gets deleted. Exploitable in principle as destruction rather than disclosure: any state that makes `@{upstream}` unresolvable — including one an operator reaches by hand mid-debug — converts a routine `sh-agent update` into an irreversible `rm -rf` of their only copy. **Measured:** in the probe home, `git -C … rev-list --count '@{upstream}..HEAD'` prints `fatal: no upstream configured for branch 'main'`, and `RemoveKeptClone` then returns `nil` after printing `removed the kept feedback clone …`; the directory and its local-only commit are gone. Remediation: treat the error as a reason to keep, not to proceed — `ahead, err := gitOut(...); if err != nil { return leave("git could not compare it with its upstream") }; if ahead != "0" { return leave(...) }`.
- **[medium / confidence: high]** `cmd/sh-agent/main.go:415` — `update --check` deletes files. `RemoveKeptClone` is called before `Behind`, before the `checkOnly` early returns, and before the dirty-tree refusal, so the documented check-only mode mutates the filesystem. `update --check` is what an unattended or scripted caller runs to ask "is anything pending"; it must not be the call that removes `~/.config/sh-agent/feedback`. The blast radius is one directory today, but the precedent — a destructive step upstream of the read-only gate — is what makes the next one easy. Remediation: move the call below the `checkOnly` returns, or guard it with `if !checkOnly`; on the check path print what it *would* remove instead.
- **[low / confidence: high]** `internal/harness/report.go:464-470` — `RemoveKeptClone`'s cleanliness test cannot see three kinds of operator data it then deletes. `git status --porcelain --untracked-files=all` does not list files matched by `.gitignore` (that needs `--ignored`), does not list stash entries, and `rev-list @{upstream}..HEAD` only compares the CURRENT branch: a second local branch with unpushed commits, a tag made locally, or `git stash` work in that clone is destroyed silently while the output says "removed the kept feedback clone". Remediation: add `git stash list` and `git for-each-ref --format='%(refname:short) %(upstream:track)' refs/heads` to the refusal set, or — simpler, and the shorter fix — stop deleting it at all and only print "this directory is no longer used; remove it when you are done with it", which keeps the whole class of judgement out of the tool.
- **[low / confidence: high]** `internal/harness/report.go:455` + `cmd/sh-agent/main.go:95` — the removal branch is unreachable in the project's own sanctioned test procedure, so it only ever runs for real against the operator's real `$HOME`. `main` does `home := *homeFlag` with no `filepath.Abs` (only the empty case falls back to `os.UserHomeDir()`), and `RemoveKeptClone` joins that value directly, unlike `ResolveFeedback`, which does `filepath.Abs(explicit)` first. With a relative `--home` — `sh-agent update --home .agents/scratch/x`, the exact form `AGENTS.md` prescribes for every development test — `verifyFeedback`'s `EvalSymlinks(dir) != EvalSymlinks(top)` comparison fails (git reports an absolute toplevel, `dir` stays relative), so a genuine kept clone is reported as `kept …: not the feedback repository`. **Measured:** the same probe home passed as a relative path is kept with that message; passed absolute, it is deleted. The direction is fail-safe, but the message is wrong about why, and the consequence is that findings 1-3 cannot be reproduced by the documented verification path. Remediation: `filepath.Abs` the home in `RemoveKeptClone` (matching `ResolveFeedback`), and word the refusal to distinguish "not a feedback checkout" from "could not be verified".
- **[low / confidence: medium]** `internal/harness/report.go:428` — the sparse-checkout pattern interpolates the hostname into a gitignore-style pattern without escaping. `hostDir` replaces only `/` and `\`, and `git sparse-checkout set --no-cone reports/<host>/` treats `*`, `?` and `[...]` as glob metacharacters. A host whose `os.Hostname()` contains `*` (a container or VM given a non-RFC name; there is no `--host` flag, so this is not remotely attacker-set) widens the pattern to `reports/*/` and checks out EVERY machine's reports onto this disk — the exact property the phase was built to remove, failing silently and in the permissive direction. The mirror case is as bad for integrity: a pattern that matches nothing leaves the work tree empty, so `runDir`'s `os.Lstat`/`os.Mkdir` uniqueness probe sees no existing run directories, picks a name that already exists on the remote, and the resulting commit is a fast-forward that OVERWRITES that run's files rather than being rejected. Remediation: fold `*?[]` in `hostDir` to `_` as `/` already is, so the pattern can only ever be literal, and assert after checkout that `reports/<host>` is present when HEAD is born.
- **[low / confidence: high]** `internal/harness/report.go:759` — "the commit stays local" is false on the throwaway path. `commitAndPush`'s non-rejection push failure returns `push failed, the commit stays local`, but for a throwaway clone the deferred `os.RemoveAll(dir)` in `SendReport` deletes that commit on the way out. The message tells the operator a recovery path that does not exist; the honest reading is the opposite — the run is gone, re-run it. Note the related classification weakness on the same line: rejection is detected with `strings.Contains(err.Error(), "rejected")` against git's stderr, which is remote- and locale-influenced. A non-English git does not say "rejected", so a real race is reported with this wrong message and the run is silently dropped; conversely a server-side hook message containing the word triggers the re-clone-and-retry path even after a push that landed, producing a duplicate run directory. Remediation: word the failure from the caller as the rejection case already is, and detect rejection from git's exit status plus `push --porcelain` output rather than a substring of prose.
- **[low / confidence: high]** `internal/harness/report.go:419` — the clone failure message prints git's stderr verbatim: `could not reach %s: %v`. `url` itself is the `FeedbackURL` constant and carries no credential, but the harness deliberately honours the operator's `url.*.insteadOf` rewrites, and git's own failure text for a rewritten HTTPS remote is `fatal: unable to access 'https://user:token@host/repo/'` — git does not redact userinfo there. That string then reaches the operator's terminal and whatever captured it (an unattended run's log, a cron mail). This is inconsistent with `verifyFeedback`, which refuses to print the configured origin for exactly this reason ("The origin itself is never printed: it can carry a token", report.go:499). Remediation: scrub `user:pass@` from git stderr before printing — one `regexp` inside `gitOut`, reusing the `scheme://user:pass@` needle the redactor already carries — rather than widening the redactor.
- **[low / confidence: high]** `internal/harness/report.go:603-612` — the throwaway clone survives a signal. Removal is a `defer` inside the loop closure, which covers a returned error, a refusal and a panic, but Go's default SIGINT/SIGTERM disposition terminates without running defers, so Ctrl-C during the clone, the sparse checkout or the push leaves `~/.config/sh-agent/report-<pid>` on disk. What it holds is this host's own already-redacted reports plus git objects, and the next run at the same recycled pid begins with `os.RemoveAll(dir)`, so the exposure is bounded and the path is inside the user's own config directory — hence low. A second, lower-confidence variant of the same mechanism: two runs sharing a home but not a pid namespace (two containers mounting the same home) collide on `report-<pid>`, and the second run's opening `os.RemoveAll` deletes the first's clone mid-flight — availability only. Remediation: sweep stale siblings matching `report-<digits>` in that exact directory at the start of a run, or `signal.Notify` and remove before exiting.

## Outcome

Read against the diff by the main agent, 2026-09-17. Both mediums were reproduced, then fixed with a test that fails without the fix. Range of the fixes: 83f3cf6..HEAD.

**Fixed**

1. **[medium] `RemoveKeptClone`'s unpushed-commit guard failed open.** Confirmed by reading it: `if ahead, err := gitOut(dir, "rev-list", "--count", "@{upstream}..HEAD"); err == nil && ahead != "0"` — a branch with no upstream makes that call fail, and a failed count fell through to `os.RemoveAll`. Fixed by counting over all local refs against all remote-tracking refs (`rev-list --count --all --not --remotes`) and leaving the clone whenever the count cannot be taken. Measured while fixing: with an unpushed commit on a branch with no upstream the new count is 1 (kept); with `.git/packed-refs` unreadable git exits 128 (kept); with only `.git/refs/remotes` unreadable git still reads packed refs and answers — the first shape I tried, which is why the test pins the `packed-refs` one. Also fixed in the same function: a symlink at that path is refused rather than followed (BUG-036's rule), a stash is treated as work (`git stash list`), ignored files count as work (`status --ignored`), and `home` is resolved with `filepath.Abs` so a relative `--home` — the form this repo's rules prescribe for testing — reaches `verifyFeedback` as an absolute path instead of always "keeping" the clone for a reason that is not true. Tests: `TestRemoveKeptClone`'s new subtests (unpushed work on an untracked branch, an uncountable clone, stashed work, a symlink, a relative home), each seen failing first.
2. **[medium] `update --check` deleted files.** The cleanup sat above every `checkOnly` return, so the read-only mode removed the kept clone. Fixed by moving it below them, beside the work that actually updates. `TestUpdateKeptCloneCleanupOnlyWhenUpdating` covers both halves: `--check` leaves it and says nothing, the same update without `--check` removes it and says so. With the call moved back above the returns the test fails, naming the removal.
3. **[low] an interrupted run left `report-<pid>` behind**, holding a clone of the feedback repository — exactly what this phase removes from a machine. A deferred removal cannot cover a signal. Fixed: `sweepInterruptedClones` runs at the start of the throwaway path and removes `report-*` directories whose process is gone, leaving one whose process is alive so two runs never delete each other's clone. `TestSendReportSweepsInterruptedClones` uses a reaped pid and pid 1.
4. **[low] git's clone error repeated a URL that a rewrite can turn into one carrying a token.** Fixed: `scrubCredentials` replaces the credential part of every URL in both the URL and git's message, consistent with `verifyFeedback` never printing an origin. `TestCloneFailureDoesNotPrintCredentials` fails without it (the token appeared verbatim).
5. **[low] a non-English git could never trigger the retry**, because the rejection is recognised by matching git's message. Fixed: that one push runs through `gitOutC`, which sets `LC_ALL=C` for the call that has to RECOGNISE a message, and the match now covers `non-fast-forward` too. Git still runs in the operator's own environment everywhere else, deliberately.

**Rebutted, with reasons**

6. **[low] a hook message containing "rejected" makes the run retry once.** Accepted behaviour, not a defect: the retry re-clones and re-applies the same run, and a hook that declines again produces `push rejected twice; re-run sh-agent report — nothing is kept locally`, exit 1, with nothing kept. The cost of a wrong guess is one extra clone and push attempt; the cost of missing a real rejection is a lost run.
7. **[low] a pid collision across pid namespaces could make two runs share `report-<pid>`.** Out of scope: `report` is a command the operator runs on a machine, not in two namespaces sharing one `$HOME`; and the first thing `cloneThrowaway` does with its own path is remove it, so the loser of such a race gets a clone error rather than a mixed directory. Named here rather than defended against, because a fix would need a lock file for a case this tool has no evidence of.
8. **[not a finding] the sparse-checkout glob case was not measured.** The pattern is `reports/<host>/` with `--no-cone`, and `hostDir` already reduces a hostname to one path element (no `/` or `\`, `.` and `..` replaced), so the pattern cannot escape the clone; `runDir` additionally refuses a `reports` or `reports/<host>` path that is not a real directory.

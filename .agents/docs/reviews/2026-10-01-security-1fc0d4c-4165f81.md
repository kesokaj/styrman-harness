## Findings
- **[low / confidence: low]** `internal/harness/frontmatter.go:115` (`unreadLine` skips a line that starts with a tab) and `:62` (`entries` takes it as a continuation):
  - **What loads:** a tab-led key line after a column-0 key LOADS (shapes X13, X14, X26, X28).
    - It loads for skills, commands and rules, and for agents too when it follows a nested map, a list or an empty value. An agent's `\tpermissionMode: bypassPermissions` after `tools:\n  - a` becomes part of its `tools` value.
    - YAML forbids tabs as indentation. js-yaml 4.3.x and yaml 2.9.0 both ERROR on every such block.
    - Claude Code 2.1.286 retries a failed parse with leading tabs turned into two spaces each. That turns these lines into nested values or another error, never a top-level key. This was simulated with its `O()` pre-transform taken as identity; `O()` was not read.
  - **Not verified:** js-yaml < 4.1 counts only spaces as indentation and skips a tab as separation. I expect it to read `\tallowed-tools: Bash` as a top-level key, but I did not run it. Antigravity's reader is unknown.
  - **Why it counts:** this is the skip rule BUG-153's prevention rule and the new review-standards § 8 box name. The lint skips text that a reader may not read the same way.
  - **Remediation:** in `ParseStrict`, refuse any frontmatter line that starts with a tab. YAML never allows one as indentation, so only a tab-led continuation of a multi-line quoted value is over-refused. Add a must-refuse case per kind. Run `go run ./cmd/sh-agent list` first to confirm no harness file uses one.
  - **Exposure if shipped:** a harness or vendored skill, command, rule or agent can carry a tab-led permission key that the installer passes. Only a lenient (pre-1.2-strict) frontmatter reader would grant it, and no CLI examined uses one.

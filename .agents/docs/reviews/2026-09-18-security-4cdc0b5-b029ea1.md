# Security review — BUG-078 PATH shadow warning, round 3 (4cdc0b5..b029ea1)

Range reviewed: 4cdc0b5..b029ea1

## Verdict: FINDINGS

Both round-2 medium findings are **fixed and correct, verified by measurement rather than by reading**: each
install block is now a single `&&` chain in which every degenerate outcome of every check exits non-zero
*before* `chmod +x` and before the `mv`, so no unverified byte can become `~/.local/bin/sh-agent`. I probed
the three shapes the brief asks about on this box's GNU coreutils 9.7 — `sha256sum -c - --ignore-missing`
with no listed file present exits **1** ("no file was verified"), with empty stdin exits **1** ("no properly
formatted checksum lines found"), and with a present-but-wrong hash exits **1** — so the missing `pipefail`
on `grep -v '^#' SHA256SUMS | sha256sum -c -` is benign here: the chain reads `sha256sum`'s status, and
every way `grep` can fail produces input `sha256sum` rejects. `D=$(mktemp -d)` failing exits non-zero and
stops the chain at the first `&&` with `D` unset, so `rm -r "$D"` is unreachable on that path. The
`pathguard.go` identity-only walk is correct, strictly better than what it replaced, and I observed it
behaving correctly end to end: a real install into a scratch home with a decoy `sh-agent` first on PATH
printed the right `warning:` line, `status` printed the right `shadowed` line, and both went quiet when the
decoy was replaced by a link to the installed file.

The worst remaining problem is new, introduced by this round's fix, and **observed, not inferred**:
`cmd/sh-agent/main.go:653,655` still print "`%s` is not on PATH" for the `onPath == false` case, but after
this change `onPath == false` no longer means that — it means *PATH does not reach the installed file*,
which is also true when the directory is on PATH and the file is simply not there yet. `sh-agent install
--dry-run` writes no binary and calls `pathHint` anyway (`main.go:273`, unconditional), so a dry run on a
home with no binary yet prints a flatly false diagnosis and advises a PATH reordering that is already done.
I ran it twice — once with the home's bin directory second on PATH, once with it absent — and got
**byte-identical output**, so the message cannot distinguish the two situations. Everything else is low:
residual scratch-directory cleanup, a signer-file name that disagrees with the section it points at, three
mutually exclusive install routes in one copy-pasteable fence, and one of the two rewritten rebuttal reasons
that still does not hold as a checkable statement.

## Findings

- **[low / confidence: high]** `cmd/sh-agent/main.go:653` and `:655` (with `:273`) — the two `onPath ==
  false` messages assert something this round's change made untrue, **observed**. `pathHint`'s doc comment
  was updated to the new meaning ("PATH not reaching it is the old note", `main.go:642-643`) but the two
  message strings were not: they still say `note: %s is not on PATH, so sh-agent runs %s instead; put %s
  ahead of it` (`:653`) and `note: %s is not on PATH; add it so sh-agent is available everywhere` (`:655`).
  Under the old lexical rule those were true statements, because `onPath` *was* "binDir appears in PATH".
  Under identity-only `onPath` (`pathguard.go:30,48` — `haveTarget` is false whenever `binPath` does not
  exist, is a directory, or has no execute bit) they are printed in a second, different situation: the
  directory is on PATH and the installed file is absent. `installFiles` calls `pathHint(home, out)`
  unconditionally, *including when `dryRun` is true* (`main.go:273`; `harness.Install` is the only thing
  gated on `dryRun`), and `--dry-run` is a documented read-only mode (`README.md:143`). Repro run here, in
  `.agents/scratch/security-bug078/`, with a decoy `sh-agent` in `fakebin` and an empty scratch home:

  ```
  # A) PATH = fakebin : <home>/.local/bin : …      <- the bin dir IS on PATH, second
  # B) PATH = fakebin : /usr/bin : /bin            <- the bin dir is NOT on PATH
  # `go run ./cmd/sh-agent install --dry-run --home <home>` prints, in BOTH cases:
  note: …/home/.local/bin is not on PATH, so `sh-agent` runs …/fakebin/sh-agent instead;
        put …/home/.local/bin ahead of it
  ```

  A and B are byte-identical, and A's statement is false. The same run *without* `--dry-run` is correct
  (`warning: …/fakebin/sh-agent comes before …/home/.local/bin/sh-agent on PATH, so `sh-agent` runs that
  one`), which confirms the trigger is precisely "no installed file yet". Why it matters beyond cosmetics:
  this message is the operator-facing half of the BUG-078 guard, the one a new machine acts on, and it now
  mis-names the situation in the direction that wastes the operator's diagnosis (reorder PATH) instead of
  the true one (nothing was installed). The global rule that a description outliving its behaviour is read
  as a guarantee applies to a printed diagnostic at least as much as to a comment, and the read-only-mode
  rule says the test should assert what `--dry-run` prints, not only what the normal mode does. Not a
  vulnerability: no decision is taken on the string, nothing is executed, and the non-dry-run path always
  has the binary written (`plan.go:189`, mode 0755) before `pathHint` runs. Remediation, smallest first:
  have `pathHint` distinguish the two by testing the installed file directly (`os.Stat(bin)`) before
  choosing its message, or return a third state from `PathShadows`; failing that, reword both strings to
  what `onPath == false` now means ("`sh-agent` on PATH is not this binary"). A test pinning `install
  --dry-run`'s output on a home with no binary would have caught it, and none of the two new tests in
  `main_test.go` covers `--dry-run`. Note for whoever fixes it: `TestOffPathInstallNamesWhatAnswersAndDoesNotWarnTwice`
  asserts that exact `note: … is not on PATH, so `sh-agent` runs … instead; put … ahead of it`
  string for a home whose bin dir is genuinely off PATH, and that assertion is correct — so the fix
  is a THIRD message for "on PATH, nothing installed there", not a rewording of this one, and the
  existing test must keep passing unchanged.

  now states the opposite behaviour by omission, in the one case (a failed verification) where the reader is
  least likely to clean up. Remediation: `trap 'rm -rf "$D"' EXIT` is wrong for a pasted interactive chain;
  the honest fix is one line of prose under the block saying a failed run leaves `$D` and to `cd ~ && rm -rf

- **[low / confidence: low]** `README.md:89`, `.agents/docs/deploy/remote.md:28` — `rm -r "$D"` with `D`
  empty. Unreachable in practice and measured as harmless if it were reached: `D=$(mktemp -d)` exits
  non-zero when `mktemp` fails and the chain stops there (probed), so the only way past it is `mktemp`
  exiting 0 with empty output. If that happened, bash's `cd ""` **succeeds** and changes nothing (probed) —
  the chain would then download, write `allowed-signers` and run the checks in the *current* directory,
  which for a reader following the README is plausibly `~` — and the final `rm -r ""` errors and removes
  nothing, so there is no deletion risk, only the round-1 trust-anchor-in-cwd shape. Remediation, if

### The two rewritten rebuttal reasons, checked

The brief asks whether each now holds as a checkable statement. One does; one is half right.

- **Control bytes in a printed PATH entry — the reason now HOLDS.** "The strings are the operator's own
  `PATH` entries, printed as `which -a` prints them, and nothing untrusted reaches them; `%q` would be Go
  quoting, not a shell-safe escape, so it is not the instrument either." Every clause is checkable and every
  clause is true. The variable part of each printed string is a `filepath.SplitList(os.Getenv("PATH"))`
  element (`pathguard.go:33`) joined to the constant `filepath.Base(binPath)` (`:29`); the resolved target
  is never printed; `which -a` does not escape either; and `%q` is Go quoting, so a `$` inside the resulting
  double quotes would expand on paste, which is the correct reason to reject my round-1 remediation rather
  than the copy-paste argument round 2 rejected. This is exactly the correction round 2 asked for.
- **Hung mount on `stat` — the conclusion still holds, the reason still does not, in the same place.** The
  first clause is the corrected one and is true: "the walk's `stat` calls are bounded by the PATH entries
  ahead of the installed file" — `PathShadows` returns at the first `os.SameFile` match
  (`pathguard.go:48-50`), so it never stats past the entry holding the installed file. The second clause
  re-introduces what round 2 rejected: "the same entries the shell's own lookup touches on every `sh-agent`
  invocation from that shell … a place whose PATH crosses a hung mount before `~/.local/bin` already hangs
  on the shell's lookup". A shell stops at the **first** executable `sh-agent`; `PathShadows` continues past
  it to the installed file. So on a PATH of `[shadow, hung-mount, ~/.local/bin]` — the BUG-078
  configuration, the one this feature exists for — the shell's lookup stops at entry 1 and never touches the
  hung mount, while `sh-agent install` and `sh-agent status` hang. The stated reason is therefore false in
  precisely the case the code is written for. The honest version is the first clause alone, plus: the extra
  entries are the ones between the winning shadow and the installed file, and a hang there is an
  availability cost on the operator's own PATH, on the operator's own command, which is acceptable. Severity
  of the underlying issue is unchanged (low, accepted); this is about the record being checkable, per the
  rule that a claim states how it was verified. Note this round did not make it worse — the old lexical
  early return exited at the same PATH position — it is the write-up that is still wrong. One clause that
  *is* fine: "the absolute-path form in the guides skips both" is true of the `./$ASSET version` call, which
  does no PATH lookup and does not reach `PathShadows`; it is not true of the `sh-agent install` that
  follows, but nothing in the rebuttal claims it is.

## Confirmed fixed and correct

- **README block, one chain from `mktemp` to `mv` (`README.md:89-96`).** Traced link by link. Order is
  right: signature (`:93`) → checksum (`:94`) → `chmod +x` → run the file (`:95`) → `mv` (`:96`). `chmod +x`
  being *after* both checks is the load-bearing detail nobody has to remember: a run that fails verification
  leaves a non-executable file, so the accident of executing it is not available. Comments moved above the
  block, so no `#` line can terminate a continuation. `D=$(mktemp -d) && cd "$D"` means both the download
  (`--dir "$D"`) and the relative paths afterwards refer to the same directory. Measured failure statuses,
  all non-zero, all before the `mv`: mktemp failure (assignment status, probed), checksum mismatch (exit 1,
  probed), no listed file present with `--ignore-missing` (exit 1, probed), empty checksum input (exit 1,
  probed). `ssh-keygen -Y verify`'s exit status is read directly by `&&`, not through a pipe.
- **`remote.md` block is now the real procedure, not a sketch (`remote.md:27-35`).** Round 2's medium is
  fixed in every particular it named: `D` is assigned (`:28`), `allowed-signers` is written with the genuine
  signer line (`:31`), `-I ostling.simon@gmail.com` replaces the `<signer>` placeholder (`:32`), and the
  chain runs `&&` from `ASSET=` through `mv … && cd ~ && rm -r "$D"` (`:35`), so the comment that promised a
  cleanup now describes a command that performs it. The `ASSET` variable is quoted at every use
  (`--pattern "$ASSET"`, `chmod +x "$ASSET"`, `"./$ASSET"`, `mv "$ASSET"`), and `"./$ASSET"` cannot be taken
  for a PATH lookup. The remaining literal placeholder is the release tag `vX.Y.Z` (`:29`), which fails
  closed: `gh release download vX.Y.Z` on a tag that does not exist errors and the chain stops.
- **The checksum pipeline's exit status is the right one, measured.** `grep -v '^#' SHA256SUMS | sha256sum
  -c - --ignore-missing` gives the `&&` chain `sha256sum`'s status, not `grep`'s. On GNU coreutils 9.7 that
  status is 1 for: a wrong hash on a present file, no listed file present (`--ignore-missing` prints "no
  file was verified"), and empty input ("no properly formatted checksum lines found") — which is the case a
  failing `grep` produces. There is no input to that pipeline for which `sha256sum` exits 0 without having
  verified a real file. So `set -o pipefail` would add nothing here, and its absence is not a finding.
- **The macOS substitution fails closed either way.** Both documents tell a macOS reader to swap in `shasum
  -a 256 -c -`. `shasum` 6.04 on this box accepts `--ignore-missing` (probed, exit 0 on a present file
  beside an absent one), so the literal substitution works; and an older `shasum` that does not know the
  flag exits non-zero, which stops the chain before `chmod +x`. Not verified on macOS itself (no macOS
  here) — but both outcomes are safe, which is the property that matters.
- **`pathguard.go` — one identity, one walk.** The lexical `binDir` comparison is gone; `grep -rn` over
  `cmd/` and `internal/` finds no `binOnPath`, no `TrimSuffix(p, "/")`, and no `filepath.Clean` of a
  directory for this purpose. `onPath` is true only when a PATH entry holds an executable that IS the
  installed file by `os.SameFile` (`:48`), which is dev+ino on Unix and so catches a symlinked directory, a
  symlinked file and a hard link alike — none of which a string comparison catches. `return shadows, true`
  at the match is correct: nothing later on PATH can win. `seen[cand] = true` moved above the
  `executableAt` check, which tightens round 2's dedupe observation. The walk still opens, reads and
  executes nothing: `os.Stat` and `filepath.{Base,Join,SplitList,Dir}` only. Both new test cases
  (`pathguard_test.go:329-330`) build a real symlinked directory with `os.Symlink`, not a string, and the
  rewritten missing-binary case (`:348-354`) pins the new `onPath == false` meaning.
- **Observed end to end, not only read.** In `.agents/scratch/security-bug078/` with a decoy `sh-agent`
  first on PATH and a scratch home's bin dir second: a real `install` printed `warning: …/fakebin/sh-agent
  comes before …/home/.local/bin/sh-agent on PATH, so `sh-agent` runs that one`, and `status` printed the
  matching `shadowed` line beside `binary b029ea12addf+dirty`. That is the BUG-078 shape being named by both
  commands, on this tree.
- **The two call sites cannot disagree.** `status` (`main.go:389`) and `pathHint` (`main.go:648`) are still
  the only callers, both taking `onPath` from the same return.
- **`local.md:87` closes the gap round 2 named in the guides** — "no `shadowed` line" is no longer offered
  as the whole pass condition; unqualified `sh-agent version` matching what was installed is now required
  beside it, and the sentence says what a mismatch means.

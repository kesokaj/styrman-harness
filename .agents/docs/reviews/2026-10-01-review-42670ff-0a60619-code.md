## Verdict: APPROVE WITH NITS

Nothing in the range is broken on the inputs it targets. The pin checkout with `"<pin>^{commit}"` plus the comparison takes the pinned commit even when a branch, an annotated tag and a remote-tracking ref all share the pin's name. It refuses a tag object's id, a tree's id and an absent id, and the new test fails without the peel (mutation M1/M3 below). The fingerprint is stable when nothing changes. It changes for a new file, a new directory, a new symlink and an append, also through a symlinked config directory, and each of its three edits is pinned by a failing test (M4–M6). The worst problem is new in this range: `-o -type l` makes `cksum` read through every link, so a link in the config directory to a fifo or a character device (`/dev/zero`, `/dev/stdin`) hangs the kit preamble forever (probed: `timeout 5` kills it, rc 124). The old `-L … -type f` never read those. The new comparison line is not pinned by any test. Two older flaws also turned up: a midnight flake in `TestRefreshCatalogScript` (observed once in this review) and a clone that keeps objects the source no longer publishes.

## Findings

- **[low / confidence: high] introduced in this range** `.agents/docs/testing/kit-preamble.sh:79` — `find -H "$kit_real_config" \( -type f -o -type l \) -exec cksum {} +` hands every symlink to `cksum`, which opens the target whatever it is. Failing input: `ln -s /dev/zero ~/.config/sh-agent/x`, or a link to any fifo. The kit hangs before the run, with no message. Probed on a scratch copy of the function: both cases were killed by `timeout 5` (rc 124). A fifo, a socket, a link to `/`, a link to a directory and a link cycle all return at once with a stable value. The old `find -L … -type f` tested the target's type and skipped these. It fails loud (a hang, not a false PASS) and needs an odd link in `~/.config/sh-agent`, hence low. Fix: keep the content pass to regular targets, e.g. `find -H dir \( -type f -o \( -type l -xtype f \) \) -exec cksum {} +`, and add a must-not-hang case with a link to a fifo under the test's temp dir. By design it also reads a linked file's target outside the directory (the comment says so). A link to a huge file is read in full.
- **[low / confidence: high] introduced in this range** `skills/google-catalog/scripts/refresh-catalog.sh:240` — the comparison `[ "$(git -C "$dir" rev-parse HEAD)" = "$3" ] || fail "pin $3 did not check out as itself …"` has no test that fails without it. Mutation M2 deleted the line and `TestRefreshCatalogScript` passed. After the `^{commit}` peel, the only input that reaches it is a pin that is a tag object's id: probed, it peels to the commit and is refused only by this line. Without the line that pin would be accepted, and the manifest would record the peeled commit, not the id the operator typed. Fix: one refuse case with an annotated tag object's id as the pin, expecting exit 1 and "did not check out as itself".
- **[low / confidence: medium] pre-existing, not introduced** `internal/harness/catalog_test.go:1441` (with `refresh-catalog.sh:327,360-364`) — `TestRefreshCatalogScript` failed once at "name with a space: could not restore the good catalog (exit 0)" on the scratch copy of 0a60619. The run straddled midnight (the next command printed 00:00:41). A rerun right after passed, and 42670ff passed. Likely mechanism: the script stamps the manifest with `date +%F` when the table changes, and the `good` snapshot was taken before midnight. A `-race` run of the full suite near midnight can fail the verifier with no code fault. Fix: pass a fixed date into the script under test (an env override) or leave the manifest's date line out of `snapshot()`.
- **[low / confidence: medium] pre-existing, not introduced** `refresh-catalog.sh:222-240` — "a pin absent from the source" is refused only when the object is truly gone. A clone from an absolute-path source (`git clone /path` copies the object store, unreachable objects included) accepts a commit the source no longer reaches: probed, a commit on a dropped detached head was present in the fresh clone (`cat-file -t` → commit). The same happens with a reused work clone after the upstream force-pushes the commit away. Neither applies to a fresh https clone of the real upstreams. Fix, if it matters: before the checkout, check the pin is reachable from a fetched ref with `git -C "$dir" branch -r --contains "$3"` or `merge-base --is-ancestor`.
- **[low / confidence: low] pre-existing wording** `skills/preflight/SKILL.md:64` (item 3, "A log in the range whose Status is FAIL or BLOCKED") — a log written in Step 1 is not committed until the release commit (Step 6), so by git's reading it is not "in the range". Who is misled: a gate reader who holds a committed PASS log from earlier today that reaches HEAD, plus a later uncommitted FAIL log from a flaky rerun (the midnight case above). Item 1 is met, and item 3 read literally does not see the FAIL. Fix: "a log in the range or written today".

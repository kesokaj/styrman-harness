### 1. Carried from round 2: `skill-matrix.md` broad grants

**[medium / confidence: high]** `.agents/docs/testing/skill-matrix.md:13-14`. This is round-2 finding 1, deferred by the range's change entry, and the text is unchanged.

**What the matrix still grants:**
- The Antigravity settings grant `command(*)`, `read_file(*)`, `write_file(*)` and `edit_file(*)`, with no trusted-workspace line.
- The Claude row allows `Bash(bash:*)`, `Bash(python3:*)` and `Bash(curl:*)`, which amount to arbitrary exec and network egress. This defeats the row's own "a cloud command is denied" mock.

**How it now conflicts with `AGENTS.md:66`:**
- On fewest grants, as round 2 found.
- New in this range: `AGENTS.md:66` says a run "counts only when … its `cli.log` [has] no 'invalid allow entry' line". A literal matrix run fails that check, because the matrix grants `list_dir(*)` and agy 1.2.8 rejects it. This partly mitigates the risk: the next matrix run cannot count until someone rewrites the settings line. But the rewrite may only drop `list_dir(*)` and keep `command(*)`.

**Deferral:** I agree it is non-blocking. Step 5 blocks only on a high security finding. The conditions are:
1. The gate report records the decision, and the release entry names it with its reason (Step 6, "Before item 1").
2. The deferral also goes where the next matrix run will see it, which is the handoff's Next Steps or the active plan's Follow-ups. A change entry drops out of the resume read (three newest `changes/`), while the file that run follows still says `command(*)`.

**Remediation:** as round 2 gave it.

### 2. Rest of round-2 finding 2: the sandbox rule never proves it did not over-grant

**[low / confidence: medium]** `AGENTS.md:66`.

**Weakness:**
- **(a) `read_file` is unscoped.** "Fewest grants the run needs" does not say whether a read grant can or must be limited to the clone. `read_file(*)` reaches `~/.ssh`, which holds the release-signing key, and the real home's credential files. The change entry neither scopes it nor records it as an accepted residual.
- **(b) Both named checks are must-pass checks.** They are "no auto-denied line" and "no invalid allow entry line". A per-run file holding `toolPermission: always-proceed` or `command(*)` passes both.
  - At f916e35 the text named `toolPermission: always-proceed` as the thing to avoid. At 56621b6 it forbids only a *copy* of the real file, "which approves every tool".
  - "Fewest grants" excludes an over-grant in principle, but no check detects one.
- **(c) The run-counts rule rewards widening grants (confidence low).** "A run counts only when its stderr has no auto-denied line" pushes the author to widen grants until nothing is denied. A denial is also what a working sandbox does to an instruction-shaped call coming from a fixture or a skill. The rule does not say to read *which* call was denied before adding a grant.

**Why it is exploitable in principle:**
- An over-granted per-run file satisfies every check the rule names.
- The run executes as the operator's uid, beside live CLI credentials, on the host that holds the signing key.
- Nothing on the record would show the over-grant.

**Remediation:**
1. Add a must-fail probe to the rule. One call outside the grant must produce the auto-denied line: a `read_file` of a path outside the clone, or an ungranted command. This is the context's own must-pass/must-fail rule for any check.
2. Name what the file must never contain: `toolPermission: always-proceed`, or `command(*)`.
3. Say that an auto-denied line is read first, and a grant is added only for a call the scenario itself makes.
4. Or record (a) to (c) as an accepted residual in the gate report.

### 3. New: the fallback scan fires on the release's own trail files

**[low / confidence: high that it fires, medium on the consequence]** `skills/preflight/SKILL.md:40`, which is where this range added the `refresh_token` needle, together with Step 6 item 3 at `:88` ("re-running the Step 1 secret scan on the staged diff first, never pushing on a hit").

**Weakness:**
- `command -v gitleaks` reports it absent on this host, so the fallback grep is the scan. Its needles are bare names, and they match prose. Measured:
  - 5 of the 8 untracked `.agents/docs/` files that ride in the v1.7.0 release commit (this report excluded) have lines with a needle: 4, 1, 7, 4 and 1 lines. Three of those files contain `refresh_token`.
  - HEAD's own `skills/preflight/SKILL.md` and this range's change entry also contain it, and so does this report.
- Every hit is a pattern name in prose. A strict token-shape scan found no credential. Its one JSON-key hit, `"refresh_token": "…"` in the untracked code review at line 28, is an ellipsis.
- Read literally, Step 6 item 3 stops the v1.7.0 push after a SHIP verdict. The skill gives no judged-hit path, even though the context says "a filter that fires is read before it counts".
- The pre-existing needles already did this, as round 2 noted. This range adds to it.

**Why it matters in principle:**
- A refuse-on-hit rule that always fires on the gate's own records gets overridden ad hoc. An unrecorded override is how a real secret later rides through.
- Today it fails closed, hence low.

**Remediation (adds no tool; `grep -E` only):**
1. Use token shapes, not names. For example:
   - `AKIA[0-9A-Z]{16}`
   - `AIza[0-9A-Za-z_-]{35}`
   - `ya29\.[0-9A-Za-z_-]{20,}`
   - `sk-ant-[a-z0-9]+-[A-Za-z0-9_-]{20,}`
   - `1//0[0-9A-Za-z_-]{20,}`
   - `"refresh_token" *: *"[^"]{20,}"`
   - `-----BEGIN [A-Z ]*PRIVATE KEY-----`
2. Add one sentence: each hit is read, and a hit judged to be prose is listed in the gate report by file and line.
3. For v1.7.0 now: the gate report records the item-3 hits as judged prose, file by file.
4. Alternatively, put gitleaks on the release host. It is already preflight's primary check, not a new dependency of the code.

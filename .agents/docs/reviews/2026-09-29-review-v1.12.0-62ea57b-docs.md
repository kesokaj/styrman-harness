## Verdict: APPROVE WITH NITS

The range is small (three commits, records plus a ten-line source/skill change) and mostly self-consistent, but the one new behavioural sentence in `skills/init-project/SKILL.md` Step 1 — "Every write this skill makes — a root file, a template copy, a `.gitignore` line, the settings file, the store — first checks that the target path and its directory are not symlinks" — overstates what the file actually implements two steps later: Step 3's root-file loop and Step 4's `.agents/` tree loop carry no `test -L` check at all, only Step 5b (settings/store) and Step 6 (`.gitignore`) do. Given this project's history with exactly this class of defect (ADR-043, BUG-098–103), a claim of blanket coverage that the adjacent code does not back up is worth flagging even though nothing else in the range is broken.

## Findings

- **[medium / confidence: high]** `skills/init-project/SKILL.md:26` vs `skills/init-project/SKILL.md:44-48,58-68` — the new sentence names "a root file" and "a template copy" as covered by the symlink check, but Step 3's copy loop (`for f in AGENTS.md REQUIREMENTS.md TODO.md ROADMAP.md; do [ -e "$f" ] || cp "$ASSETS/$f" "$f"; done`) and Step 4's `.agents/` tree loop (`[ -e "$d" ] && continue … mkdir -p "$dir" && cp …`) have no `test -L` guard on the target path, its directory, or (for Step 4) `.agents` itself — the very directory Step 5b later checks specifically for the store. If `.agents` is a symlink, Step 4 populates the entire scaffold (rules, skills, agents, workflows, commands, docs) through it, unchecked, before Step 5b ever runs. The associated changelog entry (`2026-09-29-1609-post-release-checks.md`) claims this sentence closes "the older writes the security round had named as out of range," which the code does not bear out for Steps 3–4. Fix: either add the same `test -L` guard to Steps 3 and 4's loops, or narrow the Step 1 sentence to the writes it actually covers (settings file, store, `.gitignore`).
- **[low / confidence: low, unverified]** `.agents/docs/testing/2026-09-29-verify-real-home-v1.12.0.md` (Claude Code table, `init-memory-linked-store` row) says "the five default-store files untouched," but the matrix row it is reporting on (`skill-matrix.md`'s `init-memory-linked-store`, built on the `init-memory` base) seeds the default store with "two memories and a `MEMORY.md`" — three files, not five. The five-file count matches this same log's unrelated general Fixture section (a different `.agents/memory` seed used for the context/dream/retro checks), so the number may simply have been copied from the wrong paragraph, or the operator ran a differently-seeded fixture than the row specifies. Not independently reproducible from the record alone — listed as a docs-consistency gap, not asserted as a defect.

# Cold-read — plan `.agents/docs/plans/2026-09-14-documentation-steps.md`   (2026-09-14)

Range reviewed: the plan file, plus the surfaces it names (`context/AGENTS.md`, `agents/*.md`, `skills/{review,preflight,retro,handoff,init-project}/SKILL.md`, `.agents/docs/testing/skill-matrix.md`, `.agents/docs/deploy/{local,remote}.md`, `skills/init-project/assets/agents-tree/docs/deploy/*.md`, `README.md`, and the read-only queue files under `~/.config/sh-agent/proposals/`). No git diff exists for this dispatch — it is a plan cold-read, not a code review.

## Verdict: the plan is mostly a clean, literal set of prose edits against surfaces that mostly still match the plan's description of them — but item 5 (the retro queue backfill) has two concrete defects that will produce divergent implementations or a silently wrong result, and item 4 (the Outcome section) leaves an open question about which agent is allowed to touch a past report.

## (1) Gaps — must be decided before implementation, not left to the implementer's taste

- **Item 5 backfill conflicts with the actual structure of `~/.config/sh-agent/proposals/2026-09-10-retro.md`.** That file has no per-proposal `Status:` line; instead it closes with one blanket line, `## Status: applied 2026-09-10 — all seven, harness commit 50ac771, deployed by \`sh-agent install\`` (line 215), covering all seven proposals in a single sentence. Plan item 5 asks for "a `Status:` line under every proposal heading," and the Phase 1 checklist's own verification for this step (line 58) is `grep -c 'Status:' per file equals its proposal count` — for this file that is 1 vs. 7 today. The plan does not say whether the blanket line is deleted and replaced by seven per-proposal lines, kept alongside seven new ones (redundant, and now two places can drift), or reworded. Two implementers restructure this file differently. *(cite: plan line 29, line 58; `~/.config/sh-agent/proposals/2026-09-10-retro.md:215`)*
- **The plan's own file list for the backfill is incomplete, and the gap breaks the mechanism item 5 exists to build.** Plan line 29 names "the four existing queue files (`2026-09-04`, `09-08`, `09-10`, `09-11`)," but the proposals directory holds six files, including `2026-09-03-retro-final.md`, which has two proposals (P1, P2) already applied — their headings literally say "— applied 2026-09-03" — yet carries zero `Status:` lines anywhere. Item 5's new `/retro --harness` Step 1 rule states "files older than 2026-09-14 predate the line; absent means queued" with no exception carved out. Left off the backfill list as the plan directs, this file's two already-applied proposals will be listed as still-queued findings by the very automation item 5 adds, the opposite of what the feature is for. Either the plan's file list is wrong (should be five, or six with `2026-09-03-retro.md` — which has no proposals — skipped), or the "absent means queued" rule needs an exception for headings that already say "applied." *(cite: plan line 29; `~/.config/sh-agent/proposals/2026-09-03-retro-final.md` headings for P1/P2)*
- **Item 4's "## Outcome" section names no owner or write path.** "Findings are fixed or rebutted in writing, in the report's `## Outcome` section" — but `reviewer` and `security` have no edit tools over their own past artifacts once `/review --fix` (or a later, unrelated task) closes a finding days or weeks later; `skills/review/SKILL.md` Step 5 currently has the *main* agent apply fixes while the lens agents "have no edit tools and never touch source" (their own **report**, though, they do write with `Write`). The plan doesn't say whether the main agent hand-edits the old report to append `## Outcome`, or whether the reviewer/security agent is re-dispatched against its own prior artifact to do it. This is not a stylistic choice — it changes which agent's `Records`/`Never` rules (item 8) govern the edit. *(cite: plan line 28; `skills/review/SKILL.md` Step 5, "reviewer and security have no edit tools and never touch source")*
- **No mechanism ties a later, unrelated task back to the report whose finding it fixes.** Item 4 also covers "the task that acts on the report later" (not just `--fix`), but nothing in the plan or the surfaces it touches gives that later task a way to find which `reviews/*.md` record a given fix answers, especially once findings from one report are fixed piecemeal across several commits. Left as a norm rather than a lookup, this will be inconsistently honored. *(cite: plan line 28)*

## Verdict: FINDINGS

The fixes for the prior review's findings 2, 5, 6 and 8 are correct and complete. Finding 1's code fix is correct for the shapes it names, but `README.md` still carries the dry-run claim that finding retired. The fixes for findings 3 and 4 hold for the cases their tests pin, but each leaves a gap that contradicts the claim written about it in this range.

The worst gap is the push-target check. `verifyFeedback` compares `remote.origin.url` with the feedback URL, but `git push origin` sends to `remote.origin.pushurl` when one is set, and to every `url` value when there are several. Probed on a clone of the feedback bare repository with a `pushurl` pointing at another repository: `SendReport` returned success, and the commit landed only in the other repository. The same happened when the pushurl came from `GIT_CONFIG_COUNT` in the environment, and with two `url` values the push went to both.

Two redaction gaps survive inside the finding-4 fixes, both probed:
- **Split key block:** a private key whose header and footer are separate string values on one JSON line (an array of output lines) has its body sent, while 2 redactions are reported.
- **Secret-named key:** a real JSON key such as `"api_key"` or `"password"` with a plain value is replaced only when nothing else on that line fires. Beside any other hit, it is sent.

All eight findings are low severity. The three that send data need a deliberate local git setting, or a record shape the skills do not write today; none is the everyday leak the prior round fixed. The other five are:
- a credential echoed into an error message;
- a coverage claim that runs the wrong tests;
- dry-run guidance that is stale or scoped to the first run only;
- a fail-safe loss of feedback records;
- credential shapes still unmatched.

- **[low / confidence: high]** `internal/harness/report.go:471-485` (`verifyFeedback`), `:667` (`commitAndPush`) — **the origin check does not cover where `git push origin` actually sends.**
  - **Mechanism:**
    - `git config --get remote.origin.url` returns a single value, the last one.
    - `git push origin HEAD` sends to `remote.origin.pushurl` when that is set, and otherwise to every `remote.origin.url` value.
    - Neither the pushurl nor any `url` value but the last is checked.
  - **Probed** (`TestProbePushURL`, `TestProbeSecondURLAddedFirst`, `TestProbeEnvConfigPushURL`, control `TestProbeControl`):
    - **pushurl:** a clone of the feedback bare repository with `remote.origin.pushurl` set to another bare repository. `SendReport` returned nil; the feedback repository got 0 commits and the other got 1.
    - **Two urls:** `remote.origin.url` set twice, the other repository first and the feedback one last. The check passed and the push went to both (1 commit each).
    - **Environment:** `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=remote.origin.pushurl GIT_CONFIG_VALUE_0=<other>`. Success, 1 commit, in the other repository only.
    - **Control:** the same variables setting `remote.origin.url` were refused, so the check does read environment config. It reads the wrong key.
  - **Contradicts:**
    - the `FeedbackURL` comment ("the only origin it pushes to");
    - `deploy/local.md` § Report back ("Only the feedback repository … or `report` refuses before writing anything");
    - `specs/sh-agent/delivery.md` ("It refuses any checkout whose origin is not that repository").
  - **Why low:** `.git/config` never comes from the remote. This needs a local setting someone made on purpose: `git remote set-url --add`, a pushurl, a copied config, or `GIT_CONFIG_*` exported by a wrapper. It is not the typo or wrong-path accident that the prior finding 3 was about.
  - **Remediation, stdlib via `gitOut`, no dependency:**
    - In `verifyFeedback`, require `git config --get-all remote.origin.url` to print exactly one line, equal to `url`.
    - Require `git config --get-all remote.origin.pushurl` to exit 1 (unset). Both commands read every config layer, the environment included.
    - Add the pushurl and two-url cases to `TestResolveFeedbackFailures` as must-fail tests.
  - **Residual, not raised:** a `url.<base>.pushInsteadOf` rewrite in global config is not covered. The comment deliberately compares the URL "as configured", and rewrites of the GitHub SSH prefix normally keep the repository path.
- **[low / confidence: high]** `internal/harness/report.go:131-143` (`redactLines`) — **a key block whose header and footer sit in different JSON values on one line goes to the walk, and its body is sent.**
  - **Mechanism:** the exception `!(valid && closed && end == i)` skips the whole-block rule whenever the line is valid JSON and the footer is on the same line. Its comment says "A key wholly inside one JSON line is a string value". That is true only when header and footer are in the SAME string. The walk replaces only the strings that carry a needle: the header string (`-----BEGIN`) and the footer string (`PRIVATE KEY`). Body strings carry none.
  - **Probed** (`TestProbeSplitValuePEM`):
    - `{"tool_output":["-----BEGIN OPENSSH PRIVATE KEY-----","FAKEBODYLINE1","FAKEBODYLINE2","-----END OPENSSH PRIVATE KEY-----"]}` produced `["[redacted…]","FAKEBODYLINE1","FAKEBODYLINE2","[redacted…]"]`, with 2 redactions reported.
    - `header`/`body`/`footer` fields gave the same result.
    - Control: a whole key inside one string was redacted.
  - **A second trigger, from reading the code:** the same trust in "closed on this line" misfires when a later value on the header's line merely mentions a footer, and the real body follows on raw lines.
  - **Contradicts:** `deploy/local.md` ("the whole key block from a `-----BEGIN` … to its footer") and D9's rule that no span is shorter than a structural unit.
  - **Why low:** the documented `feedback.jsonl` fields are scalar strings. But these records are written by agents, and `retros.jsonl` already carries arrays. Before this range the walk ran first, so the leak is older than this range. The fix kept it while its comment says the case is handled.
  - **Remediation, either of:**
    - **Shortest:** delete the exception. A line where a block opens and closes then goes whole, under the block marker, and `TestReportRedactJSONL` line 1 expects that marker.
    - **Keeps the line as JSON:** take the exception only when one decoded string matches both `blockOpen` and `blockClose`. That also closes the second trigger.

    Either way, add the array case as a must-fail test.
- **[low / confidence: high]** `internal/harness/report.go:145-156` (`redactLines`), `:248-259` (`redactDocument`) — **a secret under a real JSON key named `password`, `token`, `secret` or `api_key` is sent whenever anything else on that line, or in `state.json`, fires.**
  - **Mechanism:**

    - Only the raw-text fallback catches it, and that runs only when `lineRecs == nil`.
    - When another value fires, the line is re-encoded from the decoded value, and the secret-named key keeps its plain value.
  - **Probed** (`TestProbeSecretNamedKeyBesideAnotherHit`):
    - `{"config":{"api_key":"FAKEVALUE"}}` alone: redacted (control).
    - `{"user_quote":"use ghp_FAKEPREFIX","config":{"api_key":"FAKEVALUE"}}` produced `{"config":{"api_key":"FAKEVALUE"},"user_quote":"[redacted…]"}`, with 1 redaction reported.
    - `{"note":"token=x","password":"FAKEVALUE"}`: sent the same way.

  - **Contradicts:**
    - `deploy/local.md`, which says "a JSON line whose raw text still carries a shape after the walk (a duplicate key) is replaced whole". Here the output still carries the shape and is not replaced.
    - `local.md`'s "in any case an assignment to a `password` … name".
    - The prior review's Outcome for finding 4, which describes a line "the walk leaves still carrying a needle".
  - **Why low:** none of the documented record schemas has secret-named object keys. It needs an off-schema structured record.
  - **Remediation, the shortest:** test the walk's OUTPUT, not whether it fired. After `redactJSON` returns `red`, if `needleIn(string(red))` still matches, fall through to the text rule (whole line). `redactDocument` does the same with the original bytes. This extends the existing fallback, which tests the raw text only when nothing fired, to the case where something did. It over-redacts only what the text rule already over-redacts. ## Outcome

Findings 2 and 3 landed on the redaction walk and finding 1 on the push target — both mechanisms round 1 had already patched — so patching stopped and each finding went to the operator in one numbered table with a recommendation; they took every recommendation as written (plan D13). Must-fail for every code fix seen against a copy of 012b4ca (`.agents/scratch/r2-mustfail.log`, 9 assertions failing); must-pass in the working tree.

- Finding 1 (push follows `pushurl` / every `url`): fixed by a different route than the remediation — `commitAndPush` pushes to the feedback URL itself (`push -u <url> HEAD:main`), so no remote configuration decides the destination; the origin check stays, for the commit. `TestSendReportPushesOnlyToFeedbackURL` (pushurl, second url). The environment variant (`GIT_CONFIG_*`) is moot for the same reason and is not refused. `pushInsteadOf` remains the operator's own config, as the review's residual says.
- Finding 2 (key split across JSON values): fixed by deleting the mechanism — the per-value JSON walk is gone; a key block goes whole as a JSON marker, whatever structure it sat in. `TestReportRedactStructuralGaps` "key split across array values on one line".
- Finding 3 (secret-named key beside another hit): fixed the same way — any line carrying a needle, in raw or decoded text, goes whole; `state.json` goes whole on any needle. `TestReportRedactStructuralGaps` "secret-named key beside another hit" and the two `state.json` documents.
- Finding 4 (origin echoed in the refusal): fixed — the message names the expected URL only. `TestResolveFeedbackFailures` origin carrying `ghs_FAKETOKEN`; `deploy/local.md` failure row updated.
- Finding 5 (`-run TestReport` misses the git tests): fixed — `testing/sh-agent/guide.md` names a filter that lists every report test, checked with `go test -list`.
- Finding 6 (dry-run guidance): fixed — README and `local.md` say to read what was added under `~/.config/sh-agent/` since the last report, before every report; the plan's timer follow-up records that a timed `report` sends unread content.
- Finding 7 (unterminated block in JSONL drops later records): deferred, owned — fail-safe, and `unterminated: true` in `report.json` shows when it happens; recorded in `local.md` beside the over-redaction note and in D13.
- Finding 8 (unmatched shapes): fixed in part — `Authorization: <any scheme>` and an empty URL user (`redis://:pass@`) now match (`TestReportRedactShapes`); `/` in a URL password, `ghr_`, `npm_`, `--password VALUE` and `passphrase` are not chased, per D13 — `local.md` already says anything unmatched is sent.

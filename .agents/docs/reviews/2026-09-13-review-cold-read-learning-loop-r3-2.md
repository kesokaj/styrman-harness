## Verdict: design needs revision (one new, evidence-backed blocking gap); every blocking gap from the r2 rounds is now resolved in this text.

The plan converges well: R7 is now handled correctly (D5/D12 propose the clarification to the operator rather than silently editing an immutable file), D6 now defines how a finding acquires a `rule_ref` when it isn't a verbatim `feedback.jsonl` line (the r2-1 blocking gap), old retro Step 2's harness-only table is explicitly deleted rather than left to contradict D6 (the r2-3 blocking gap), and Phase 2 now includes a false-positive check for model-invocable skills. ## Findings (gaps a first-pass implementer must resolve)

- **[BLOCKING]** D6 (plan line 34) says every finding's `rule_ref` uses "one controlled vocabulary shared with the feedback skill" (`AGENTS.md § <section>`, `skill:<name>`, `agent:<name>`, `rule:<name>`, or `null`), and its promotion mechanism (command 1) is a literal `grep -F` for that exact string inside `~/.config/sh-agent/feedback.jsonl`. But `skills/feedback/SKILL.md:50,81` still defines `rule_ref` as free text ("global standards section or skill-name, or null") and no task schedules a change to that definition — Phase 3's only feedback task (plan line 120) is "one paragraph on where the retro's outputs land." I read the operator's actual `feedback.jsonl` (13 entries) and none of its non-null `rule_ref` values match D6's vocabulary: `"context/dev-setup.md Machines"`, `"feature (Step 1 scope)"`, `"skills/handoff/SKILL.md"`, `"agents/verifier.md log format; AGENTS.md Testing"` — none is `skill:handoff`, `skill:feature`, or `agent:verifier`. Only one of thirteen (`"AGENTS.md § Definition of Done / Resume, then checkpoint"`) happens to fit the `AGENTS.md § <section>` shape. Two implementers diverge here: one updates `skills/feedback/SKILL.md`'s Log Format section to constrain `rule_ref` to D6's vocabulary going forward (a real, unscheduled spec change to an append-only log format, plus the question of what to do with the twelve already-noncompliant historical lines); the other ships D6 exactly as specified and the promotion grep silently never matches feedback-sourced findings against past or future entries, because the two skills write two different string shapes into the field the mechanism treats as a shared key. This is the same class of bug r2-1 and r2-3 already found and got fixed on other mechanisms (retro's own `rule_ref` assignment, Step 2 vs D6) — it has simply moved one hop over, to the feedback/retro boundary, and the plan's "Surfaces touched" list already names `skills/feedback/SKILL.md` as touched, so the fix is in scope, just not yet decided or scheduled.

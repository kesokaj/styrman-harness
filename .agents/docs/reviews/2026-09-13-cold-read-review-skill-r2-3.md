## Verdict: design needs revision / implementation not ready

This is a well-specified revision — the D1–D9 table answers nearly everything the three prior rounds flagged. What remains is one real actor-ambiguity in the `--fix` flow that collides with two subagents' hard-coded refusal to edit source, plus three smaller loose ends. None of these are as severe as the prior rounds' findings, but the `--fix` one is still a fork in the actual code an implementer writes.

## Gaps — must be decided before implementation

- **[cite plan D5, line 24; `agents/reviewer.md` "You never modify source, config, or tests"; `agents/security.md` "you never edit source"]** — D5 says a `--fix` round is "apply the findings (or rebut...), run the project's checks, then re-dispatch the same lens agents..." and "Per lens: `--code`, `--simplify`, `--security` → edit the source." It never names WHO edits the source. The `reviewer` and `security` agent definitions are hard rules that neither agent may touch source — D3 explicitly says "the agents are not edited," so those refusals stand. The only way D5 is coherent is if the main `/review` skill itself applies the fixes from the findings (as D5 already spells out explicitly for `--tests`: "the main agent writes the missing tests (the verifier never does)") — but D5 says that in words for `--tests` and not for `--code`/`--simplify`/`--security`, leaving the parallel case to inference. A first-pass implementer who takes "→ edit the source" as an instruction to give the re-dispatched `reviewer`/`security` agent (e.g. "here are your own findings, please fix them") ships a `--fix` loop that the agent will refuse mid-flight, because both agent files say they only ever write their own report.

- **[cite plan D4, line 23; agent report templates in `agents/reviewer.md`, `agents/security.md`, `agents/verifier.md`, `agents/explorer.md`]** — D4 gives the merged record same-day collision handling ("a second one the same day gets `-2`, `-3`") but the per-lens agent artifacts it links to (`review-<scope>-code.md`, `security-<scope>.md`, etc.) have no such handling in their own hard-coded templates (`$(date +%F)-review-<slug>.md` etc., unconditional overwrite). Two separate `/review` invocations against the same scope on the same day — not a `--fix` round, which D5 explicitly says "overwrite their artifacts" — silently overwrite each other's underlying evidence files while the first run's merged record (now `-2`-suffixed and un-overwritten) still links to paths whose content has since changed. The plan doesn't say whether this is accepted (evidence is transient, only the merged record is durable) or needs the same lens-artifacts to also get run-scoped names.

- **[cite plan D9, line 28]** — D9 gives four token classes ("a token starting with `--` is a flag; `#<digits>` is a PR; a token containing `..` or that `git rev-parse --verify` accepts is a range or ref; an existing path is a path") plus two explicit errors (`--project` combined with another scope selector; empty target). It does not say (a) the precedence order when a token could satisfy two classes at once — e.g. a directory that shares its name with a branch, where both "existing path" and "`git rev-parse --verify` accepts it" are true — or (b) what happens to a token that satisfies none of the four classes (a typo, a nonexistent path/ref). A reasonable implementer would error on (b), but the plan doesn't say so, so nothing stops an implementer from silently falling through to "empty target" or treating the token as a literal (and probably-wrong) path passed straight to `git diff`.

- **[cite plan line 13 (Scope), `skills/preflight/SKILL.md:3` and `:50`]** — the Scope line names "`skills/preflight/SKILL.md` Step 2" for repointing away from "the vendor's built-in review command," but that exact phrase also appears in `skills/preflight/SKILL.md`'s frontmatter `description:` (line 3: "...use the reviewer agent or the vendor's built-in review command)."), a second, separate location the Scope line doesn't name. An implementer who edits only Step 2 (line 50) leaves the frontmatter description stale, still pointing users at a vendor built-in that D8 says the harness should never mention.

## Readiness — questions a first-pass implementer would have to ask

- **BLOCKING** — For `--fix` on the `--code`/`--simplify`/`--security` lenses, does the main `/review` skill apply the edits itself (the only reading consistent with `agents/reviewer.md`/`agents/security.md`'s hard "never edit source" rule and D3's "agents are not edited"), or is the re-dispatched agent expected to fix its own findings? Two implementers diverge here — one writes an edit loop in the skill itself, the other tries to make the subagent do it and hits the agent's own refusal at runtime.
- **NON-BLOCKING** — Do same-day, non-`--fix` re-runs need run-scoped (not just date-scoped) filenames for the per-lens agent artifacts, or is overwriting them between separate `/review` calls acceptable since only the merged record is the durable artifact? A reasonable implementer accepts the overwrite (matching how `--fix` rounds already overwrite by design) and just notes it; the ambiguity only matters if the user expects every past run's evidence to stay retrievable.
- **NON-BLOCKING** — Exact behavior for an unparseable target token (neither flag, PR, ref/range, nor existing path). A reasonable implementer errors with a message naming the token, matching the spirit of the two errors D9 already specifies.
- **NON-BLOCKING** — Whether `--project` alone (no `--all`) runs every lens over the whole tree, or only the lens(es) actually given (defaulting to `--code`) plus `explorer`. D3's "`--project` adds `explorer`... and every lens runs over the whole tree instead of a diff" is slightly ambiguous read on its own, but D7's explicit `/review --project --all` example (needing `--all` to get all four dispatch types) resolves it by example; a careful implementer follows the worked example over the loose sentence.
- **NON-BLOCKING** — Fixing the second "vendor's built-in review command" mention in `skills/preflight/SKILL.md`'s frontmatter description (Gap 4) — a competent implementer doing a repo-wide grep for the phrase (which D8's intent implies) catches it without being told twice.

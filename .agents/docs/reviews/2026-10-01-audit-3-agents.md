### BUG-139 — is a prose lane the right mechanism?

No, not alone, and the record is right that it cannot be: a definition's prohibition competes with an explicit instruction in the dispatch, and the dispatch wins roughly one run in three (7 of 9 since Phase 4: d4-d6 3/3, p5 2/3, p7 2/3; both misses are the same move, a new "Later" section). Adding more prose to the definition is the weakest remaining lever (it already says it in the body, Rules 4, and Records) and the misses did not follow any edit to it. The stronger mechanisms are on the other two sides of the dispatch: (1) the dispatcher side, where an instruction to touch ROADMAP would come from in real use: the only places that dispatch `documentation` are skill texts, so a Go test in `internal/harness` (the shape of `TestSkillLinksResolve`) that fails when a skill line naming `documentation`/`changelog`/`bugs` also tells it to edit `ROADMAP.md`, `TODO.md` or `DECISIONS.md` makes the dispatcher rule mechanical, and today it holds only by absence (I found none); (2) detection after the fact: the context already requires `git status --short --untracked-files=all` after every dispatch that can write, and "a path the dispatch did not name is a stop sign" — that is the real guard for a miss, costs nothing, and it works for every lane, not just this one. A permission deny on the path in the project's settings would be mechanical but also blocks the main agent, which owns the file, so it is the wrong tool. Recommendation: record BUG-139 as accepted (`wontfix` with the 7-of-9 figure), keep (1) as a test, rely on (2), and stop re-running the adversarial dispatch after each edit unrelated to the rule.

# Security review — Phase 2 round 2, the `ConfigDir` fix round (3209cf3..e7fec88)

Range reviewed: 3209cf3..e7fec88 (`git diff 3209cf3..e7fec88 -- . ':!.agents/docs'`; HEAD confirmed `e7fec88`, tree frozen)

## Verdict: FINDINGS

**Finding 5 is closed — measured, not reasoned.** A fresh scratch home installs
with `~/.config/sh-agent` at **0700**; `chmod 755` on it followed by a second
`install` puts it back to **0700**. The round-1 defect (a `MkdirAll(…, 0700)`
that no-ops on an existing directory) is gone, and the operator's own
`~/.config/sh-agent`, **0755 right now** with `feedback/` 0775, `proposals/`
0775 and two 0664 jsonl files inside it, tightens on their next `install` or
`update`.

What the fix brought with it is one **medium**: when the tighten *cannot*
succeed, `install` fails at the very end and leaves a **fully deployed home with
no manifest**. Measured with a `~/.config/sh-agent` the caller does not own:
**260 files written**, `state.json` absent, exit 1, message
`saving manifest: chmod …: operation not permitted`. The manifest is the file
`Uninstall` calls "the only thing uninstall trusts", so that home cannot be
cleanly uninstalled, `status` can never report a stale file, and the next
`install`'s resync has no previous set to prune from. Failing is the right
instinct; failing *there* is not, and it contradicts this file's own policy 30
lines away (`apply.go:46-57`: "a chmod that fails is not worth failing an
install over"). The remaining four are low: a symlinked runtime directory has
its **target** chmodded (a tightening, not a weakening), `~/.config` itself is
now created 0700, the tighten does not reach the directory's **contents**, and
the relink advice is keyed on ownership where the operation needs writability.
Nothing here is high; nothing reopens the work.

## The brief's questions, as checkable statements

1. **Is finding 5 closed? Yes — measured.** Probe under
   `.agents/scratch/security-phase2-2/home1-871137/` (gitignored):
   `install` → `.config` **700**, `.config/sh-agent` **700**; `chmod 755` →
   **755**; `install` again → **700**. umask on this box is `0002`, so the 0700
   is the explicit `Chmod` doing the work, not the umask. `ConfigDir`
   (`state.go:76-91`) is reached from all four writers of that directory
   (`SaveState` state.go:64, `cloneThrowaway` report.go:455, `Diff`
   apply.go:223, the release base release.go:135), and grep confirms **no fifth
   creation site**: the only other `MkdirAll` that can make it is
   `writeAtomic` (apply.go:303, 0755), which in `SaveState` runs *after*
   `ConfigDir`. `TestInstallMakesTheConfigDirPrivate` covers both the absent and
   the pre-existing-0755 arrangements and passes; `TestThrowawayParentIsPrivate`
   now pre-creates the directory 0755, which is the arrangement the old fix
   could not pass. Both run green here.
2. **Tightening a directory the caller does not own: handled, but in the wrong
   place.** The chain is exactly as the brief describes — `Chmod` EPERM →
   `ConfigDir` error → `SaveState` error → `Install` returns
   `saving manifest: …` → exit 1. Measured, not inferred. For a shared `--home`
   this is **too strict as sited, not too strict as a policy**: see finding 1.
3. **A symlinked `~/.config/sh-agent` gets its TARGET chmodded — measured, and
   it is not a weakening.** Probe `home2-871499`: target 755 → **700** after
   `install`, the link itself survives, `state.json` lands in the target.
   `os.Stat`/`os.Chmod` are path-based and follow symlinks. Direction matters:
   `chmod(2)` succeeds only for a directory the caller **owns**, and 0700 only
   ever removes bits, so this cannot widen anything and cannot touch another
   user's files. It is a silent mode change *outside* sh-agent's namespace on a
   path the operator chose — finding 2.
4. **The directory-owner test and `Geteuid` give the right advice in two of the
   three cases, and a harmless wrong one in the third.**
   - *(a) A user-owned `sh-agent` in root's `/usr/local/bin`* — **right, and
     this is the case the fix was for.** `os.Stat("/usr/local/bin")` is
     root-owned (verified 0755 root:root here), `ownedByCaller` false, so the
     note says "remove it, with the rights that own its directory" instead of
     offering an `ln -sfn` that would fail with EACCES.
   - *(b) root running `update` over a user-owned directory* — **conservative
     and inverted, no consequence.** euid 0 ≠ uid 1000, so every directory in
     the user's home reads as foreign and root is told the file is "not yours
     to relink" when root can relink anything. The note writes nothing and
     touches nothing, so this is wording only; `Geteuid` is still the correct
     choice over `Getuid` for a "can I do this" question.
   - *(c) `sudo -u other`* — **right.** euid is `other`, a directory owned by
     the invoking user reads as foreign, and the advice to use the owning
     rights is the true one.
   - Residual: ownership is not writability — finding 5.
5. **Can `os.Stat(real)`/`os.Stat(home)` call two different directories the
   same, and does it matter? Practically no, and no.** `os.SameFile` compares
   dev+ino. A **bind mount** of `$HOME` is the same inode on the same
   superblock, so it compares equal — which is *correct*, it is the same
   directory, and it is an improvement on the lexical compare it replaced
   (`TestNoteRunningElsewhereThroughASymlinkedHome` pins the symlink case and
   is a genuine must-fail: the old `filepath.Clean` compare returns early and
   prints nothing). Two **genuinely different** directories comparing equal
   needs a dev+ino collision, which Linux does not produce across distinct
   mounts and which only a synthesizing filesystem (some FUSE/9p/overlay
   setups) could. It does not matter: `NoteRunningElsewhere` **writes one line
   of text and performs no operation**. The worst outcome is an advisory
   sentence printed for a `--home` that is not the real home — the same class
   of wrong sentence the gate exists to avoid, not a new capability. No finding.
6. **`diffOne`'s `defer os.Remove` — closed.** `apply.go:236-242`: the temp
   file is removed on every path, including the `tmp.Write` failure and the
   `diff`-exploded path, and the `Close` error is folded into `werr` so a
   deferred-close failure is no longer swallowed. README's "removed after" is
   now true unconditionally.
7. **The read-only modes do not reach `ConfigDir` — verified by reading the
   control flow.** `install --dry-run`: `SaveState` is inside `if !dryRun`
   (`apply.go:132-135`), so a dry run creates and chmods nothing. `update
   --check`: `if checkOnly { … return ErrNewerRelease }` (`release.go:123-126`)
   precedes `ConfigDir` at `:135`. The global rule about side effects below a
   read-only mode's early returns is honoured. `sh-agent diff` is the exception
   — see finding 3's note.

## Findings

- **[medium / confidence: high]** `internal/harness/state.go:86` reached from
  `internal/harness/apply.go:133` — **a tighten that cannot succeed aborts
  `install` after every file is written, leaving a deployed home with no
  manifest.** Measured (`.agents/scratch/security-phase2-2/home3-871499`, a
  `~/.config/sh-agent` symlinked to a root-owned directory so `Chmod` returns
  EPERM without changing anything): **260 files on disk**, `state.json`
  **absent**, exit 1, `sh-agent: saving manifest: chmod …: operation not
  permitted`. Why that is exploitable in principle: `State` is documented at
  `state.go:12-14` as "the only thing uninstall trusts: a path not listed here
  is not sh-agent's to delete", and `Uninstall` (`apply.go:266-269`) prints
  "nothing installed" and removes nothing when the manifest is missing — so a
  home reaching this state holds 260 sh-agent-written files that sh-agent will
  never account for or remove, `Status` loses `st.Files` and can never report a
  `stale` entry, and `Install`'s resync loop (`apply.go:224-…` over
  `old.Files`) prunes nothing on every later run. The trigger is any `--home`
  whose `.config/sh-agent` exists and is not the caller's: a shared or
  handed-over home, a directory a previous `sudo` run created, a dotfiles
  symlink pointing at something another uid owns. It also contradicts the
  codebase's own stated policy for exactly this situation 30 lines earlier
  (`apply.go:46-57`: "a chmod that fails is not worth failing an install over —
  the next run with changed bytes will set it"), which warns and continues.
  Remediation, smallest first: call `ConfigDir(home)` **once at the top of
  `Install`**, before the first write, so an unusable runtime directory fails
  the run before it half-deploys — fail-closed, and the operator sees the error
  instead of 260 lines then an error. Or, matching the existing policy, let
  `ConfigDir` return the directory with a printed
  `note: could not tighten ~/.config/sh-agent (%v); its contents are readable
  by others` and keep the manifest landing. Do **not** silently skip the chmod
  when the directory is unowned — that restores the exposure without saying so.
  Stdlib only either way; no dependency.
- **[low / confidence: high]** `internal/harness/state.go:81-89` — **`os.Stat`
  and `os.Chmod` follow symlinks, so a symlinked runtime directory has its
  target's mode changed.** Measured: a `~/.config/sh-agent` symlinked to a
  directory the caller owns at 0755 comes out **0700** after `install`, the
  link intact, `state.json` in the target. Recorded explicitly as the brief
  asks: **this is a tightening, not a weakening** — 0700 only clears bits, and
  `chmod(2)` requires ownership (or CAP_FOWNER), so it cannot widen anything
  and cannot reach another user's directory. The defect is scope and silence: a
  dotfiles repository directory the operator deliberately keeps group-readable
  is silently made 0700, and that mode change is then committed by their own
  dotfiles workflow; a runtime directory symlinked into a shared project
  directory is tightened for everyone who legitimately read it. Nothing is
  printed. The *write*-through-the-link is not new — every writer already
  followed it — only the mode change is. Remediation: `os.Lstat(dir)` first and,
  when it is a symlink, either leave the mode alone or print one line naming
  the target that was tightened; `os.Lstat` is stdlib `os`, nothing added.
- **[low / confidence: high]** `internal/harness/state.go:78` — **`MkdirAll(dir,
  0o700)` also creates the intermediate `~/.config` at 0700**, one level above
  sh-agent's own namespace. Measured on a fresh scratch home: `.config` is
  **700**, where before this range `writeAtomic`'s `MkdirAll(…, 0o755)` left it
  755. Same uid throughout, so there is no exposure and no lockout; the cost is
  a surprise for any other tool the operator later expects to share that
  directory, and a doc comment (`state.go:70`, "returns ~/.config/sh-agent,
  created 0700") that **describes less than the code does** — the
  behaviour-outlives-its-description rule cuts both ways. Remediation:
  `os.MkdirAll(filepath.Dir(dir), 0o755)` then `os.Mkdir(dir, 0o700)` treating
  `ErrExist` as fine, or widen the comment to say `~/.config` is created 0700
  when absent.
- **[low / confidence: high]** `internal/harness/state.go:76-91` — **the tighten
  reaches the directory, not its contents.** Measured on the operator's own
  `~/.config/sh-agent` today: `feedback/` **0775**, `proposals/` **0775**,
  `feedback.jsonl` **0664**, `retros.jsonl` **0664**, `state.json` 0644. After
  the next `install` the 0700 parent denies traversal to group and other, which
  **does** close the local-account read that round 1 named — on a multi-user
  host that finding is genuinely fixed. What survives is that the loose modes
  travel with the bytes: a backup, a dotfiles sync, an archive, or a `--home`
  placed under a directory a second account can traverse re-exposes the
  feedback log, the retro proposals and the legacy `feedback/` tree with no
  further mistake. On *this* box the residual is nil — `getent group kesokaj`
  is empty of other members, `/etc/passwd` holds exactly one account ≥1000, and
  `~/.config` (0775, group-writable) is therefore writable by nobody else, so
  the symlink-plant precondition for the two findings above is also not met
  here. Remediation: a one-time `os.Chmod` sweep of the direct children inside
  `ConfigDir`, or accept it with this line as the record.
- **[low / confidence: medium]** `internal/harness/pathguard.go:141` — **the
  axis is now right and the predicate is still ownership, not writability.**
  Moving from `os.Lstat(from)` to `os.Stat(filepath.Dir(from))` fixes the case
  that occurs on these machines (question 4a above) and is the correct axis: a
  relink is a directory operation. Two residual mismatches remain, both
  advice-only and both erring toward the *stronger* remedy, which is the safe
  direction: (a) a directory the caller does not own but can write — macOS's
  `/usr/local/bin` is conventionally `root:admin` 0775 and Homebrew's is owned
  by the admin user, so on the Mac the note would say "not yours to relink"
  where `ln -sfn` would in fact succeed; (b) a sticky directory on PATH, where
  the entry's own owner governs replacement. Neither gates an operation —
  `ownedByCaller` still selects **wording only** — so the consequence is an
  operator told to use rights they did not need, never the reverse. `Geteuid`
  is the right uid for the question and `sh-agent` is not setuid, so real and
  effective coincide today. Remediation: `syscall.Access(dir, W_OK)` is stdlib
  on unix and would close (a); I would **leave it** — the current form is
  conservative in the only direction that matters, and the extra syscall buys a
  nit.
- **[low / confidence: high]** `internal/harness/apply.go:220-234` — carried
  from round 1 and now slightly wider: `sh-agent diff`, a read-only verb, does
  not merely write into the home it inspects, it **changes a directory's mode**
  there (`ConfigDir` at `:223`), and on a symlinked runtime directory the
  target's mode. It fires only when a file actually differs, and only inside
  sh-agent's own directory, so this is a note rather than a defect against the
  read-only rule (which is scoped to `--check`/`--dry-run`, both verified clean
  in question 7). Remediation unchanged and still the smaller code: run
  `diff -u -L … <dest> -` with `cmd.Stdin = bytes.NewReader(f.Data)` and drop
  the temp file, the `ConfigDir` call and this whole question.

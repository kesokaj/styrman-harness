All three of round 2's blocking/near-blocking findings are resolved in this revision, checked against the actual files: (1) r2-1's "how does a finding acquire a `rule_ref` for the non-`feedback.jsonl` case" is now answered by D6's explicit per-finding controlled vocabulary; (2) r2-3's Step 2/D6 contradiction is resolved — the plan now states plainly "old Steps 2–5 replaced wholesale — the old Step 2 table... is gone" (line 59); (3) r2-1's missing false-positive verification step for Phase 2 is now present ("a plain unrelated request... loads none of the five", line 98/114). r2-2's REQUIREMENTS.md R7 conflict got a new decision (D12) rather than a full resolution — see Gap 1 below, which I judge no longer a build-fork but still a real process risk worth surfacing. ## Gaps (must be decided before implementation)

- **New — D6's "controlled vocabulary shared with the feedback skill" is not wired into `feedback`'s own spec.** Plan line 34 (D6) defines a fixed enum for `rule_ref` (`AGENTS.md § <section title>`, `project AGENTS.md § <section>`, `skill:<name>`, `agent:<name>`, `rule:<name>`, or `null`) and calls it "shared with the feedback skill." But `skills/feedback/SKILL.md:50` currently documents `rule_ref` as freeform text: `"global standards section or skill-name, or null if no existing rule covers this"` — not the same shape (no `AGENTS.md § <section title>` / `skill:<name>` prefixing convention). Phase 3's task list (plan line 120) only asks for "`skills/feedback/SKILL.md`: one paragraph on where the retro's outputs land" — it never says to rewrite the `rule_ref` field definition to the new enum. Left as written, `feedback.jsonl` keeps logging `rule_ref` in the old freeform shape while `retro`'s new Step 2 emits the new enum shape, and D6's "mechanical, no similarity judgement" promotion grep (an **exact string match** on `rule_ref` across projects) silently stops matching for exactly the cross-session `feedback.jsonl` case the mechanism's worked example (BUG-041) depends on. Two implementers diverge: one rewrites `feedback`'s `rule_ref` docs to the shared enum (because D6 says "shared"), the other leaves `feedback` alone because Phase 3's literal task line doesn't mention it.

- **Carried from r2-2, downgraded but not closed — R7 vs. project-level retro records.** `REQUIREMENTS.md:31` (R7) states the harness's own state, explicitly including "retro proposals," "lives in `~/.config/sh-agent/` and nowhere else." D5 (plan line 33) now argues project-scope proposals aren't "the harness's own state" (they're the project's own trail, like bugs/plans) and defers only a *clarifying* edit to R7, proposed "to the operator for approval **with the report**" (D12, line 39) — i.e., after Phase 3 is already built, not before. `AGENTS.md`'s hard rule is explicit about order: "propose the exact edit → approval → ADR → update `REQUIREMENTS.md`... in one commit." D5 is precise enough that two implementers would build the *same* code (so this is not a readiness fork), but building it before the operator has actually blessed the R7 reading — rather than after, as D12 schedules it — inverts the hard rule's sequencing for a document R7 itself calls immutable without explicit approval. Recommend surfacing D5's reading to the operator for a yes/no *before* Phase 3 starts, not bundling it into the end-of-plan report.

- **Minor, non-blocking — scratch build directory has no concurrency story.** `Reinstall` (D2) builds to and `defer os.RemoveAll`s a single fixed path, `<repo>/.agents/scratch/sh-agent-build/sh-agent`. Two concurrent `sh-agent install`/`update` invocations against the same checkout (plausible in this harness, where multiple agent sessions can run in parallel against the same repo) race on that path: one process's cleanup can remove the directory while another's `go build -o` is mid-write. Not in the Failure modes section. Low likelihood, one sentence would close it — not a fork in what a single implementer builds.
